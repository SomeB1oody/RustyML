# 3.9. 权重保存与加载

RustyML 只用两个方法持久化训练好的 [`Sequential`](./3.1._Sequential模型.md) 模型：`save_to_path` 和 `load_from_path`。它们的职责刻意收得很窄。如果你从 Keras 过来，习惯了 `model.save()` 写出一个自描述的打包文件、能连同计算图、编译配置和优化器状态一起还原，那现在就要调整预期：RustyML 只保存各层的*权重*，文件里没有任何能让你从头重建模型的信息。加载分两步走——先用代码搭出一模一样的层栈，再把保存下来的数组灌回去。本节讲清楚磁盘上到底存了什么、这条边界为什么划在这里、有哪些出错方式，以及哪些范式能让这套“只存权重”的模型用起来顺手。

## 3.9.1. 磁盘上究竟写了什么

`save_to_path` 遍历所有层，为每一层记录一小段元数据标签外加它的权重，再用 [postcard](https://docs.rs/postcard) 把整个向量序列化成紧凑的二进制块，经缓冲写入器写盘。`load_from_path` 把文件读回来、反序列化，核对你搭出的模型与文件是否吻合，然后逐层把数组应用回去。函数签名如下：

```rust,ignore
pub fn save_to_path(&self, path: impl AsRef<std::path::Path>) -> RustymlResult<()>;
pub fn load_from_path(&mut self, path: impl AsRef<std::path::Path>) -> RustymlResult<()>;
```

两个方法都接受任何 `AsRef<Path>` 类型——`&str`、`String`、`Path`、`PathBuf`——所以下文里的 `"model.bin"` 字面量只是写着顺手而已。扩展名纯属摆设；不管你给文件起什么名字，postcard 写进去的都是裸字节。`save_to_path` 用的是 `File::create`，它会截断并覆盖，所以往同一路径重新保存会直接盖掉上一个 checkpoint——这正是“只保留最优”循环想要的行为。

最需要吃透的一点，是这些逐层元数据的*用途*。每一层贡献一个类型名字符串（`"Dense"`、`"Conv2D"` 等）和一个输出形状字符串，但它们是校验用的标签，不是重建模型的配方。文件里不记录任何一层的激活函数，不记录 `epsilon` 或 `momentum`，也不记录步长、卷积核大小、膨胀系数或分组数。你没法丢给 `load_from_path` 一个空的 `Sequential` 就换回一个能用的模型。这就是文档把它称作“只存权重”的原因：架构活在你的源码里，文件只承载往里填的那些数字。

| 写进文件的 | 不写进文件的 |
| --- | --- |
| 逐层的类型名标签（加载时校验） | 激活函数、超参数（`epsilon`、`momentum`、步长……） |
| 逐层的输出形状标签（仅供参考） | 优化器及其累积状态（Adam 的矩、SGD 的动量） |
| 每一层的权重数组（见 [3.9.2](#392-layerweight-枚举逐层载荷)） | 损失函数与编译状态 |
| BatchNormalization 的运行均值与运行方差 | 训练时的打乱种子、训练模式标志 |

## 3.9.2. `LayerWeight` 枚举：逐层载荷

磁盘上的权重格式*本身就是*一个 Rust 枚举 `LayerWeight<'a>`：每种受支持的层类型对应一个变体，另有一个 `Empty` 变体留给无参数的层。每个变体包裹一个小结构体，其中的数组以 [`Cow`](https://doc.rust-lang.org/std/borrow/enum.Cow.html) 存储——正是这个技巧让同一个类型能兼顾两个方向：保存时 [`Sequential::get_weights`](./3.1._Sequential模型.md) 借用活着的数组（`Cow::Borrowed`，不克隆），而 `load_from_path` 反序列化成拥有所有权的数组（`Cow::Owned`）。枚举采用 serde 默认的外部标签（externally-tagged）表示，因为 postcard 不是自描述格式，需要把判别标记显式写进去。

每个变体究竟保存了什么值得记牢，因为它决定了一次往返是否精确：

| 变体 | 载荷 |
| --- | --- |
| `Dense` | `weight (in, out)`、`bias (1, out)` |
| `SimpleRNN` | `kernel`、`recurrent_kernel`、`bias` |
| `LSTM` / `GRU` | 融合的 `kernel`、`recurrent_kernel`、`bias`（门块 `[i\|f\|g\|o]` / `[r\|z\|h]`） |
| `Conv1D` / `Conv2D` / `Conv3D` | 卷积 `weight` 核与 `bias` |
| `SeparableConv2D` / `DepthwiseConv2D` | depthwise / pointwise 核与 `bias` |
| `BatchNormalization` | `gamma`、`beta`、**`running_mean`、`running_var`** |
| `LayerNormalization` / `InstanceNormalization` / `GroupNormalization` | 仅 `gamma`、`beta` |
| `Empty` | 无（Dropout、池化、flatten、纯激活层） |

归一化层之间的这种不对称是有意为之，也是正确的。[BatchNormalization](./3.8._正则化与归一化层.md) 在训练中累积运行统计量，并*在推理时用到它们*，所以这两个数组属于训练出来的状态，必须挺过序列化——丢掉它们，重新加载的模型就会拿默认统计量去归一化推理模式的输入，结果全是垃圾。层归一化、实例归一化和组归一化每次前向传播都从当前输入现算统计量，不保留任何运行状态；能存的只有 `gamma` 和 `beta`。[3.9.4](#394-归一化的运行统计量能完整往返) 会明确演示 BatchNorm 这种情形。

## 3.9.3. 一次完整的往返

下面是端到端的完整流程：搭建、简单训练、保存、重建*同样*的层栈、加载，最后确认恢复出的模型预测结果一模一样。留意 `make_arch` 函数——把架构定义一次、给活着的模型和重新加载的目标共用，是“只存权重”持久化里最有用的一个习惯，因为它保证两个层栈绝不会各走各的。

```rust
use ndarray::Array;
use rustyml::error::Error;
use rustyml::neural_network::Tensor;
use rustyml::neural_network::layers::activation::linear::Linear;
use rustyml::neural_network::layers::dense::Dense;
use rustyml::neural_network::losses::MeanSquaredError;
use rustyml::neural_network::optimizers::SGD;
use rustyml::neural_network::sequential::Sequential;

// 架构的唯一真实来源，实时模型和重新加载的模型共用同一份定义。
fn make_arch() -> Sequential {
    let mut m = Sequential::new();
    m.add(Dense::new(4, 3, Linear::new()).unwrap())
        .add(Dense::new(3, 2, Linear::new()).unwrap());
    m
}

fn main() -> Result<(), Error> {
    let x: Tensor = Array::from_shape_vec((2, 4), vec![0.1f32, 0.2, 0.3, 0.4, -0.1, -0.2, -0.3, -0.4])
        .unwrap()
        .into_dyn();
    let y: Tensor = Array::from_shape_vec((2, 2), vec![1.0f32, 0.0, 0.0, 1.0])
        .unwrap()
        .into_dyn();

    let mut model = make_arch();
    model.compile(SGD::new(0.01, 0.0, false, 0.0).unwrap(), MeanSquaredError::new());
    model.fit(&x, &y, 5)?;
    let before = model.predict(&x)?;

    // 保存权重，然后重建完全相同的层栈并加载进去。
    let path = "roundtrip_demo.bin";
    model.save_to_path(path)?;

    let mut restored = make_arch();
    restored.load_from_path(path)?;
    let after = restored.predict(&x)?;

    // 两个预测张量必须逐元素相等。
    let max_diff = (&after - &before)
        .mapv(f32::abs)
        .iter()
        .cloned()
        .fold(0.0f32, f32::max);
    println!("max abs difference after round-trip: {max_diff:e}");
    assert!(max_diff < 1e-6);

    std::fs::remove_file(path).unwrap();
    Ok(())
}
```

这次往返是精确的，不是近似的：postcard 无损地保存每一个 `f32`，`load_from_path` 又把数组直接写进各层，所以重新加载的模型在逐位层面执行的是完全相同的计算。上面的 `1e-6` 容差是防御性的余量，不是在给可能的漂移留后路。

## 3.9.4. 归一化的运行统计量能完整往返

BatchNorm 的推理路径会读取 `running_mean` 和 `running_var`，所以有意思的测试是：把这些统计量训练到偏离默认值，保存，再加载进一个*全新未训练*的模型，看推理模式下的预测是否依然吻合。答案是吻合——这些运行数组随 `BatchNormalization` 变体一起走。

```rust
use ndarray::Array;
use rustyml::neural_network::Tensor;
use rustyml::neural_network::layers::regularization::normalization::batch_normalization::BatchNormalization;
use rustyml::neural_network::losses::MeanSquaredError;
use rustyml::neural_network::optimizers::SGD;
use rustyml::neural_network::sequential::Sequential;

fn make_arch() -> Sequential {
    let mut m = Sequential::new();
    m.add(BatchNormalization::new(vec![4, 3], 0.9, 1e-5).unwrap());
    m
}

fn main() {
    let x: Tensor = Array::from_shape_vec(
        (4, 3),
        vec![0.5f32, -1.0, 2.0, 1.5, 0.2, -0.7, -1.2, 0.8, 1.1, 0.3, -0.4, 0.9],
    )
    .unwrap()
    .into_dyn();

    // 训练一轮，让 running_mean / running_var 偏离初始值。
    let mut model = make_arch();
    model.compile(SGD::new(0.001, 0.0, false, 0.0).unwrap(), MeanSquaredError::new());
    model.fit(&x, &x, 8).unwrap();
    let before = model.predict(&x).unwrap(); // 推理模式使用运行统计量

    let path = "batchnorm_demo.bin";
    model.save_to_path(path).unwrap();

    let mut restored = make_arch(); // 全新模型：运行统计量仍是默认值
    restored.load_from_path(path).unwrap();
    let after = restored.predict(&x).unwrap();

    let max_diff = (&after - &before)
        .mapv(f32::abs)
        .iter()
        .cloned()
        .fold(0.0f32, f32::max);
    println!("running-stat round-trip max abs difference: {max_diff:e}");
    assert!(max_diff < 1e-6);

    std::fs::remove_file(path).unwrap();
}
```

要是运行统计量没被持久化，`after` 会和 `before` 大幅偏离，因为全新模型的默认值对不上那 8 个 epoch 累积下来的批统计量。

## 3.9.5. 哪些东西没被保存，又为何会咬你一口

优化器、它的累积状态、损失函数，以及整套编译配置都被留在了原地。这是与 Keras 差别最大的地方——Keras 的默认保存格式会把优化器一并打包，好让 `fit` 无缝续训。在 RustyML 里，加载给你的是一个空白模型上的权重——`optimizer` 和 `loss` 都是 `None`——由此引出两个后果。

其一，在能 `fit`、乃至模型进入可训练状态之前，你必须重新调用一次 `compile`；预测则立刻可用，因为 `predict` 不需要优化器。其二，也是容易漏掉的一点：加载之后续训会**从零重启优化器**。[Adam](./3.4._优化器.md) 的一阶矩和二阶矩估计归零，SGD 的动量缓冲清空，Adam 用于偏差修正的时间步也重新从 1 开始。对几步微调来说，这无伤大雅。但如果一段长训练被一道保存/加载的分界线切成两半，加载后的头几步会比不间断训练走出更大、阻尼更弱的更新——损失曲线上冒出一个瞬时的凸起，这是持久化留下的假象，而非数据的问题。如果你要在不出现这种断裂的前提下暂停再恢复长时间的优化，那就让进程一直活着，别绕道磁盘往返，因为 RustyML 没有提供序列化优化器矩的 API。训练时的打乱种子同样不会被保存；加载后如果你想让恢复的打乱可复现，用 [`set_seed`](../Chapter-07/7.1._可复现性与随机种子.md) 重新设置一次。

## 3.9.6. 加载时的错误变体

每一种失败都以 `Error::Io(...)` 的形式浮现（见 [1.6. 错误处理](../Chapter-01/1.6._错误处理.md)）。恰好有四种形态，它们干净地对应四类可能出错的东西：

| 错误 | 原因 |
| --- | --- |
| `IoError::Std` | 文件无法打开/读取（路径不存在、权限不足）或无法写入 |
| `IoError::UnsupportedModelFormat` | 文件没有带上本次构建的魔数和格式版本：它要么不是 RustyML 模型，要么出自一个磁盘权重布局不同的版本——见 [3.9.8](#398-工作流范式) |
| `IoError::Serialization` | 在头部合法的**前提下**，字节流对预期的 schema 而言不是合法的 postcard（损坏或截断） |
| `IoError::ModelStructureMismatch` | 你搭出的模型和文件对不上：层*数*不对、某个位置的层*类型*不对，或某个权重的*形状*和目标层不一致 |

头部是最先校验的，所以这四种是有先后的：根本不是模型的文件走不到 postcard 解码器，而出自不兼容版本的文件走不到结构检查。

`ModelStructureMismatch` 是你迭代开发时最常撞上的一个。它在三处被抛出：层数检查、逐位置的类型名检查，以及——不那么显眼地——在应用权重的过程中，某一层 `set_weights` 报出的形状不一致会被包进同一个变体。所以一个 `Dense::new(2, 2, ...)` 的文件加载进 `Dense::new(3, 3, ...)` 的目标，会过了层数和类型检查，却栽在形状上，报的仍是 `ModelStructureMismatch`。消息字符串会告诉你是哪一种。匹配它很直接：

```rust
use rustyml::error::{Error, IoError};
use rustyml::neural_network::layers::activation::linear::Linear;
use rustyml::neural_network::layers::dense::Dense;
use rustyml::neural_network::sequential::Sequential;

fn main() {
    // 保存一个单层模型。
    let mut saved = Sequential::new();
    saved.add(Dense::new(2, 2, Linear::new()).unwrap());
    let path = "mismatch_demo.bin";
    saved.save_to_path(path).unwrap();

    // 用错误的层数重建，然后尝试加载。
    let mut wrong = Sequential::new();
    wrong
        .add(Dense::new(2, 2, Linear::new()).unwrap())
        .add(Dense::new(2, 2, Linear::new()).unwrap());

    match wrong.load_from_path(path) {
        Err(Error::Io(IoError::ModelStructureMismatch(msg))) => {
            println!("rejected as expected: {msg}");
        }
        Err(other) => panic!("unexpected error: {other:?}"),
        Ok(()) => panic!("load must not succeed on a structure mismatch"),
    }

    std::fs::remove_file(path).unwrap();
}
```

类型名检查是按字符串比对的，所以能抓住常见错误——本该是 Dense 的地方冒出一个 Conv 层、少一层或多一层——但它管不了那些不改变类型名和权重形状的超参数。两个形状相同、激活函数不同的 `Dense` 层会毫无怨言地加载成功，因为激活函数根本不在磁盘上。这就是“只存元数据标签、不存完整架构”的实打实的代价，也是“坚持用 `make_arch` 函数”这条纪律要紧的原因。

## 3.9.7. postcard 格式：体积、速度、可移植性

postcard 是一种紧凑、非自描述的二进制格式。非自描述意味着流里不含字段名——只按声明顺序写入各个值——这既是文件小的原因，也是文件被牢牢绑定在写出它的那个 crate 的确切结构体/枚举布局上的原因。体积很好预估：每个参数是一个 `f32`，四字节，再加上一点固定开销，用于记录数组维度（varint 编码）、枚举判别标记（这些小枚举各占一字节）以及那几段简短的元数据字符串。因此 `Sequential::summary` 打印的 `Total params: N (N*4 B)` 那一行，就是磁盘体积一个相当接近的上界估计——一个 10 万参数的模型落在 400 KB 左右。序列化是单趟线性扫描加一次缓冲写入，所以瓶颈在 I/O 而非 CPU。

这个格式可以跨机器移植。postcard 规定了自己的字节序，而不是直接倾泻本机字节序的内存，所以在一种架构上写出的 checkpoint 能在另一种架构上正确反序列化，与主机的字节序无关——不需要转换步骤，也没有分平台的变体。它*唯独不能*跨越的是 crate 版本；那是下一节的主题。

## 3.9.8. 工作流范式

**为最优模型打 checkpoint。** 分成若干短轮次训练，每轮结束后评估一个验证指标，只要指标改善就覆盖同一个文件。由于 `save_to_path` 会截断，文件里始终装着到目前为止最好的权重，而内存中最终的那个模型——它可能已经越过最优点过拟合了——则被丢弃，改用重新加载的版本。指标怎么算随你；这里手写了一个 MSE，好让示例自成一体。

```rust
use ndarray::Array;
use rustyml::error::Error;
use rustyml::neural_network::Tensor;
use rustyml::neural_network::layers::activation::linear::Linear;
use rustyml::neural_network::layers::dense::Dense;
use rustyml::neural_network::losses::MeanSquaredError;
use rustyml::neural_network::optimizers::SGD;
use rustyml::neural_network::sequential::Sequential;

fn make_arch() -> Sequential {
    let mut m = Sequential::new();
    m.add(Dense::new(4, 3, Linear::new()).unwrap())
        .add(Dense::new(3, 2, Linear::new()).unwrap());
    m
}

fn mse(pred: &Tensor, target: &Tensor) -> f32 {
    (pred - target).mapv(|v| v * v).mean().unwrap()
}

fn main() -> Result<(), Error> {
    let x: Tensor = Array::from_shape_vec((2, 4), vec![0.1f32, 0.2, 0.3, 0.4, -0.1, -0.2, -0.3, -0.4])
        .unwrap()
        .into_dyn();
    let y: Tensor = Array::from_shape_vec((2, 2), vec![1.0f32, 0.0, 0.0, 1.0])
        .unwrap()
        .into_dyn();

    let mut model = make_arch();
    model.compile(SGD::new(0.05, 0.0, false, 0.0).unwrap(), MeanSquaredError::new());

    let path = "best.bin";
    let mut best = f32::INFINITY;
    for round in 0..10 {
        model.fit(&x, &y, 2)?;
        let val = mse(&model.predict(&x)?, &y);
        if val < best {
            best = val;
            model.save_to_path(path)?; // 覆盖上一个 checkpoint
            println!("round {round}: new best {val:.6}, checkpoint written");
        }
    }

    // best.bin 保存的是损失最低的权重，未必是最后一轮的权重。
    let mut deployed = make_arch();
    deployed.load_from_path(path)?;
    println!("restored best MSE: {:.6}", mse(&deployed.predict(&x)?, &y));

    std::fs::remove_file(path).unwrap();
    Ok(())
}
```

**在程序之间迁移权重。** 一个训练用的二进制搭出架构、训练、调用 `save_to_path`；另一个独立的服务用二进制搭出*完全相同*的架构、调用 `load_from_path`。把 `make_arch` 函数放进公共模块或公共 crate 里给两边共用，这样两个程序就不可能不一致——类型名和层数检查确实能抓到分歧，但要等到一次失败的加载之后，而共用同一个构造函数在编译期就能抓到。服务用的二进制永远不需要 `compile`，因为它只调用 `predict`。

**跨 crate 升级的版本管理。** 这一条从前会悄无声息地咬你，挡住它的正是文件头。每个保存下来的模型都以一个魔数和一个格式版本开头，`load_from_path` 在解码任何其他内容之前先校验这两者，所以一个出自不同权重布局版本的 checkpoint 会立刻以 `IoError::UnsupportedModelFormat` 失败，而不是解析成看着像模像样、实则错误的数组。这比听上去更要紧：排在它后面的结构检查比的是层数、类型名和权重的*尺寸*，而这些**恰好都能被一个过时文件蒙对**——一个方形卷积核在轴被置换后尺寸不变，而 `Dense` 的权重形状无论上游张量是什么布局都一样。

这道防线的可靠程度取决于背后的纪律。只要某个权重容器的张量布局、秩或字段顺序有变，版本就必须跟着 bump；跟着 bump 的漂移会被拦下，忘了 bump 的则不会——因为 postcard 依然是非自描述的，字节里再没有别的东西带标签。所以对任何需要在几周后、几个版本后重新加载的 checkpoint，都要在 `Cargo.toml` 里锁定 RustyML 版本；而一旦有意升级，就重新跑一遍训练（或者在旧版本下加载、再用新版本重新保存），而不是拿旧的二进制块去赌新代码。文件头给你的，是把失败从悄无声息变成又响又早。想更深入了解这套持久化机制——`get_weights` 的查看路径、`SerializableSequential` 包装器，以及权重如何通过向下转型（downcasting）被应用回去——见 [7.2. 深入模型持久化](../Chapter-07/7.2._深入模型持久化.md)。
