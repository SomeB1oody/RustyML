# 3.9. 权重保存与加载

RustyML 用 3 个方法持久化训练好的 [`Sequential`](./3.1._Sequential模型.md) 模型：`save_to_path`、`load_from_path`，以及需要显式选用的宽松加载 `load_partial_from_path`。这几个方法的职责刻意收得很窄。RustyML 只保存各层的*权重*，文件里没有足够的信息能重建出一个模型。加载分两步：第一步，把一模一样的层栈收集进一个 `SequentialBuilder`，并对着同一个输入形状 build。第二步，把保存下来的数组加载进这个构建好的模型。本节讲清楚文件里存了什么、这条边界为什么划在这里、有哪些出错方式，以及“只存权重”模型的工作流范式。

## 3.9.1. 磁盘上究竟写了什么

`save_to_path` 遍历所有层。对每一层，它记录该层的类型名，以及这一层持有的每一个具名数组。然后它用 [postcard](https://docs.rs/postcard) 把整个 checkpoint 序列化成紧凑的二进制块，再由缓冲写入器把这块数据写盘。这一路上不发生任何拷贝，因为每条记录都借用着活着的数组，直到 postcard 读取它为止。`load_from_path` 把文件读回来、反序列化，核对构建好的模型是否与文件吻合，然后逐层把数组应用回去。函数签名如下：

```rust,ignore
pub fn save_to_path(&self, path: impl AsRef<std::path::Path>) -> RustymlResult<()>;
pub fn load_from_path(&mut self, path: impl AsRef<std::path::Path>) -> RustymlResult<()>;
pub fn load_partial_from_path(&mut self, path: impl AsRef<std::path::Path>) -> RustymlResult<LoadReport>;
```

这 3 个方法都接受任何实现了 `AsRef<Path>` 的类型：`&str`、`String`、`Path` 或 `PathBuf`。下面示例里的 `"model.bin"` 字面量只是最常见的写法。扩展名对格式没有任何影响，因为不管文件叫什么名字，postcard 写进去的都是裸字节。`save_to_path` 用的是 `File::create`，它会截断并覆盖文件，所以往同一路径再次保存会替换掉上一个 checkpoint。这个行为正好适合“只保留最优”这种循环。

逐层元数据只有 1 个作用：校验，而不是重建。每一层贡献 1 个类型名字符串，比如 `"Dense"` 或 `"Conv2D"`。每个数组贡献它自己的名字和它的 kind。这些都是校验用的标签，不是搭建层的配方。文件不记录任何一层的激活函数，也不记录 `epsilon`、`momentum`、步长、卷积核大小、膨胀系数或分组数。把一个空的 `Sequential` 丢给 `load_from_path`，换不回一个能用的模型。RustyML 把这种格式称为“只存权重”正是因为这一点：架构活在源码里，文件只承载填充这套架构所需的那些数字。

文件里还存着**每一层构建时所用的那些形状**。层在 `build` 里、依据各个输入的形状分配它持有的每一个数组，所以那些形状决定了这个层持有的每一个尺寸。这条构建记录**每个输入存 1 个形状**：只有 1 个输入的层记 1 个形状，有 3 个输入的 merge 层记 3 个。把它们记下来，加载就能拒绝一个为另一种输入构建的模型，而且拒绝时会点名那个层和两边的形状。

这条记录的 batch 轴是自由的。一个层服务任意 batch 大小，所以一个按 1 个样本构建的模型写出的 checkpoint，能加载进一个按 32 个样本构建的模型。不持有任何数组、也不读取输入任何长度的层，比如激活层或 `Dropout`，根本不带这条构建记录，加载时会跳过对它的比较。

| 写进文件的 | 不写进文件的 |
| --- | --- |
| 逐层的类型名标签，以及构建形状（两者加载时都校验） | 激活函数、超参数（`epsilon`、`momentum`、步长……） |
| 每个数组的名字与 kind（加载时校验） | 优化器及其累积状态（Adam 的矩、SGD 的动量） |
| 每一层的权重数组（见 [3.9.2](#392-具名-checkpoint每个数组-1-个地址)） | 损失函数与编译状态 |
| BatchNormalization 的 `moving_mean` 与 `moving_variance` | 训练时的打乱种子、训练模式标志 |

## 3.9.2. 具名 checkpoint：每个数组 1 个地址

文件按一条点分路径 `<scope>.<name>` 给每个数组寻址。`scope` 是这个层从输入数起的位置，`name` 是这个层给该数组取的名字。所以模型第一层的 kernel 是 `0.kernel`，位置 1 上的 `BatchNormalization` 的滑动均值是 `1.moving_mean`。这与优化器索引自己状态时用的是同一对键，于是 1 个地址同时服务训练循环和文件（见 [3.4. 优化器](./3.4._优化器.md)）。

`Graph` 模型写的是同一种格式、同一套路径。它的 `scope` 是这个层在层 arena 里的位置，而不是某个节点的位置。所以被多个节点调用的 1 个层，无论有几个节点读它，都只持有 1 套路径。

每条记录还带着一个 `WeightKind`。`Trainable` 表示优化器会更新这个数组，它涵盖每一个 kernel、每一个 bias，以及归一化的每一个缩放与平移。`NonTrainable` 表示这个数组由层自己保管，任何优化器都不写它。目前 crate 里唯一的不可训练数组，就是 `BatchNormalization` 的那 2 个滑动统计量。加载会把 kind 和形状放在一起比对，所以一个在层保管状态的位置上给出可训练数组的文件会被拒绝，而不会被施加上去。

`weight_paths()` 按文件里的顺序列出模型的每一个地址。`weight(path)` 读取其中 1 个，给出的视图借用着活着的数组：

```rust
use rustyml::neural_network::Shape;
use rustyml::neural_network::layers::activation::linear::Linear;
use rustyml::neural_network::layers::dense::Dense;
use rustyml::neural_network::layers::regularization::normalization::batch_normalization::BatchNormalization;
use rustyml::neural_network::sequential::SequentialBuilder;

fn main() {
    let model = SequentialBuilder::new()
        .add(Dense::new(3, Linear::new()).unwrap())
        .add(BatchNormalization::new(0.9, 1e-5).unwrap())
        .add(Dense::new(2, Linear::new()).unwrap().with_use_bias(false))
        .build(&Shape::with_free_batch(&[2, 4]))
        .unwrap();

    // 模型的每一个数组，都用保存文件给它的那个地址列出来。
    for path in model.weight_paths() {
        println!("{path:<18} {:?}", model.weight(&path).unwrap().shape());
    }
}
```

```text
0.kernel           [4, 3]
0.bias             [1, 3]
1.gamma            [3]
1.beta             [3]
1.moving_mean      [3]
1.moving_variance  [3]
2.kernel           [3, 2]
```

这个模型的第三层展示了可选数组对这份清单的影响。`with_use_bias(false)` 把 `2.bias` 从模型里拿掉，于是它也就不在文件里。其余路径一个都不移位，因为路径命名的是一个数组，而绝不是层内部的某个位置。`with_center(false)` 和 `with_scale(false)` 对 4 个归一化层的 `beta` 和 `gamma` 做的是同样的事。

各个层持有的数组：

| 层 | 具名数组 |
| --- | --- |
| `Dense` | `kernel (构建宽度, units)`、`bias (1, units)` |
| `Embedding` | `embeddings (input_dim, output_dim)` |
| `SimpleRNN` | `kernel`、`recurrent_kernel`、`bias` |
| `LSTM` / `GRU` | 融合的 `kernel`、`recurrent_kernel`、`bias`（门块 `[i\|f\|g\|o]` / `[z\|r\|h]`） |
| `Conv1D` / `Conv2D` / `Conv3D` | `kernel` 与 `bias` |
| `Conv1DTranspose` / `Conv2DTranspose` / `Conv3DTranspose` | `kernel` 与 `bias`（这个核的 filter 轴排在通道轴前面） |
| `SeparableConv1D` / `SeparableConv2D` | `depthwise_kernel`、`pointwise_kernel`，以及 `bias` |
| `DepthwiseConv1D` / `DepthwiseConv2D` | `kernel` 与 `bias`（没有 pointwise 核） |
| `BatchNormalization` | `gamma`、`beta`、**`moving_mean`、`moving_variance`** |
| `LayerNormalization` / `InstanceNormalization` / `GroupNormalization` | 仅 `gamma` 与 `beta` |
| `PReLU` | `alpha`，其秩跟随输入，每个共享轴上为 `1` |
| Dropout、池化、flatten、merge、纯激活层 | 无，因此不贡献任何路径 |

归一化层之间的这种差异是有意为之，也合乎设计。[BatchNormalization](./3.8._正则化与归一化层.md) 在训练中累积滑动统计量，并*在推理时用到它们*。这两个数组是训练出来的状态的一部分，所以必须挺过序列化。如果重新加载时丢掉它们，模型就会拿默认统计量去归一化推理模式的输入，得到错误的结果。层归一化、实例归一化和组归一化每次前向传播都从当前输入现算统计量，不保留任何滑动状态，能存的只有 `gamma` 和 `beta`。[3.9.4](#394-归一化的运行统计量能完整往返) 会详细展示 `BatchNormalization` 这种情形。

## 3.9.3. 一次完整的往返

完整的流程有 5 步：搭建、简单训练、保存、重建*同样*的层栈、加载。最后一步要确认恢复出的模型预测出同样的值。留意 `make_arch` 函数：它把架构连同输入形状一起定义一次，让活着的模型和重新加载的目标都调用它。这个习惯是“只存权重”持久化里最有用的实践，因为它保证这 2 个层栈绝不会各走各的。构建形状也一起写进了文件，所以这方面的偏离会在加载时被抓到，而不是等到第一次预测。

```rust
use ndarray::Array;
use rustyml::error::Error;
use rustyml::neural_network::Tensor;
use rustyml::neural_network::layers::activation::linear::Linear;
use rustyml::neural_network::layers::dense::Dense;
use rustyml::neural_network::losses::MeanSquaredError;
use rustyml::neural_network::optimizers::SGD;
use rustyml::neural_network::Shape;
use rustyml::neural_network::sequential::{Sequential, SequentialBuilder};

// 架构连同输入形状的唯一真实来源，实时模型和重新加载的模型共用同一份定义。
fn make_arch() -> Sequential {
    SequentialBuilder::new()
        .add(Dense::new(3, Linear::new()).unwrap())
        .add(Dense::new(2, Linear::new()).unwrap())
        .build(&Shape::with_free_batch(&[2, 4]))
        .unwrap()
}

fn main() -> Result<(), Error> {
    let x: Tensor = Array::from_shape_vec((2, 4), vec![0.1f32, 0.2, 0.3, 0.4, -0.1, -0.2, -0.3, -0.4])
        .unwrap()
        .into_dyn();
    let y: Tensor = Array::from_shape_vec((2, 2), vec![1.0f32, 0.0, 0.0, 1.0])
        .unwrap()
        .into_dyn();

    let mut model = make_arch();
    model.compile(SGD::new(0.01, 0.0, false, 0.0).unwrap(), MeanSquaredError::new());
    model.fit(&x, &y, 5)?;
    let before = model.predict(&x)?;

    // 保存权重，然后重建完全相同的层栈并加载进去。
    let path = "roundtrip_demo.bin";
    model.save_to_path(path)?;

    let mut restored = make_arch();
    restored.load_from_path(path)?;
    let after = restored.predict(&x)?;

    // 两个预测张量必须逐元素相等。
    let max_diff = (&after - &before)
        .mapv(f32::abs)
        .iter()
        .cloned()
        .fold(0.0f32, f32::max);
    println!("max abs difference after round-trip: {max_diff:e}");
    assert!(max_diff < 1e-6);

    std::fs::remove_file(path).unwrap();
    Ok(())
}
```

这次往返是精确的，而不是近似的：postcard 无损地保存每一个 `f32`，`load_from_path` 又把数组直接写进各层，所以重新加载的模型在逐位层面执行的是完全相同的计算。上面的 `1e-6` 容差是防御性的余量，而不是在给可能的漂移留后路。

## 3.9.4. 归一化的运行统计量能完整往返

`BatchNormalization` 的推理路径会读取 `moving_mean` 和 `moving_variance`。这个示例把这些统计量训练到偏离默认值，保存模型，再把权重加载进一个*全新、未训练过*的模型。然后检查推理模式下的预测是否依然吻合。答案是吻合的。这 2 个数组各走自己的路径，标着 `NonTrainable`，与同一层里可训练的 `gamma` 和 `beta` 并排。

```rust
use ndarray::Array;
use rustyml::neural_network::Tensor;
use rustyml::neural_network::layers::regularization::normalization::batch_normalization::BatchNormalization;
use rustyml::neural_network::losses::MeanSquaredError;
use rustyml::neural_network::optimizers::SGD;
use rustyml::neural_network::Shape;
use rustyml::neural_network::sequential::{Sequential, SequentialBuilder};

fn make_arch() -> Sequential {
    SequentialBuilder::new()
        .add(BatchNormalization::new(0.9, 1e-5).unwrap())
        .build(&Shape::with_free_batch(&[4, 3]))
        .unwrap()
}

fn main() {
    let x: Tensor = Array::from_shape_vec(
        (4, 3),
        vec![0.5f32, -1.0, 2.0, 1.5, 0.2, -0.7, -1.2, 0.8, 1.1, 0.3, -0.4, 0.9],
    )
    .unwrap()
    .into_dyn();

    // 训练一轮，让 moving_mean / moving_variance 偏离初始值。
    let mut model = make_arch();
    model.compile(SGD::new(0.001, 0.0, false, 0.0).unwrap(), MeanSquaredError::new());
    model.fit(&x, &x, 8).unwrap();
    let before = model.predict(&x).unwrap(); // 推理模式使用滑动统计量

    let path = "batchnorm_demo.bin";
    model.save_to_path(path).unwrap();

    let mut restored = make_arch(); // 全新模型：滑动统计量仍是默认值
    restored.load_from_path(path).unwrap();
    let after = restored.predict(&x).unwrap();

    let max_diff = (&after - &before)
        .mapv(f32::abs)
        .iter()
        .cloned()
        .fold(0.0f32, f32::max);
    println!("running-stat round-trip max abs difference: {max_diff:e}");
    assert!(max_diff < 1e-6);

    std::fs::remove_file(path).unwrap();
}
```

要是滑动统计量没被持久化，`after` 会和 `before` 大幅偏离，因为全新模型的默认值对不上那 8 个 epoch 累积下来的批统计量。

## 3.9.5. 哪些东西没被保存，又为何会咬你一口

优化器、它的累积状态、损失函数，以及整套编译配置都会被留在原地。加载给出的是一个空白模型上的权重，`optimizer` 和 `loss` 字段都是 `None`，由此引出两个后果。

其一，在模型能 `fit` 或开始训练之前，必须重新调用一次 `compile`。预测则可以立刻用，因为 `predict` 不需要优化器。其二，加载之后续训会**从零重启优化器**，这一点很容易被忽略。[Adam](./3.4._优化器.md) 的一阶矩和二阶矩估计归零，SGD 的动量缓冲也会清空，Adam 用于偏差修正的时间步同样重新从 1 开始。对几步微调来说，这次重置无伤大雅。但如果一段长训练被一次保存和加载切成两半，加载后的头几步会比不间断训练走出更大、阻尼更弱的更新。损失曲线上会冒出一个暂时的凸起，这是持久化留下的假象，而不是数据的问题。想在不出现这种断裂的前提下暂停再恢复长时间训练，就让进程一直运行，而不是绕道磁盘保存再加载。RustyML 没有提供序列化优化器矩的 API。训练时的打乱种子同样不会被保存。想让恢复后的打乱可复现，加载后用 [`set_seed`](../Chapter-07/7.1._可复现性与随机种子.md) 重新设置一次。

## 3.9.6. 加载时的错误变体

每一种失败都以 `Error::Io(...)` 的形式出现（见 [1.6. 错误处理](../Chapter-01/1.6._错误处理.md)）。恰好有 4 个变体，每一个都对应一类不同的失败原因：

| 错误 | 原因 |
| --- | --- |
| `IoError::Std` | 文件无法打开/读取（路径不存在、权限不足）或无法写入 |
| `IoError::UnsupportedModelFormat` | 文件没有带上本次构建的魔数和格式版本：它要么不是 RustyML 模型，要么出自一个磁盘权重布局不同的版本，见 [3.9.8](#398-工作流范式) |
| `IoError::Serialization` | 在头部合法的**前提下**，字节流对预期的 schema 而言不是合法的 postcard（损坏或截断） |
| `IoError::ModelStructureMismatch` | 模型和文件对不上：层*数*不对、某个位置的层*类型*不对、*构建形状*不对、出现层里没有的*名字*、*kind* 不一致，或*形状*不一致 |

加载流程会先校验头部，所以这 4 种错误有先后顺序：根本不是模型的文件走不到 postcard 解码器，出自不兼容版本的文件走不到结构检查。

`ModelStructureMismatch` 是开发模型时最常撞上的错误。严格加载按这个顺序跑 6 项检查：层数、每个位置的层类型、双方都带形状时的构建形状、一个层的数组个数与每个数组的名字、每个数组的 kind，以及每个数组的形状与元素个数。整个第一趟只读模型，一个字节都不写。所以一次拒绝会让模型原封不动，一个模型也就永远不会同时装着来自 2 个文件的数组。

消息里会点出 checkpoint 路径。整层级别的不一致则点出层的位置。通常最先触发的是构建形状那一项，它在任何数组被比较之前就触发。一个按 `(None, 4)` 构建的 `Dense` 模型，去加载一个由按 `(None, 5)` 构建的模型写出的文件，会以 ``model structure mismatch: layer 0 (`Dense`) was built for input shape (None, 4), and the file records (None, 5)`` 失败。merge 层则会在这条消息的两边各点出每个输入 1 个形状。匹配这个错误很直接：

```rust
use rustyml::error::{Error, IoError};
use rustyml::neural_network::Shape;
use rustyml::neural_network::layers::activation::linear::Linear;
use rustyml::neural_network::layers::dense::Dense;
use rustyml::neural_network::sequential::SequentialBuilder;

fn main() {
    // 保存一个单层模型。
    let saved = SequentialBuilder::new()
        .add(Dense::new(2, Linear::new()).unwrap())
        .build(&Shape::with_free_batch(&[2, 2]))
        .unwrap();
    let path = "mismatch_demo.bin";
    saved.save_to_path(path).unwrap();

    // 用错误的层数重建，然后尝试加载。
    let mut wrong = SequentialBuilder::new()
        .add(Dense::new(2, Linear::new()).unwrap())
        .add(Dense::new(2, Linear::new()).unwrap())
        .build(&Shape::with_free_batch(&[2, 2]))
        .unwrap();

    match wrong.load_from_path(path) {
        Err(Error::Io(IoError::ModelStructureMismatch(msg))) => {
            println!("rejected as expected: {msg}");
        }
        Err(other) => panic!("unexpected error: {other:?}"),
        Ok(()) => panic!("load must not succeed on a structure mismatch"),
    }

    std::fs::remove_file(path).unwrap();
}
```

类型名检查是按字符串比对的。它能抓住常见错误：本该是 Dense 的地方冒出一个 Conv 层，或者少一层、多一层。但它抓不住那些不改变类型名和权重形状的超参数变化。两个形状相同、激活函数不同的 `Dense` 层会毫无怨言地加载成功，因为激活函数根本不在磁盘上。这就是“只存元数据标签、不存完整架构”的实打实的代价，也是“坚持用 `make_arch`”这条纪律要紧的原因。

**严格是默认，而类型名正是原因。** 名字加形状，作为键比一套封闭的逐层容器要弱。`InstanceNormalization`、`GroupNormalization` 和秩为 2 的 `LayerNormalization` 暴露出来的都是一模一样的 `gamma [C]` 和 `beta [C]`，能把这 3 者分开的，除了逐层的类型名再无别物。所以宽松的默认行为会把一个对该模型而言错误的文件加载进去、把它的每个数组都施加上去，再把差异留到日后以一个错误的预测冒出来。因此加载在任何不一致上都拒绝，宽松那条路是另外的 `load_partial_from_path`，需要调用方指名去要。[3.9.9](#399-有意只加载文件的一部分) 讲的就是它。

## 3.9.7. postcard 格式：体积、速度、可移植性

postcard 是一种紧凑、非自描述的二进制格式。非自描述意味着流里不含字段名，只按声明顺序写入各个值。这个设计让文件体积很小，同时也把每个文件绑定在写出它的那个 crate 版本的确切结构体和枚举布局上。文件体积很好预估：每个参数是一个 `f32`，占 4 字节，再加上一点固定开销，用于记录数组形状（varint 编码）、每个数组的 kind（1 字节）、各个构建形状，以及那几段简短的字符串：每层 1 个类型名，每个数组 1 个名字。因此 `Sequential::summary` 打印的 `Total params: N (N*4 B)` 那一行，就是文件体积一个相当接近的上界估计，一个 10 万参数的模型大约落在 400 KB。序列化是单趟线性扫描加 1 次缓冲写入，所以瓶颈在 I/O 时间而非 CPU 时间。

这个格式可以跨机器移植。postcard 规定了自己的字节序，而不是直接倾泻本机字节序的内存。所以在一种架构上写出的 checkpoint，能在另一种架构上正确反序列化，与主机的字节序无关。这种可移植性不需要任何转换步骤，也没有分平台的变体。它*不能*跨越的是 crate 版本，这一点是下一节的主题。

## 3.9.8. 工作流范式

**为最优模型打 checkpoint。** 分成若干短轮次训练，每轮结束后用 `evaluate` 给模型打分，只要分数改善就覆盖同一个文件。`save_to_path` 会截断文件，所以它始终装着目前为止最好的权重。内存里最终的那个模型可能已经越过最优点、开始过拟合了，所以要丢弃它，改用重新加载的版本。打分要用 `evaluate`，而不是 `fit` 返回的 `History` 的最后一项。history 里的每一项，都是在该 epoch *进行当中*、取自那次权重更新之前的前向传播测出的损失。所以最后一项描述的是模型已经不再持有的权重，照着它挑 checkpoint 会整整晚存一轮。`evaluate` 在整份数据上跑 1 次推理模式的前向传播，用编译进去的损失函数打分。它什么都不更新：不算梯度、不动参数，也不碰 `BatchNormalization` 的滑动统计量。所以建立在 `evaluate` 之上的筛选规则，不会改变它正在度量的这次训练。

```rust
use ndarray::Array;
use rustyml::error::Error;
use rustyml::neural_network::Tensor;
use rustyml::neural_network::layers::activation::linear::Linear;
use rustyml::neural_network::layers::dense::Dense;
use rustyml::neural_network::losses::MeanSquaredError;
use rustyml::neural_network::optimizers::SGD;
use rustyml::neural_network::Shape;
use rustyml::neural_network::sequential::{Sequential, SequentialBuilder};

fn make_arch() -> Sequential {
    SequentialBuilder::new()
        .add(Dense::new(3, Linear::new()).unwrap())
        .add(Dense::new(2, Linear::new()).unwrap())
        .build(&Shape::with_free_batch(&[2, 4]))
        .unwrap()
}

fn main() -> Result<(), Error> {
    let x: Tensor = Array::from_shape_vec((2, 4), vec![0.1f32, 0.2, 0.3, 0.4, -0.1, -0.2, -0.3, -0.4])
        .unwrap()
        .into_dyn();
    let y: Tensor = Array::from_shape_vec((2, 2), vec![1.0f32, 0.0, 0.0, 1.0])
        .unwrap()
        .into_dyn();

    let mut model = make_arch();
    model.compile(SGD::new(0.05, 0.0, false, 0.0).unwrap(), MeanSquaredError::new());

    let path = "best.bin";
    let mut best = f32::INFINITY;
    for round in 0..10 {
        model.fit(&x, &y, 2)?;
        let val = model.evaluate(&x, &y)?;
        if val < best {
            best = val;
            model.save_to_path(path)?; // 覆盖上一个 checkpoint
            println!("round {round}: new best {val:.6}, checkpoint written");
        }
    }

    // best.bin 保存的是损失最低的权重，未必是最后一轮的权重。
    let mut deployed = make_arch();
    deployed.load_from_path(path)?;
    // evaluate 要的是编译进来的损失函数。顺手传给它的优化器它一次都不会碰。
    deployed.compile(SGD::new(0.05, 0.0, false, 0.0).unwrap(), MeanSquaredError::new());
    assert_eq!(deployed.evaluate(&x, &y)?, best);

    std::fs::remove_file(path).unwrap();
    Ok(())
}
```

最后这一步用的是精确相等，而不是容差。重新加载的权重与保存下去的逐位相同，而 `evaluate` 在不含 dropout 的模型上是确定性的。所以恢复出的 checkpoint 打出的分数，必须等于当初让它被写下的那个分数。

**在程序之间迁移权重。** 一个训练用的二进制搭建架构、训练模型、调用 `save_to_path`。另一个独立的服务用二进制搭建*完全相同*的架构、调用 `load_from_path`。把 `make_arch` 函数放进公共模块或公共 crate 里给两边共用，这样这 2 个程序在架构上、以及在它构建所用的输入形状上，都不可能产生分歧。类型名、层数和构建形状这几项检查确实能抓到分歧，但要等到一次失败的加载之后。共用同一个构造函数则能在编译期就抓到同样的分歧。服务用的二进制永远不需要调用 `compile`，因为它只调用 `predict`。

**跨 crate 升级的版本管理。** 每个保存下来的模型都以一个魔数和一个格式版本开头，`load_from_path` 会在解码任何其他内容之前先校验这两者。所以一个出自不同权重布局版本的 checkpoint，会立刻以 `IoError::UnsupportedModelFormat` 报错。要是没有这道检查，加载过程可能会把文件解析成看起来正确、实际数值却错误的数组。头部之后运行的结构检查，比的是层数、类型名、构建形状，以及每个数组的名字、kind 和形状。一个过时文件可能把它们统统凑巧满足：一个方形卷积核在轴被置换后尺寸不变，而一个 `Dense` 权重的形状无论上游是什么张量布局都长得一样。

这道防线能不能起作用，取决于背后的开发纪律。`MODEL_FORMAT_VERSION` 是 3，而版本 3 就是 [3.9.2](#392-具名-checkpoint每个数组-1-个地址) 里那套具名 checkpoint。它的构建记录每个输入存 1 个形状，所以 merge 层每个输入记 1 个形状，只有 1 个输入的层记 1 个。更早的版本一律不再能加载，拒绝的消息里会同时点出两个版本号。这类 checkpoint 要用本版本下搭出的模型重新保存一份。

只要记录的布局、结构体字段的顺序，或者某个字段的含义发生变化，RustyML 就把版本号往上跳一格。而新增一个层不需要跳版本号，因为新层带来的是一个类型名和若干数组名，两者在文件里都以字符串的形式传递。

跟着跳了的漂移会被拦下来，忘了跳的则拦不住，因为 postcard 依然是非自描述的，文件里再没有别的东西带标签。对于任何需要在几周后、几个版本后重新加载的 checkpoint，都要在 `Cargo.toml` 里锁定 RustyML 的版本。经过一次有意的升级之后，要么重新跑一遍训练，要么在旧版本下加载文件、再用新版本重新保存。不要拿一个旧文件去赌新代码。文件头带来的效果，是让版本相关的失败变得又响又早，而不是悄无声息。

## 3.9.9. 有意只加载文件的一部分

`load_partial_from_path` 是宽松加载，需要调用方指名去要。只要某个位置上的层类型相同、双方在构建形状上一致，且文件里给出相同的名字、相同的 kind 和相同的形状，它就写入这个数组。整份层名单一律不会失败。它返回一个 `LoadReport`，里面是 3 组 checkpoint 路径：`applied` 是拿到了值的，`missing` 是模型里没拿到值的，`unused` 是文件里没落到任何数组上的。形状或 kind 对不上的数组会同时出现在 `missing` 和 `unused` 里，因为模型没为它拿到值，而文件里的值也没去处。层类型或构建形状不一致的位置，会把这个层的每一条路径同时放进两份名单，因为名字加形状分不开 2 个归一化层。

文件头依旧会被校验。另一个格式版本的文件，其字节含义完全不同，所以在这里同样是错误。

```rust
use rustyml::error::Error;
use rustyml::neural_network::Shape;
use rustyml::neural_network::layers::activation::linear::Linear;
use rustyml::neural_network::layers::dense::Dense;
use rustyml::neural_network::sequential::SequentialBuilder;

fn main() -> Result<(), Error> {
    let saved = SequentialBuilder::new()
        .add(Dense::new(3, Linear::new()).unwrap())
        .add(Dense::new(2, Linear::new()).unwrap())
        .build(&Shape::with_free_batch(&[2, 4]))
        .unwrap();
    let path = "partial_demo.bin";
    saved.save_to_path(path)?;

    // 目标模型保留第一层，把第二层加宽。
    let mut target = SequentialBuilder::new()
        .add(Dense::new(3, Linear::new()).unwrap())
        .add(Dense::new(5, Linear::new()).unwrap())
        .build(&Shape::with_free_batch(&[2, 4]))
        .unwrap();

    // 严格加载会拒绝，消息里点名那条对不上的路径。
    let refusal = target.load_from_path(path).unwrap_err();
    println!("strict: {refusal}");

    // 宽松加载取走对得上的部分，并报告其余部分。
    let report = target.load_partial_from_path(path)?;
    println!("applied: {:?}", report.applied);
    println!("missing: {:?}", report.missing);
    println!("unused:  {:?}", report.unused);

    std::fs::remove_file(path).unwrap();
    Ok(())
}
```

```text
strict: model structure mismatch: `1.kernel` has shape [3, 5] in the model, and [3, 2] in the file
applied: ["0.kernel", "0.bias"]
missing: ["1.kernel", "1.bias"]
unused:  ["1.kernel", "1.bias"]
```

这就是迁移学习那条路：把训练好的骨干加载进一个换了头或改了头尺寸的模型，然后读 `missing`，确认没被填上的只有头部。再读 `unused`，确认文件里没有本想留下的东西被丢掉。要把非空的 `missing` 当成一个需要核对的结果，而绝不是一条可以略过的警告。其余场合仍然该用严格加载，包括恢复一次训练，因为那里文件和模型必须完全一致。

想更深入了解这套持久化机制，见 [7.2. 深入模型持久化](../Chapter-07/7.2._深入模型持久化.md)：那一节讲了文件的记录布局、两趟式的加载，以及同一套 postcard 格式如何服务于经典估计器。
