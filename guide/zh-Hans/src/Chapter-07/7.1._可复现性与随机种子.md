# 7.1. 可复现性与随机种子

RustyML 里每个带随机性的组件，都通过同一个关口取随机数：crate 级别的 `random` 模块。一个种子就能锁定整场实验。规则本身很简单，但有两条推论和 NumPy 进程全局的 `np.random` 不一样，那就是顺序敏感和线程局部。RustyML 同时提供 scikit-learn 那种按估计器设置的 `random_state`，也提供 Keras 那种全局的 `keras.utils.set_random_seed`。本页说明这两者如何相互配合。

## 7.1.1. 两个公开入口

整个公开接口就是两个自由函数，在 crate 根部重新导出：

```rust,ignore
pub fn set_global_seed(seed: u64);
pub fn clear_global_seed();
```

`set_global_seed` 为调用它的线程装上一个种子。`clear_global_seed` 把它移除，恢复到基于熵的行为。没有 getter，也没有需要到处传递的全局对象。你不需要自己构造按次调用的 RNG。

取而代之，每个组件接收一个 `Option<u64>` 种子，通常表现为 `.with_random_state(seed)` 构建器方法，或者 `random_state` 参数。内部的解析器会把这个值和全局种子协调起来。在构造那些想固定随机性的模型之前，先调用一次 `set_global_seed`。这样一来，下游的一切也都随之变得可复现。

两个内部解析器负责协调组件的种子和全局种子。`make_rng(random_state)` 总是返回一个具体的 RNG。没有种子生效时，它会回退到操作系统熵。几乎每个组件都用它。

`make_rng_opt(random_state)` 则返回 `Option<StdRng>`。当局部种子和全局种子都不生效时，它给出 `None`。这个 `None` 意味着没有人请求随机化。`DecisionTree` 用的正是这第二种形式（见 [2.4. 决策树](../Chapter-02/2.4._决策树.md)）。这让分裂时的平局处理，在你没有要求随机性时保持完全确定。用了 `make_rng_opt`，一棵未播种的树完全不会对平局做随机化，连熵都不会用上。

## 7.1.2. 三路种子解析规则

给定一个组件的 `random_state: Option<u64>` 和线程局部的全局种子，规则的解析方式如下：

| 组件的 `random_state` | 是否设置了全局种子？ | 结果 |
| --- | --- | --- |
| `Some(seed)` | 任意 | 直接使用 `seed`。**忽略全局流，也不去动它**。 |
| `None` | 是 | 让全局流前进一步，派生出一个独立的子种子。 |
| `None` | 否 | 从操作系统熵播种。**不可复现**。 |

下面的代码展示了这个机制：

```rust,ignore
match random_state {
    Some(seed) => StdRng::seed_from_u64(seed),           // 独立；不动全局
    None => match global_seed_rng {
        Some(global) => StdRng::seed_from_u64(global.next_u64()), // 从流里取子种子
        None => StdRng::from_rng(&mut rng()),            // 到处都没种子：操作系统熵
    },
}
```

两个分支并不对称。显式的 `Some(seed)` 只根据那个数字构建 RNG。它从不在全局流上调用 `next_u64()`。而全局种子之下的 `None` 会*从流里消耗一次抽取*。

全局种子的行为就像一台子种子发生器：它按未播种抽取请求它们的先后顺序，把子种子分发出去。显式的 `Some` 种子完全不碰这条流就能完成解析。这是否会让*整个组件*都变得惰性，取决于组件在什么时候抽取。7.1.3 节会说明组件何时才算真正惰性。

## 7.1.3. 顺序敏感，以及种子何时真正惰性

这条规则有两个推论在实践中要紧。其中一个是常见的陷阱。

第一个推论是顺序敏感。未播种的组件按请求的先后顺序从共享流里取子种子，因此它们能否复现取决于构造顺序。先建模型 A 再建模型 B，各自会拿到一个特定的子种子。换成先建 B 再建 A，两个子种子就会对调。这正是 Keras 全局种子的行为，也意味着全局种子只能复现那些构造顺序同样相同的运行。

第二个推论是惰性，这里你必须精确说清什么才算惰性。解析器保证 `make_rng(Some(seed))` 绝不在全局流上调用 `next_u64()`。显式种子不会从流里消耗任何东西。但这是否让*整个组件*都惰性，取决于组件究竟在何时抽取。RustyML 把组件分成两大类：

- **延迟抽取的估计器**：`KMeans`、`SVC`、`LinearSVC`、`IsolationForest`、`DecisionTree`、`t-SNE`、`train_test_split`，以及 `Sequential` 的 shuffle 种子。它们把 `random_state` 存成一个普通字段，只在 `fit` 内部解析一次。对它们而言，惰性自始至终成立。用 `.with_random_state(s)` 构造时不碰任何东西。拟合时用种子 `s`，不会推进全局流。所以把这样一个估计器插进流水线，其他每个未播种估计器的子种子都不受影响。
- **急切初始化的 NN 层**：`Dense`、dropout 和噪声层，以及卷积层和循环层。它们在*构造时*就通过 `make_rng(None)` 初始化各自的权重或掩码，这会从全局流里抽走一个子种子。`.with_random_state(s)` 是一次事后的重新初始化。它会覆盖该层自己的权重，但它的 `Dense::new` 已经取走的那个子种子再也回不来了。一个已播种的层照样会把全局流推进整整一步。决定它之后所建各层子种子的，是它的*构造*，而不是它有没有播种。

急切初始化这一类最容易出错。下面的程序在两个未播种的层之间插进一个 `.with_random_state(999)` 的层，看看它*之后*那个层如何发生偏移，原因是被插进来的层的 `Dense::new` 在进场路上消耗了一个子种子：

```rust
use ndarray::Array2;
use rustyml::neural_network::Tensor;
use rustyml::neural_network::layers::Activation;
use rustyml::neural_network::layers::dense::Dense;
use rustyml::neural_network::traits::Layer;
use rustyml::{clear_global_seed, set_global_seed};

fn row() -> Tensor {
    Array2::from_shape_vec((1, 4), vec![0.5, -1.0, 2.0, 0.25])
        .unwrap()
        .into_dyn()
}

fn max_abs_diff(a: &Tensor, b: &Tensor) -> f32 {
    a.iter()
        .zip(b.iter())
        .map(|(x, y)| (x - y).abs())
        .fold(0.0_f32, f32::max)
}

fn main() {
    let x = row();

    // 运行 A：两个连续的未播种层依次取走子种子 #1 和子种子 #2。
    set_global_seed(42);
    let a1 = Dense::new(4, 3, Activation::Linear).unwrap();
    let a2 = Dense::new(4, 3, Activation::Linear).unwrap();

    // 运行 B：完全相同，只是中间插进了一个 .with_random_state(999) 的层。
    set_global_seed(42);
    let b1 = Dense::new(4, 3, Activation::Linear).unwrap();
    let _seeded = Dense::new(4, 3, Activation::Linear)
        .unwrap()
        .with_random_state(999);
    let b2 = Dense::new(4, 3, Activation::Linear).unwrap();
    clear_global_seed();

    let (pa1, pa2) = (a1.predict(&x).unwrap(), a2.predict(&x).unwrap());
    let (pb1, pb2) = (b1.predict(&x).unwrap(), b2.predict(&x).unwrap());

    // 第一个未播种层不受影响：同样的种子，同样的构造位置。
    assert_eq!(max_abs_diff(&pa1, &pb1), 0.0);

    // 两个连续的未播种层各不相同：它们之间流前进了一步。
    assert!(max_abs_diff(&pa1, &pa2) > 1e-4);

    // b2 与 a2 不匹配。被插入层的 Dense::new 在 with_random_state 重新初始化
    // 它之前就取走了一个子种子，所以 b2 拿到的是子种子 #3，而不是 #2。
    assert!(max_abs_diff(&pa2, &pb2) > 1e-4);

    println!("layer construction advances the global stream, seeded or not");
}
```

两类的结论是一样的：想让一次运行在插入或重排随机组件的重构中存活下来，就给每个组件配上它自己的显式 `random_state`。不要依赖全局流的顺序。

对延迟抽取的估计器来说，显式种子能把它彻底解耦。对急切初始化的层来说，显式种子固定的是该层自己的权重，此外你还必须保证从播种调用到每次抽取之间，层的构造顺序保持稳定。固定、线性的流水线适合用全局种子。真正稳健的选择，是给每个组件配上显式种子。

## 7.1.4. 线程局部语义

全局种子存放在一个 `thread_local!` 单元里。这让 `set_global_seed` 无锁，也不会有争用。但它也带来一个硬性后果。**种子只影响调用了 `set_global_seed` 的那个线程。** 在构造模型的同一个线程上设置它，一切正常。把构造挪到另一个线程，种子在那里就变得不可见了。

这一点在三种场景下要紧。

**派生线程与异步运行时。** 你用 `std::thread::spawn` 启动的 worker 线程，或者 `tokio`、`rayon` 里的任务，一开始都没有全局种子，会回退到熵。在每个 worker 顶部调用 `set_global_seed`。更好的办法，是给每个组件一个显式 `random_state`，因为它天生与线程无关。

**内部并行。** 有些估计器会在并行化之前，先在调用线程上把 RNG 构建好。`KMeans` 每次重启都会新建一个 k-means++ RNG，并且总是发生在任何并行工作之前。`n_init` 默认是 10。所以全局种子每次重启都够得着。

`IsolationForest` 是个例外。它*在每棵树的闭包内部*各构造一个 RNG。一旦 `n_estimators >= 10`，这些闭包就会通过 `into_par_iter()` 跑在 Rayon 的 worker 线程上。

走 `None` 路径时，每个 worker 都会调用解析器。worker 找不到线程局部的全局种子，因为种子在你的线程上，不在 worker 的线程上，于是它回退到熵。**单靠一个全局种子，并不能让并行的 `IsolationForest` 可复现。**

显式路径正是为了绕开这个问题而设计的。`.with_random_state(s)` 给第 `i` 棵树种子 `s + i`。它不引用任何线程局部状态，所以无论哪个 worker 跑哪棵树，结果都能一模一样地复现。

凡是在 worker 线程上构建随机性的组件，都用显式 `random_state`，别用全局种子。并行何时开始起作用，见 [7.3. 性能调优与并行](./7.3._性能调优与并行.md)。

**测试框架。** Rust 默认的测试框架会为每个测试派生一个全新线程，因此每个测试起步时全局种子都是未设置的，这带来了干净的隔离。可一旦用 `cargo test -- --test-threads=1`，所有测试就会改成跑在同一个共享线程上。某个调用了 `set_global_seed` 的测试，会把那个种子泄漏给之后每一个本该走未播种（熵）行为的测试。之后要用一个 drop guard 把种子清掉，这样即使 panic 也能正常清理。crate 自己的集成测试用的正是这个模式：

```rust,ignore
#[must_use]
pub struct GlobalSeedGuard;

impl GlobalSeedGuard {
    pub fn set(seed: u64) -> Self {
        rustyml::set_global_seed(seed);
        GlobalSeedGuard
    }
}

impl Drop for GlobalSeedGuard {
    fn drop(&mut self) {
        rustyml::clear_global_seed(); // 即使 panic/展开也会运行
    }
}
```

把它绑到一个变量上，比如 `let _seed = GlobalSeedGuard::set(123);`。这样它就能活过整个测试主体，并在退出时清理。一个没绑定的调用，`GlobalSeedGuard::set(123);`，会立即析构。它会在你用上种子之前，就把种子清掉。这就是为什么这个类型带着 `#[must_use]`。

## 7.1.5. 整个 crate 中哪些地方会抽取随机数

下面列出的一切都走同一个解析器。在构造它们的那个线程上，一个全局种子就能全部覆盖，但要记得上一节里关于并行的例外。每一行还列出了按组件的覆盖方式。想摆脱构造顺序或调用线程的束缚时，就用这个覆盖。

| 组件 | 如何播种 | 全局种子能否到达？ | 说明 |
| --- | --- | --- | --- |
| NN 层权重初始化（`Dense`、卷积、循环……） | `.with_random_state(seed)` | 能 | 重跑 Xavier/Glorot 均匀初始化。要在训练*之前*调用。见 [3.2](../Chapter-03/3.2._全连接层与激活函数.md)。 |
| Dropout / 空间 dropout / 高斯噪声掩码 | `.with_random_state(seed)` | 能 | 掩码 RNG 归该层所有。见 [3.8](../Chapter-03/3.8._正则化与归一化层.md)。 |
| `Sequential` 小批量 shuffle | `.set_seed(seed)` 或 `Sequential::new_with_seed(seed)` | 能（种子字段默认为 `None`） | 只影响 `fit_with_batches`。不碰层的权重。见 [3.1](../Chapter-03/3.1._Sequential模型.md)。 |
| `KMeans`（k-means++ 初始化） | `.with_random_state(seed)` | 能 | RNG 在调用线程上按 k-means++ 的每次重启重新构建（`n_init` 默认为 10）。见 [2.7](../Chapter-02/2.7._KMeans聚类.md)。 |
| `SVC` / `LinearSVC` | `.with_random_state(seed)` | 能 | 工作集选择（`SVC`）与小批量 shuffle（`LinearSVC`）。见 [2.5](../Chapter-02/2.5._支持向量机.md)。 |
| `estimate_bandwidth`（Mean Shift 辅助函数） | `estimate_bandwidth(x, quantile, n_samples, Some(seed))` | 能 | 随机性在于子采样。`MeanShift::fit` 本身，包括 bin seeding，是确定的。见 [2.9](../Chapter-02/2.9._MeanShift.md)。 |
| `IsolationForest` | `.with_random_state(seed)` | **并行路径上不能** | 一旦 `n_estimators >= 10`，要复现就必须用显式种子。每棵树的种子是 `seed + i`。见 [2.13](../Chapter-02/2.13._孤立森林.md)。 |
| 决策树分裂平局处理 | `.with_random_state(seed)` | 能 | 使用 `make_rng_opt`：只有种子生效时才对平局做随机化，否则完全确定。 |
| `t-SNE` 随机初始化 | `.with_random_state(seed)` **且** `.with_init(Init::Random)` | 能 | 默认的 `Init::PCA` 是确定的，会忽略 `random_state`。见 [2.12](../Chapter-02/2.12._t-SNE.md)。 |
| `train_test_split` / `train_test_split_stratified` | `random_state: Option<u64>` 参数 | 能 | 控制索引 shuffle。见 [4.1](../Chapter-04/4.1._训练集与测试集划分.md)。 |

有两行值得再看一眼。`t-SNE` 的种子在默认代码路径上什么也不做。`Init::PCA` 用最大的几个主成分来初始化嵌入，这是确定的。所以只有当你切换到 `.with_init(Init::Random)` 之后，`random_state` 才有意义。

Mean Shift 常被误认为是带种子的估计器。`MeanShift` 结构体压根没有 `random_state` 字段。那个模块里唯一的抽取，是自由函数 `estimate_bandwidth` 内部那次可选的子采样。而这个辅助函数是你自己调用来挑选带宽的。

### 有意排除在外的部分

并不是 crate 里每一次伪随机抽取都会经过这个模块，只有那些对结果有持久影响的才会。`pca` 和 `kernel_pca` 这两个降维器是有意排除在外的。

它们的迭代特征求解器（幂迭代、Lanczos）用一个固定常数去播种随机的*起始向量*。这类方法无论起始向量取什么，都会收敛到同一组特征向量。所以这个种子在可观测的意义上是惰性的。它只固定了本来任意的特征向量符号。把它接进全局状态，只会让这个符号选择*更*不可复现，没有任何好处。

随机化 SVD（`pca` 的 `SVDSolver::Randomized(u64)`）把种子放在公开的求解器变体里接收。调用方总是显式固定它，根本没有留给全局去填的 `None` 路径。总的规则是：只有当一次抽取会做出改变结果的伪随机选择时，才让它经过这个模块。

## 7.1.6. 种子固定不了什么

种子让*伪随机选择*可复现，但它并不能让一次运行的每个部分都逐位相同。

**浮点归约顺序是另一个维度。** 并行地对一个向量求和，或者做矩阵乘积，结果的最后几位可能跟串行求和不同。浮点加法不满足结合律，这跟播种毫无关系。如果你需要逐位稳定的数值结果，请用并行相关的控制项去调，而不是种子。见 [6.3. 并行归约](../Chapter-06/6.3._并行归约.md) 和 [7.3. 性能调优与并行](./7.3._性能调优与并行.md)。

**跨机器的逐位一致没有保证。** 同一个种子下，两台机器会做出同样的随机选择。但浮点舍入、SIMD 宽度、线程数，以及不依赖 BLAS 的矩阵乘法后端在归约顺序上的差异，仍可能让最终权重在低位上不同。同一个种子给出的是同一*串决策*，它不会给你跨架构逐字节相同的浮点数。

**种子既跨不过线程跳转，也不会自己越过保存或加载的边界。** 从磁盘重新加载一个训练好的模型，得到的是它冻结的权重，而不是产生这些权重的 RNG 流。如果你要在重新加载的模型上继续训练，请在当前线程上重新设定种子。见 [7.2. 深入模型持久化](./7.2._深入模型持久化.md)。

## 7.1.7. 实用范式

### 可复现实验模板

对于单线程上一条线性的构造序列，在开头调用一次 `set_global_seed`。这是让整条流水线可复现最简单的办法。把每个组件都留成未播种（`random_state == None`），让它们按顺序从流里取各自的子种子。这也包括 `Sequential` 的 shuffle，它的种子字段默认为 `None`，因此同样归全局种子管：

```rust
use ndarray::Array2;
use rustyml::neural_network::Tensor;
use rustyml::neural_network::layers::Activation;
use rustyml::neural_network::layers::dense::Dense;
use rustyml::neural_network::losses::MeanSquaredError;
use rustyml::neural_network::optimizers::SGD;
use rustyml::neural_network::sequential::Sequential;
use rustyml::set_global_seed;

fn t2(rows: usize, cols: usize, data: Vec<f32>) -> Tensor {
    Array2::from_shape_vec((rows, cols), data).unwrap().into_dyn()
}

fn main() {
    // 开头调用一次。下面每次未播种的抽取都按顺序从它派生。
    set_global_seed(2026);

    #[rustfmt::skip]
    let x = t2(4, 4, vec![
        0.5, -1.0,  2.0,  0.25,
        1.0,  0.0, -0.5,  1.5,
       -2.0,  0.5,  1.0, -1.0,
        0.25, 2.0, -1.5,  0.0,
    ]);
    let y = t2(4, 1, vec![1.0, 0.0, -1.0, 0.5]);

    let mut model = Sequential::new(); // 没有按层种子，也没有显式 set_seed
    model
        .add(Dense::new(4, 3, Activation::ReLU).unwrap())   // 子种子 #1
        .add(Dense::new(3, 1, Activation::Linear).unwrap()) // 子种子 #2
        .compile(SGD::new(0.05, 0.0, false, 0.0).unwrap(), MeanSquaredError::new());

    // batch_size < n_samples 会触发每个 epoch 的 shuffle（子种子 #3）。
    model.fit_with_batches(&x, &y, 5, 2).unwrap();

    let p = model.predict(&t2(1, 4, vec![0.5, -1.0, 2.0, 0.25])).unwrap();
    println!("prediction shape: {:?}", p.shape());
}
```

跑两遍这个程序，训练出的权重是逐字节相同的。构造顺序——两次层初始化，然后是 shuffle 的 RNG——每次都从 `2026` 这条流里取走同样的三个子种子。你一旦重排那几个 `.add` 调用，子种子的分配就会变化，这就是 7.1.3 节里顺序敏感的具体体现。

### 按组件的 `random_state` 覆盖

当你想让每个组件都独立于构造顺序、也独立于哪个线程在运行它时，就直接在每个组件上设置 `random_state`。对库代码、并行估计器，以及你经常重构的代码来说，这都是稳健的选择。显式种子完全无视全局流，这也是你在放开其余组件的同时、单独复现某一个组件的办法：

```rust
use ndarray::{Array1, Array2, array};
use rustyml::prelude::*;

fn main() {
    // 两团彼此分得很开的点，6 个样本，2 个特征。
    let x: Array2<f64> = array![
        [0.0, 0.0], [0.2, 0.1], [0.1, -0.2],
        [5.0, 5.0], [5.2, 4.9], [4.8, 5.1],
    ];
    let y: Array1<usize> = array![0, 0, 0, 1, 1, 1];

    // 相同的 random_state => 相同的索引 shuffle => 每次运行都是相同的划分。
    let split_a = train_test_split(x.clone(), y.clone(), Some(0.5), Some(42)).unwrap();
    let split_b = train_test_split(x.clone(), y.clone(), Some(0.5), Some(42)).unwrap();
    assert_eq!(split_a.0, split_b.0); // x_train 相同
    assert_eq!(split_a.2, split_b.2); // y_train 相同

    // 相同的 random_state => 相同的 k-means++ 初始化 => 相同的标签，与上面无关。
    let labels_1 = KMeans::new(2, 100, 1e-4)
        .unwrap()
        .with_random_state(7)
        .fit_predict(&x)
        .unwrap();
    let labels_2 = KMeans::new(2, 100, 1e-4)
        .unwrap()
        .with_random_state(7)
        .fit_predict(&x)
        .unwrap();
    assert_eq!(labels_1, labels_2);

    println!("split and k-means both reproducible under explicit seeds");
}
```

两种风格可以随意混用。一种常见的写法是：用 `set_global_seed` 给环境定下默认值，再在你需要固定住的那个估计器上加一个显式的 `random_state`，同时对其余一切做扫描。显式种子对全局流是惰性的，所以固定这一个估计器，不会扰动其他每个组件拿到的子种子。
