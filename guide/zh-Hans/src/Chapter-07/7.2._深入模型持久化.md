# 7.2. 深入模型持久化

RustyML 提供两套模型持久化方案，它们共用同一种 wire format，但在关键处各走各的路——分清这条分界线，你手上要么是一份可信赖的 checkpoint，要么是个会悄悄读回错误数字的文件。经典 estimator 序列化的是*整个*模型：超参数、学到的参数、训练时的元数据一并写入，加载后直接得到一个能预测的对象，无需任何重建。神经网络只序列化*权重*：架构要你在代码里重新搭出来，再把数组灌回去。两者写出的都是 [postcard](https://docs.rs/postcard)——一种紧凑、非自描述的二进制格式，这一个选择就解释了为什么文件这么小、为什么只有 Rust 读得了、以及为什么跨版本加载会成为一个隐患。而两条路应对这个隐患的方式并不相同：神经网络的文件以一个魔数和一个格式版本开头，加载器最先校验它们，所以不兼容的版本会响亮地失败；经典模型的文件则完全没有头部，跨版本这道坎全得你自己兜。本页是 [3.9. 权重保存与加载](../Chapter-03/3.9._权重保存与加载.md) 的幕后篇：3.9 教你神经网络的工作流，这里则把两个世界都拆到字节层面，讲清它们的失败面，以及那两个便捷方法不会白送给你的运维套路——版本管理、原子写入和互操作。

## 7.2.1. 两套 API，同一种格式

两个子系统故意暴露出不同的签名；要是你以为它们是同一个方法，这点差异就会咬你一口。

```rust,ignore
// 经典 ML 模型——由 lib.rs 中的 `model_save_and_load_methods!` 宏生成：
impl LinearRegression {
    pub fn save_to_path(&self, path: &str) -> Result<(), rustyml::error::Error>;
    pub fn load_from_path(path: &str) -> Result<Self, rustyml::error::Error>;
}

// Sequential 神经网络：
impl Sequential {
    pub fn save_to_path(&self, path: impl AsRef<std::path::Path>) -> rustyml::error::RustymlResult<()>;
    pub fn load_from_path(&mut self, path: impl AsRef<std::path::Path>) -> rustyml::error::RustymlResult<()>;
}
```

有三处不对称值得记住。第一，经典的 `save_to_path`/`load_from_path` 只收 `&str`，不是 `impl AsRef<Path>`，所以一个 `PathBuf` 得显式写 `.to_str().unwrap()`，否则就是类型错误；而神经网络那两个方法接受任意 `AsRef<Path>`。第二，经典的 `load_from_path` 是一个*关联函数*，返回一个拥有所有权的 `Self`（没有什么可以*加载进去*的对象，因为整个模型都从磁盘上取回来了），而 `Sequential::load_from_path` 收 `&mut self`，改写的是一个你已经搭好的模型。第三，`RustymlResult<()>` 不过是 `Result<(), Error>` 的别名，所以两边的错误类型完全一致——每一次失败都是本 crate 统一 [`Error`](../Chapter-01/1.6._错误处理.md) 的某个变体。生成经典这一对方法的宏，就是 `lib.rs` 里的 `model_save_and_load_methods!`，它原样套用到 `LinearRegression`、`LogisticRegression`、`KNN`、`DecisionTree`、`SVC`、`LinearSVC`、`LDA`、`KMeans`、`DBSCAN`、`MeanShift`、`PCA`、`KernelPCA` 和 `IsolationForest` 上——经典模块里的每一个模型都得到同样的两个方法，行为也一样。

## 7.2.2. 经典 ML：整个模型落盘

宏体短到可以整个装进脑子里：`save_to_path` 调用 `postcard::to_allocvec(self)`，再通过一个带缓冲的 writer 把字节写出去；`load_from_path` 读入文件，调用 `postcard::from_bytes::<Model>(&bytes)`。由于模型结构体 derive 了 `Serialize` 和 `Deserialize`，*每一个字段*都会随之传输——对 `LinearRegression` 而言就是 `coefficients`、`intercept`、`fit_intercept`、拟合后的 `n_iter`、`regularization_type`，以及 `solver` 枚举——它是 `LeastSquaresSolver`，选中梯度下降时，`learning_rate` / `max_iter` / `tol` 这套载荷就装在它自己里面。这里没有分开的“配置”和“权重”；在神经网络那一侧占主导地位的那条界线，在这里根本不存在。这正是加载出来的模型可以立刻使用的原因：`load_from_path` 交还给你的对象，与你训练出的那个别无二致，不用 `fit`，不用重新配参，也没有编译步骤。

```rust
use rustyml::machine_learning::*;
use ndarray::{Array1, Array2};

fn main() {
    let x = Array2::from_shape_vec((4, 2), vec![1.0, 2.0, 2.0, 1.0, 3.0, 5.0, 4.0, 3.0]).unwrap();
    let y = Array1::from_vec(vec![5.0, 5.0, 13.0, 11.0]);

    let mut model = LinearRegression::new(true);
    model.fit(&x, &y).unwrap();

    let path = "lr_whole_model.bin";
    model.save_to_path(path).unwrap();

    // 加载得到一个完全可用的模型——无需重新拟合、无需重建、无需编译步骤。
    let restored = LinearRegression::load_from_path(path).unwrap();

    // 学到的参数和超参数都熬过了这趟往返。
    assert_eq!(restored.get_solver(), model.get_solver());
    assert_eq!(restored.get_coefficients().unwrap().len(), 2);

    let probe = Array2::from_shape_vec((1, 2), vec![2.0, 4.0]).unwrap();
    let a = model.predict(&probe).unwrap();
    let b = restored.predict(&probe).unwrap();
    println!("live vs restored prediction gap: {:e}", (a[0] - b[0]).abs());

    std::fs::remove_file(path).unwrap();
}
```

如果你是从 scikit-learn 的 `pickle`/`joblib` 过来的，这在*心智*模型上是一回事——整个 estimator 往返一趟——但有两点老实话要交代。postcard 不是 `pickle`：它加载时不执行任何代码，所以恶意文件带不来任意代码执行的风险，只可能有畸形或对不上号的字节。而且 postcard 不携带类身份、没有 `__module__`、没有版本戳——这恰恰是接下来几节要谈的内容。

## 7.2.3. 神经网络：权重，以及承载它们的枚举

神经网络这条路在 [3.9](../Chapter-03/3.9._权重保存与加载.md) 里有从头到尾的讲解；这里把机制往下再挖一层。`Sequential::save_to_path` 会构建一个 `SerializableSequential { magic, format_version, layers: Vec<SerializableLayer> }`，其中每个 `SerializableLayer` 把一个 `LayerInfo { layer_type, output_shape }` 元数据标签，和一个从 `layer.get_weights()` 拿到的 `LayerWeight<'a>` 枚举值配成一对。开头那两个 `u32` 就是文件头——`MODEL_MAGIC`（`"RMLM"`）和 `MODEL_FORMAT_VERSION`——它们排在最前面是刻意的：在头部存在之前写出的文件是以层数开头的，于是加载器会在本该是魔数的位置读到那个小整数，从而在解析到足以应用任何一个权重之前就把它拒掉。排在它们后面的枚举，才是落盘时的权重格式：

```rust,ignore
pub enum LayerWeight<'a> {
    Dense(DenseLayerWeight<'a>),
    SimpleRNN(SimpleRNNLayerWeight<'a>),
    LSTM(LSTMLayerWeight<'a>),
    GRU(GRULayerWeight<'a>),
    Conv1D(Conv1DLayerWeight<'a>),
    Conv2D(Conv2DLayerWeight<'a>),
    Conv3D(Conv3DLayerWeight<'a>),
    SeparableConv2D(SeparableConv2DLayerWeight<'a>),
    DepthwiseConv2D(DepthwiseConv2DLayerWeight<'a>),
    BatchNormalization(BatchNormalizationLayerWeight<'a>),
    LayerNormalization(LayerNormalizationLayerWeight<'a>),
    InstanceNormalization(InstanceNormalizationLayerWeight<'a>),
    GroupNormalization(GroupNormalizationLayerWeight<'a>),
    Empty, // 没有可训练参数的层：Dropout、pooling、flatten、纯激活层
}
```

有两处设计选择值得钉牢。每个 per-layer 结构体用 [`Cow`](https://doc.rust-lang.org/std/borrow/enum.Cow.html) 存放它的数组，于是同一个类型能服务于两个方向——`get_weights` 用 `Cow::Borrowed` 借用活着的数组（保存时什么都不克隆），反序列化则填入 `Cow::Owned` 的数组，在加载路径上以 `LayerWeight<'static>` 的身份使用。枚举采用 serde 默认的*外部标签（externally tagged）*表示法，在负载之前写入一个显式的变体判别值，因为 postcard 非自描述，否则根本分不清一段 `Dense` 负载和一段 `Conv2D` 负载。文件里刻意*缺席*的，是任何*构造器*信息：没有激活函数，没有 `epsilon`、`momentum`、stride、kernel size、dilation，也没有 group count。这些都活在你的源代码里。`LayerInfo` 中的 `layer_type` 和 `output_shape` 字符串是校验标签，不是搭建配方——这正是为什么加载需要一个预先搭好的模型来接住权重。

正是这个预先搭好的模型，让神经网络加载器能做到经典加载器做不到的事：**校验结构**。`load_from_path` 会检查层数，逐个位置拿 `layer_type` 字符串和你搭的模型比对，并且——在 `apply_weights_to_layer` 内部——把每一层向下转型成它的具体类型再调用 `set_weights`，于是形状不一致也逃不掉。这些检查中任何一个失败，都会抛出带具体信息、告诉你是哪一处出错的 `Error::Io(IoError::ModelStructureMismatch)`。经典那套宏没有对应物：它把字节直接反序列化进目标结构体，一点防护都没有。把一个 `LinearRegression` 文件喂给 `KMeans::load_from_path`，不会被任何类型检查拒绝——postcard 按位置读字节，你要么拿到一个 `Serialization` 错误（通常如此，当两边布局差得够远时），要么在字节碰巧凑得上另一套布局的倒霉情形下，得到一个看似解析成功、实则毫无意义的模型。对经典模型而言，横在你与这个结局之间的唯一屏障就是文件名或某个外部标签——请务必把它当回事。

## 7.2.4. postcard 的 wire format

postcard 是一种极简的二进制序列化格式，它有一个左右着其余一切的性质：**非自描述**。字节里按字段顺序装的是值，别无其他——没有字段名、没有类型名、没有 schema，也没有一个可供跳过的带长度前缀的信封。序列化 `LinearRegression` 不会在任何地方写下字符串 `"learning_rate"`；它写的是那个 `f64` 的八个字节，就摆在 `learning_rate` 在序列化后的 `LeastSquaresSolver` 里所处的位置上。这既是文件小得可怜的全部原因，也同样是它脆弱的原因：能否正确解读，完全取决于反序列化的一方是否持有与序列化一方*完全相同*的类型布局。

当你要推算文件大小、或调试一个损坏文件时，了解各类型的编码是值得的：

| Rust 类型 | postcard 编码 | 字节数 |
| --- | --- | --- |
| `bool` | 单字节 `0`/`1` | 1 |
| `f32`（神经网络权重） | 定宽小端 | 4 |
| `f64`（经典参数） | 定宽小端 | 8 |
| `usize` / `u64`（如 `max_iter`、长度） | LEB128 varint | 1–10 |

这份脆弱性并非空谈：本次发布里有好几个估计器改了字段布局。`LinearRegression` 把三个散落的迭代设置折进了求解器载荷，`KMeans` 多了 `n_init`，`LDA` 多了训练集总体均值。旧版本写出的二进制块加载不了——请重新拟合、重新保存。`MeanShift` 和 `IsolationForest` 更麻烦，因为它们改的是*含义*而不是布局：`MeanShift` 的二进制块里装的仍是旧高斯核找出来的中心，而 `IsolationForest` 的 `offset` 现在符号相反。这两个也请重新拟合。
| 枚举变体（`Solver`、`LayerWeight`） | varint 判别值 | 1（+ 负载） |
| `Option<T>` | 1 个标签字节（`0`=None，`1`=Some） | 1（Some 时 + `T`） |
| `String`（层类型标签） | varint 长度 + UTF-8 字节 | 不定 |
| ndarray `Array`（经 serde） | 小的版本/形状头 + varint 元素数量 + 元素 | 不定 |

浮点是定宽的，所以 `N` 个值的数组就是 `N × 4`（`f32`）或 `N × 8`（`f64`）字节，再加上形状头和长度前缀的那么几个字节——这趟往返无损，不是有损。整数和长度是 varint，所以小的计数只花一个字节。没有压缩，也没有对齐填充。格式的紧凑，恰恰就是它的脆弱：因为什么都没有标注，一个布局漂移过的结构体——写文件与读文件的两个版本之间，字段有增删、有重排，或改了类型——反序列化时没有任何名字可供核对。大概率的结果是一个 “unexpected end of input” 或坏标签的 `Serialization` 错误；危险的结果，是当漂移后的布局仍然恰好把字节消费完时，发生一次悄无声息的错误解析。这不是 postcard 的 bug——这是你为小文件付出的代价——也正因如此，版本管理（见下文）是你的责任，不是格式的责任。

## 7.2.5. 文件大小：一份可信的粗略估算

由于编码既无压缩也无分帧，文件大小可以精确预测到几个字节之内。对经典模型，负载由它学到的数组主导：一个有 `p` 个特征的 `LinearRegression`，本质上就是 `p × 8` 字节的系数，加上二三十字节的标量超参数和头部。对神经网络，则是逐层累加 `(weight_elements + bias_elements) × 4` 字节——因为神经网络权重是 `f32`——再加上每层那点类型/形状字符串。一个 `Dense(784 → 128)` 层是 `784 × 128 + 128 = 100,480` 个参数 ≈ 392 KB；同样的层放在经典的 `f64` 世界里则要翻一倍。与其猜，不如直接量：

```rust
use rustyml::machine_learning::*;
use ndarray::{Array1, Array2};

fn main() {
    let n_features = 8usize;
    let n_samples = 20usize;
    let x = Array2::from_shape_fn((n_samples, n_features), |(i, j)| (i + j) as f64 * 0.1);
    let y = Array1::from_shape_fn(n_samples, |i| i as f64);

    let mut model = LinearRegression::new(true);
    model.fit(&x, &y).unwrap();

    let path = "lr_size_probe.bin";
    model.save_to_path(path).unwrap();

    let on_disk = std::fs::metadata(path).unwrap().len();
    // 主导项：每个系数一个 f64。其余都是标量 + 小头部。
    let coefficient_bytes = (n_features * std::mem::size_of::<f64>()) as u64;
    println!("file: {on_disk} bytes, coefficient payload ~= {coefficient_bytes} bytes");

    std::fs::remove_file(path).unwrap();
}
```

由此带来的实际好处：postcard checkpoint 便宜到可以多留几份。对一个小模型跑“每个 epoch 存一次、留最好那份”的循环，每个 checkpoint 只花几个 KB，所以你多久快照一次，受限的是磁盘写入延迟，而非大小。对大型卷积堆叠，`f32` 权重占了大头，文件几乎精确地跟着参数量走，这让容量规划变得毫不费力：数一数参数，乘以四。

## 7.2.6. 加载到底会拒绝什么

每一次持久化失败都以 `Error::Io(...)` 浮现，底下正好有四种形态。`IoError::Std` 包裹一个 `std::io::Error`——路径不存在、权限问题、读或写失败。`IoError::UnsupportedModelFormat` 是神经网络专属的，来自头部校验：魔数或格式版本不是本次构建的那一个。`IoError::Serialization` 包裹一个 `postcard::Error`——字节对期望的布局来说不是有效的 postcard：损坏、截断，或 schema 不再匹配。`IoError::ModelStructureMismatch` 同样是神经网络专属的，如 7.2.3 所述，没有经典对应物。`error.rs` 里那两个 `From` 实现，正是让 `?` 能把一个裸的 `std::io::Error` 提升成 `IoError::Std`、把一个裸的 `postcard::Error` 提升成 `IoError::Serialization` 的东西，于是这个映射在两个子系统之间都自动且一致。`Error` 和 `IoError` 都是 `#[non_exhaustive]`，所以匹配它们时永远要带上一个兜底分支。

```rust
use rustyml::machine_learning::*;
use rustyml::error::{Error, IoError};

fn main() {
    // 一个装满字节、但对 LinearRegression 来说不是有效 postcard 的文件。
    let junk = "corrupt_lr.bin";
    std::fs::write(junk, b"\xff\xff\xff not a model").unwrap();

    match LinearRegression::load_from_path(junk) {
        Ok(_) => println!("unexpected success"),
        Err(Error::Io(IoError::Serialization(e))) => println!("bad bytes -> Serialization: {e}"),
        Err(Error::Io(IoError::Std(e))) => println!("io failure: {e}"),
        Err(e) => println!("other: {e}"),
    }
    std::fs::remove_file(junk).unwrap();

    // 一个不存在的路径会以 IoError::Std 的形式浮现，而不是 Serialization。
    match LinearRegression::load_from_path("no_such_model_9f3a.bin") {
        Err(Error::Io(IoError::Std(e))) => println!("missing file -> Std: {e}"),
        other => println!("unexpected: {other:?}"),
    }
}
```

神经网络的测试套件对照真实 API 把这些映射钉死了：一个不存在的路径产生 `IoError::Std`，错误的魔数或格式版本产生 `IoError::UnsupportedModelFormat`，*在头部合法的前提下*被弄坏的字节产生 `IoError::Serialization`，而层数、层类型、权重形状的不一致则统统产生 `IoError::ModelStructureMismatch`。给经典模型的教训，藏在这份清单的缺口里——没有结构性错误可抓，所以 `Serialization` 是文件出错的*唯一*信号，而它并不可靠。要是一个损坏的经典文件碰巧反序列化成功了，`load_from_path` 就返回 `Ok`。用你自己的完整性检查来防这一手——接下来两节要搭的正是它。

## 7.2.7. 跨 RustyML 版本的版本管理

postcard 文件不带版本戳，而 RustyML 也不保证模型结构体的字段布局在各版本间稳定。给 `LinearRegression` 加一个超参数、重排一个字段，或改一个类型，旧版本写出的文件对新版本来说就成了未定义到出错的输入——通常是一次 `Serialization` 失败，偶尔是一次悄无声息的错误解析。没有内建的迁移路径。两个习惯能让它不至于在生产环境里给你惊吓。

第一，把写出你那些长命 checkpoint 的 `rustyml` 版本精确锁定，这样一次例行的 `cargo update` 就没法在一整目录已保存的模型底下悄悄换掉磁盘布局：

```toml
[dependencies]
rustyml = { version = "=0.13.0", features = ["full"] }
```

第二，写一个版本*旁挂文件（sidecar）*：模型旁边一个记录格式身份的小小伴生文件，当它和你的二进制期望的版本对不上时就拒绝加载。这把一次悄无声息的错误解析，变成一个响亮而及早的错误。注意这里谁更需要它是分裂的：`Sequential` 的文件自带魔数和格式版本，跨不兼容版本时神经网络这条路本来就会响亮地失败，sidecar 只是在此之上再叠一层*你自己的* schema 身份。而经典模型那条宏路径压根没有头部，对它们来说 sidecar 就是全部防线。

```rust
use rustyml::machine_learning::*;
use ndarray::{Array1, Array2};

// 每当你升级写出 checkpoint 的 rustyml 依赖时，就把这个值往上抬一档。
const CHECKPOINT_FORMAT: &str = "rustyml-0.13";

fn main() {
    let x = Array2::from_shape_vec((3, 2), vec![1.0, 2.0, 2.0, 3.0, 3.0, 4.0]).unwrap();
    let y = Array1::from_vec(vec![6.0, 9.0, 12.0]);

    let mut model = LinearRegression::new(true);
    model.fit(&x, &y).unwrap();

    let model_path = "sidecar_model.bin";
    let version_path = "sidecar_model.bin.version";
    model.save_to_path(model_path).unwrap();
    std::fs::write(version_path, CHECKPOINT_FORMAT).unwrap();

    // 加载时，用记录下来的格式字符串给反序列化把关。
    let recorded = std::fs::read_to_string(version_path).unwrap();
    if recorded != CHECKPOINT_FORMAT {
        panic!("checkpoint written by {recorded}, this binary expects {CHECKPOINT_FORMAT}");
    }
    let restored = LinearRegression::load_from_path(model_path).unwrap();
    println!("loaded {} coefficients", restored.get_coefficients().unwrap().len());

    std::fs::remove_file(model_path).unwrap();
    std::fs::remove_file(version_path).unwrap();
}
```

用一个足够细、细到有意义的版本字符串——至少是 `rustyml` 版本，如果你把模型包进更大的记录里，再加上你自己的 schema 计数器。旁挂文件写起来不花什么成本，却把这个格式最糟的失败模式（悄悄给出错误数字）换成了一个你在测试里就能抓到的 `panic`。

## 7.2.8. 原子 checkpoint

两个 `save_to_path` 变体都调用 `File::create`，而它**会立刻截断目标文件**。如果进程崩溃、磁盘写满，或训练循环写到一半被杀，你就会在重启逻辑将要加载的那个确切路径上，留下一个被截断的文件——而截断，往好了说是一个 `Serialization` 错误，往坏了说是一个微妙地少了几个元素的数组。标准的防御是先写后改名：序列化到同一文件系统上的一个临时路径，再用 `std::fs::rename` 把它盖到最终路径上。在 POSIX 文件系统上 rename 是原子的，所以读者要么看到完整的旧文件、要么看到完整的新文件，绝不会看到写到一半的那个。

```rust
use rustyml::machine_learning::*;
use ndarray::{Array1, Array2};

/// 经由临时文件加一次原子 rename 来保存，这样写到一半崩溃也绝不会
/// 在 `final_path` 留下一个只写了一半的 checkpoint。
fn save_atomically(model: &LinearRegression, final_path: &str) -> std::io::Result<()> {
    let tmp_path = format!("{final_path}.tmp");
    model
        .save_to_path(&tmp_path)
        .expect("serialize to temp file");
    std::fs::rename(&tmp_path, final_path)
}

fn main() {
    let x = Array2::from_shape_vec((3, 2), vec![1.0, 2.0, 2.0, 3.0, 3.0, 4.0]).unwrap();
    let y = Array1::from_vec(vec![6.0, 9.0, 12.0]);

    let mut model = LinearRegression::new(true);
    model.fit(&x, &y).unwrap();

    let path = "atomic_model.bin";
    save_atomically(&model, path).unwrap();

    let restored = LinearRegression::load_from_path(path).unwrap();
    println!("intercept present after atomic save: {}", restored.get_intercept().is_some());

    std::fs::remove_file(path).unwrap();
}
```

把临时文件放在和目标同一个文件系统上——跨文件系统的 `rename` 不是原子的，会退化成复制加删除。把它和 7.2.7 的旁挂文件配起来用，做法是*先*给模型改名、*后*给版本文件改名，这样一次撕裂的写入，留下的是指向上一个完整模型的版本旁挂文件，而不是一个损坏的新模型。对一个“只留最好那份”的循环，原子替换还意味着你那份目前最优的文件永远不会有哪怕一瞬的缺席。

## 7.2.9. 跨越语言边界

postcard 是 Rust 生态的格式。没有一个有人维护的 Python 或 R 读取器，而且就算有，那些非自描述的字节没有一份手写的、镜像 RustyML 确切结构体布局的 schema 也毫无用处——而这个布局在版本间还会变。所以就把一个 `.bin` checkpoint 当成 RustyML 到 RustyML 的产物，别的什么都不是。当另一个工具必须消费一个训练好的模型时，别去解析那个 postcard 文件；**通过 getter 把参数导出**成对方本就能读的可移植格式。经典模型把你需要的一切都暴露了出来：`LinearRegression::get_coefficients` 和 `get_intercept`、`KMeans::get_centroids`，以及其他 estimator 上对应的访问器。

```rust
use rustyml::machine_learning::*;
use ndarray::{Array1, Array2};

fn main() {
    let x = Array2::from_shape_vec(
        (3, 3),
        vec![1.0, 0.0, 2.0, 0.0, 1.0, 1.0, 2.0, 2.0, 0.0],
    )
    .unwrap();
    let y = Array1::from_vec(vec![4.0, 3.0, 6.0]);

    let mut model = LinearRegression::new(true);
    model.fit(&x, &y).unwrap();

    // 通过 getter 把学到的参数取出来，输出可移植的 CSV，让
    // Python / R / 电子表格的消费方能直接读——不牵涉 postcard。
    let coefficients = model.get_coefficients().expect("model is fitted");
    let intercept = model.get_intercept().unwrap_or(0.0);

    let mut csv = String::from("term,value\n");
    for (i, c) in coefficients.iter().enumerate() {
        csv.push_str(&format!("x{i},{c}\n"));
    }
    csv.push_str(&format!("intercept,{intercept}\n"));

    print!("{csv}");
}
```

同样的套路可以推广：把 getter 的输出转储成 CSV 给电子表格或 pandas 的 `read_csv`，或者拼装成一个你的服务本就会说的 JSON 对象。对神经网络，遍历 `Sequential::get_weights()`，把每个 `LayerWeight` 变体的数组逐层写出——这些数组是 ndarray，所以 `.iter()` 加上你挑的格式化工具就够了。这么做，你付出的代价是 postcard 的紧凑，以及同格式往返所给的精确性保证，所以请把 postcard 文件留作你*加载回 RustyML* 的规范 checkpoint，把导出的 CSV/JSON 当成给其他工具用的单向视图。导出时，记住 getter 包含什么、不包含什么——经典导出捕获的是拟合出的参数，但和 postcard 文件不同，它丢掉了超参数和元数据；而神经网络导出只有权重，原因和 [3.9](../Chapter-03/3.9._权重保存与加载.md) 讲清楚的一样。

至于相邻的运维关切——加载后给模型重新设种子，好让恢复的洗牌仍然可复现，或是并行下写出大量 checkpoint 的吞吐量——参见 [7.1. 可复现性与随机种子](./7.1._可复现性与随机种子.md) 和 [7.3. 性能调优与并行](./7.3._性能调优与并行.md)。
