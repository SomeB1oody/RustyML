# 7.2. 深入模型持久化

RustyML 提供两种持久化模型的方式。两者写出的是同一种 wire format，但有一处关键分歧。经典 estimator 序列化*整个*模型：超参数、学到的参数，以及训练时的元数据。加载回来之后，你直接得到一个能预测的对象，不需要做任何额外工作。神经网络只序列化*权重*：架构要你在代码里重新搭出来，再把数组加载回去。

两条路径写出的都是 [postcard](https://docs.rs/postcard)——一种紧凑、非自描述的二进制格式。这一个选择就解释了为什么文件这么小、为什么只有 Rust 能读，也解释了为什么跨版本加载会是个隐患。两条路径应对这个隐患的方式并不一样。神经网络的文件以一个魔数和一个格式版本开头，加载器最先校验这两样，所以不兼容的版本会响亮地失败。经典模型的文件完全没有头部，跨版本这道坎全得你自己兜。

本页是 [3.9. 权重保存与加载](../Chapter-03/3.9._权重保存与加载.md) 的底层篇：3.9 讲的是神经网络的工作流，本页把两条路径都下沉到字节层面。它讲清两条路径各自的失败面，也讲版本管理、原子写入、跨语言互操作这些运维套路——那两个便捷方法并不会替你把这些都做好。

## 7.2.1. 两套 API，同一种格式

这两个子系统的方法签名故意就长得不一样。要是把它们当成同一个方法用，麻烦就来了。

```rust,ignore
// 经典 ML 模型：由 lib.rs 中的 `model_save_and_load_methods!` 宏生成
impl LinearRegression {
    pub fn save_to_path(&self, path: &str) -> Result<(), rustyml::error::Error>;
    pub fn load_from_path(path: &str) -> Result<Self, rustyml::error::Error>;
}

// Sequential 神经网络：
impl Sequential {
    pub fn save_to_path(&self, path: impl AsRef<std::path::Path>) -> rustyml::error::RustymlResult<()>;
    pub fn load_from_path(&mut self, path: impl AsRef<std::path::Path>) -> rustyml::error::RustymlResult<()>;
    pub fn load_partial_from_path(&mut self, path: impl AsRef<std::path::Path>) -> rustyml::error::RustymlResult<LoadReport>;
}
```

这里有四处差异要记住。第一，经典的 `save_to_path` 和 `load_from_path` 只收 `&str`，不收 `impl AsRef<Path>`。传一个 `PathBuf` 得显式调用 `.to_str().unwrap()`，不然编译不过。神经网络那两个方法则接受任意 `AsRef<Path>`。

第二，经典的 `load_from_path` 是一个关联函数，返回一个拥有所有权的 `Self`——没有什么可以加载进去的对象，因为整个模型都是从文件里取回来的。`Sequential::load_from_path` 则不同：它收 `&mut self`，改写的是你已经搭好的一个模型。

第三，`RustymlResult<()>` 就是 `Result<(), Error>` 的别名，所以两条路径的错误类型完全一样：每一次失败都是本 crate 统一 [`Error`](../Chapter-01/1.6._错误处理.md) 的某个变体。

第四，神经网络这边多出第三个方法。`load_partial_from_path` 施加文件与模型一致的那部分，并返回其余部分的报告。经典那条路没有对应物，因为一个经典文件要么完整反序列化进整个结构体，要么就失败。

层构成有向图的模型 `Graph`，带着同样的 3 个方法，签名也一样。本页关于 `Sequential` 文件所讲的一切，对图模型的文件同样成立。见 [3.10. 图模型与合并层](../Chapter-03/3.10._图模型与合并层.md)。

生成经典这一对方法的宏，就是 `lib.rs` 里的 `model_save_and_load_methods!`。它原样套用在 `machine_learning` 模块的 13 个类型上：`LinearRegression`、`LogisticRegression`、`KNN`、`DecisionTree`、`SVC`、`LinearSVC`、`LDA`、`KMeans`、`DBSCAN`、`MeanShift`、`PCA`、`KernelPCA` 和 `IsolationForest`。它同样套用在 `utils` 模块的 5 个 scaler 上：`MaxAbsScaler`、`MinMaxScaler`、`Normalizer`、`RobustScaler` 和 `StandardScaler`。这 18 个类型，每一个都得到同样的 2 个方法，行为也一样。

## 7.2.2. 经典 ML：整个模型落盘

宏体很短：`save_to_path` 调用 `postcard::to_allocvec(self)`，再把字节通过一个带缓冲的 writer 写出去；`load_from_path` 读入文件，再调用 `postcard::from_bytes::<Model>(&bytes)`。

模型结构体 derive 了 `Serialize` 和 `Deserialize`，所以每一个字段都会随之传输。对 `LinearRegression` 而言，这包括 `coefficients`、`intercept`、`fit_intercept`、拟合后的 `n_iter`、`regularization_type`，以及 `solver` 字段。`solver` 字段是一个 `LeastSquaresSolver`：选中梯度下降时，这个枚举本身还会带上 `learning_rate`、`max_iter` 和 `tol` 这几项设置。

经典持久化没有“配置”和“权重”这条分界线——这条线在神经网络那一侧很重要，但在这里根本不存在。这正是加载出来的模型可以立刻使用的原因：`load_from_path` 交还给你的对象，和你训练出的那个别无二致。不用再调用 `fit`，不用重新设置任何参数，也没有编译步骤。

```rust
use rustyml::machine_learning::*;
use ndarray::{Array1, Array2};

fn main() {
    let x = Array2::from_shape_vec((4, 2), vec![1.0, 2.0, 2.0, 1.0, 3.0, 5.0, 4.0, 3.0]).unwrap();
    let y = Array1::from_vec(vec![5.0, 5.0, 13.0, 11.0]);

    let mut model = LinearRegression::new(true);
    model.fit(&x, &y).unwrap();

    let path = "lr_whole_model.bin";
    model.save_to_path(path).unwrap();

    // 加载得到一个可以直接用的模型：无需重新拟合、无需重建、无需编译步骤。
    let restored = LinearRegression::load_from_path(path).unwrap();

    // 这一趟往返保留了学到的参数和超参数。
    assert_eq!(restored.get_solver(), model.get_solver());
    assert_eq!(restored.get_coefficients().unwrap().len(), 2);

    let probe = Array2::from_shape_vec((1, 2), vec![2.0, 4.0]).unwrap();
    let a = model.predict(&probe).unwrap();
    let b = restored.predict(&probe).unwrap();
    println!("live vs restored prediction gap: {:e}", (a[0] - b[0]).abs());

    std::fs::remove_file(path).unwrap();
}
```

如果你熟悉 scikit-learn 的 `pickle` 或 `joblib`，这套心智模型是一样的：整个 estimator 走一趟往返。但有两点实打实的差异。

第一，postcard 不是 `pickle`：它加载文件时不执行任何代码，恶意文件触发不了任意代码执行，唯一的风险是字节畸形或对不上号。

第二，postcard 不带类身份，没有 `__module__` 字段，也没有版本戳——这恰恰是接下来几节要讲的代价。

## 7.2.3. 神经网络：按名字寻址的权重

3.9 节从头到尾讲了神经网络这条路径，本节则往下再挖一层机制。

`Sequential::save_to_path` 会构建一个 `ModelCheckpoint { magic, format_version, layers }`。每个 `LayerCheckpoint` 装着 `LayerBase::layer_type` 返回的那个字符串、该层每个输入各一份的构建形状，以及该层持有几个数组就有几条的 `WeightRecord`。每条记录装着数组的 `name`、它的 `WeightKind`、它的 `shape`，以及按逻辑 C 序排列的全部元素。整个结构借用着活着的模型：一条记录取的是它所描述的那个数组的名字和元素，所以在 postcard 读到之前不发生任何拷贝。唯一的例外是某个层没有把数组存成 1 段连续内存，这时它的记录自己拥有一份 C 序的副本。

开头两个 `u32` 就是文件头：`MODEL_MAGIC`（`"RMLM"`）和 `MODEL_FORMAT_VERSION`，它们排在最前面是刻意的。在这个头部存在之前写出的文件，是以层数开头的，于是加载器会在本该是魔数的位置读到那个小整数，从而拒掉这个文件——这发生在加载器解析到足以应用哪怕 1 个权重之前。

本次发布里 `MODEL_FORMAT_VERSION` 是 3。版本 3 把构建记录加宽了：版本 2 里它只装 1 个形状，现在则是该层每个输入各一份。几乎每个层都只取 1 个输入，也就只记录 1 个形状。合并层取好几个输入，会把每一个输入的形状都记录下来，把图模型的 2 个分支接起来的 `Concatenate` 就是这样的层。因此版本 2 的文件一律加载不了，消息里会点出双方的版本号。

这套布局小到可以手写出来，而手写正是读懂它最清楚的办法：

```rust
use rustyml::neural_network::Shape;
use rustyml::neural_network::layers::checkpoint::{
    BuildConfig, LayerCheckpoint, MODEL_FORMAT_VERSION, MODEL_MAGIC, ModelCheckpoint, WeightRecord,
};
use rustyml::neural_network::traits::WeightKind;
use std::borrow::Cow;

fn main() {
    // 2 个层：一个持有数组、只取 1 个输入，另一个是不持有数组、
    // 取 2 个输入的合并层。保存下来的文件就长这个样子。
    let file = ModelCheckpoint {
        magic: MODEL_MAGIC,
        format_version: MODEL_FORMAT_VERSION,
        layers: vec![
            LayerCheckpoint {
                layer_type: Cow::Borrowed("Dense"),
                // 每个输入各 1 个形状。`BuildConfig::unary` 会把批轴置为自由。
                build: Some(BuildConfig::unary(&Shape::known(&[8, 4]))),
                weights: vec![WeightRecord {
                    name: Cow::Borrowed("kernel"),
                    kind: WeightKind::Trainable,
                    shape: vec![4, 3],
                    data: Cow::Owned(vec![0.0f32; 12]),
                }],
            },
            LayerCheckpoint {
                layer_type: Cow::Borrowed("Concatenate"),
                // 合并层会把它拼接的每一个输入的形状都记录下来。
                build: Some(BuildConfig::new(&[
                    Shape::known(&[8, 3]),
                    Shape::known(&[8, 5]),
                ])),
                weights: Vec::new(),
            },
        ],
    };

    println!("format version {}", file.format_version);
    for (scope, layer) in file.layers.iter().enumerate() {
        let built: Vec<String> = match &layer.build {
            Some(build) => build.input_shapes.iter().map(Shape::to_string).collect(),
            None => Vec::new(),
        };
        let held: Vec<String> = layer
            .weights
            .iter()
            .map(|record| format!("{scope}.{} {:?} {:?}", record.name, record.kind, record.shape))
            .collect();
        println!(
            "layer {scope} `{}` built for {built:?}, holding {held:?}",
            layer.layer_type
        );
    }
}
```

```text
format version 3
layer 0 `Dense` built for ["(None, 4)"], holding ["0.kernel Trainable [4, 3]"]
layer 1 `Concatenate` built for ["(None, 3)", "(None, 5)"], holding []
```

这里有三处设计选择值得记住。第一，每个数组都用 `<scope>.<name>` 寻址，其中 `scope` 是层的位置，`name` 是层给这个数组取的名字。这与优化器索引自己状态时用的是同一对键，于是 1 个地址同时服务训练循环和文件。格式在层内部没有任何按位置的东西，所以像偏置这样的可选数组可以离开某个层，而不挪动任何其他路径。在图模型里，`scope` 是层在 arena 里的位置，而不是节点的位置：被多个节点调用的层因此只持有 1 组路径，也只接收 1 组值。

第二，那几个 `Cow` 字段让同一个类型服务于两个方向：保存时借用活着的名字和元素，加载时两者都归自己所有，成为一个 `ModelCheckpoint<'static>`。

第三，`build` 装着该层构建时所针对的形状，每个输入各 1 份。层在 `Layer::build_many` 里、按各个输入的形状分配它持有的每个数组。所以构建形状就是一个全新的层唯一不具备的东西，而它决定了该层分配的每一个尺寸。这条记录会把每个形状的批轴都置为自由，因为 1 个层服务于所有批大小。于是为 32 个样本构建的模型，可以接收为 1 个样本构建的模型的 checkpoint。只有当文件和层双方都带着形状时，加载才比较这个字段，其余情况一律跳过。既不持有数组、也不读输入任何尺寸的层，例如激活层，就不带这个字段。

让这个字段挣得一席之地的正是卷积。`Conv2D` 的核在任何空间尺寸下都是 `[kh, kw, Cin, filters]`，所以逐数组的形状检查看不出这个文件来自一个为另一种图像尺寸构建的模型。唯一能看出来的就是构建形状。

文件里刻意不带任何构造器信息：没有激活函数，没有 `epsilon`、`momentum`、stride、kernel size、dilation，也没有 group count。这些设置活在你的源代码里，不在文件里。`layer_type` 字符串、各个数组名和各个 kind 都是校验标签，不是搭建配方——这正是为什么加载需要一个预先搭好、随时准备接收权重的模型。

正是这个预先搭好的模型，让神经网络加载器能做到经典加载器做不到的事：校验结构。`load_from_path` 跑 2 趟，第一趟一个字节都不写。它先检查层数，再检查每个位置的 `layer_type`。接着是双方都带构建形状时各层的这些形状。再接着是一个层的数组个数，以及每个数组按顺序的名字。最后是每个数组的 kind，以及每个数组的形状与记录里的元素个数。只有到这时第二趟才开始写，写入走的是层自己的 `weights_mut` 视图。任何一项检查失败，都会抛出 `Error::Io(IoError::ModelStructureMismatch)`，消息里点出 checkpoint 路径，整层级别的不一致则点出层的位置。因此一次拒绝会让模型原封不动，一个模型也就永远不会同时装着来自 2 个文件的数组。

这种严格是刻意设成默认的。名字加形状这个键，比它取代掉的那套封闭的逐层容器要弱。`InstanceNormalization`、`GroupNormalization` 和秩为 2 的 `LayerNormalization` 暴露出来的都是一模一样的 `gamma [C]` 和 `beta [C]`，能把它们分开的除了逐层的类型名再无别物。宽松的默认行为会把一个对该模型而言错误的文件加载进去，再把差异留到日后以一个错误的预测冒出来。宽松那条路是 `load_partial_from_path`，需要调用方指名去要：它施加对得上的部分，并返回一个由 checkpoint 路径组成的 `LoadReport { applied, missing, unused }`。[3.9.9](../Chapter-03/3.9._权重保存与加载.md#399-有意只加载文件的一部分) 节把它走了一遍。

宽松这条路不会绕开构建形状。为另一种形状构建的层会被整层跳过，而不是把权重写进去。该层的每一条路径于是同时进入 `missing` 和 `unused`：模型在那里没拿到值，文件里的值也没去处。下面的程序对同一个文件跑了两种加载：

```rust
use rustyml::neural_network::Shape;
use rustyml::neural_network::layers::{Activation, Conv2D, Dense, GlobalAveragePooling2D};
use rustyml::neural_network::sequential::{Sequential, SequentialBuilder};

fn stack(height: usize, width: usize) -> Sequential {
    SequentialBuilder::new()
        .add(Conv2D::new(2, (3, 3), (1, 1), Activation::ReLU).unwrap())
        .add(GlobalAveragePooling2D::new())
        .add(Dense::new(4, Activation::Linear).unwrap())
        .build(&Shape::known(&[1, height, width, 1]))
        .unwrap()
}

fn main() {
    // 保存自一个为 8x8 图像构建的模型。
    let source = stack(8, 8);
    let path = "build_shape_demo.bin";
    source.save_to_path(path).unwrap();

    // 同样的栈，但为 6x6 图像构建。两边的卷积核都是 [3, 3, 1, 2]，
    // 所以能把它们分开的只有记录下来的构建形状。
    let mut target = stack(6, 6);

    // 严格：加载被拒，消息点出双方的形状。
    println!("strict: {}", target.load_from_path(path).unwrap_err());

    // 宽松：卷积层被整层跳过，它的路径同时落进 `missing` 和 `unused`。
    // Dense 层在两边都是为 (None, 2) 构建的，所以它拿到了值。
    let report = target.load_partial_from_path(path).unwrap();
    println!("applied: {:?}", report.applied);
    println!("missing: {:?}", report.missing);
    println!("unused:  {:?}", report.unused);

    std::fs::remove_file(path).unwrap();
}
```

```text
strict: model structure mismatch: layer 0 (`Conv2D`) was built for input shape (None, 6, 6, 1), and the file records (None, 8, 8, 1)
applied: ["2.kernel", "2.bias"]
missing: ["0.kernel", "0.bias"]
unused:  ["0.kernel", "0.bias"]
```

经典那套宏没有这样的防护：它把字节直接反序列化进目标结构体，一点检查都没有。把一个 `LinearRegression` 文件喂给 `KMeans::load_from_path`，不会被任何类型检查拒绝。postcard 只按位置读字节：多数情况下，两边布局差得够远，你会拿到一个 `Serialization` 错误；倒霉的情况下，字节碰巧凑得上另一套布局，你就得到一个看起来合法、实则毫无意义的模型。对经典模型而言，文件名或者某个外部标签，是唯一能拦住你犯这个错误的东西。

## 7.2.4. postcard 的 wire format

postcard 是一种极简的二进制格式，有一个性质左右着它的一切：postcard 是非自描述的。

字节里按字段顺序装的是值，别无其他：没有字段名、没有类型名、没有 schema，也没有一段可以跳过的、带长度前缀的区块。序列化一个 `LinearRegression`，不会在任何地方写下字符串 `"learning_rate"`，它写的是那个 `f64` 值的 8 个字节，就摆在 `learning_rate` 在序列化后的 `LeastSquaresSolver` 里所处的确切位置上。这既是文件保持小巧的全部原因，也是它脆弱的原因：能否正确读回字节，完全取决于读的一方是否拥有和写的一方完全相同的类型布局。

当你要推算文件大小、或者调试一个损坏的文件时，各类型的编码方式就很重要：

| Rust 类型 | postcard 编码 | 字节数 |
| --- | --- | --- |
| `bool` | 单字节，`0` 或 `1` | 1 |
| `f32`（神经网络权重） | 定宽，小端 | 4 |
| `f64`（经典参数） | 定宽，小端 | 8 |
| `usize` / `u64`（例如 `max_iter`，或某个长度） | LEB128 varint | 1 到 10 |
| 枚举变体（`Solver`、`WeightKind`） | varint 判别值 | 1（外加负载） |
| `Option<T>` | 1 个标签字节（`0` = None，`1` = Some） | 1（Some 时外加 `T`） |
| `String`（层类型标签） | varint 长度，再加 UTF-8 字节 | 不定 |
| ndarray `Array`（经由 serde） | 小的版本与形状头，再加一个 varint 元素数量，再加元素本身 | 不定 |

浮点数是定宽的：`N` 个值的数组，`f32` 就是 `N x 4` 字节，`f64` 就是 `N x 8` 字节，再加上一个小的形状头和长度前缀。这趟往返是无损的，不是有损的。

整数和长度用的是 varint，所以小的计数只花 1 个字节。postcard 不做压缩，也没有对齐填充。

这个格式的小巧，同时也是它的脆弱：文件里什么都没有标注。设想一个结构体的布局，在写文件和读文件的两个版本之间发生了漂移：一个字段被增加、删除、重排，或者换了类型。反序列化这样一个文件，没有任何名字可供核对。大概率的结果是一个 "unexpected end of input" 错误，或者一个坏标签的 `Serialization` 错误；危险的结果，是一次悄无声息的错误解析——漂移后的布局恰好消费掉同样数量的字节。

这不是 postcard 的 bug，而是你为小文件付出的代价——也正因如此，版本管理（本页后面会讲）是你的责任，不是格式的责任。

本次发布里，好几个经典 estimator 改了自己的落盘布局。`LinearRegression` 把 3 个散落的迭代设置折进了求解器负载里；`KMeans` 多了一个新的 `n_init` 字段；`LDA` 多了一个记录训练集总体均值的新字段。这 3 个类型中，任何一个用旧版本保存的文件都加载不了——请重新拟合，再重新保存。

`MeanShift` 的布局也变了，而且同时改了含义。它的 `labels` 字段换了类型，从 `usize` 变成了 `isize`；一个未被分配的点，它的标签含义也变了——以前等于簇的数量，现在是 `-1`。除此之外，簇中心本身现在也是由不同的算法算出来的：一个旧的 `MeanShift` 文件，就算侥幸还能加载进来，装的也是旧高斯核算出的中心，而不是现在的 flat kernel（平顶核）算出的。

`IsolationForest` 只改了含义，没有改布局：它的 `offset` 字段类型和位置都没变，但存的那个数现在符号相反了。就算形状还能对得上，`MeanShift` 和 `IsolationForest` 这两个模型也请一并重新拟合、重新保存。

同一次发布里，神经网络的格式也从版本 2 升到了版本 3，因为构建记录现在按每个输入各存 1 个形状。版本 2 的文件一律加载不了，消息里会点出双方的版本号。请在本次发布下把这类模型重新训练一遍，再重新保存。

## 7.2.5. 文件大小：一份可信的粗略估算

postcard 不压缩，也不分帧，所以你能把文件大小预测到几个字节以内。

对经典模型而言，负载由学到的数组主导：一个有 `p` 个特征的 `LinearRegression`，系数大约花费 `p x 8` 字节，再加上二三十字节的标量超参数和头部。

对神经网络而言，把每一层的 `(weight_elements + bias_elements) x 4` 字节加起来即可，因为神经网络权重用的是 `f32`；再加上每层那点类型和形状字符串的开销。

一个 `Dense(784 -> 128)` 层有 `784 x 128 + 128 = 100,480` 个参数，约 392 KB；同样的层放在经典的、基于 `f64` 的世界里则要翻一倍。与其猜，不如直接量：

```rust
use rustyml::machine_learning::*;
use ndarray::{Array1, Array2};

fn main() {
    let n_features = 8usize;
    let n_samples = 20usize;
    let x = Array2::from_shape_fn((n_samples, n_features), |(i, j)| (i + j) as f64 * 0.1);
    let y = Array1::from_shape_fn(n_samples, |i| i as f64);

    let mut model = LinearRegression::new(true);
    model.fit(&x, &y).unwrap();

    let path = "lr_size_probe.bin";
    model.save_to_path(path).unwrap();

    let on_disk = std::fs::metadata(path).unwrap().len();
    // 主导项是每个系数一个 f64。其余都是标量和小的头部。
    let coefficient_bytes = (n_features * std::mem::size_of::<f64>()) as u64;
    println!("file: {on_disk} bytes, coefficient payload ~= {coefficient_bytes} bytes");

    std::fs::remove_file(path).unwrap();
}
```

实际用起来，这让 postcard checkpoint 便宜到可以大量留存：对一个小模型，跑“每个 epoch 存一次、只留最好那份”的循环，每个 checkpoint 只花几个 KB。多久存一次快照，受限的是磁盘写入速度，而不是文件大小。

对大型卷积堆叠，`f32` 权重占了文件的大头，文件大小几乎精确跟着参数量走。这让容量规划变得简单：数一数参数，再乘以 4。

## 7.2.6. 加载到底会拒绝什么

每一次持久化失败都以 `Error::Io(...)` 的形式浮现，底下正好有 4 种形态。

`IoError::Std` 包裹一个 `std::io::Error`：路径不存在、权限问题，或者一次读写失败。

`IoError::UnsupportedModelFormat` 只用于神经网络，来自头部校验：魔数或格式版本和当前构建对不上。

`IoError::Serialization` 包裹一个 `postcard::Error`：字节对代码期望的布局来说不是有效的 postcard，原因可能是损坏、截断，或者 schema 不再匹配。

`IoError::ModelStructureMismatch` 同样只用于神经网络，如 7.2.3 节所讲。经典模型没有与之对应的东西。

`error.rs` 里的两个 `From` 实现，让 `?` 操作符能把一个裸的 `std::io::Error` 提升成 `IoError::Std`，把一个裸的 `postcard::Error` 提升成 `IoError::Serialization`——这个映射在两个子系统里都是一样的。`Error` 和 `IoError` 都带着 `#[non_exhaustive]`，匹配它们时永远要加一个兜底分支。

```rust
use rustyml::machine_learning::*;
use rustyml::error::{Error, IoError};

fn main() {
    // 这个文件里装的字节，对 LinearRegression 来说不是有效的 postcard。
    let junk = "corrupt_lr.bin";
    std::fs::write(junk, b"\xff\xff\xff not a model").unwrap();

    match LinearRegression::load_from_path(junk) {
        Ok(_) => println!("unexpected success"),
        Err(Error::Io(IoError::Serialization(e))) => println!("bad bytes -> Serialization: {e}"),
        Err(Error::Io(IoError::Std(e))) => println!("io failure: {e}"),
        Err(e) => println!("other: {e}"),
    }
    std::fs::remove_file(junk).unwrap();

    // 一个不存在的路径会以 IoError::Std 浮现，而不是 Serialization。
    match LinearRegression::load_from_path("no_such_model_9f3a.bin") {
        Err(Error::Io(IoError::Std(e))) => println!("missing file -> Std: {e}"),
        other => println!("unexpected: {other:?}"),
    }
}
```

神经网络的测试套件对照真实 API 核对了这些映射：不存在的路径产生 `IoError::Std`；错误的魔数或格式版本产生 `IoError::UnsupportedModelFormat`；藏在合法头部之后的坏字节产生 `IoError::Serialization`；层数、层类型、数组名字、数组 kind 或数组形状上的不一致，产生的都是 `IoError::ModelStructureMismatch`。

经典模型在这份清单里有个缺口：没有结构性错误可抓，`Serialization` 就成了文件出错的唯一信号，而它并不可靠。要是一个损坏的经典文件碰巧还是反序列化成功了，`load_from_path` 就会返回 `Ok`。用你自己的完整性检查来防这一手——接下来两节要搭的正是这个。

## 7.2.7. 跨 RustyML 版本的版本管理

postcard 文件不带版本戳，RustyML 也不保证模型结构体的字段布局在各版本间保持稳定。给 `LinearRegression` 加一个超参数，重排一个字段，或者改一个字段的类型——这些都会让旧版本写出的文件，对新版本来说变成糟糕的输入：通常表现为一次 `Serialization` 失败，偶尔则是一次悄无声息的错误解析。

RustyML 没有内建的迁移路径。养成下面这两个习惯，能让这件事不至于在生产环境里给你惊吓。

第一，把写出你那些长命 checkpoint 的 `rustyml` 版本精确锁定，这样一次例行的 `cargo update` 就没法在一整目录已保存的模型底下，悄悄换掉磁盘布局：

```toml
[dependencies]
rustyml = { version = "=0.15.0", features = ["full"] }
```

第二，写一个版本旁挂文件（sidecar）：一个保存在模型旁边的小伴生文件，记录格式身份。当它和你的二进制期望的版本对不上时，就拒绝加载模型——这把一次悄无声息的错误解析，变成了一个响亮、及早的错误。

注意谁最需要这个 sidecar。`Sequential` 的文件自带魔数和格式版本，跨不兼容版本时神经网络这条路本来就会响亮地失败，sidecar 在这里只是再叠上你自己的 schema 身份。经典那条宏路径完全没有头部，对那些模型来说，sidecar 就是你的全部防线。

```rust
use rustyml::machine_learning::*;
use ndarray::{Array1, Array2};

// 每次升级写出 checkpoint 的 rustyml 依赖时，就把这个值往上抬一档。
const CHECKPOINT_FORMAT: &str = "rustyml-0.15";

fn main() {
    let x = Array2::from_shape_vec((3, 2), vec![1.0, 2.0, 2.0, 3.0, 3.0, 4.0]).unwrap();
    let y = Array1::from_vec(vec![6.0, 9.0, 12.0]);

    let mut model = LinearRegression::new(true);
    model.fit(&x, &y).unwrap();

    let model_path = "sidecar_model.bin";
    let version_path = "sidecar_model.bin.version";
    model.save_to_path(model_path).unwrap();
    std::fs::write(version_path, CHECKPOINT_FORMAT).unwrap();

    // 加载时，先核对记录下来的格式字符串，再反序列化。
    let recorded = std::fs::read_to_string(version_path).unwrap();
    if recorded != CHECKPOINT_FORMAT {
        panic!("checkpoint written by {recorded}, this binary expects {CHECKPOINT_FORMAT}");
    }
    let restored = LinearRegression::load_from_path(model_path).unwrap();
    println!("loaded {} coefficients", restored.get_coefficients().unwrap().len());

    std::fs::remove_file(model_path).unwrap();
    std::fs::remove_file(version_path).unwrap();
}
```

让版本字符串足够具体、具体到有意义：至少用 `rustyml` 的版本号；如果你把模型包进了更大的记录里，再加上你自己的 schema 计数器。这个 sidecar 写起来几乎不花成本，却把这个格式最糟的失败模式——悄悄给出错误数字——换成了一个你在测试阶段就能抓到的 `panic`。

## 7.2.8. 原子 checkpoint

两个 `save_to_path` 方法都调用 `File::create`，它会立刻截断目标文件。设想进程崩溃、磁盘写满，或者训练循环写到一半被杀掉——你就会在重启逻辑要加载的那个确切路径上，留下一个被截断的文件。截断往好了说是一个 `Serialization` 错误，往坏了说，会悄悄给你一个偏短的数组。

标准的防御是先写后改名：把模型序列化到同一个文件系统上的一个临时路径，再调用 `std::fs::rename` 把它移到最终路径上。在 POSIX 文件系统上，rename 是原子的，所以读者要么看到完整的旧文件，要么看到完整的新文件，绝不会看到写到一半的那个。

```rust
use rustyml::machine_learning::*;
use ndarray::{Array1, Array2};

/// 经由一个临时文件，再做一次原子 rename 来保存。写入过程中的崩溃，
/// 绝不会在 `final_path` 留下一个只写了一半的 checkpoint。
fn save_atomically(model: &LinearRegression, final_path: &str) -> std::io::Result<()> {
    let tmp_path = format!("{final_path}.tmp");
    model
        .save_to_path(&tmp_path)
        .expect("serialize to temp file");
    std::fs::rename(&tmp_path, final_path)
}

fn main() {
    let x = Array2::from_shape_vec((3, 2), vec![1.0, 2.0, 2.0, 3.0, 3.0, 4.0]).unwrap();
    let y = Array1::from_vec(vec![6.0, 9.0, 12.0]);

    let mut model = LinearRegression::new(true);
    model.fit(&x, &y).unwrap();

    let path = "atomic_model.bin";
    save_atomically(&model, path).unwrap();

    let restored = LinearRegression::load_from_path(path).unwrap();
    println!("intercept present after atomic save: {}", restored.get_intercept().is_some());

    std::fs::remove_file(path).unwrap();
}
```

把临时文件放在和目标同一个文件系统上：跨文件系统的 rename 不是原子的，会退化成先复制再删除。

把这个做法和 7.2.7 节的 sidecar 配合起来：先给模型文件改名，再给版本文件改名。这样一次撕裂的写入，留下的版本 sidecar 指向的是上一个完整的模型，而不是一个损坏的新模型。

对一个只保留最优 checkpoint 的循环，原子替换还意味着你那份目前最好的文件，永远不会有哪怕一瞬间的缺席。

## 7.2.9. 跨越语言边界

postcard 属于 Rust 生态。没有一个有人维护的 Python 或 R 读取器能读它；就算有，那些非自描述的字节也需要一份手写的、镜像 RustyML 确切结构体布局的 schema——而这个布局在版本之间还会变。

把一个 `.bin` checkpoint 当成 RustyML 到 RustyML 的产物，别的什么都不是。当另一个工具需要读一个训练好的模型时，不要去解析那个 postcard 文件，而是通过 getter 把参数导出成对方本就能读的可移植格式。经典模型把你需要的一切都暴露了出来：`LinearRegression::get_coefficients` 和 `get_intercept`、`KMeans::get_centroids`，以及其他 estimator 上对应的访问器。

```rust
use rustyml::machine_learning::*;
use ndarray::{Array1, Array2};

fn main() {
    let x = Array2::from_shape_vec(
        (3, 3),
        vec![1.0, 0.0, 2.0, 0.0, 1.0, 1.0, 2.0, 2.0, 0.0],
    )
    .unwrap();
    let y = Array1::from_vec(vec![4.0, 3.0, 6.0]);

    let mut model = LinearRegression::new(true);
    model.fit(&x, &y).unwrap();

    // 通过 getter 把学到的参数取出来，再写出可移植的 CSV。
    // Python、R 或电子表格的消费方能直接读这个文件，postcard 完全不参与。
    let coefficients = model.get_coefficients().expect("model is fitted");
    let intercept = model.get_intercept().unwrap_or(0.0);

    let mut csv = String::from("term,value\n");
    for (i, c) in coefficients.iter().enumerate() {
        csv.push_str(&format!("x{i},{c}\n"));
    }
    csv.push_str(&format!("intercept,{intercept}\n"));

    print!("{csv}");
}
```

同样的套路可以用在别处：把 getter 的输出转储成 CSV，给电子表格或者 pandas 的 `read_csv` 用；或者把它拼装成一个你的服务本就会读的 JSON 对象。

对神经网络，遍历 `Sequential::weight_paths()`，用 `Sequential::weight(path)` 读出每个地址上的数组再写出去。路径本身就是导出时一个稳定的列名，而这些视图是 ndarray，所以 `.iter()` 加上你自己的格式化方式就够了。

这么做要付出两个代价：postcard 的紧凑，以及同格式往返的精确性保证。把 postcard 文件留作你的规范 checkpoint，用来加载回 RustyML；把导出的 CSV 或 JSON 只当成给其他工具用的单向视图。

导出时，记住 getter 包含什么、不包含什么：经典导出捕获的是拟合出的参数，但和 postcard 文件不同，它丢掉了超参数和元数据；神经网络导出则只有权重，原因和 [3.9](../Chapter-03/3.9._权重保存与加载.md) 节讲的一样。

另外两个相邻的运维话题，参见邻近的两页：[7.1. 可复现性与随机种子](./7.1._可复现性与随机种子.md) 讲加载后如何给模型重新设种子，好让恢复的洗牌仍然可复现；[7.3. 性能调优与并行](./7.3._性能调优与并行.md) 讲并行写出大量 checkpoint 时的吞吐量。
