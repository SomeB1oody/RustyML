# 1.2. 安装与Feature配置

RustyML 在 crates.io 上是单独一个 crate，但内部被刻意切成一个个由 feature 控制的模块，你只编译用得上的部分。习惯了 `pip install scikit-learn` 那种一整块装下来的人，第一个坑往往就在这里：flag 开错了，想用的类型压根不在 crate 里，编译器直接报 unresolved import，而不是等到运行时才蹦出一个找不到符号的错误。这一页把话说清楚：哪个 flag 解锁哪个模块、每个 flag 会牵进哪些第三方 crate，以及怎样在自己的 manifest 里把 RustyML 和 `ndarray` 配好，否则连数组都构造不出来。

## 1.2.1. 将 RustyML 加入你的项目

最快的方式是 `cargo add`，它会帮你把依赖那一行写好：

```bash
cargo add rustyml
cargo add ndarray@0.17
```

第一条命令拉取 RustyML 及其默认 feature（`machine_learning` + `neural_network`）。第二条可不是可有可无的点缀——你几乎总是还需要把 `ndarray` 作为*直接*依赖引入，原因见 [1.2.5](#125-搭配-ndarray-017)。完整写出来，一份典型的 `Cargo.toml` 长这样：

```toml
[dependencies]
rustyml = { version = "0.13", features = ["full"] }
ndarray = "0.17"
```

按你实际要构建的东西挑选 feature 组合。几种常见搭配：

```toml
# 默认组合：经典机器学习 + 神经网络（`cargo add rustyml` 给你的就是这套）
rustyml = "0.13"

# 仅神经网络框架
rustyml = { version = "0.13", features = ["neural_network"] }

# 全量：machine_learning、neural_network、utils、metrics、math
rustyml = { version = "0.13", features = ["full"] }

# 全量，外加训练时的终端进度条
rustyml = { version = "0.13", features = ["full", "show_progress"] }
```

反过来想大刀阔斧地裁剪，就关掉默认 feature，只点名你需要的——这正是模块拆分的意义所在，[7.4 按需裁剪与模块化集成](../Chapter-07/7.4._按需裁剪与模块化集成.md) 会深入讲这一点：

```bash
cargo add rustyml --no-default-features --features metrics
```

```toml
rustyml = { version = "0.13", default-features = false, features = ["metrics"] }
```

## 1.2.2. Feature 一览表

构建由七个 feature 控制。其中五个各自解锁一个同名的公开模块；`default` 和 `full` 则是方便打包的组合。

| Feature | 解锁 | 说明 |
|---------|---------|-------|
| `machine_learning` | `rustyml::machine_learning` | 回归、分类、聚类、降维、异常检测 |
| `neural_network` | `rustyml::neural_network` | Keras 风格的 `Sequential`、层、优化器、损失函数 |
| `utils` | `rustyml::utils` | 标准化、归一化、标签编码、训练/测试集划分 |
| `metrics` | `rustyml::metrics` | 回归、分类、聚类的评估指标 |
| `math` | `rustyml::math` | 距离度量、`gemm` 支持的矩阵乘积、确定性并行归约 |
| `default` | `machine_learning` + `neural_network` | 不指定任何 feature 时的默认组合 |
| `full` | `machine_learning` + `neural_network` + `utils` + `metrics` + `math` | 全部模块 |
| `show_progress` | （无新模块） | 渲染训练进度条；见 [1.2.6](#126-show_progress) |

这张表里看不出来的一层依赖是 `math`。`machine_learning`、`neural_network`、`utils`、`metrics` 每一个都会自动启用 `math`，因为它们都依赖住在那里的共享数值原语——成对距离、GEMM/GEMV、分块归约。你从不需要在引入别的模块时再手动加上 `math`；只有当你除了原始数值内核之外什么都不想要时，才会单独点名 `math`（详见 [6. 数学工具](../Chapter-06/6.0._数学工具.md)）。

还有几个横切模块会顺带被编译进来，它们的开关挂在*任意一个*上层 feature 上，而不是自己独立的 flag。`rustyml::error`（统一的 `Error` 类型，见 [1.6 错误处理](./1.6._错误处理.md)）和 `rustyml::random`（全局种子控制，见 [7.1 可复现性与随机种子](../Chapter-07/7.1._可复现性与随机种子.md)）只要 `machine_learning`、`neural_network` 或 `utils` 有一个开着就会出现——但 `metrics` 单独构建或 `math` 单独构建时不会，因为这两个叶子模块既不返回 `RustymlResult`，也不消费随机性。`rustyml::tuning`（运行时并行度开关，见 [7.3 性能调优与并行](../Chapter-07/7.3._性能调优与并行.md)）则无论开哪个 feature 都会出现，因为每个模块都至少有一个值得重新调节的开关。`rustyml::prelude` 模块总是会被编译，但它的每个子模块（`prelude::machine_learning`、`prelude::metrics` 等等）本身也受 feature 控制，所以 prelude 只会重新导出你打开的那部分——这套机制正是 [1.5 Prelude与模块导入](./1.5._Prelude与模块导入.md) 要讲的内容。

## 1.2.3. 每个 feature 引入哪些第三方 crate

RustyML 的每一个依赖都标了 `optional = true`，由某个 feature 拉进来。关掉一个 feature，就意味着它带的那些 crate 根本不会被编译，构建时间的节省正来自于此。下面是完整的对应关系，`math` 的传递依赖也一并算在内：

| Feature | 它激活的第三方 crate |
|---------|---------------------------------|
| `math` | `ndarray`、`ahash`、`rayon`、`gemm` |
| `machine_learning` | `ndarray`、`rayon`、`ndarray-rand`、`ahash`、`serde`、`postcard`、`thiserror`、`gemm` |
| `neural_network` | `ndarray`、`rayon`、`ndarray-rand`、`indicatif`、`serde`、`postcard`、`thiserror`、`gemm` |
| `utils` | `ndarray`、`rayon`、`ndarray-rand`、`ahash`、`serde`、`postcard`、`thiserror`、`gemm` |
| `metrics` | `ndarray`、`ahash`、`rayon`、`gemm` |
| `show_progress` | `indicatif` |

RustyML 实际构建所依赖的精确版本是：`ndarray` 0.17、`rayon` 1.12、`ndarray-rand` 0.16、`ahash` 0.8、`serde` 1.0（带 `derive`）、`postcard` 1.1（带 `use-std`）、`thiserror` 2.0、`indicatif` 0.18，以及 `gemm` 0.19（带 `rayon`）。它们各自的作用：`ndarray` 是贯穿整个公开 API 的数组类型；`rayon` 和 `gemm` 是并行计算的主干；`ndarray-rand` 为随机初始化器提供种子；`ahash` 提供标签编码和聚类背后的高速哈希表；`serde` + `postcard` 是每个 `save_to_path` / `load_from_path` 背后的序列化组合；`thiserror` 负责派生 `Error` 枚举；`indicatif` 负责画进度条。

有两处不对称值得记牢。第一，`metrics` 是除 `math` 之外最精简的模块：它既不激活 `serde`/`postcard`（指标没有什么要持久化的），也不激活 `thiserror`（指标函数在违反前置条件时直接 panic，而不是返回 `Result`，这让这个叶子模块的依赖保持很轻）。因此，`metrics` 单独构建的编译成本，比任何带上序列化栈的组合都要低得多。第二，`neural_network` 在自己的依赖集里列了 `indicatif`，所以只要开了神经网络，这个 crate 就会被编译——但进度条本身仍然带着 `#[cfg(feature = "show_progress")]`，只有你同时启用那个 flag 时才会渲染。对经典模型来说，`indicatif` *只*由 `show_progress` 拉进来。不管怎样，面向用户的规则很简单：没开 `show_progress`，任何地方都不会有进度条。

对编译时间的影响是直接的。`serde`、`postcard`、`thiserror` 连同它们的过程宏派生，是冷构建里最重的一块；把它们甩掉（只留 `metrics` 和/或 `math`）是压缩构建时间和依赖数量最有效的一根杠杆。如果你只是把 RustyML 当作某个更大服务里的一个组件，比方说只需要它的聚类指标，那么 `default-features = false, features = ["metrics"]` 编译出来的量，只是 `full` 的一小部分。

## 1.2.4. 一个最小的端到端验证

装好默认组合后，下面是一个经典估计器从编译、训练到预测的完整流程。注意这里有两处导入：RustyML 提供模型，`ndarray` 提供数据。

```rust
use rustyml::prelude::machine_learning::*;
use ndarray::array;

fn main() {
    // 3 个样本，2 个特征；目标值是输入的线性组合
    let x = array![[1.0, 2.0], [2.0, 3.0], [3.0, 4.0]];
    let y = array![6.0, 9.0, 12.0];

    // new(fit_intercept, learning_rate, max_iterations, tolerance) -> Result
    let mut model = LinearRegression::new(true, 0.01, 1000, 1e-6).unwrap();
    model.fit(&x, &y).unwrap();

    let predictions = model.predict(&x).unwrap();
    println!("predicted {} values", predictions.len());
}
```

## 1.2.5. 搭配 ndarray 0.17

RustyML 的每个入口都讲 `ndarray`：经典估计器接收 `Array2<f64>` 特征矩阵和 `Array1<f64>` 目标向量，神经网络则操作 `Tensor`，也就是 `ArrayD<f32>` 的别名（注意元素类型——机器学习和工具模块用 `f64`，网络用 `f32`）。RustyML 不会重新导出 `ndarray` 的构造函数，所以要*构造*你喂进去的那些数组——用 `array!`、`Array2::from_shape_vec`、`Array::ones` 之类——你得直接调用 `ndarray`。这就是为什么它必须是你自己 `Cargo.toml` 里的直接依赖，而不只是一个传递依赖；传递依赖里的东西对你的代码来说不在作用域内。[1.3 使用ndarray准备数据](./1.3._使用ndarray准备数据.md) 讲了估计器期望的那些数组构造写法。

版本必须对齐。RustyML 基于 `ndarray` 0.17 构建，而一个 crate 的各个 `0.x` 版本之间在 semver 上是互不兼容的。如果你的 manifest 锁的是另一个大版本号——比如 `ndarray = "0.16"`——Cargo 会把*两份* `ndarray` 一起解析进构建，你用自己那份构造出来的 `Array2`，跟 RustyML 签名期望的 `Array2` 是货真价实的两个不同类型。报错会是一句让人摸不着头脑的“expected `ndarray::ArrayBase<...>`, found `ndarray::ArrayBase<...>`”，而这两个类型打印出来一模一样。改成依赖 `ndarray = "0.17"`，问题就消失了：Cargo 会把两个 crate 统一到同一个 semver 兼容的版本上。

神经网络这边套路一样，只是换了构造函数。`Sequential` 本身不在 prelude 里，得显式导入：

```rust
use rustyml::neural_network::sequential::Sequential;
use rustyml::prelude::neural_network::*;
use ndarray::Array;

fn main() {
    // 6 个样本，4 个输入特征，2 个输出类别
    let x = Array::ones((6, 4)).into_dyn();
    let y = Array::ones((6, 2)).into_dyn();

    let mut model = Sequential::new();
    model
        .add(Dense::new(4, 8, Activation::ReLU).unwrap())
        .add(Dense::new(8, 2, Activation::Softmax).unwrap())
        .compile(
            Adam::new(0.001, 0.9, 0.999, 1e-8, 0.0).unwrap(),
            CategoricalCrossEntropy::new(false),
        );

    model.fit(&x, &y, 3).unwrap();

    let predictions = model.predict(&x).unwrap();
    println!("prediction shape: {:?}", predictions.shape());
}
```

`metrics` 模块也遵循同样的约定——每个函数都以借用的一维数组形式接收 `(y_true, y_pred)`，参数顺序与 scikit-learn 一致：

```rust
use rustyml::metrics::{ConfusionMatrix, accuracy};
use ndarray::array;

fn main() {
    let y_true = array![1.0, 0.0, 0.0, 1.0, 1.0];
    let y_pred = array![1.0, 0.0, 1.0, 1.0, 0.0];

    println!("accuracy: {:.3}", accuracy(&y_true, &y_pred));

    let cm = ConfusionMatrix::new(&y_true, &y_pred);
    println!("f1 score: {:.3}", cm.f1_score());
}
```

## 1.2.6. show_progress

`show_progress` 和模块 flag 是正交的：它不添加任何类型，也不解锁任何模块。它做的事情是把那些原本在构建时会被剥掉的、由 `indicatif` 驱动的进度条编译进来。启用后，`Sequential::fit` 会为每个 epoch 渲染一根进度条，显示已用时间、进度位置和当前损失，模板是 `[{elapsed_precise}] {bar:40} {pos}/{len} | Loss: {msg}`，结束时打印一句“Training completed”。小批量循环（`fit_with_batches`）按 epoch 报告滑动平均损失；每个带迭代式 `fit` 的经典估计器——从 `LinearRegression` 的梯度下降、`LogisticRegression` 的损失循环，到 `DecisionTree` 逐节点的生长、`KMeans`、`SVC` 等等——都用同样的方式点亮各自的进度条。不带这个 flag，上面这些 `#[cfg(feature = "show_progress")]` 代码块统统消失，训练循环不会为一个用不到的 feature 付出任何代价。

在你已有的模块上顺带把它加上：

```toml
rustyml = { version = "0.13", features = ["full", "show_progress"] }
```

库代码、CI，以及任何输出到非 TTY 日志的场景，把它关掉——把进度条塞进日志文件只会变成一堆噪声。交互式使用时再打开它，那时候盯着损失曲线一点点往下走，值得占用这点终端空间。因为它是编译期开关，开或不开都没有运行时成本；这个选择在你构建的那一刻就定下了。

## 1.2.7. MSRV 与 edition

RustyML 使用 edition 2024，并设置了 `rust-version = "1.89.0"`，因此它的最低支持 Rust 版本是 1.89。Cargo 默认会强制这一点：在更旧的工具链上，解析器会用一句清清楚楚的“requires rustc 1.89.0”拒绝这个 crate，而不是在某次宏展开的深处报错。如果你的版本落后了，`rustup update stable` 就能解决。没有系统库要装，没有 BLAS，也没有 C 或 C++ 工具链——一套能用的 stable Rust 1.89+ 就是全部前提。

## 1.2.8. 诊断未启用的 feature

在一个按 feature 拆分的 crate 上最常见的栽跟头，就是去调用一个你没打开的模块。因为模块带着 `#[cfg(feature = "...")]`，它在你的构建里压根不存在，失败发生在编译期，是一次 unresolved import——绝不会是运行时的意外。假设你依赖 RustyML 时只启用了 `neural_network`，然后伸手去够一个经典估计器：

```rust,ignore
use rustyml::machine_learning::LinearRegression; // machine_learning feature 是关着的
```

编译器会停在 `error[E0432]: unresolved import`，并附带一句“could not find `machine_learning` in `rustyml`”。类型名没拼错，crate 也没坏——是那个模块被编译掉了。要认出这个模式：一个 unresolved import，它*第一个*缺失的路径段是模块名之一（`machine_learning`、`neural_network`、`utils`、`metrics`、`math`），几乎总是意味着对应的 feature 没开。prelude 有一个更隐蔽的同类失败——用 `use rustyml::prelude::*` 而 `metrics` 关着时，那些指标函数干脆就不存在，你得到的会是 `error[E0425]: cannot find function \`accuracy\` in this scope`。根因相同，所以先检查你的 feature 列表。

修法永远是把 feature 加上。如果你用了 `default-features = false`，就把名字加进 `features` 数组；如果你用的是默认组合却去够 `utils` 或 `metrics`，记住它们只在 `full` 里（或者单独点名），不在 `default` 里：

```toml
rustyml = { version = "0.13", features = ["neural_network", "machine_learning"] }
```

两个习惯能让你远离这个坑。在 [docs.rs/rustyml](https://docs.rs/rustyml) 上看 API 时，留意受 feature 控制的条目旁边那些小小的 feature 徽章——docs.rs 是开着所有 feature 构建的，所以每个条目都有文档，而徽章会告诉你它需要哪个 flag。开发中拿不准时，用 `--features full` 构建让所有东西都能解析通过，等代码编译过了再裁回最小集；[7.4 按需裁剪与模块化集成](../Chapter-07/7.4._按需裁剪与模块化集成.md) 会带你走一遍面向生产二进制的裁剪方法。
