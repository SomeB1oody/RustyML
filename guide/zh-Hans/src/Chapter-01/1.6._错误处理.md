# 1.6. 错误处理

RustyML 只有一种错误类型。crate 里每一个可能失败的操作——训练模型、预测、变换、保存、加载、构建层、校验超参数——都返回 `Result<T, rustyml::error::Error>`。没有按模块划分的 `LinearRegressionError`，没有从公开 API 里漏出来的 `Box<dyn Error>`，而且——除了 `metrics` 和 `math` 这两个叶子模块（它们在前置条件不满足时按约定 panic）之外——也不会因为用户输入非法就 `panic!`。如果你从 scikit-learn 过来（它把 `NotFittedError`、`ValueError`、`ConvergenceWarning` 之类抛成一个个不同的 Python 异常类型），或者从一个动辄就上 `anyhow` 的 Rust 项目过来，这里的设计要窄得多：一个 `#[non_exhaustive]` 枚举，配上少数几个命名清晰的变体，再为那些需要自己一套词汇的部分嵌套几个小的领域枚举。正是这种“窄”，让你能用一个 `match` 兜住 crate 抛出的任何东西，而不必导入一大堆错误类型。

## 1.6.1. 一种错误类型，一个 result 别名

这个类型定义在 `rustyml::error` 里，紧挨着它的 result 别名：

```rust,ignore
pub type RustymlResult<T> = std::result::Result<T, Error>;
```

`Error` 是一个由 `thiserror` 派生的枚举，因此免费获得 `std::error::Error` 和 `Display` 的实现，每个变体都携带固定的信息格式。它**不在** prelude 里——`use rustyml::prelude::*` 给你的是各种估计器、层和指标，错误相关的东西要单独引入：`use rustyml::error::Error;`（需要时再加上 `RustymlResult`、`Context` 或 `IoError`）。把它排除在 prelude 之外是有意为之：示例代码大多在调用点 `.unwrap()`，真实代码里则用 `?`，两者都不需要把类型名写出来。

下面列出你真正会去匹配的顶层变体，以及各自的触发场景和 `Display` 渲染出的确切文本：

| 变体 | 触发场景 | `Display` 信息（`{}` / `to_string()`） |
|---|---|---|
| `EmptyInput(String)` | 需要数据的地方传入了空数组、空向量或空数据集 | `input is empty: <what>` |
| `DimensionMismatch { expected, found }` | 两个标量计数对不上（predict 时的特征数与 fit 时不符，`len(x)` 与 `len(y)` 不符） | `dimension mismatch: expected <e>, found <f>` |
| `ShapeMismatch { expected, found }` | 两个完整张量的形状对不上（梯度与它流入的那个激活值） | `shape mismatch: expected [..], found [..]` |
| `NonFinite(String)` | 数据中、或计算产出的某个值为 `NaN` / `inf` | `non-finite value (NaN or infinity) encountered in <where>` |
| `InvalidParameter { name, reason }` | 用户传入的超参数超出取值范围 | ``invalid parameter `<name>`: <reason>`` |
| `InvalidInput(String)` | 没有更具体变体可用的校验失败（rank 不对、样本太少） | `invalid input: <msg>` |
| `NotFitted(&'static str)` | 在 `fit` 之前调用了需要已训练模型的方法 | ``model `<name>` has not been fitted; call `fit` before this operation`` |
| `NotConverged(String)` | 迭代算法始终未达到收敛条件 | `failed to converge: <msg>` |
| `Computation { context, source }` | 数值崩溃、不变量被破坏，或包装了一个外部错误 | `computation failed: <context>` |
| `NeuralNetwork(NnError)` | 神经网络特有的失败（见 §1.6.2） | 透明转发自 `NnError` |
| `Tree(TreeError)` | 决策树特有的失败（见 §1.6.2） | 透明转发自 `TreeError` |
| `Io(IoError)` | 文件系统或（反）序列化失败（见 §1.6.2） | 透明转发自 `IoError` |

表里有两条约定值得留心，因为大家最容易在这两处弄错。第一，你传进去的非有限**超参数**属于 `InvalidParameter`（`reason` 里会提到有限性），而出现在你的**数据**里、或从**计算**中掉出来的非有限值则是 `NonFinite`。第二，`DimensionMismatch` 比较的是标量计数——特征数、向量长度——而 `ShapeMismatch` 针对整个张量的形状不一致，主要出现在神经网络代码里。调试“这两个东西本该一样大”的错误时，你拿到的是哪个变体，就能看出 crate 当时比较的是计数还是形状。

`Error` 标注了 `#[non_exhaustive]`。将来的版本可以新增变体而不构成破坏性更改，这也意味着你在 crate 外部对它写的每一个 `match` 都**必须**带一个通配 `_ =>`（或 `Err(e) =>`）分支。这是编译器强制的，不是可选项。这点小小的代价，换来的是 RustyML 能扩充自己的错误词汇，而不必抬升主版本号。

优先使用这些智能构造器——`Error::not_fitted("KMeans")`、`Error::invalid_parameter("C", "must be > 0")`、`Error::dimension_mismatch(3, 5)`、`Error::empty_input("target vector")` 等等——而不要手工拼装变体。它们保证各处措辞完全一致，而这正是错误信息可 grep 的前提（§1.6.6）。除非你要把 RustyML 包进自己的库里，否则很少需要自己构造错误；真要构造时，就用这些。

## 1.6.2. 领域子错误及其嵌套方式

顶层的三个变体各自包装了一个更小的枚举。这部分设计让共享变体得以保持干净：只与神经网络相关的问题（层状态、权重形状、编译）和只与树相关的问题（分类还是回归）都待在各自的枚举里，顶层 `Error` 再通过 `#[from]` 桥接把它们聚合进来，于是 `?` 能自动把它们抬升上去。

**`NnError`**（位于 `rustyml::neural_network::NnError`）包含 `ForwardPassNotRun(&'static str)`、`WeightShape { name, expected, found }`、`NotCompiled(&'static str)` 和 `EmptyModel`，通过 `Error::NeuralNetwork` 浮现出来。由于该变体标注了 `#[error(transparent)]`，`Error::NeuralNetwork(NnError::EmptyModel).to_string()` 渲染出的文本和 `NnError::EmptyModel` 一模一样——`model has no layers`——没有任何包装前缀。所以一个你忘了 `compile()` 的 `Sequential` 会这样失败：

```rust
use rustyml::neural_network::sequential::Sequential;
use rustyml::neural_network::layers::Dense;
use rustyml::neural_network::layers::activation::ReLU;
use rustyml::neural_network::NnError;
use rustyml::error::Error;
use ndarray::Array;

fn main() {
    let mut model = Sequential::new();
    model.add(Dense::new(4, 2, ReLU::new()).unwrap());

    let x = Array::ones((3, 4)).into_dyn();
    let y = Array::ones((3, 2)).into_dyn();

    // 没有调用 compile()，所以还没配置优化器和损失函数。
    match model.fit(&x, &y, 1) {
        Ok(_) => unreachable!("training should not have started"),
        Err(Error::NeuralNetwork(NnError::NotCompiled(missing))) => {
            println!("compile the model first: `{missing}` is not specified");
        }
        Err(e) => println!("unexpected: {e}"),
    }
}
```

这个 match 一直探进两层深处的 `Error::NeuralNetwork(NnError::NotCompiled(_))`，靠它就能把“你忘了 compile”和“你的 batch 大小对不上”（`Error::DimensionMismatch`）区分开——尽管两者都来自同一次 `fit` 调用。完整的先 compile 再 fit 生命周期见 [3.1. Sequential 模型](../Chapter-03/3.1._Sequential模型.md)。

**`TreeError`**（位于 `rustyml::machine_learning::TreeError`）有 `NotClassificationTree` 和 `CorruptStructure(&'static str)` 两个变体，通过 `Error::Tree` 浮现。当你在一棵回归树上调用 `predict_proba` 这类只属于分类的方法时，就会撞上第一个；而且由于这项检查跑在“是否已训练”检查之前，你甚至能在一棵尚未训练的树上把它触发出来：

```rust
use rustyml::machine_learning::{Algorithm, DecisionTree, TreeError};
use rustyml::error::Error;
use ndarray::array;

fn main() {
    // 回归树（is_classifier = false）没有各类别的概率。
    let tree = DecisionTree::new(Algorithm::CART, false).unwrap();
    let x = array![[1.0, 2.0]];

    match tree.predict_proba(&x) {
        Err(Error::Tree(TreeError::NotClassificationTree)) => {
            println!("predict_proba is classification-only");
        }
        other => println!("unexpected: {other:?}"),
    }
}
```

**`IoError`**（位于 `rustyml::error::IoError`）是模型每次碰到文件系统时都会遇到的那个。它有三个变体：`Std(std::io::Error)` 对应文件系统失败，`Serialization(postcard::Error)` 对应二进制格式（RustyML 用 [postcard](https://docs.rs/postcard) 序列化），`ModelStructureMismatch(String)` 对应加载的神经网络文件与目标架构对不上的情况（层数不同、某个位置的层类型不同，或某个权重的形状放不进目标层）。三者都通过 `Error::Io` 浮现。

两个 `From` 转换让常见场景无缝衔接：`From<std::io::Error> for Error` 产出 `Error::Io(IoError::Std(..))`，`From<postcard::Error> for Error` 产出 `Error::Io(IoError::Serialization(..))`。也就是说，在一个返回 `RustymlResult<T>` 的函数里，直接写 `std::fs::read(path)?` 就能用——`?` 会把 `io::Error` 向上抬两层，纳入统一的类型。从一个不存在的路径加载模型，能反过来展示这层嵌套：

```rust
use rustyml::machine_learning::LinearRegression;
use rustyml::error::{Error, IoError};

fn main() {
    match LinearRegression::load_from_path("model_that_does_not_exist.bin") {
        Ok(_) => unreachable!("the file should not exist"),
        Err(Error::Io(IoError::Std(io_err))) => {
            // io_err 是底层的 std::io::Error（这里的 kind 是 NotFound）。
            println!("filesystem error: {io_err}");
        }
        Err(Error::Io(IoError::Serialization(e))) => {
            println!("the file exists but is not a valid model: {e}");
        }
        Err(e) => println!("unexpected: {e}"),
    }
}
```

匹配 `Error::Io(IoError::Std(..))` 还是 `Error::Io(IoError::Serialization(..))`，正是你把“文件不在 / 读不了”和“文件在，但已损坏或来自不兼容版本”区分开的办法——当你要决定是重新训练还是直接高声报错时，这个区分很关键。格式与版本控制的来龙去脉见 [7.2. 深入模型持久化](../Chapter-07/7.2._深入模型持久化.md)。

## 1.6.3. 匹配具体的变体

最日常的失败是在 `fit` 之前就调用 `predict`。每个估计器都对此加了防护，返回 `Error::NotFitted`，并把自己的名字作为 `&'static str` 带上，于是一个分支就能处理它，而错误信息本身已经告诉用户是哪个模型：

```rust
use rustyml::machine_learning::LinearRegression;
use rustyml::error::Error;
use ndarray::array;

fn main() {
    // 已构造，但从未训练。
    let model = LinearRegression::new(true, 0.01, 1000, 1e-6).unwrap();
    let x = array![[1.0, 2.0], [3.0, 4.0]];

    match model.predict(&x) {
        Ok(preds) => println!("{preds:?}"),
        Err(Error::NotFitted(name)) => {
            println!("`{name}` was not fitted; call fit() first");
        }
        Err(Error::DimensionMismatch { expected, found }) => {
            println!("wrong feature count: model wants {expected}, got {found}");
        }
        // 必须：Error 是 #[non_exhaustive]，所以通配分支是强制的。
        Err(e) => println!("other error: {e}"),
    }
}
```

留意这个 `match` 的形状：两个针对“你能做点什么”的错误的具体分支，再加一个强制的兜底分支。`DimensionMismatch` 分支放在这里是为了展示写法——这次调用实际触发的是 `NotFitted`——但如果给一个已训练的模型喂进列数不对的矩阵，走的就是第二个分支了，此时 `expected` 是 `fit` 时看到的特征数，`found` 是你刚传进去的那个。[2.0. 经典机器学习](../Chapter-02/2.0._经典机器学习.md) 里的那些估计器 trait 全都返回同一个 `Error`，所以一个 `match` 就能通吃每个模型。

## 1.6.4. 用 `?` 传播，无需 anyhow

整个 crate 都汇入同一种错误类型，所以把失败串过一整条流水线，除了朴素的 `Result` 和 `?` 之外什么都不需要。你用不上 `anyhow`、`eyre`，也不用自己定义一个错误枚举——RustyML 的 `Error` 本身就是那个公分母。给你自己的函数签名用上 `RustymlResult<T>` 别名，`-> RustymlResult<T>` 就明确无误地表示*这个* crate 的错误：

```rust
use rustyml::machine_learning::LinearRegression;
use rustyml::error::RustymlResult;
use ndarray::{array, Array1, Array2};

fn train_and_predict(x: &Array2<f64>, y: &Array1<f64>) -> RustymlResult<Array1<f64>> {
    // 下面每个 ? 都会从一次可能失败的调用中抬出一个 rustyml::error::Error。
    let mut model = LinearRegression::new(true, 0.05, 500, 1e-9)?; // 可能是 InvalidParameter
    model.fit(x, y)?;                                              // 可能是 EmptyInput / DimensionMismatch / NonFinite
    let preds = model.predict(x)?;                                 // 可能是 NotFitted / DimensionMismatch
    Ok(preds)
}

fn main() {
    let x = array![[1.0], [2.0], [3.0]];
    let y = Array1::from_vec(vec![2.0, 4.0, 6.0]);

    match train_and_predict(&x, &y) {
        Ok(preds) => println!("got {} predictions", preds.len()),
        Err(e) => eprintln!("pipeline failed: {e}"),
    }
}
```

`train_and_predict` 里每个 `?` 返回的都是同一个 `Error`，所以没有任何在错误类型之间来回转换的 `.map_err` 样板代码——那种在混用多个错误枚举的代码库里把错误处理拖得啰嗦的东西，这里根本不会出现。

当你*确实*需要把一个外部错误（来自标准库或别的 crate）折进这套体系、同时保留它的成因链时，就用 `Context` 扩展 trait。它为任何 `E` 满足 `Send + Sync + 'static` 且实现了 `std::error::Error` 的 `Result<T, E>` 都做了实现，因此能和 `?` 配合。`context` 会立即取用信息；`with_context` 接收一个只在错误路径上运行的闭包——只要构造信息会带来分配（凡是用到 `format!` 的），就优先用闭包形式，这样成功路径不用付出任何代价：

```rust
use rustyml::error::{Context, Error, RustymlResult};

fn parse_threshold(raw: &str) -> RustymlResult<f64> {
    // 一个标准库的 ParseFloatError，连同我们的 context 一起包装成 Error::Computation，
    // 它的 source() 链得以保留，供之后向下转型使用。
    let value: f64 = raw
        .parse()
        .with_context(|| format!("parsing threshold from {raw:?}"))?;
    Ok(value)
}

fn main() {
    match parse_threshold("not-a-number") {
        Ok(v) => println!("threshold = {v}"),
        Err(Error::Computation { context, source }) => {
            println!("{context}");
            if let Some(cause) = source {
                println!("  caused by: {cause}");
            }
        }
        Err(e) => println!("unexpected: {e}"),
    }
}
```

外部错误会成为 `Error::Computation` 的 `source`，可以经由标准的 `std::error::Error::source()` 链拿到，并向下转型回原本的具体类型——所以把它折进来不会丢失任何信息。

## 1.6.5. 及早校验，而非 panic

RustyML 的约定是：**构造器以及 fit/predict 方法会及早校验并返回 `Result`，而不是在遇到非法输入时 panic**。学习率为零，不会等到梯度下降跑了十轮才炸掉；它在你构建模型的那一刻就被拒绝，错误信息会点名是哪个参数、又为什么：

```rust
use rustyml::machine_learning::LinearRegression;
use rustyml::error::Error;

fn main() {
    // learning_rate 必须为正且有限——0.0 在构造时就会被拒绝。
    match LinearRegression::new(true, 0.0, 1000, 1e-6) {
        Ok(_) => unreachable!("a zero learning rate must not be accepted"),
        Err(Error::InvalidParameter { name, reason }) => {
            // 打印：bad parameter `learning_rate`: must be positive and finite, got 0
            println!("bad parameter `{name}`: {reason}");
        }
        Err(e) => println!("unexpected: {e}"),
    }
}
```

同样的纪律贯穿整个 crate：`Dense::new` 会用 `InvalidParameter` 拒绝为零的 `input_dim` 或 `units`；`KMeans::new`、`PCA::new` 以及其余构造器，都在返回 `Ok` 之前校验各自的超参数。输入矩阵会在 `fit` 和 `predict` 处检查是否为空、特征数是否一致、取值是否有限，分别对应 `EmptyInput`、`DimensionMismatch` 和 `NonFinite`。这样做的回报是：错误指向你真正犯的那个错，而不是某个下游症状。

不过 panic 并没有彻底消失，说它绝迹是不诚实的。它们出现在两类地方：一类是 RustyML 有意用 panic 代替校验，另一类是 Rust 本身就会 panic、而 RustyML 不去拦截：

- **`metrics` 与 `math` 两个叶子模块**——它们的函数在前置条件不满足时（长度不匹配、输入为空、Minkowski 阶数越界）按约定直接 panic，而不返回 `Result`，正是这一点让这两个叶子模块保持依赖轻量。这是对上文“及早返回 `Result`”约定的唯一一处有意例外；[1.1.3](./1.1._认识RustyML.md#113-模块地图)、§1.5.2 的指标说明以及 [5. 模型评估](../Chapter-05/5.0._模型评估.md) 都点明了这一点。
- **你自己代码里的索引误用**——`array[[i, j]]` 越界索引、对 `None` 调用 `.unwrap()`、debug 构建下的整数溢出。这些是调用方的 bug，用 `Result` 反而会把它们藏起来。
- **crate 掌控之外的 `ndarray` 形状操作**——用对不上的数据和形状构造数组，或 reshape 到不兼容的尺寸。注意 `Array2::from_shape_vec` 返回的是你可以处理的 `Result`，但 `ndarray` 的索引和某些 reshape 路径按设计就是 panic 的。你交给 RustyML 的那些输入数组，其构造是你自己的事；见 [1.3. 使用 ndarray 准备数据](./1.3._使用ndarray准备数据.md)。

一条经验法则：在估计器、层和 I/O 这套 API 里，凡是 RustyML 对*你的数据或超参数*所做的校验，都会以一个你能 match 的 `Error` 返回（`metrics`/`math` 两个叶子模块是上文提到的那处有意例外）；凡是*编程 bug*——错误的索引、你以为是 `Some` 的 `None`——则保持为 panic，因为 panic 本就是干这个用的。

## 1.6.6. 调试：读懂信息，以及该 grep 什么

crate 里每一条信息都由同一小组智能构造器产出，这意味着措辞稳定，可以拿去 grep。用户丢给你一行日志，你就能很快定位到确切的源码位置。

拿到 ``invalid parameter `learning_rate`: must be positive and finite, got 0`` 这样一条信息，其中不变的部分（`must be positive and finite`）直接来自构造器调用，所以在源码里搜它，就能落到那处校验：

```bash
# 找出某条特定信息是在哪里产出的：
grep -rn "must be positive and finite" src/
# 找出所有能抛出某个变体的位置：
grep -rn "Error::not_fitted\|NotFitted" src/
grep -rn "Error::invalid_parameter\|InvalidParameter" src/
grep -rn "dimension_mismatch\|DimensionMismatch" src/
```

既然变体本身就是这套词汇，最快的排查方式通常是读 `Display` 输出的开头几个词，再对回 §1.6.1 的那张表：`input is empty` → `EmptyInput`，`dimension mismatch` → `DimensionMismatch`，`non-finite value` → `NonFinite`，`model \`...\` has not been fitted` → `NotFitted`，`model has not been compiled` → `NnError::NotCompiled`，依此类推。这些信息刻意做成全小写、前缀一致，就是为了让这套映射毫不含糊。

手里拿到 `Error::Computation` 时——它是唯一能包装外部成因的变体——有用的细节往往在下一层。顺着 `std::error::Error::source()` 链走（或者像 §1.6.4 那样匹配 `Error::Computation { source: Some(s), .. }`）就能取回原始错误，需要据此分支时再 `downcast_ref` 成它的具体类型。其余情况下，`{}` 给你人类可读的信息，`{:?}` 给你完整的 `Debug` 形式，包含嵌套的变体及其字段——这正是你在测试断言和开发期 `eprintln!` 里想要的。

最后一个值得养成的习惯：在 RustyML 之上写库代码时，坚持返回 `RustymlResult<T>`（或 `Result<T, rustyml::error::Error>`），别把一切都塌缩成 `String` 或 `Box<dyn Error>`。你免费继承整套可匹配的变体，你的调用方仍然能把“未训练”、“坏文件”、“没收敛”区分开，而且你永远不必为了让它组合起来去写一个 `From` 实现。这份可组合性，正是 crate 最终选定一种错误类型、而非多种的全部理由。
