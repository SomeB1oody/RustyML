# 6.3. 并行归约

如果你是奔着 `sum()` 和 `mean()` 来的，得先调整一下预期：`rustyml::math::reduction` 不提供任何有名字的归约函数。它给的是两个泛型折叠组合子——[`det_reduce`](https://docs.rs/rustyml/latest/rustyml/math/reduction/fn.det_reduce.html) 和 [`det_reduce_range`](https://docs.rs/rustyml/latest/rustyml/math/reduction/fn.det_reduce_range.html)——外加一个常量 [`DET_REDUCE_BLOCK`](https://docs.rs/rustyml/latest/rustyml/math/reduction/constant.DET_REDUCE_BLOCK.html)。这个 crate 里所有需要并行归约的地方——线性回归里的误差平方和、clip-by-global-norm 用到的全局梯度范数、标准化里一遍扫完的 Welford 矩、k-means 的惯性、逻辑回归的对数损失——全都架在这两个函数之上。它们的存在只为了一件普通并行求和给不了你的事：一个不取决于当时恰好跑了多少个线程的结果。

## 6.3.1. 模块到底暴露了什么

整个公开接口就三个条目。它们躲在 `math` feature 后面，而其他每个 feature（`machine_learning`、`neural_network`、`utils`、`metrics`）都会把它拉进来，所以只要 RustyML 能编译，它们就一定可用（见 [1.2. 安装与Feature配置](../Chapter-01/1.2._安装与Feature配置.md)）。

| 条目 | 签名（省略约束） | 作用 |
| --- | --- | --- |
| `DET_REDUCE_BLOCK` | `pub const DET_REDUCE_BLOCK: usize = 16_384` | 定义分组粒度的固定块大小，以元素为单位 |
| `det_reduce` | `fn det_reduce<T, A, F, M>(slice: &[T], parallel: bool, fold_block: F, merge: M, identity: A) -> A` | 按固定块折叠一个切片 |
| `det_reduce_range` | `fn det_reduce_range<A, F, M>(n: usize, parallel: bool, fold_block: F, merge: M, identity: A) -> A` | 按固定块折叠索引区间 `0..n` |

完整的约束值得读一遍，因为围绕它们的编译器报错常常把人绕晕：

```rust,ignore
pub fn det_reduce<T, A, F, M>(slice: &[T], parallel: bool, fold_block: F, merge: M, identity: A) -> A
where
    T: Sync,
    A: Send,
    F: Fn(&[T]) -> A + Sync + Send,   // 对单个块做串行折叠
    M: Fn(A, A) -> A,                 // 合并两个部分结果
{ /* ... */ }
```

`fold_block` 把一个块归约成累加器类型 `A` 的一个部分结果；`merge` 合并两个部分结果；`identity` 是空输入时返回的值，也是最终合并的种子。`fold_block` 必须是 `Sync + Send`（rayon 可能在任意 worker 上调用它），哪怕你传的是 `parallel = false`——约束加在类型上，而不是那个 flag 上——但 `merge` 两者都不需要，因为它永远在单个线程上按块顺序运行。`A` 可以是任何 `Send` 的东西：一个标量、一个元组 `(sum, sum_of_squares)`、一个 Welford 三元组、一个按桶分组的和数组。`det_reduce_range` 是同一套机制，只不过作用在索引区间而非切片上，适合那些一次读多个数组、或者按行索引矩阵的归约——它的 `fold_block` 收到的是 `Range<usize>`，而不是 `&[T]`。

这里刻意没有 `sum` 包装函数。在并行阈值之下，一行 `slice.iter().sum()` 已经是对的工具；阈值之上，调用方几乎总想把一个 map（平方、`exp`、距离）融进同一遍扫描里，而不是先物化出一个中间结果。把折叠交给你、而不是给你一个写死的归约，正是为了让这种融合留在调用点。

## 6.3.2. 为什么朴素的并行求和不确定

浮点加法不满足结合律：`(a + b) + c` 和 `a + (b + c)` 可能舍入到不同的 `f64` 值。这不是你硬件的 bug，而是每次运算后都舍入到 53 位这一定义本身。只要求和在单个线程上从左到右进行，次序就是固定的，结果也就可复现。可一旦你把它并行化，次序就不再固定。

一个裸的 `slice.par_iter().sum::<f64>()`（或者 `fold().reduce()`）会自适应地切分工作，把哪个 worker 折叠哪段子区间、部分和又以什么次序合并，统统交给 rayon 的工作窃取调度器决定。在一台有 4 个空闲核心的机器上跑，得到一种分组；同样的输入用 `RAYON_NUM_THREADS=1` 跑，又是另一种；在一台繁忙的 16 核机器上跑两遍，两次结果也可能对不上，因为某个线程在不同的时刻被抢占了。这些结果每一个都是同一组数字的正确求和——它们只是舍入方式不同，通常差在最后几个 ULP 上。

对很多数值代码来说，这种抖动无伤大雅。但对一个机器学习库，它是腐蚀性的。低位来回晃动的损失值，会让早停检查在不同运行里于不同迭代触发；依赖线程数的梯度范数，会让 clip-by-global-norm 剪裁得略有出入；它还会把「同一份拟合我跑了两遍，得到两个模型」变成一个真实的用户报障。可复现性在 RustyML 里是头等承诺（见 [7.1. 可复现性与随机种子](../Chapter-07/7.1._可复现性与随机种子.md)），而一个依赖调度器的归约会从底层把它拆穿，无论你的 RNG 种子撒得多小心。

## 6.3.3. 分块算法

解法是把分组从调度器手里夺回来，钉死到一个常量上。`det_reduce` 把输入切成固定 `DET_REDUCE_BLOCK` 个元素的块，用你的 `fold_block` 串行折叠每个块，**按块顺序**收集每块的部分结果，再用你的 `merge` 从左到右合并。并行路径与串行路径的唯一差别，只在于块怎么被分派出去：

```rust,ignore
if parallel {
    let parts: Vec<A> = slice.par_chunks(DET_REDUCE_BLOCK).map(fold_block).collect();
    parts.into_iter().fold(identity, merge)          // 按块顺序合并
} else {
    slice.chunks(DET_REDUCE_BLOCK).map(fold_block).fold(identity, merge)
}
```

起承重作用的细节是，rayon 的 `par_chunks(...).collect::<Vec<_>>()` 是一个**有序（indexed）**并行迭代器：无论工作窃取把这些块怎样分到各个线程上，收集回来的 `Vec` 都会保持原本的块顺序。于是那棵归约树——哪些元素落进哪个块、块又以什么次序合并——就是输入长度和 `DET_REDUCE_BLOCK` 的纯函数。它不依赖线程数，不依赖调度，也不依赖 `parallel` 这个 flag。两条路径折叠的都是同样的 16 384 个元素的块，次序相同，合并方式也相同。`det_reduce_range` 在 `n.div_ceil(DET_REDUCE_BLOCK)` 个索引块上做完全相同的事，其中第 `b` 块覆盖 `b * BLOCK .. ((b + 1) * BLOCK).min(n)`。

这就让 `parallel` 参数变成一个纯粹的性能提示。它绝不改变哪些数字以什么次序相加——只决定这些块是跑在 rayon 线程池上，还是跑在一个普通的顺序循环里。crate 自己的测试用逐位 `==`（不是某个 epsilon）跨空输入、不足一块、恰好一块、以及参差不齐的多块长度断言了这一点。所以在给定的一次构建里，两条路径逐位相同，改动 `RAYON_NUM_THREADS` 也无法改变结果。模块文档仍然留了一句「不保证逐位一致」——那条附注针对的是*跨机器*和*跨构建*的差异（不同的 libm `sin`、被不同 target-cpu 拨动的 FMA 收缩、你自己 `fold_block` 里不同的舍入），而不是线程数，线程数已经被分块彻底钉死。

`DET_REDUCE_BLOCK` 取 16 384，是因为吞吐量的平台期恰好落在这里：在一个 420 万元素的平方和上，块大小从 4K 到 64K，加速比都是平的（大约 17–18 倍），其中 16K 最快，而到了 256K 就开始下滑，因为此时块太少，无法在核心之间均衡。这个常量数的是**元素**，不是字节，并且被所有元素类型共用——16 384 个 `f32`（每块 64 KB）和 16 384 个 `f64`（128 KB）都稳稳落在平台期中段。因为这个值定义了分组，它就成了可复现性接口的一部分：改动它会（在仍然确定的前提下）改变结果的低位，所以它是一个 `const`，而不是一个旋钮。

## 6.3.4. 精度是副产品，不是目标

选择分块是为了确定性，但它顺带白赚了一份实打实的精度提升，这一点值得弄明白，因为它对**两条**路径都成立——串行路径同样切块，所以即便 `parallel = false` 也不是对整个数组的朴素左折叠。

从左到右把 `n` 个浮点数相加，最坏情况的舍入误差按 `(n - 1) * ε * Σ|xᵢ|` 增长——关于 `n` 是线性的。`det_reduce` 是一个两级方案：每个块串行折叠 `b = 16 384` 项，然后 `⌈n / b⌉` 个块的部分结果再串行折叠。误差上界于是大致变成 `(b + n/b) * ε * Σ|xᵢ|`。对一个 420 万元素的求和，这大约是 `(16 384 + 256) * ε`，对比朴素做法的 `4.2M * ε`——最坏情况上界收紧了约 250 倍，而且无论你把这些块并行还是串行地跑，改进都一样。不过要诚实地说清它到底是什么：它是扁平分块加一次串行合并，不是完整的成对（`log n`）求和树。实践中，累加器的位宽比树的形状更要紧——留意 `global_grad_norm` 是在 `fold_block` 内部把 `f32` 梯度归约进 `f64` 累加器（SSE 循环全程就是 `f64`），这对精度的贡献远大于分块本身。分块是确定性的底线；而当精度才是你真正在意的问题时，宽累加器才是你该伸手去拿的东西。

## 6.3.5. 并行路径何时开启

`det_reduce` 不替你决定 `parallel`——由你来传。在这个 crate 里，那个布尔值是一道校准过的尺寸阈值的输出，因为在大约一块以下没什么可并行的（一个短于 16 384 元素的输入就是单独一块，把它 fork 到 rayon 上只会平添 join 开销）。这些阈值住在 `rustyml::tuning::reduction` 里，并且按成本类别共享，而不是按调用点：

| 阈值（`tuning::reduction` 中的 getter） | 默认值 | 守护对象 |
| --- | --- | --- |
| `get_sum_f64` | 262 144 | `f64` 求和类归约（SSE、Welford 矩、k-means 惯性） |
| `get_sq_sum_f32` | 65 536 | clip-by-global-norm 的 `f32`→`f64` 平方和 |
| `get_scan_f64` | 262 144 | 短 `f64` 逐行扫描（arg-min、距离扫描） |
| `get_exp_reduce` | 32 768 | exp 密集的逻辑回归对数损失归约 |

每个调用点的写法都一样——把 `slice.len() >= gate()` 当作 flag 传进去——所以阈值能挪动切换点，却从不触碰正确性，恰恰因为分块折叠在切换点两侧给的是同一个答案。每道阈值都配有一个对应的 setter（`set_sum_f64`、`set_sq_sum_f32`……），你想按自己的硬件调切换点就用它；具体机制和校准的来龙去脉见 [7.3. 性能调优与并行](../Chapter-07/7.3._性能调优与并行.md)。exp 归约那道阈值设得最低（32 768），因为那里每个元素都要付一次 `exp` 和一次 `ln`，所以并行比普通加法更早摊平成本。

## 6.3.6. 在你自己的代码里使用它们

最小的调用——在一个 `Vec<f64>` 上做融合的平方和，保持串行：

```rust
use rustyml::math::reduction::det_reduce;

fn main() {
    let data: Vec<f64> = (0..1_000).map(|i| (i as f64).sin()).collect();
    let sum_sq = det_reduce(
        &data,
        false, // 性能提示；输入小，保持串行
        |block| block.iter().map(|&x| x * x).sum::<f64>(),
        |a, b| a + b,
        0.0,
    );
    println!("sum of squares = {sum_sq}");
}
```

这里有两处坑人。第一，`det_reduce` 接收的是 `&[T]`，所以数据必须是一段连续的切片；一个 `ndarray` 数组只能通过 `as_slice()` 给出连续切片，而对非标准布局的视图，`as_slice()` 会返回 `None`。惯用的写法——也是 crate 自己用的——是在连续的快路径上用 `det_reduce` 归约，其余情况回退到 ndarray 的串行内核，并把 flag 按尺寸类别来门控：

```rust
use ndarray::Array1;
use rustyml::math::reduction::det_reduce;
use rustyml::tuning::reduction::get_sum_f64;

fn main() {
    let v: Array1<f64> = (0..10_000).map(|i| i as f64).collect();
    let sum = match v.as_slice() {
        Some(slice) => det_reduce(
            slice,
            slice.len() >= get_sum_f64(),
            |block| block.iter().sum::<f64>(),
            |a, b| a + b,
            0.0,
        ),
        None => v.sum(), // 非连续：走 ndarray 的串行折叠
    };
    println!("sum = {sum}");
}
```

第二，累加器不必是标量——这正是把折叠交给你的全部意义。一遍扫描同时返回和与平方和（足够算出均值和方差），就是一个元组累加器配一个元组 `merge`：

```rust
use rustyml::math::reduction::det_reduce;

fn main() {
    let data: Vec<f64> = (0..10_000).map(|i| (i as f64).sin()).collect();
    let (sum, sum_sq) = det_reduce(
        &data,
        false,
        |block| block.iter().fold((0.0f64, 0.0f64), |(s, sq), &x| (s + x, sq + x * x)),
        |(sa, sqa), (sb, sqb)| (sa + sb, sqa + sqb),
        (0.0, 0.0),
    );
    let n = data.len() as f64;
    let mean = sum / n;
    let variance = sum_sq / n - mean * mean;
    println!("mean = {mean}, variance = {variance}");
}
```

当归约需要一次读多个数组时——点积、距离累加、逐行挑选——就改用 `det_reduce_range`，在块内部做索引：

```rust
use rustyml::math::reduction::det_reduce_range;

fn main() {
    let xs: Vec<f64> = (0..5_000).map(|i| i as f64).collect();
    let ys: Vec<f64> = (0..5_000).map(|i| (i as f64).cos()).collect();
    let dot = det_reduce_range(
        xs.len(),
        false,
        |range| range.map(|i| xs[i] * ys[i]).sum::<f64>(),
        |a, b| a + b,
        0.0,
    );
    println!("dot = {dot}");
}
```

### `det_reduce` 对比 ndarray 的 `.sum()`

ndarray 的 `.sum()`、`.dot()` 和 `.mean()` 是串行、单线程的，内部分组自成一套——一般不会和 `det_reduce` 的分块逐位吻合。对小数组，它们才是对的选择：写起来更短，没有闭包，而且在阈值之下 `det_reduce` 反正也是串行跑，还多一堆仪式。什么时候伸手去拿 `det_reduce`？当你手里有一段确实很大的连续缓冲区，*并且*想让它并行归约，*并且*需要这个并行结果可复现——这恰好是 ndarray 不提供的组合，因为即便开了 ndarray 的 `rayon` feature，一个裸的并行求和也会退回到依赖调度器。当你想把一个 map 融进归约、或者累加比标量更丰富的东西时，它同样是趁手的工具。一条好用的准则：默认用 ndarray 图个方便、应付小数据；到了你正要写下一个 `par_iter().sum()`、又在意答案是否稳定的那个点，就切换到 `det_reduce`。互操作的细节见 [1.3. 使用ndarray准备数据](../Chapter-01/1.3._使用ndarray准备数据.md)，而 [4.2. 标准化与归一化](../Chapter-04/4.2._标准化与归一化.md) 里有一个正是架在这套折叠之上的真实 Welford 归约。

## 6.3.7. 跨线程数验证确定性

这个论断从外部就能验证，值得亲手做一次好让你信服。下面这个程序在 rayon 路径上归约两百万个值，并以完整精度打印出和：

```rust
use rustyml::math::reduction::det_reduce;

fn main() {
    let data: Vec<f64> = (0..2_000_000).map(|i| (i as f64 * 0.001).sin()).collect();
    let sum = det_reduce(
        &data,
        true, // 强制走并行路径
        |block| block.iter().sum::<f64>(),
        |a, b| a + b,
        0.0,
    );
    // 完整精度打印，这样低位的差异也会显形
    println!("{sum:.17e}");
}
```

编译一次，然后通过设置 `RAYON_NUM_THREADS` 在不同线程数下运行它——这个变量给 rayon 的全局线程池设了上限：

```bash
RAYON_NUM_THREADS=1 ./target/release/demo
RAYON_NUM_THREADS=2 ./target/release/demo
RAYON_NUM_THREADS=8 ./target/release/demo
```

三次都打印出完全相同的 17 位尾数，因为每次运行折叠的都是同样的 16 384 个元素的块，并按同样的块顺序合并，跟当时有多少个 worker 扛着这些块毫无关系。把 flag 翻成 `false`，输出照样纹丝不动。拿它对比一下：把函数体换成 `data.par_iter().sum::<f64>()`——在不同 `RAYON_NUM_THREADS` 取值下，只要输入够大，那个版本打印出的和就会在最后几位数字上出现差异，而这正是 `det_reduce` 当初为了堵住而写的那个失效模式。相关的数值原语共享同一套确定性纪律：见 [6.1. 距离度量](./6.1._距离度量.md) 和 [6.2. 矩阵乘法](./6.2._矩阵乘法.md)，以及更宏观的 [6.0. 数学工具](./6.0._数学工具.md) 概览。
