# 1.2. Installation and Feature Flags

RustyML ships as a single crate on crates.io, but it is deliberately carved into feature-gated modules so you compile only the parts you use. Coming from `pip install scikit-learn`, where you get one monolith, this is the first thing that will bite you: switch on the wrong flag and the type you want simply is not in the crate, and the compiler reports an unresolved import rather than a missing symbol at runtime. This page pins down exactly which flag unlocks which module, which third-party crates each one drags in, and how to pair RustyML with `ndarray` in your own manifest so array construction works at all.

## 1.2.1. Adding RustyML to your project

The fastest path is `cargo add`, which writes the dependency line for you:

```bash
cargo add rustyml
cargo add ndarray@0.17
```

The first command pulls RustyML with its default features (`machine_learning` + `neural_network`). The second is not optional decoration — you almost always need `ndarray` as a *direct* dependency too, for reasons covered in [1.2.5](#125-pairing-with-ndarray-017). Written out, a typical `Cargo.toml` looks like this:

```toml
[dependencies]
rustyml = { version = "0.13", features = ["full"] }
ndarray = "0.17"
```

Pick the feature set that matches what you actually build. A few common shapes:

```toml
# Default bundle: classical ML + neural networks (what `cargo add rustyml` gives you)
rustyml = "0.13"

# Just the neural-network framework
rustyml = { version = "0.13", features = ["neural_network"] }

# Everything: machine_learning, neural_network, utils, metrics, math
rustyml = { version = "0.13", features = ["full"] }

# Everything, plus terminal progress bars during training
rustyml = { version = "0.13", features = ["full", "show_progress"] }
```

To go the other way and trim aggressively, disable the defaults and name only what you need — this is the whole point of the split, and [7.4 Minimal Builds and Modular Integration](../Chapter-07/7.4._Minimal_Builds_and_Modular_Integration.md) treats it in depth:

```bash
cargo add rustyml --no-default-features --features metrics
```

```toml
rustyml = { version = "0.13", default-features = false, features = ["metrics"] }
```

## 1.2.2. The feature matrix

Seven features control the build. Five of them unlock a public module of the same name; `default` and `full` are convenience bundles.

| Feature | Unlocks | Notes |
|---------|---------|-------|
| `machine_learning` | `rustyml::machine_learning` | Regression, classification, clustering, dimensionality reduction, anomaly detection |
| `neural_network` | `rustyml::neural_network` | Keras-style `Sequential`, layers, optimizers, losses |
| `utils` | `rustyml::utils` | Standardize, normalize, label encoding, train/test split |
| `metrics` | `rustyml::metrics` | Regression, classification, and clustering evaluation metrics |
| `math` | `rustyml::math` | Distances, `gemm`-backed matrix products, deterministic parallel reductions |
| `default` | `machine_learning` + `neural_network` | The bundle you get if you name no features |
| `full` | `machine_learning` + `neural_network` + `utils` + `metrics` + `math` | All modules |
| `show_progress` | (no new module) | Renders training progress bars; see [1.2.6](#126-show_progress) |

The dependency you cannot see in that table is `math`. Every one of `machine_learning`, `neural_network`, `utils`, and `metrics` enables `math` automatically, because each of them leans on the shared numeric primitives — pairwise distances, GEMM/GEMV, blocked reductions — that live there. You never need to add `math` by hand alongside another module; you would only ask for `math` on its own if you want nothing but the raw numeric kernels (covered in [6. Math Utilities](../Chapter-06/6.0._Math_Utilities.md)).

A handful of cross-cutting modules come along for the ride and are gated on *any* of the higher-level features rather than a flag of their own. `rustyml::error` (the unified `Error` type, see [1.6 Error Handling](./1.6._Error_Handling.md)) and `rustyml::random` (global-seed control, see [7.1 Reproducibility and Random Seeds](../Chapter-07/7.1._Reproducibility_and_Random_Seeds.md)) appear whenever `machine_learning`, `neural_network`, or `utils` is on — but not for a `metrics`-only or `math`-only build, since those leaf modules neither return `RustymlResult` nor consume randomness. `rustyml::tuning` (runtime parallelism gates, see [7.3 Performance Tuning and Parallelism](../Chapter-07/7.3._Performance_Tuning_and_Parallelism.md)) shows up for any feature at all, because every module has at least one gate worth retuning. The `rustyml::prelude` module is always compiled, but each of its submodules (`prelude::machine_learning`, `prelude::metrics`, and so on) is itself feature-gated, so the prelude only re-exports what you switched on — that mechanism is the subject of [1.5 The Prelude and Imports](./1.5._The_Prelude_and_Imports.md).

## 1.2.3. Which third-party crates each feature activates

Every dependency in RustyML is `optional = true` and pulled in by a feature. Turning a feature off means its crates are never compiled, which is where the build-time savings come from. This is the mapping, transitive `math` dependencies included:

| Feature | Third-party crates it activates |
|---------|---------------------------------|
| `math` | `ndarray`, `ahash`, `rayon`, `gemm` |
| `machine_learning` | `ndarray`, `rayon`, `ndarray-rand`, `ahash`, `serde`, `postcard`, `thiserror`, `gemm` |
| `neural_network` | `ndarray`, `rayon`, `ndarray-rand`, `indicatif`, `serde`, `postcard`, `thiserror`, `gemm` |
| `utils` | `ndarray`, `rayon`, `ndarray-rand`, `ahash`, `serde`, `postcard`, `thiserror`, `gemm` |
| `metrics` | `ndarray`, `ahash`, `rayon`, `gemm` |
| `show_progress` | `indicatif` |

The exact versions RustyML builds against are `ndarray` 0.17, `rayon` 1.12, `ndarray-rand` 0.16, `ahash` 0.8, `serde` 1.0 (with `derive`), `postcard` 1.1 (with `use-std`), `thiserror` 2.0, `indicatif` 0.18, and `gemm` 0.19 (with `rayon`). What each buys: `ndarray` is the array type used across the entire public API; `rayon` and `gemm` are the parallel-compute backbone; `ndarray-rand` seeds randomized initializers; `ahash` provides the fast hash maps behind label encoding and clustering; `serde` + `postcard` are the serialization pair behind every `save_to_path` / `load_from_path`; `thiserror` derives the `Error` enum; and `indicatif` draws the progress bars.

Two asymmetries are worth internalizing. First, `metrics` is the leanest non-`math` module: it activates neither `serde`/`postcard` (metrics have nothing to persist) nor `thiserror` (metric functions panic on precondition violations instead of returning `Result`, keeping this leaf dependency-light). A `metrics`-only build is therefore dramatically cheaper to compile than anything that carries the serialization stack. Second, `neural_network` lists `indicatif` in its own dependency set, so the crate is compiled whenever neural networks are on — but the bars themselves are still `#[cfg(feature = "show_progress")]` and only render when you also enable that flag. For the classical models, `indicatif` is pulled in *only* by `show_progress`. The user-facing rule is simple regardless: no `show_progress`, no progress bars, anywhere.

The compile-time implication is direct. `serde`, `postcard`, and `thiserror` together with their proc-macro derives are the heaviest part of a cold build; dropping them (by staying on `metrics` and/or `math`) is the single biggest lever on build time and dependency count. If you are embedding RustyML as one component of a larger service and only need, say, its clustering metrics, `default-features = false, features = ["metrics"]` compiles a small fraction of what `full` does.

## 1.2.4. A minimal end-to-end check

With the default bundle in place, here is the full compile-train-predict loop for a classical estimator. Note the two imports: RustyML for the model, `ndarray` for the data.

```rust
use rustyml::prelude::machine_learning::*;
use ndarray::array;

fn main() {
    // 3 samples, 2 features; the target is a linear combination of the inputs.
    let x = array![[1.0, 2.0], [2.0, 3.0], [3.0, 4.0]];
    let y = array![6.0, 9.0, 12.0];

    // new(fit_intercept, learning_rate, max_iterations, tolerance) -> Result.
    let mut model = LinearRegression::new(true, 0.01, 1000, 1e-6).unwrap();
    model.fit(&x, &y).unwrap();

    let predictions = model.predict(&x).unwrap();
    println!("predicted {} values", predictions.len());
}
```

## 1.2.5. Pairing with ndarray 0.17

Every RustyML entry point speaks `ndarray`: classical estimators take `Array2<f64>` feature matrices and `Array1<f64>` targets, while the neural network operates on `Tensor`, an alias for `ArrayD<f32>` (note the element type — ML and utilities are `f64`, the network is `f32`). RustyML does not re-export `ndarray`'s constructors, so to *build* the arrays you feed in — with `array!`, `Array2::from_shape_vec`, `Array::ones`, and friends — you call `ndarray` directly. That is why it must be a direct dependency in your own `Cargo.toml`, not merely a transitive one; a transitive dependency's items are not in scope for your code. [1.3 Working with ndarray](./1.3._Working_with_ndarray.md) covers the array-building patterns the estimators expect.

The version has to line up. RustyML builds against `ndarray` 0.17, and `0.x` releases of a crate are semver-incompatible with one another. If your manifest pins a different major-minor — say `ndarray = "0.16"` — Cargo will resolve *two* copies of `ndarray` into the build, and the `Array2` you construct from your copy is a genuinely different type from the `Array2` RustyML's signatures expect. The error is a baffling "expected `ndarray::ArrayBase<...>`, found `ndarray::ArrayBase<...>`" where the two types print identically. Depend on `ndarray = "0.17"` and the problem disappears: Cargo unifies both crates onto one semver-compatible version.

For the neural network the shape is the same, only the constructors change. `Sequential` itself is not in the prelude, so import it explicitly:

```rust
use rustyml::neural_network::sequential::Sequential;
use rustyml::prelude::neural_network::*;
use ndarray::Array;

fn main() {
    // 6 samples, 4 input features, 2 output classes.
    let x = Array::ones((6, 4)).into_dyn();
    let y = Array::ones((6, 2)).into_dyn();

    let mut model = Sequential::new();
    model
        .add(Dense::new(4, 8, Activation::ReLU).unwrap())
        .add(Dense::new(8, 2, Activation::Softmax).unwrap())
        .compile(
            Adam::new(0.001, 0.9, 0.999, 1e-8, 0.0).unwrap(),
            CategoricalCrossEntropy::new(false),
        );

    model.fit(&x, &y, 3).unwrap();

    let predictions = model.predict(&x).unwrap();
    println!("prediction shape: {:?}", predictions.shape());
}
```

The `metrics` module follows the same convention — every function takes `(y_true, y_pred)` as borrowed 1-D arrays, matching scikit-learn's argument order:

```rust
use rustyml::metrics::{ConfusionMatrix, accuracy};
use ndarray::array;

fn main() {
    let y_true = array![1.0, 0.0, 0.0, 1.0, 1.0];
    let y_pred = array![1.0, 0.0, 1.0, 1.0, 0.0];

    println!("accuracy: {:.3}", accuracy(&y_true, &y_pred));

    let cm = ConfusionMatrix::new(&y_true, &y_pred);
    println!("f1 score: {:.3}", cm.f1_score());
}
```

## 1.2.6. show_progress

`show_progress` is orthogonal to the module flags: it adds no types and unlocks no module. What it does is compile in the `indicatif`-backed progress bars that are otherwise stripped out at build time. With it enabled, `Sequential::fit` renders a per-epoch bar showing elapsed time, position, and the running loss, using an `[{elapsed_precise}] {bar:40} {pos}/{len} | Loss: {msg}` template, and finishes with a "Training completed" message. The mini-batch loop (`fit_with_batches`) reports the running average loss per epoch, and every classical estimator with an iterative fit — from `LinearRegression`'s gradient descent and `LogisticRegression`'s loss loop to `DecisionTree`'s node-by-node growth, `KMeans`, `SVC`, and the rest — lights up its own bar the same way. Without the flag, every one of those `#[cfg(feature = "show_progress")]` blocks vanishes, so the training loop pays nothing for a feature it is not using.

Enable it alongside whatever modules you already have:

```toml
rustyml = { version = "0.13", features = ["full", "show_progress"] }
```

Leave it off for library code, CI, and anything writing to a non-TTY log — a progress bar streamed into a log file is just noise. Turn it on for interactive work where watching the loss curve tick down is worth the terminal real estate. Because it is compile-time gated, there is no runtime cost either way; the choice is made when you build.

## 1.2.7. MSRV and edition

RustyML is edition 2024 and sets `rust-version = "1.89.0"`, so its minimum supported Rust version is 1.89. Cargo enforces this by default: on an older toolchain the resolver refuses the crate with a clear "requires rustc 1.89.0" message rather than failing deep in a macro expansion. If you are behind, `rustup update stable` is the fix. There are no system libraries, no BLAS, and no C or C++ toolchain to install — a working stable Rust 1.89+ is the entire prerequisite.

## 1.2.8. Diagnosing a feature that is off

The most common stumble with a feature-split crate is calling into a module you did not switch on. Because the module is `#[cfg(feature = "...")]`, it does not exist in your build at all, and the failure is a compile-time unresolved import — never a runtime surprise. Say you depend on RustyML with only `neural_network` enabled and then reach for a classical estimator:

```rust,ignore
use rustyml::machine_learning::LinearRegression; // machine_learning feature is OFF
```

The compiler stops with `error[E0432]: unresolved import` and the note "could not find `machine_learning` in `rustyml`". The type is not misspelled and the crate is not broken — the module was compiled out. The pattern to recognize: an unresolved import whose *first* missing path segment is one of the module names (`machine_learning`, `neural_network`, `utils`, `metrics`, `math`) almost always means the matching feature is disabled. The prelude has a quieter variant of the same failure — with `use rustyml::prelude::*` and `metrics` off, the metric functions are simply absent, and you get `error[E0425]: cannot find function \`accuracy\` in this scope` instead. Same root cause, so check your feature list first.

The fix is always to add the feature. If you had `default-features = false`, add the name to the `features` array; if you were on the default bundle and reached for `utils` or `metrics`, remember those are only in `full` (or named individually), not in `default`:

```toml
rustyml = { version = "0.13", features = ["neural_network", "machine_learning"] }
```

Two habits keep you out of this hole. When reading the API on [docs.rs/rustyml](https://docs.rs/rustyml), note the small feature badges beside gated items — docs.rs builds with all features on, so every item is documented, and the badge tells you which flag it costs. And when in doubt during development, build with `--features full` to make everything resolve, then trim back to the minimal set once the code compiles; [7.4 Minimal Builds and Modular Integration](../Chapter-07/7.4._Minimal_Builds_and_Modular_Integration.md) walks through that trimming discipline for a production binary.
