# 1.1. What is RustyML

RustyML is a machine learning and deep learning library written entirely in Rust. It covers the full workflow that a data-science project needs — data preprocessing, feature engineering, model training, and evaluation — for both classical estimators (linear models, trees, SVMs, clustering, dimensionality reduction, anomaly detection) and a Keras-style neural-network framework. This page is about what the library *is* and the deliberate choices behind it, so you know what you are buying into before the rest of the guide walks you through the APIs.

The version this guide documents is `0.13`. It is pre-1.0: the API is stabilizing but breaking changes can still land in minor releases, so pin a version in `Cargo.toml` rather than tracking `*` in production. The canonical API reference lives at [docs.rs/rustyml](https://docs.rs/rustyml) and the source at [github.com/SomeB1oody/RustyML](https://github.com/SomeB1oody/RustyML).

## 1.1.1. Pure Rust, end to end

The defining constraint of the project is that there is no C or C++ in the runtime path — no BLAS to link, no LAPACK, no CUDA, no Python interpreter embedded behind an FFI boundary. This is the opposite of how the mainstream Python stack is built: NumPy and scikit-learn wrap compiled C and Fortran, and PyTorch/TensorFlow wrap large C++/CUDA runtimes. Those libraries are excellent, but the FFI seam is where a lot of operational pain lives — version-matched shared libraries, ABI mismatches, `manylinux` wheel roulette, and memory-safety bugs that live below the language you actually write in.

RustyML pushes everything into safe Rust instead. The dense linear algebra the estimators need — symmetric eigendecomposition, SVD, thin QR, and the iterative top-`k` eigensolvers behind PCA and Kernel PCA — is hand-written in an internal `linalg` module rather than pulled from an external algebra crate. (`nalgebra` appears in the repository, but only as a *dev-dependency* used to cross-check those hand-rolled factorizations against a reference implementation in the test suite; it is not part of what you ship.) The heavy matrix products route through [`gemmkit`](https://crates.io/crates/gemmkit), a pure-Rust GEMM engine that dispatches at run time to the widest SIMD the CPU actually offers (AVX-512F, AVX2+FMA, NEON, wasm `simd128`, over a scalar floor) and decides on its own whether a given product is worth threading and across how many workers. The result is that every fallible operation is checked Rust code you can read, step through, and reason about, with the memory-safety guarantees of the language holding all the way down to the arithmetic kernels.

The dependency surface is small and, like the rest of the crate, pure Rust: [`ndarray`](https://docs.rs/ndarray/) for tensors, [`rayon`](https://docs.rs/rayon/) for data parallelism, `gemmkit` plus its zero-copy `gemmkit-ndarray` adapter for matrix multiplication, [`serde`](https://serde.rs/) + [`postcard`](https://docs.rs/postcard/) for compact binary model persistence, `ahash` for fast hashing, `thiserror` for the error type, `ndarray-rand` for random initialization, and `indicatif` for optional progress bars.

## 1.1.2. Parallelism and zero-cost abstractions

RustyML parallelizes its heavy kernels with Rayon, but it does not blindly spawn work. Small problems run serially — thread hand-off costs more than the arithmetic saves below a certain size — and each kernel class has a calibrated size threshold that selects the parallel path only once it pays off. Those thresholds are not baked in as constants: the crate exposes a `tuning` facade that lets you override the gates at runtime without a recompile, which matters when you deploy the same binary to machines with very different core counts. [Performance Tuning and Parallelism](../Chapter-07/7.3._Performance_Tuning_and_Parallelism.md) covers how to measure and adjust these.

Two consequences of the pure-Rust design are worth stating plainly, because they are exactly the properties that bite people on other stacks. First, the parallel reductions are *deterministic*: the blocked fold sums in a fixed order regardless of how many threads run it, so a result does not drift as you scale cores. Second, performance is predictable — there is no garbage collector introducing pauses, no JIT warmup, and no global interpreter lock serializing your threads. Combined with a global seed for every randomized component (see [Reproducibility and Random Seeds](../Chapter-07/7.1._Reproducibility_and_Random_Seeds.md)), a run is repeatable across machines.

The "zero-cost abstractions" claim is concrete here, not marketing. The shared estimator traits — `Fit`, `Predict`, `Transform`, `FitTransform` — are generic over the ndarray storage type and monomorphized at compile time, so writing code generic over "any estimator" costs nothing at runtime versus calling a specific model. Every model also exposes the same operations as plain inherent methods (`model.fit(..)`, `model.predict(..)`); the trait implementations just forward to them, and Rust's method resolution keeps the inherent method first. You reach for the traits only when you genuinely want to be generic.

## 1.1.3. The module map

The crate is organized into five modules, each behind a Cargo feature flag, plus a shared `prelude`. You compile only what you use. `machine_learning`, `neural_network`, `utils`, and `metrics` each pull in `math` automatically, since they all build on the same numeric primitives.

| Feature / module | What lives in it |
|---|---|
| `machine_learning` | Classical estimators: `LinearRegression`, `LogisticRegression`, `KNN`, `DecisionTree` (ID3 / C4.5 / CART), `SVC` (kernel SMO), `LinearSVC`, `LDA`, `KMeans`, `DBSCAN`, `MeanShift`, `PCA`, `KernelPCA`, `TSNE`, `IsolationForest`, and the shared `Fit`/`Predict`/`Transform`/`FitTransform` traits |
| `neural_network` | A Sequential model plus layers (`Dense`, convolution, pooling, recurrent, dropout, normalization), activations, optimizers (`SGD`, `Adam`, `AdamW`, `RMSprop`, `AdaGrad`), and losses |
| `utils` | Preprocessing (`standardize`, `normalize`, the `StandardScaler` / `MinMaxScaler` / `MaxAbsScaler` / `RobustScaler` / `Normalizer` family, `to_categorical` and friends) and dataset splitting (`train_test_split`, `train_test_split_stratified`) |
| `metrics` | Evaluation metrics for regression, classification (`ConfusionMatrix`, ROC AUC, log loss, ...), and clustering (ARI, silhouette, ...) |
| `math` | Stateless numeric primitives: `gemmkit`-backed matrix products, deterministic parallel reductions, pairwise distances, and the `DistanceCalculationMetric` dispatcher |

Two composite features cover the common cases: `default` turns on `machine_learning` + `neural_network`, and `full` turns on everything. A separate `show_progress` feature adds training progress bars. The full breakdown, including which errors and types each feature unlocks, is in [Installation and Feature Flags](./1.2._Installation_and_Feature_Flags.md).

`math` is the foundation the other modules stand on, and it is genuinely usable on its own — if all you want are fast, deterministic parallel reductions and matrix products, depend on `math` alone. It is also the honest dividing line in the crate's error strategy: `math` and `metrics` are leaf modules that panic on precondition violations (mismatched lengths, empty input) rather than returning `Result`, which keeps them dependency-light. Everywhere else, fallible calls return a `Result`. The `prelude` re-exports the most-used items from each enabled module, split by domain so you can pull in exactly one area; [The Prelude and Imports](./1.5._The_Prelude_and_Imports.md) is the reference for what each one brings into scope.

## 1.1.4. Coming from scikit-learn and Keras

The API is deliberately familiar. Classical estimators follow scikit-learn's `fit` / `predict` shape, and the neural-network side mirrors Keras's `Sequential` → `add` → `compile` → `fit` → `predict` flow. If you have written either, the muscle memory transfers; what changes is that you are in Rust, so data is `ndarray` arrays instead of NumPy, and fallible calls return `Result` instead of raising exceptions.

A classical model, end to end. Note the constructor returns a `Result` (it validates hyperparameters up front), and so do `fit` and `predict`:

```rust
use rustyml::prelude::machine_learning::*;
use ndarray::array;

fn main() {
    // fit_intercept, learning_rate, max_iterations, tolerance
    let mut model = LinearRegression::new(true);

    let x = array![[1.0, 2.0], [2.0, 3.0], [3.0, 4.0]];
    let y = array![6.0, 9.0, 12.0];

    model.fit(&x, &y).unwrap();
    let predictions = model.predict(&x).unwrap();
    println!("predictions: {:?}", predictions);
}
```

A neural network in the same style. `Sequential::new()`, stack layers with `add`, `compile` with an optimizer and loss, then `fit`. Every tensor here is `f32`; keep the epoch count small so the example runs fast:

```rust
use rustyml::neural_network::sequential::Sequential;
use rustyml::prelude::neural_network::*;
use ndarray::Array;

fn main() {
    // 4 samples, 8 input features, 1 output
    let x = Array::ones((4, 8)).into_dyn();
    let y = Array::ones((4, 1)).into_dyn();

    let mut model = Sequential::new();
    model
        .add(Dense::new(8, 16, Activation::ReLU).unwrap())
        .add(Dense::new(16, 1, Activation::Linear).unwrap())
        .compile(
            Adam::new(0.001, 0.9, 0.999, 1e-8, 0.0).unwrap(),
            MeanSquaredError::new(),
        );

    model.summary(); // prints the architecture, like Keras
    model.fit(&x, &y, 5).unwrap();

    let predictions = model.predict(&x).unwrap();
    println!("prediction shape: {:?}", predictions.shape());
}
```

Evaluation follows the same convention scikit-learn uses — every metric takes `(y_true, y_pred)` in that order:

```rust
use rustyml::metrics::*;
use ndarray::array;

fn main() {
    let y_true = array![1.0, 0.0, 0.0, 1.0, 1.0];
    let y_pred = array![1.0, 0.0, 1.0, 1.0, 0.0];

    let cm = ConfusionMatrix::new(&y_true.view(), &y_pred.view());
    println!("accuracy: {:.3}", cm.accuracy());
    println!("f1 score: {:.3}", cm.f1_score());
}
```

The differences from Python are the ones you would expect from a typed, checked language, and they are features rather than friction. Errors are values: a fallible call hands back a structured `Error` you can `match` on instead of a stack trace, so "this model was never fitted" and "these two shapes disagree" are distinct, catchable outcomes — see [Error Handling](./1.6._Error_Handling.md). Hyperparameters are validated where they are supplied, so an illegal learning rate is rejected on the spot rather than silently producing `NaN` twenty iterations into training. Configuration uses a builder pattern: an estimator takes its essentials in `new` and layers optional settings through chained `with_*` methods, each validating what it receives (for example `LinearRegression::new(true).with_regularization(..)?`). And you work in `ndarray` throughout; if that is new to you, [Working with ndarray](./1.3._Working_with_ndarray.md) is the on-ramp, and [Your First End-to-End Model](./1.4._Your_First_End_to_End_Model.md) builds a complete project.

## 1.1.5. What pure Rust buys you at deploy time

The payoff for the constraint in 1.1.1 shows up when you ship. A RustyML program compiles to a single self-contained binary. There is no Python runtime to install, no virtualenv to reproduce, no system BLAS whose version has to match, no `LD_LIBRARY_PATH` to get right on the target host. You cross-compile for the architecture you are deploying to and copy one file. For containers this collapses the image to a static binary on a minimal base; for edge or embedded targets it removes the interpreter entirely.

Persistence is built for the same story. Trained classical models and neural-network weights serialize to compact binary through Serde and postcard via `save_to_path` / `load_from_path`, so the artifact you deploy is a small blob loaded by the same pure-Rust code that produced it — no format bridge, no framework runtime on the far side. [Model Persistence in Depth](../Chapter-07/7.2._Model_Persistence_in_Depth.md) covers the format and its compatibility rules. And because there is no GC and no interpreter, latency is predictable: no warmup, no pause-the-world, no GIL contention when you fan work across threads.

## 1.1.6. Honest scope notes

RustyML is CPU-only. There is no GPU or CUDA backend, and none is planned as part of the pure-Rust design; parallelism comes from Rayon across CPU cores. For large convolutional networks this is a real ceiling — the neural-network framework is well-suited to small-to-medium models, teaching, embedded inference, and classical-ML-adjacent deep learning, not to training large vision or language models where you would want a GPU stack.

Numeric precision is fixed per domain, and the split is intentional. The classical `machine_learning` and `utils` estimators operate on `f64` feature matrices — the default `ndarray::array!` literals you write are already `f64`, so this is usually invisible. The neural-network stack operates on `f32`: its tensor type is `Tensor = ArrayD<f32>`, chosen because `f32` halves memory traffic and is standard for deep learning. The practical implication is that you cannot hand an `f64` array straight to a layer; convert to `f32` at the boundary. (Label types are the exception to the `f64` rule on the classical side — `KNN` is generic over its label type and `LDA` takes `i32` labels.)

The neural-network framework does not build a dynamic autodiff graph the way PyTorch does. Each layer implements its own forward and backward pass, and `Sequential` chains them; this keeps the runtime lean and predictable but means you compose from the provided layer set rather than differentiating arbitrary expressions. Finally, everything runs on a single machine — there is no distributed training — and, as noted at the top, the pre-1.0 API may still shift between minor versions.
