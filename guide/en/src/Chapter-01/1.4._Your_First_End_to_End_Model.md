# 1.4. Your First End-to-End Model

This is the page where the pieces from [1.3. Working with ndarray](./1.3._Working_with_ndarray.md) turn into a working classifier. We build a tiny 2-class dataset in code, split it, standardize it, fit a `LogisticRegression`, score it with accuracy and a confusion matrix, and finally serialize the trained model to disk and read it back. Every call below was compiled against RustyML 0.13 with the `full` and `show_progress` features, so the signatures are exactly what you will type.

One expectation to reset before you start: RustyML has no `Pipeline` object. If you are coming from scikit-learn, that absence is the thing to internalize here. You get sharp, standalone pieces — functions (`train_test_split`, `standardize`, `accuracy`), a `StandardScaler` that carries its training statistics, and model structs that own their own `fit`/`predict`/`save_to_path` — but nothing chains them for you. Wiring them together is your job, which means the leakage boundary between train and test is also your job: the scaler will faithfully reapply whatever statistics you fitted it on, including ones you should never have fitted on test rows. That is the recurring theme of this walkthrough.

## 1.4.1. The complete program

Here is the whole thing in one file. Read it once top to bottom, then the sections that follow dissect each step and explain what breaks if you skip it.

```rust
use ndarray::{Array1, Array2};
use rustyml::machine_learning::LogisticRegression;
use rustyml::metrics::{ConfusionMatrix, accuracy};
use rustyml::set_global_seed;
use rustyml::utils::StandardScaler;
use rustyml::utils::train_test_split::train_test_split;

fn main() {
    // (1) Pin every seeded component on this thread up front.
    set_global_seed(42);

    // (2) Build a synthetic 2-class dataset. Two blobs, and feature 2 lives on a
    // ~100x larger scale than feature 1 on purpose, so standardization matters.
    let n_per_class = 30usize;
    let mut rows: Vec<f64> = Vec::with_capacity(2 * n_per_class * 2);
    let mut labels: Vec<f64> = Vec::with_capacity(2 * n_per_class);
    for i in 0..n_per_class {
        let a = (i % 6) as f64;
        let b = (i / 6) as f64;
        // class 0: centered near -0.6; class 1 near +0.6 with the spreads overlapping.
        rows.push(-0.6 + 0.3 * a);
        rows.push((-0.6 + 0.3 * b) * 100.0);
        labels.push(0.0);
        rows.push(0.6 + 0.3 * a);
        rows.push((0.6 + 0.3 * b) * 100.0);
        labels.push(1.0);
    }
    let n = labels.len();
    let x: Array2<f64> = Array2::from_shape_vec((n, 2), rows).unwrap();
    let y: Array1<f64> = Array1::from(labels);

    // (3) Split. x and y are consumed by value.
    let (x_train, x_test, y_train, y_test) =
        train_test_split(x, y, Some(0.25), Some(42)).unwrap();

    // (4) Standardize: fit the statistics on TRAIN ONLY, then apply them to both splits.
    let mut scaler = StandardScaler::new();
    let x_train_std = scaler.fit_transform(&x_train).unwrap();
    let x_test_std = scaler.transform(&x_test).unwrap();

    // (5) Train.
    let mut model = LogisticRegression::new(true, 0.5, 1000, 1e-6).unwrap();
    model.fit(&x_train_std, &y_train).unwrap();

    // (6) Predict on the held-out test split.
    let preds: Array1<f64> = model.predict(&x_test_std).unwrap();

    // (7) Evaluate.
    let acc = accuracy(&y_test, &preds);
    let cm = ConfusionMatrix::new(&y_test, &preds);
    let (tp, fp, tn, fn_) = cm.get_counts();
    println!("test accuracy = {:.3}", acc);
    println!("TP={tp} FP={fp} TN={tn} FN={fn_}");
    println!("{}", cm.summary());
    println!("iterations run: {:?}", model.get_actual_iterations());

    // (8) Persist and reload.
    let path = "logreg_model.bin";
    model.save_to_path(path).unwrap();
    let loaded = LogisticRegression::load_from_path(path).unwrap();
    let preds_loaded = loaded.predict(&x_test_std).unwrap();
    assert_eq!(preds, preds_loaded);
    std::fs::remove_file(path).unwrap();
    println!("round-trip predictions identical: {}", preds == preds_loaded);
}
```

The `println!` calls produce a small report; the exact counts depend on which rows land in the test split, so treat the shape below as the layout, not the numbers:

```text
test accuracy = 0.XXX
TP=.. FP=.. TN=.. FN=..
Confusion Matrix:
+-----------------+--------------------+--------------------+
|                 | Predicted Positive | Predicted Negative |
+-----------------+--------------------+--------------------+
| Actual Positive | TP: ..             | FN: ..             |
| Actual Negative | FP: ..             | TN: ..             |
+-----------------+--------------------+--------------------+
... derived metrics ...
iterations run: Some(..)
round-trip predictions identical: true
```

## 1.4.2. Seeding for reproducibility

`rustyml::set_global_seed(42)` is re-exported from the crate root and takes a single `u64`. It sets a thread-local seed that every unseeded (`random_state == None`) component constructed on the same thread will then derive its RNG from. This is the Keras-style global-seed model, and it is covered in full in [7.1. Reproducibility and Random Seeds](../Chapter-07/7.1._Reproducibility_and_Random_Seeds.md).

Be honest with yourself about what it actually does in *this* pipeline: nothing to the numbers. `LogisticRegression::fit` is plain full-batch gradient descent with zero randomness — two fits on identical data produce bit-identical weights — and `standardize` is deterministic too. The only stochastic step is the shuffle inside `train_test_split`, and I pass it an explicit `Some(42)`, which per the seed-resolution rules **ignores the global seed entirely** and uses the local one. So `set_global_seed` here is a habit, not a lever. The moment you swap in a component that you leave unseeded and that genuinely draws randomness — `KMeans`, `SVC`, a neural-network weight initializer — the global seed becomes the one thing standing between you and unreproducible results. Set it at the top of every experiment so that when you add such a component later, you do not have to remember to.

If you prefer the global seed to be load-bearing even for the split, pass `None` as the `random_state` and let `set_global_seed` drive it. I use the explicit `Some(42)` because it keeps the split reproducible on its own, independent of call order, which is the safer default when you are copying one line into a different program.

## 1.4.3. The dataset and the label contract

The features are an `Array2<f64>` of shape `(n_samples, n_features)`; the labels are an `Array1<f64>`. The label element type is not incidental. `LogisticRegression::fit` requires `y` to be an `f64` array whose values are **exactly** `0.0` or `1.0` — anything else (`0.5`, `2.0`, even the `-1.0`/`+1.0` convention some SVM texts use) returns `Error::InvalidInput`. There is no `LabelEncoder` step folded into `fit`; if your labels are strings or arbitrary integers you convert them yourself first (see [4.3. Label Encoding](../Chapter-04/4.3._Label_Encoding.md)).

I deliberately put feature 2 on a scale about 100x larger than feature 1. That is not cosmetic — it is the reason the standardization step exists, and it sets up the failure mode described next.

## 1.4.4. Splitting the data

```rust,ignore
let (x_train, x_test, y_train, y_test) =
    train_test_split(x, y, Some(0.25), Some(42)).unwrap();
```

The signature is `train_test_split(x: Array2<f64>, y: Array1<A>, test_size: Option<f64>, random_state: Option<u64>) -> Result<TrainTestSplit<A>, Error>`, where `TrainTestSplit<A>` is the tuple `(x_train, x_test, y_train, y_test)` in exactly that order. Two things bite newcomers. First, `x` and `y` are taken **by value** — the function consumes them. If you need the originals afterward, clone before calling. Second, both configuration arguments are `Option`: `None` for `test_size` means `0.3` (a 70/30 split), and `None` for `random_state` means seed-from-entropy (or from the global seed, if one is set).

The error arms are worth knowing before they surprise you: an empty dataset is `Error::EmptyInput`, mismatched `x`/`y` lengths are `Error::DimensionMismatch`, a `test_size` outside the open interval `(0, 1)` is `Error::InvalidParameter`, and a dataset too small to split (a single sample) is `Error::InvalidInput`. The function also clamps: it always keeps at least one row on each side, so `test_size = 0.99` on ten rows still leaves one training row rather than zero.

If you skip the split and evaluate on the same rows you trained on, your accuracy number measures memorization, not generalization — the whole point of holding out `x_test` is to score the model on data it never saw. For classification specifically, a plain random split can, on imbalanced data, drop a class entirely from one side. The fix is `train_test_split_stratified`, which splits each class independently. It carries one real constraint, though: its labels must be `Clone + Eq + Hash`, and `f64` is neither `Eq` nor `Hash`. So you cannot stratify on the `f64` labels that `fit` wants — you stratify on integer (or string) labels and convert to `f64` afterward:

```rust,ignore
use rustyml::utils::train_test_split::train_test_split_stratified;

// integer labels satisfy Eq + Hash; convert to f64 only when you hand them to `fit`
let (x_train, x_test, y_train_i, y_test_i) =
    train_test_split_stratified(x, y_int, Some(0.25), Some(42)).unwrap();
let y_train: Array1<f64> = y_train_i.mapv(|v| v as f64);
```

The split mechanics and the stratified variant are covered in depth in [4.1. Train-Test Split](../Chapter-04/4.1._Train_Test_Split.md).

## 1.4.5. Standardizing without leaking test information

Logistic regression is fit by gradient descent, and gradient descent cares about feature scale. With feature 2 a hundred times larger than feature 1, the gradient is dominated by feature 2, the loss surface is badly conditioned, and convergence is slow and lopsided. Standardizing each feature to zero mean and unit variance fixes the conditioning and lets a single learning rate work for every column. This is why the step earns its place; it is not decoration.

There are two ways to do it, and picking the wrong one is what trips people. The free function `standardize(data, axis)` is a **stateless, one-shot transform**: it computes the mean and standard deviation from *the array you pass it* and returns a new standardized array, keeping nothing. `StandardScaler` is the stateful form: `fit` learns the statistics and stores them, `transform` reapplies exactly those numbers to any array you hand it later.

That difference decides this step. The tempting move with the free function is to call `standardize` on `x_train` and again on `x_test` — but the second call standardizes the test set by the *test set's own* statistics, so train and test end up on two different scales, and the model, trained on train-scaled inputs, is scored on differently-scaled ones. Worse is standardizing the full matrix *before* splitting, which folds the test set's mean and variance into the numbers the model trains on: textbook leakage that inflates your reported accuracy.

The scaler makes the correct pattern the short one — fit once on train, transform everything:

```rust,ignore
use rustyml::utils::StandardScaler;

let mut scaler = StandardScaler::new();
let x_train_std = scaler.fit_transform(&x_train).unwrap(); // learns mean/std HERE, from train
let x_test_std = scaler.transform(&x_test).unwrap();       // SAME numbers applied to test
```

Read that as a rule about which method sees which data: `fit`/`fit_transform` may only ever touch training rows, and `transform` is what everything else goes through. The statistics are inspectable (`scaler.get_mean()`, `get_scale()`) and the scaler is `save_to_path`-able, which matters more than it looks: a saved model without its saved scaler is unusable, because nothing else records what its inputs were divided by.

The divisor is the population standard deviation (`ddof = 0`, matching scikit-learn's `StandardScaler`), and a constant column — where a naive `x / std` would produce `NaN` — gets a scale of `1.0` and maps to zeros instead. The free function is still the right call when there is no second batch to stay consistent with, or when you need the `Row`/`Global` axes the scaler does not cover:

```rust
use ndarray::array;
use rustyml::utils::standardize::{standardize, StandardizationAxis};

fn main() {
    // One-shot: uses this exact array's own column mean/std, nothing persisted.
    let x = array![[1.0, 200.0], [3.0, 400.0], [5.0, 600.0]];
    let z = standardize(&x, StandardizationAxis::Column).unwrap();
    println!("standardized shape: {:?}", z.dim());
    println!("{:?}", z);
}
```

The fuller story — both forms side by side, the `Row`/`Column`/`Global` axes, `partial_fit`, and the normalization alternatives — is in [4.2. Standardization and Normalization](../Chapter-04/4.2._Standardization_and_Normalization.md).

## 1.4.6. Training the model

```rust,ignore
let mut model = LogisticRegression::new(true, 0.5, 1000, 1e-6).unwrap();
model.fit(&x_train_std, &y_train).unwrap();
```

`LogisticRegression::new(fit_intercept, learning_rate, max_iterations, tolerance)` returns `Result<Self, Error>` because it validates its hyperparameters up front: a non-positive or non-finite learning rate, a zero `max_iterations`, or a non-positive tolerance each come back as `Error::InvalidParameter` rather than blowing up mid-training. `LogisticRegression::default()` gives you `fit_intercept = true`, `learning_rate = 0.01`, `max_iter = 100`, `tol = 1e-4`; I override to a larger rate and iteration budget because standardized features tolerate a bigger step and I want a well-fit model. Regularization is off by default; add it with `.with_regularization(RegularizationType::L2(alpha))`, which is also fallible (a negative or non-finite `alpha` is rejected). If you are porting a penalty strength over from Python, note that RustyML measures an undivided penalty against a *mean* data term — exactly scikit-learn's `SGDClassifier`/`SGDRegressor` objective — so `alpha` transfers 1:1 from those, while a `LogisticRegression(C=c)` becomes `alpha = 1 / (c * n)` for `n` training samples. `RegularizationType`'s own documentation carries the full conversion table.

`fit(&x, &y) -> Result<&mut Self, Error>` takes both arrays by reference (it does not consume them, unlike the split). Beyond the `0.0`/`1.0` label check, it guards against empty input (`Error::EmptyInput`), `x`/`y` length mismatch (`Error::DimensionMismatch`), and non-finite feature values (`Error::NonFinite`); it also trips `Error::NonFinite` mid-loop if the weights or loss overflow, which is exactly what an un-standardized large-scale feature paired with a too-large learning rate will do. Training stops when the loss change between iterations drops below `tol`, or when it exhausts `max_iter`, whichever comes first. `model.get_actual_iterations()` returns `Option<usize>` — reading it back tells you which of the two happened. If it equals your `max_iter`, the model hit the ceiling rather than converging, and you should raise `max_iter` or revisit the learning rate. Because there is no randomness in the optimizer, none of this depends on the seed. The model's own chapter, [2.2. Logistic Regression](../Chapter-02/2.2._Logistic_Regression.md), covers regularization, the intercept term, and polynomial feature expansion.

## 1.4.7. Predicting

```rust,ignore
let preds: Array1<f64> = model.predict(&x_test_std).unwrap();
```

`predict` returns `Result<Array1<f64>, Error>`: hard class labels `0.0` or `1.0`, obtained by thresholding the sigmoid probability at `0.5`. The element type matches what you trained on, which is the point — the labels go straight into the metrics in the next step, and straight back into `fit` if you want to, with no conversion in between. If you need the underlying probabilities instead of hard labels — for a custom threshold, or for ROC/PR analysis — call `predict_proba`, which returns `Result<Array1<f64>, Error>` in the open interval `(0, 1)`. The two differ only by that `>= 0.5` cutoff.

`predict` fails loudly in the two ways you would expect: calling it before `fit` is `Error::NotFitted`, and passing a feature count different from what the model was trained on is `Error::DimensionMismatch`. The second is why the leakage discipline from the previous section is not just statistical hygiene — feeding `predict` the *raw* `x_test` while the model was trained on standardized inputs would not error (the shape still matches), it would just quietly return worse predictions. The types cannot catch a scale mismatch; only your pipeline discipline can.

## 1.4.8. Accuracy and the confusion matrix

```rust,ignore
let acc = accuracy(&y_test, &preds);
let cm = ConfusionMatrix::new(&y_test, &preds);
let (tp, fp, tn, fn_) = cm.get_counts();
println!("{}", cm.summary());
```

`accuracy(y_true, y_pred) -> f64` is the fraction of matching labels; it compares within `f64::EPSILON`, so it works on integer-valued labels stored as `f64`, and it is symmetric in its arguments. A single number, though, hides *how* the model is wrong. `ConfusionMatrix::new(y_true, y_pred)` builds the 2x2 breakdown, and `get_counts()` returns the counts as `(tp, fp, tn, fn)` in that fixed order. It takes **hard** labels only: every element of both arrays must be exactly `0.0` or `1.0`, and anything else panics. It does not threshold at `0.5` — handing it `predict_proba` output is a panic, not a quiet binarization, which is deliberate, because a silent threshold is how a probability column ends up scored as if it were a decision. `predict`'s output goes straight in, as here. For a different label pair — the `-1.0`/`+1.0` a margin classifier emits, say — use `ConfusionMatrix::new_with_labels(y_true, y_pred, negative_label, positive_label)`, the binary counterpart of scikit-learn's `confusion_matrix(..., labels=[neg, pos])`. Both arguments carry independent storage types, so an owned `Array1` and an `ArrayView1` mix freely without a `.to_owned()`. From the struct you can read `accuracy()`, `precision()`, `recall()`, `specificity()`, `f1_score()`, `balanced_accuracy()`, and `mcc()`, or print `summary()` for the formatted table shown earlier. On imbalanced data, reach for `balanced_accuracy()` or `mcc()` rather than raw accuracy — a classifier that always predicts the majority class can post a high accuracy while being useless, and the confusion matrix makes that failure visible at a glance.

One sharp edge distinguishes the metrics from everything above: they **panic** rather than return `Result`. `accuracy` and `ConfusionMatrix::new` panic on a length mismatch or empty input, and `ConfusionMatrix::new` panics on a label outside `{0.0, 1.0}`. That is fine here because `y_test` and `preds` are the same length by construction and both hold hard labels, but it means you validate lengths — and, for the confusion matrix, the label domain — yourself before calling them on untrusted data. The full classification-metrics surface — the multi-class confusion matrix, ROC AUC, average precision, log loss, Cohen's kappa — lives in [5.2. Classification Metrics](../Chapter-05/5.2._Classification_Metrics.md).

## 1.4.9. Saving and loading the model

```rust,ignore
model.save_to_path("logreg_model.bin").unwrap();
let loaded = LogisticRegression::load_from_path("logreg_model.bin").unwrap();
```

`save_to_path(&self, path: &str) -> Result<(), Error>` serializes the entire model — weights, intercept flag, learning rate, iteration count, regularization setting — to a compact binary blob using [postcard](https://docs.rs/postcard). `load_from_path(path: &str) -> Result<Self, Error>` reads it back. The format is binary regardless of the file extension; I use `.bin` to say so honestly (the integration tests happen to use a `.json` name, but the bytes are postcard either way — the extension is cosmetic). Failures surface as `Error::Io`, wrapping either a filesystem error or a deserialization error if the file is truncated or was written by an incompatible build.

The round-trip is exact: because logistic regression's `predict` is deterministic and the weights are serialized verbatim, `loaded.predict(...)` produces predictions identical to the original, which is why the `assert_eq!` in the program holds. Delete the file afterward with `std::fs::remove_file` when it is a throwaway, as here. This same `save_to_path`/`load_from_path` pair is generated for every model in the crate, so once you know it for `LogisticRegression` you know it for `KMeans`, `SVC`, and the rest. Neural networks persist their weights through a parallel mechanism covered in [3.9. Saving and Loading Weights](../Chapter-03/3.9._Saving_and_Loading_Weights.md), and the versioning and compatibility details are in [7.2. Model Persistence in Depth](../Chapter-07/7.2._Model_Persistence_in_Depth.md).
