# 1.6. Error Handling

RustyML has exactly one error type. Every fallible operation in the crate — fitting a model, predicting, transforming, saving, loading, building a layer, validating a hyperparameter — returns `Result<T, rustyml::error::Error>`. There is no per-module `LinearRegressionError`, no `Box<dyn Error>` leaking out of the public API, and — outside the `metrics` and `math` leaf modules, which panic by contract on precondition violations — no `panic!` on bad user input. If you come from scikit-learn (which raises `NotFittedError`, `ValueError`, `ConvergenceWarning`, and friends as distinct Python exception types) or from a Rust project that reaches for `anyhow` at the first sign of trouble, the design here is deliberately narrower: a single `#[non_exhaustive]` enum with a handful of well-named variants, plus small domain enums nested inside it for the parts of the crate that need their own vocabulary. That narrowness is what lets you write one `match` that handles anything the crate can throw at you, without importing a dozen error types.

## 1.6.1. One error type, one result alias

The type lives in `rustyml::error`, alongside its result alias:

```rust,ignore
pub type RustymlResult<T> = std::result::Result<T, Error>;
```

`Error` is a `thiserror`-derived enum, so it implements `std::error::Error` and `Display` for free, and each variant carries a fixed message format. It is **not** in the prelude — `use rustyml::prelude::*` gives you the estimators, layers, and metrics, but you import the error machinery separately with `use rustyml::error::Error;` (and `RustymlResult`, `Context`, or `IoError` when you need them). Keeping it out of the prelude is intentional: most call sites `.unwrap()` in examples and `?` in real code, and neither needs the type named.

Here are the top-level variants you will actually match on, with what triggers each and the exact `Display` text the message renders to:

| Variant | Trigger | `Display` message (`{}` / `to_string()`) |
|---|---|---|
| `EmptyInput(String)` | An array/vector/dataset was empty where data was required | `input is empty: <what>` |
| `DimensionMismatch { expected, found }` | Two scalar counts disagreed (feature count at predict vs. fit, `len(x)` vs. `len(y)`) | `dimension mismatch: expected <e>, found <f>` |
| `ShapeMismatch { expected, found }` | Two whole tensor shapes disagreed (a gradient vs. the activation it flows into) | `shape mismatch: expected [..], found [..]` |
| `NonFinite(String)` | A value in the data or produced by a computation was `NaN`/`inf` | `non-finite value (NaN or infinity) encountered in <where>` |
| `InvalidParameter { name, reason }` | A user-supplied hyperparameter was out of range | ``invalid parameter `<name>`: <reason>`` |
| `InvalidInput(String)` | A validation failure with no more specific variant (bad rank, too few samples) | `invalid input: <msg>` |
| `NotFitted(&'static str)` | A method needing a trained model was called before `fit` | ``model `<name>` has not been fitted; call `fit` before this operation`` |
| `NotConverged(String)` | An iterative algorithm never met its convergence criterion | `failed to converge: <msg>` |
| `Computation { context, source }` | A numerical breakdown, a violated invariant, or a wrapped foreign error | `computation failed: <context>` |
| `NeuralNetwork(NnError)` | A neural-network-specific failure (see §1.6.2) | forwarded transparently from `NnError` |
| `Tree(TreeError)` | A decision-tree-specific failure (see §1.6.2) | forwarded transparently from `TreeError` |
| `Io(IoError)` | A filesystem or (de)serialization failure (see §1.6.2) | forwarded transparently from `IoError` |

Two conventions in that table repay attention because they are the ones people get wrong. First, a non-finite **hyperparameter** you passed in is an `InvalidParameter` (the `reason` mentions finiteness), whereas a non-finite value that shows up in your **data** or falls out of a **computation** is a `NonFinite`. Second, `DimensionMismatch` compares scalar counts — number of features, length of a vector — while `ShapeMismatch` is for whole-tensor shape disagreements and shows up mostly in the neural-network code. When you are debugging a "these two things should have been the same size" error, which variant you got tells you whether the crate was comparing a count or a shape.

`Error` is `#[non_exhaustive]`. New variants can be added in a future release without a breaking change, which means every `match` you write on it from outside the crate **must** include a wildcard `_ =>` (or `Err(e) =>`) arm. The compiler enforces this; it is not optional. That is a small tax you pay so that RustyML can grow its error vocabulary without a major-version bump.

Prefer the smart constructors — `Error::not_fitted("KMeans")`, `Error::invalid_parameter("C", "must be > 0")`, `Error::dimension_mismatch(3, 5)`, `Error::empty_input("target vector")`, and so on — over building variants by hand. They keep the wording identical everywhere, which is exactly what makes the messages greppable (§1.6.6). You rarely construct errors yourself unless you are wrapping RustyML in your own library, but when you do, use these.

## 1.6.2. The domain sub-errors and how they nest

Three of the top-level variants wrap smaller enums. This is the part of the design that lets the shared variants stay clean: concerns that only apply to neural networks (layer state, weight shapes, compilation) or only to trees (classification-vs-regression) live in their own enum, and the top-level `Error` aggregates them through `#[from]` bridges so that `?` lifts them automatically.

**`NnError`** (at `rustyml::neural_network::NnError`) carries `ForwardPassNotRun(&'static str)`, `WeightShape { name, expected, found }`, `NotCompiled(&'static str)`, and `EmptyModel`. It surfaces through `Error::NeuralNetwork`. Because that variant is `#[error(transparent)]`, `Error::NeuralNetwork(NnError::EmptyModel).to_string()` renders exactly as `NnError::EmptyModel` would — `model has no layers` — with no wrapper prefix. So a `Sequential` you forgot to `compile()` fails like this:

```rust
use rustyml::neural_network::sequential::Sequential;
use rustyml::neural_network::layers::Dense;
use rustyml::neural_network::layers::activation::ReLU;
use rustyml::neural_network::NnError;
use rustyml::error::Error;
use ndarray::Array;

fn main() {
    let mut model = Sequential::new();
    model.add(Dense::new(4, 2, ReLU::new()).unwrap());

    let x = Array::ones((3, 4)).into_dyn();
    let y = Array::ones((3, 2)).into_dyn();

    // No compile() call, so no optimizer or loss is configured yet.
    match model.fit(&x, &y, 1) {
        Ok(_) => unreachable!("training should not have started"),
        Err(Error::NeuralNetwork(NnError::NotCompiled(missing))) => {
            println!("compile the model first: `{missing}` is not specified");
        }
        Err(e) => println!("unexpected: {e}"),
    }
}
```

The match reaches two levels deep, into `Error::NeuralNetwork(NnError::NotCompiled(_))`, which is how you distinguish "you forgot to compile" from "your batch sizes disagree" (`Error::DimensionMismatch`) even though both come back from the same `fit` call. See [3.1. The Sequential Model](../Chapter-03/3.1._The_Sequential_Model.md) for the full compile-then-fit lifecycle.

**`TreeError`** (at `rustyml::machine_learning::TreeError`) has `NotClassificationTree` and `CorruptStructure(&'static str)`, surfaced through `Error::Tree`. You hit the first one when you call a classification-only method like `predict_proba` on a regression tree — and, because that check runs before the fitted-state check, you can even trigger it on an unfitted tree:

```rust
use rustyml::machine_learning::{Algorithm, DecisionTree, TreeError};
use rustyml::error::Error;
use ndarray::array;

fn main() {
    // A regression tree (is_classifier = false) has no per-class probabilities.
    let tree = DecisionTree::new(Algorithm::CART, false).unwrap();
    let x = array![[1.0, 2.0]];

    match tree.predict_proba(&x) {
        Err(Error::Tree(TreeError::NotClassificationTree)) => {
            println!("predict_proba is classification-only");
        }
        other => println!("unexpected: {other:?}"),
    }
}
```

**`IoError`** (at `rustyml::error::IoError`) is the one you meet whenever a model touches the filesystem. It has three variants: `Std(std::io::Error)` for filesystem failures, `Serialization(postcard::Error)` for the binary format (RustyML serializes with [postcard](https://docs.rs/postcard)), and `ModelStructureMismatch(String)` for when a loaded neural-network file does not match the architecture you are loading it into (a different number of layers, a different layer type at some position, or a weight whose shape does not fit the target layer). All three surface through `Error::Io`.

Two `From` conversions make the common cases seamless: `From<std::io::Error> for Error` produces `Error::Io(IoError::Std(..))`, and `From<postcard::Error> for Error` produces `Error::Io(IoError::Serialization(..))`. That means inside a function returning `RustymlResult<T>`, a raw `std::fs::read(path)?` just works — the `?` lifts the `io::Error` two levels up into the unified type. Loading a model from a path that does not exist demonstrates the nesting on the way back out:

```rust
use rustyml::machine_learning::LinearRegression;
use rustyml::error::{Error, IoError};

fn main() {
    match LinearRegression::load_from_path("model_that_does_not_exist.bin") {
        Ok(_) => unreachable!("the file should not exist"),
        Err(Error::Io(IoError::Std(io_err))) => {
            // io_err is the underlying std::io::Error (kind NotFound here).
            println!("filesystem error: {io_err}");
        }
        Err(Error::Io(IoError::Serialization(e))) => {
            println!("the file exists but is not a valid model: {e}");
        }
        Err(e) => println!("unexpected: {e}"),
    }
}
```

Matching `Error::Io(IoError::Std(..))` versus `Error::Io(IoError::Serialization(..))` is exactly how you tell "the file isn't there / I can't read it" apart from "the file is there but corrupt or from an incompatible version" — a distinction that matters when you decide whether to retrain or to fail loudly. [7.2. Model Persistence in Depth](../Chapter-07/7.2._Model_Persistence_in_Depth.md) covers the format and versioning story.

## 1.6.3. Matching on specific variants

The everyday failure is calling `predict` before `fit`. Every estimator guards this and returns `Error::NotFitted` carrying its own name as a `&'static str`, so a single arm handles it and the message already tells the user which model:

```rust
use rustyml::machine_learning::LinearRegression;
use rustyml::error::Error;
use ndarray::array;

fn main() {
    // Constructed but never fitted.
    let model = LinearRegression::new(true, 0.01, 1000, 1e-6).unwrap();
    let x = array![[1.0, 2.0], [3.0, 4.0]];

    match model.predict(&x) {
        Ok(preds) => println!("{preds:?}"),
        Err(Error::NotFitted(name)) => {
            println!("`{name}` was not fitted; call fit() first");
        }
        Err(Error::DimensionMismatch { expected, found }) => {
            println!("wrong feature count: model wants {expected}, got {found}");
        }
        // Required: Error is #[non_exhaustive], so a wildcard arm is mandatory.
        Err(e) => println!("other error: {e}"),
    }
}
```

Note the shape of that `match`: two specific arms for the errors you can do something about, then a mandatory catch-all. The `DimensionMismatch` arm is there to show the pattern — this particular call triggers `NotFitted` — but a fitted model fed a matrix with the wrong number of columns takes that second arm instead, with `expected` set to the feature count seen at `fit` time and `found` set to what you just passed. The estimator traits in [2.0. Classical Machine Learning](../Chapter-02/2.0._Classical_Machine_Learning.md) all return this same `Error`, so one `match` generalizes across every model.

## 1.6.4. Propagating with `?` and no `anyhow`

Because the whole crate funnels into one error type, threading failures through a pipeline needs nothing beyond plain `Result` and `?`. You do not need `anyhow`, `eyre`, or a custom error enum of your own — RustyML's `Error` already is the common denominator. Use the `RustymlResult<T>` alias for your own function signatures so a `-> RustymlResult<T>` unmistakably means *this* crate's error:

```rust
use rustyml::machine_learning::LinearRegression;
use rustyml::error::RustymlResult;
use ndarray::{array, Array1, Array2};

fn train_and_predict(x: &Array2<f64>, y: &Array1<f64>) -> RustymlResult<Array1<f64>> {
    // Every `?` below lifts a rustyml::error::Error out of a fallible call.
    let mut model = LinearRegression::new(true, 0.05, 500, 1e-9)?; // InvalidParameter?
    model.fit(x, y)?;                                              // EmptyInput / DimensionMismatch / NonFinite?
    let preds = model.predict(x)?;                                 // NotFitted / DimensionMismatch?
    Ok(preds)
}

fn main() {
    let x = array![[1.0], [2.0], [3.0]];
    let y = Array1::from_vec(vec![2.0, 4.0, 6.0]);

    match train_and_predict(&x, &y) {
        Ok(preds) => println!("got {} predictions", preds.len()),
        Err(e) => eprintln!("pipeline failed: {e}"),
    }
}
```

Every `?` in `train_and_predict` returns the same `Error`, so there is no `.map_err` boilerplate converting between error types — the thing that makes error handling verbose in a codebase that mixes several error enums simply does not arise here.

When you *do* need to fold a foreign error (something from the standard library or another crate) into this scheme while keeping its cause chain, reach for the `Context` extension trait. It is implemented for any `Result<T, E>` whose `E` is a `Send + Sync + 'static` `std::error::Error`, so it composes with `?`. `context` takes the message eagerly; `with_context` takes a closure that runs only on the error path — prefer the closure form whenever building the message allocates (anything with `format!`), so the success path pays nothing:

```rust
use rustyml::error::{Context, Error, RustymlResult};

fn parse_threshold(raw: &str) -> RustymlResult<f64> {
    // A std ParseFloatError, wrapped as Error::Computation with our context,
    // its source() chain preserved for downcasting later.
    let value: f64 = raw
        .parse()
        .with_context(|| format!("parsing threshold from {raw:?}"))?;
    Ok(value)
}

fn main() {
    match parse_threshold("not-a-number") {
        Ok(v) => println!("threshold = {v}"),
        Err(Error::Computation { context, source }) => {
            println!("{context}");
            if let Some(cause) = source {
                println!("  caused by: {cause}");
            }
        }
        Err(e) => println!("unexpected: {e}"),
    }
}
```

The wrapped error becomes the `source` of an `Error::Computation`, reachable through the standard `std::error::Error::source()` chain and downcastable back to the original concrete type — so you lose no information by folding it in.

## 1.6.5. Eager validation instead of panics

RustyML's contract is that **constructors and fit/predict methods validate eagerly and return `Result`, rather than panicking on bad input**. A learning rate of zero does not blow up ten iterations into gradient descent; it is rejected the moment you build the model, with a message naming the parameter and why:

```rust
use rustyml::machine_learning::LinearRegression;
use rustyml::error::Error;

fn main() {
    // learning_rate must be positive and finite — 0.0 is rejected at construction.
    match LinearRegression::new(true, 0.0, 1000, 1e-6) {
        Ok(_) => unreachable!("a zero learning rate must not be accepted"),
        Err(Error::InvalidParameter { name, reason }) => {
            // Prints: bad parameter `learning_rate`: must be positive and finite, got 0
            println!("bad parameter `{name}`: {reason}");
        }
        Err(e) => println!("unexpected: {e}"),
    }
}
```

The same discipline runs through the crate: `Dense::new` rejects a zero `input_dim` or `units` with `InvalidParameter`; `KMeans::new`, `PCA::new`, and the rest validate their hyperparameters before returning `Ok`. Input matrices are checked at `fit` and `predict` for emptiness, feature-count agreement, and finiteness, yielding `EmptyInput`, `DimensionMismatch`, or `NonFinite` respectively. The payoff is that an error points at the mistake you actually made, not at some downstream symptom.

Panics are not entirely gone, though, and it would be dishonest to claim otherwise. They remain both where RustyML deliberately trades validation for a panic and where Rust itself panics and RustyML does not intercept:

- **The `metrics` and `math` leaf modules** — their functions panic by contract on a precondition violation (mismatched lengths, empty input, an out-of-range Minkowski order) instead of returning `Result`, which is what keeps these leaf modules dependency-light. This is the one deliberate exception to the eager-`Result` rule above; the crate flags it in [1.1.3](./1.1._What_is_RustyML.md#113-the-module-map), §1.5.2's metric note, and [5. Model Evaluation](../Chapter-05/5.0._Model_Evaluation.md).
- **Index misuse in your own code** — `array[[i, j]]` with an out-of-bounds index, `.unwrap()` on a `None`, integer overflow in debug builds. These are bugs in the caller, and a `Result` would only obscure them.
- **`ndarray` shape operations outside the crate's control** — constructing an array with mismatched data and shape, or reshaping to an incompatible size. Note that `Array2::from_shape_vec` returns a `Result` you can handle, but `ndarray`'s indexing and some reshape paths panic by design. When you build the input arrays you hand to RustyML, that construction is on you; see [1.3. Working with ndarray](./1.3._Working_with_ndarray.md).

The rule of thumb: across the estimator, layer, and I/O API, anything RustyML validates about *your data or hyperparameters* comes back as an `Error` you can match on (the `metrics`/`math` leaf modules being the deliberate exception noted above); anything that is a *programming bug* — a bad index, a `None` you assumed was `Some` — stays a panic, because that is what panics are for.

## 1.6.6. Debugging: reading messages and what to grep

Every message in the crate is produced by the same small set of smart constructors, which means the wording is stable and you can grep for it. If a user hands you a log line, you can find the exact source site fast.

Given a message like ``invalid parameter `learning_rate`: must be positive and finite, got 0``, the constant part (`must be positive and finite`) comes straight from the constructor call, so searching the source for it lands you on the validation:

```bash
# Find where a specific message is produced:
grep -rn "must be positive and finite" src/
# Find every site that can raise a given variant:
grep -rn "Error::not_fitted\|NotFitted" src/
grep -rn "Error::invalid_parameter\|InvalidParameter" src/
grep -rn "dimension_mismatch\|DimensionMismatch" src/
```

Because the variants themselves are the vocabulary, the fastest triage is usually to read the leading word of the `Display` output and map it back to the table in §1.6.1: `input is empty` → `EmptyInput`, `dimension mismatch` → `DimensionMismatch`, `non-finite value` → `NonFinite`, `model \`...\` has not been fitted` → `NotFitted`, `model has not been compiled` → `NnError::NotCompiled`, and so on. The messages are lowercase and prefix-consistent on purpose so this mapping is unambiguous.

When you have an `Error::Computation` in hand — the one variant that can wrap a foreign cause — the useful detail is often one level down. Walk the `std::error::Error::source()` chain (or match `Error::Computation { source: Some(s), .. }` as in §1.6.4) to recover the original error, which you can then `downcast_ref` to its concrete type if you need to branch on it. For everything else, `{}` gives you the human message and `{:?}` gives you the full `Debug` form including the nested variant and its fields, which is what you want in test assertions and `eprintln!` during development.

One last habit worth forming: when you write library code on top of RustyML, keep returning `RustymlResult<T>` (or `Result<T, rustyml::error::Error>`) rather than collapsing everything into a `String` or a `Box<dyn Error>`. You inherit the whole matchable variant set for free, your callers can still distinguish "not fitted" from "bad file" from "did not converge", and you never have to write a `From` impl to make it compose. That composability is the entire reason the crate settled on one error type instead of many.
