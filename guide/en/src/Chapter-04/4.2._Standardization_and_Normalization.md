# 4.2. Standardization and Normalization

Two operations get filed under the same mental folder — "make the numbers comparable" — and they do completely different things. Standardization recenters and rescales each feature so it has zero mean and unit variance (a z-score). Normalization rescales each sample so its vector norm equals 1. RustyML exposes both as `rustyml::utils::standardize` and `rustyml::utils::normalize`, and — this is the part that catches scikit-learn refugees — both are **stateless free functions**: each call computes its statistics from the array you hand it and returns a new one, with nowhere to keep a training mean.

Both also have stateful counterparts, in `rustyml::utils`: `StandardScaler`, `MinMaxScaler`, `MaxAbsScaler`, `RobustScaler`, and `Normalizer` — `fit`/`transform` objects that store what they learned from the training matrix and reapply it to every later batch. Which form you reach for is the decision this page keeps coming back to, and it turns on one question: *is there a second batch that has to be scaled the same way?* If yes (a test split, a validation fold, a live sample at inference), you want a scaler; [section 4.2.5](#425-reusing-training-statistics-the-scaler-family) is the whole story. If you have not read [4.1. Train-Test Split](./4.1._Train_Test_Split.md) yet, do that first; the leakage trap here only exists relative to a split.

## 4.2.1. Two operations, one common confusion

Before the mechanics, get the vocabulary straight, because the two functions answer different questions and are almost never interchangeable. If you came here expecting a min-max scaler that squashes features into `[0, 1]`, that is a third thing again, and it lives with the stateful scalers as [`MinMaxScaler`](#the-rest-of-the-family) — not here: `normalize` scales by a **vector norm** (L1/L2/Max/Lp), not by feature range, and `standardize` produces z-scores.

| | `standardize` | `normalize` |
|---|---|---|
| What it makes uniform | each feature's **mean and variance** | each sample's **length (norm)** |
| Typical axis | `Column` (per feature) | `Row` (per sample) |
| Output guarantee | column mean 0, population variance 1 | lane norm equals 1 |
| Couples across samples? | yes — a column's mean/std depend on every row | row-wise: no; column/global: yes |
| scikit-learn analogue | `StandardScaler`, or the stateless `standardize` | `Normalizer`, or the stateless `normalize` |
| Divisor for a degenerate lane | `1.0` (constant column → zeros) | `1.0` (near-zero lane left as-is) |

The "couples across samples" row is the one that decides whether you have a leakage problem at all, and it comes back in [section 4.2.5](#425-reusing-training-statistics-the-scaler-family).

## 4.2.2. Standardization (z-score)

The signature is a single generic free function over any `f64` array dimension:

```rust,ignore
pub fn standardize<S, D>(
    data: &ArrayBase<S, D>,
    axis: StandardizationAxis,
) -> Result<Array<f64, D>, Error>
where
    S: Data<Elem = f64>,
    D: Dimension;
```

It borrows the input and returns a fresh owned array of the same shape — the original is never mutated. `StandardizationAxis` has three variants, and the mapping to physical axes is worth pinning down because it is the reverse of what "row" and "column" might suggest at a glance:

- `Column` standardizes along `Axis(0)` — each lane is one column, so this gives **per-feature** z-scores. For the usual samples-as-rows, features-as-columns layout, this is the one you want.
- `Row` standardizes along the last axis — each lane is one row. Useful when a "sample" is itself a signal whose internal scale should be normalized, rarely what you want for tabular features.
- `Global` flattens the whole array and standardizes it as one dataset.

For N-D arrays (N > 2), `Row` operates on the last axis and `Column` on the second-to-last; `Row`/`Column` on a 1-D array is an error (there is only one axis), returning `Error::InvalidInput`. `Global` works on any rank including 1-D.

The divisor is the **population** standard deviation — `sqrt(variance)` with variance divided by `n`, not `n - 1`. This matches scikit-learn's `StandardScaler` (which also uses `ddof=0`), so z-scores line up if you are porting a pipeline. The mean and variance come from a single numerically stable Welford pass, merged in parallel above an internal size gate, so results are deterministic run-to-run on the same machine but not guaranteed bit-for-bit (see [7.3. Performance Tuning and Parallelism](../Chapter-07/7.3._Performance_Tuning_and_Parallelism.md)).

```rust
use ndarray::{array, Axis};
use rustyml::utils::standardize::{standardize, StandardizationAxis};

fn main() {
    // Rows are samples, columns are features living on wildly different scales.
    let x = array![
        [1.0, 2000.0],
        [2.0, 3000.0],
        [3.0, 4000.0],
        [4.0, 5000.0],
    ];

    // Standardize each FEATURE (column) to zero mean, unit variance.
    let z = standardize(&x, StandardizationAxis::Column).unwrap();
    println!("shape: {:?}", z.shape()); // [4, 2]

    // Every column now has population mean ~0 and population variance ~1.
    for (j, col) in z.axis_iter(Axis(1)).enumerate() {
        let n = col.len() as f64;
        let mean = col.sum() / n;
        let var = col.iter().map(|v| (v - mean).powi(2)).sum::<f64>() / n;
        println!("feature {j}: mean={mean:.3e} var={var:.3}");
    }
}
```

## 4.2.3. Normalization (unit norm)

`normalize` takes an axis and a norm order, and divides each lane by its norm so that lane's norm becomes 1:

```rust,ignore
pub fn normalize<S, D>(
    data: &ArrayBase<S, D>,
    axis: NormalizationAxis,
    order: NormalizationOrder,
) -> Result<Array<f64, D>, Error>
where
    S: Data<Elem = f64>,
    D: Dimension;
```

`NormalizationAxis` mirrors the standardization variants (`Row` = last axis, `Column` = second-to-last, `Global` = whole array flattened), with the same 1-D restriction on `Row`/`Column`. `NormalizationOrder` picks which norm:

| Variant | Norm | A lane `[3, 4]` becomes |
|---|---|---|
| `L1` | sum of absolute values | `[3/7, 4/7]` |
| `L2` | Euclidean (sqrt of sum of squares) | `[0.6, 0.8]` |
| `Max` | largest absolute value (infinity norm) | `[0.75, 1.0]` |
| `Lp(p)` | `(sum \|x\|^p)^(1/p)`, custom `p` | depends on `p` |

`Lp(1.0)` and `Lp(2.0)` are exactly `L1` and `L2`; the dedicated variants exist because they avoid the `powf` call. Signs are preserved — dividing by a positive norm never flips a value — so `[-3, 4]` under L2 becomes `[-0.6, 0.8]`. The most common use is per-sample L2 normalization (`Row`, `L2`), which projects each sample onto the unit sphere so that only its direction, not its magnitude, matters — exactly what a cosine-similarity or dot-product model wants. That row-wise case also has an object form, `Normalizer`, covered in [section 4.2.5](#425-reusing-training-statistics-the-scaler-family); it is the same arithmetic, wrapped in the estimator contract.

```rust
use ndarray::array;
use rustyml::utils::normalize::{normalize, NormalizationAxis, NormalizationOrder};

fn main() {
    let x = array![[3.0, 4.0], [1.0, 2.0]];

    // Scale each ROW (sample) to unit L2 length: row 0 -> [0.6, 0.8].
    let l2 = normalize(&x, NormalizationAxis::Row, NormalizationOrder::L2).unwrap();
    for row in l2.rows() {
        let norm = row.iter().map(|v| v * v).sum::<f64>().sqrt();
        println!("row L2 norm = {norm:.6}");
    }

    // Same data under the Max (infinity) norm: each row's largest |value| becomes 1.
    let mx = normalize(&x, NormalizationAxis::Row, NormalizationOrder::Max).unwrap();
    println!("Max-normalized: {mx:?}");

    // A custom Lp order; p must be positive and finite or you get Error::InvalidParameter.
    let lp = normalize(&x, NormalizationAxis::Row, NormalizationOrder::Lp(3.0)).unwrap();
    println!("Lp(3)-normalized: {lp:?}");
}
```

## 4.2.4. Which models actually need scaling

Scaling is not universally beneficial; whether it matters depends entirely on how the model measures the data. Three families behave differently.

| Model family | Members | Scaling matters? | Why |
|---|---|---|---|
| Distance-based | [KNN](../Chapter-02/2.3._K_Nearest_Neighbors.md), [KMeans](../Chapter-02/2.7._KMeans_Clustering.md), [DBSCAN](../Chapter-02/2.8._DBSCAN.md), [Mean Shift](../Chapter-02/2.9._Mean_Shift.md), [SVC with RBF](../Chapter-02/2.5._Support_Vector_Machines.md) | critically | Euclidean distance is dominated by the highest-variance feature; a feature measured in thousands drowns one measured in units |
| Gradient-based | [Linear Regression](../Chapter-02/2.1._Linear_Regression.md), [Logistic Regression](../Chapter-02/2.2._Logistic_Regression.md), [neural networks](../Chapter-03/3.0._Neural_Networks.md) | strongly | Wildly different feature scales stretch the loss surface into a ravine; gradient descent zig-zags and needs a tiny learning rate to stay stable |
| Variance-based | [PCA](../Chapter-02/2.10._Principal_Component_Analysis.md), [Kernel PCA](../Chapter-02/2.11._Kernel_PCA.md), [t-SNE](../Chapter-02/2.12._t-SNE.md) | strongly | Components chase the axes of largest variance; an unscaled feature can define the first component purely because its units are bigger |
| Tree-based | [Decision Trees](../Chapter-02/2.4._Decision_Trees.md), [Isolation Forest](../Chapter-02/2.13._Isolation_Forest.md) | no | Splits are thresholds on one feature at a time; any monotonic rescaling produces the identical tree, so scaling is wasted work |

The distance-based row is the sharpest case, and it ties back to [6.1. Distance Metrics](../Chapter-06/6.1._Distance_Metrics.md): these models literally sum squared per-feature differences, so a feature's contribution scales with its variance. Standardize the columns and every feature enters the distance on equal footing. For the gradient-based family, standardization is the cheapest single thing you can do to let a neural network train at a sane learning rate. Trees are the honest "don't bother" case — spending cycles standardizing before a `DecisionTree` changes nothing about the fit.

Note that `standardize` (per-feature) and `normalize` (per-sample) are not substitutes here. Distance- and gradient-based models almost always want **column standardization**; row normalization is for when sample magnitude is noise and only direction carries signal (text term-frequency vectors are the classic example).

## 4.2.5. Reusing training statistics: the scaler family

Here is the failure the free function makes easy to walk into. Every call to `standardize` recomputes the statistics from the array you hand it, which has two distinct consequences — and conflating them is where people go wrong.

**Consequence one — the leakage trap.** If you call `standardize(&x_full, Column)` on the whole dataset and split afterward, the per-feature mean and variance were computed over rows that later land in the test set. The training transform has quietly absorbed information about the test distribution, and your validation score is optimistic. The fix is ordering: split first, then scale.

**Consequence two — inconsistent transforms.** Even if you split first, calling `standardize(&x_test, Column)` scales the test set by the *test set's own* column statistics — a different linear map than the one applied to training. A model trained on train-scaled features then sees test features scaled by different numbers, which silently degrades every distance- and gradient-based model. It is also simply impossible at real inference time, where a single incoming sample has no meaningful per-column standard deviation of its own.

Both point to the same discipline: compute the statistics **once, on the training matrix only**, and apply those frozen numbers to every later batch. `StandardScaler` is the object that holds them for you — the same `fit`/`transform` contract as scikit-learn's:

```rust,ignore
use rustyml::utils::StandardScaler;

let mut scaler = StandardScaler::new();
scaler.fit(&x_train)?;                       // learn mean & std from training rows only
let x_train_z = scaler.transform(&x_train)?; // or fit_transform(&x_train) in one call
let x_test_z = scaler.transform(&x_test)?;   // SAME numbers, applied to the test split
```

Note the split of responsibilities: `fit` is the only method that looks at data statistically, and `transform` is a pure application of what `fit` stored. Once fitted, the scaler is a fixed linear map — hand it one row, a thousand, or the training matrix again, and every value passes through the identical `(x - mean) / scale`. Ordering is still yours to get right: split before you fit, and never re-`fit` on anything but training data.

```rust
use ndarray::{array, Array1};
use rustyml::utils::StandardScaler;
use rustyml::utils::train_test_split::train_test_split;

fn main() {
    let x = array![
        [1.0, 100.0],
        [2.0, 150.0],
        [3.0, 200.0],
        [4.0, 250.0],
        [5.0, 300.0],
        [6.0, 350.0],
    ];
    let y = Array1::from(vec![0, 1, 0, 1, 0, 1]);

    // 1. Split FIRST, before touching any feature value.
    let (x_train, x_test, _y_train, _y_test) =
        train_test_split(x, y, Some(0.34), Some(42)).unwrap();

    // 2. Fit on the TRAINING matrix only; fit_transform returns the scaled training data.
    let mut scaler = StandardScaler::new();
    let x_train_z = scaler.fit_transform(&x_train).unwrap();

    // 3. The test split goes through the stored training statistics.
    let x_test_z = scaler.transform(&x_test).unwrap();

    // 4. A single live sample works the same way - which the free function cannot do.
    let one_sample = scaler.transform(&array![[2.5, 175.0]]).unwrap();

    println!("train mean: {:?}", scaler.get_mean().unwrap());
    println!("train scale: {:?}", scaler.get_scale().unwrap());
    println!("x_train_z shape: {:?}", x_train_z.shape());
    println!("x_test_z shape:  {:?}", x_test_z.shape());
    println!("one sample:      {one_sample:?}");
}
```

### What `StandardScaler` holds and what it offers

| Method / accessor | What it does | scikit-learn |
|---|---|---|
| `fit(&x)` | Learns and stores the per-feature mean and scale, discarding any previous fit | `fit` |
| `transform(&x)` | Applies the stored `(x - mean) / scale`; returns a new array | `transform` |
| `fit_transform(&x)` | Both, in one call — the training-matrix entry point | `fit_transform` |
| `inverse_transform(&x)` | Maps standardized values back to the original units | `inverse_transform` |
| `partial_fit(&x)` | Merges another batch into the statistics instead of replacing them | `partial_fit` |
| `get_mean()` / `get_var()` / `get_scale()` | The learned statistics, `None` before `fit` | `mean_` / `var_` / `scale_` |
| `get_n_samples_seen()` / `get_n_features()` | How many rows the statistics cover, and their width | `n_samples_seen_` / `n_features_in_` |
| `with_mean(bool)` / `with_std(bool)` | Builder switches for centering and scaling | constructor arguments |
| `save_to_path` / `load_from_path` | Persists the fitted scaler (postcard binary) | `pickle` |

`partial_fit` is the answer when the training set does not fit in memory: feed it one chunk at a time and the per-feature moments merge (Chan et al.) into the same result a single `fit` over the concatenation would give. `inverse_transform` matters whenever you need an answer in the units the data arrived in — reading back a reconstruction, or de-scaling a target you scaled before fitting a regressor.

The scaler is *part of the trained pipeline*, not scratch state: a model saved without its scaler is unusable, because nothing records what the model's inputs were divided by. Save both:

```rust,ignore
scaler.save_to_path("scaler.bin")?;
model.save_to_path("model.bin")?;

// At serving time
let scaler = StandardScaler::load_from_path("scaler.bin")?;
let model = LinearRegression::load_from_path("model.bin")?;
let prediction = model.predict(&scaler.transform(&incoming)?)?;
```

Two error paths are worth knowing before you meet them: calling `transform` on an unfitted scaler is `Error::NotFitted("StandardScaler")`, and handing it a matrix whose column count differs from the fitted one is `Error::DimensionMismatch` — the feature-order bug that silently corrupts predictions in a dynamically typed pipeline is a typed error here. Non-finite input is rejected exactly as the free function rejects it (`Error::NonFinite`), which is a deliberate difference from scikit-learn: its scaler treats `NaN` as missing data and skips it, while RustyML asks you to impute or drop first.

The scaler also implements the crate's shared [`Fit` / `Transform` / `FitTransform`](../Chapter-01/1.5._The_Prelude_and_Imports.md) traits, so it composes with generic code written over any transformer:

```rust,ignore
use rustyml::traits::{Fit, Transform};

Fit::fit(&mut scaler, &x_train)?;
let z = Transform::transform(&scaler, &x_test)?;
```

### The rest of the family

`StandardScaler` is the default, not the only option. Four siblings share its entire contract — same `fit` / `transform` / `fit_transform`, same `NotFitted` and `DimensionMismatch` guards, same `save_to_path` — and differ only in what they learn:

| Scaler | Maps each feature by | Learns | Reach for it when |
|---|---|---|---|
| `StandardScaler` | `(x - mean) / std` | mean, variance | the default for distance- and gradient-based models |
| `MinMaxScaler` | `(x - min) / (max - min)`, then into a target range | min, max | a component needs bounded inputs |
| `MaxAbsScaler` | `x / max(\|x\|)` | max magnitude | zero has to keep meaning "absent" |
| `RobustScaler` | `(x - median) / IQR` | median, quantile spread | the data has outliers you will not remove |
| `Normalizer` | *each sample* divided by its own norm | nothing but the feature count | only a sample's direction carries signal |

**`MinMaxScaler`** squashes each feature onto `[0, 1]` by default; `with_feature_range(-1.0, 1.0)` retargets it (on an already-fitted scaler too — the extrema are kept and only the destination moves). Two behaviours to know. First, a later batch that exceeds the training extrema lands *outside* the range, which is the honest answer — it is how you notice that production data drifted past what you trained on. Pass `with_clip(true)` when a downstream component genuinely requires bounded input, remembering that clipping is lossy and `inverse_transform` cannot undo it. Second, it is the most outlier-sensitive of the three: one extreme training value stretches the denominator and squeezes every other sample into a sliver of the range. A constant feature has no range at all, so its divisor becomes `1.0` and the column lands flat on `feature_range.0`.

**`MaxAbsScaler`** divides by `max(|x|)` and never shifts, so a zero stays exactly zero and every sign survives. That is the whole point: for count vectors, one-hot blocks, or TF-IDF rows, zero means "absent", and min-max's shift turns those structural zeros into an arbitrary nonzero value that no longer means anything. Training values land in `[-1, 1]`; an all-zero feature keeps a divisor of `1.0` and stays zero.

**`RobustScaler`** replaces the mean and standard deviation with the median and the interquartile range. Both are order statistics, so an extreme value changes them barely at all — where one outlier drags `StandardScaler`'s mean and inflates its standard deviation, and stretches `MinMaxScaler`'s denominator until the rest of the data is squeezed into a sliver. Use it when the data has outliers you are not going to remove. `with_quantile_range(10.0, 90.0)` widens the spread it measures (more of the distribution, more reaction to the tails); note this **discards any fitted statistics**, since the stored quantiles were read at the old positions and cannot be moved without the data. Two limits worth knowing: there is no `partial_fit` (quantiles do not merge across batches the way moments and extrema do), and robustness needs samples — with only four rows the 75th percentile interpolates straight into the outlier, which is the quantile rule working as specified rather than a failure. The output has neither a fixed range nor unit variance, only a comparable middle.

**`Normalizer`** is the row-wise one, and the odd one out: a sample's norm depends on that sample alone, so `fit` learns nothing but the feature count. It exists so row normalization can take part in the same estimator contract as the rest (and so a mis-shaped batch is a typed error rather than a silent wrong answer). It takes the same `NormalizationOrder` as the free function, has no `inverse_transform` — dividing away a magnitude discards it — and for the `Column`/`Global` axes or N-D arrays you still call `normalize` directly.

```rust
use ndarray::array;
use rustyml::utils::normalize::NormalizationOrder;
use rustyml::utils::{MaxAbsScaler, MinMaxScaler, Normalizer};

fn main() {
    let x_train = array![[1.0, 0.0, -4.0], [2.0, 3.0, 0.0], [3.0, 0.0, 2.0]];
    let x_test = array![[4.0, 1.0, -1.0]];

    // Bounded to [0, 1] by the TRAINING extrema; the test row exceeds them on purpose.
    let mut min_max = MinMaxScaler::new();
    let train_scaled = min_max.fit_transform(&x_train).unwrap();
    println!("train (min-max): {train_scaled:?}");
    println!("test  (min-max): {:?}", min_max.transform(&x_test).unwrap()); // > 1.0 in col 0

    // Clipped variant: same map, clamped into the range.
    let mut clipped = MinMaxScaler::new().with_clip(true);
    clipped.fit(&x_train).unwrap();
    println!("test  (clipped): {:?}", clipped.transform(&x_test).unwrap());

    // Magnitude only: the zeros in columns 1 and 2 stay exactly zero.
    let mut max_abs = MaxAbsScaler::new();
    println!("train (max-abs): {:?}", max_abs.fit_transform(&x_train).unwrap());

    // Per-sample direction; each row ends up with L2 norm 1.
    let mut normalizer = Normalizer::new(NormalizationOrder::L2).unwrap();
    println!("train (rows):    {:?}", normalizer.fit_transform(&x_train).unwrap());
}
```

Robust scaling is easiest to see against a column that has an outlier in it:

```rust
use ndarray::array;
use rustyml::utils::{RobustScaler, StandardScaler};

fn main() {
    // Two identical features, except that column 1's last value is a wild outlier.
    let x = array![
        [1.0, 1.0], [2.0, 2.0], [3.0, 3.0], [4.0, 4.0], [5.0, 5.0],
        [6.0, 6.0], [7.0, 7.0], [8.0, 8.0], [9.0, 1000.0],
    ];

    let mut robust = RobustScaler::new();
    robust.fit(&x).unwrap();
    let mut standard = StandardScaler::new();
    standard.fit(&x).unwrap();

    // Robust: both columns get the SAME center and scale - the outlier enters neither.
    println!("robust center: {:?}", robust.get_center().unwrap()); // [5, 5]
    println!("robust scale:  {:?}", robust.get_scale().unwrap());  // [4, 4]

    // Standard: column 1's mean and std are dominated by the single extreme value.
    println!("mean:  {:?}", standard.get_mean().unwrap());  // [5, ~115]
    println!("scale: {:?}", standard.get_scale().unwrap()); // [~2.6, ~313]
}
```

`MinMaxScaler` and `MaxAbsScaler` also support `partial_fit` (the extrema merge exactly, so batches give the same answer as one big fit), and every per-feature scaler here has `inverse_transform`. What is *not* here yet: the quantile and power transforms (`QuantileTransformer`, `PowerTransformer`), and `RobustScaler`'s `unit_variance` option, which needs an inverse normal CDF the crate does not provide — for those, compute the statistics yourself and apply them with the same freeze-on-train discipline.

### When the free function is still the right call

`standardize` has not been superseded — it is the right tool whenever there is no second batch to stay consistent with:

- **One-shot exploration**: you are looking at one matrix, not training anything.
- **`Row` or `Global` axes, or N-D arrays**: `StandardScaler` is a 2-D, per-feature transformer, exactly like scikit-learn's. Row-wise and whole-array standardization live only in the free function.
- **Transforms that do not couple samples**: **row** normalization scales each sample by its own norm and nothing else, so `normalize(&x_train, Row, L2)` and `normalize(&x_test, Row, L2)` are consistent by construction — there is no cross-sample statistic to leak or freeze. `Column`/`Global` normalization does couple, and has no scaler object; if you need it applied consistently across a split, hoist the norms yourself.

And for a transform the family does not cover — a quantile or power transform, say — the discipline transfers unchanged: compute the statistics on the training matrix, keep them, and apply those same numbers to every later batch by hand.

## 4.2.6. Edge cases: constant features, zeros, and non-finite input

**Constant feature (zero variance).** A column whose values are all equal has variance 0, and naively dividing by `sqrt(0)` yields NaN. `standardize` detects this with a magnitude-relative, variance-based bound (the Chan–Golub–LeVeque error bound at machine precision) and sets the divisor to `1.0`. The centered values — already ~0 — then map to exactly 0.0, with no NaN or Inf, and other columns are untouched. Crucially, the detection is *variance-based*, not an exact `== 0` test, so a genuinely tiny-but-real spread (say two values differing by `1e-8`) is still treated as a real feature and standardized normally; only spread within floating-point noise is flattened. `StandardScaler` shares this rule verbatim — the constant column's `get_scale()` entry reads `1.0` — which is also why `inverse_transform` cannot resurrect such a feature: every value comes back as the training mean. `MinMaxScaler`, `MaxAbsScaler`, and `RobustScaler` guard the same failure with the coarser test scikit-learn uses for them (a divisor below `10 * f64::EPSILON` becomes `1.0`), landing a constant column on `feature_range.0` under min-max, and on zero under the other two.

**Near-zero lane in normalization.** A lane whose norm falls below `10 * f64::EPSILON` is treated as having norm `1.0` and left exactly as-is — a zero (or near-zero) vector has no direction to rescale, so dividing it would only manufacture NaN. An all-zero row stays all-zero; `Global` normalization of an all-zero array stays all-zero.

**Non-finite and degenerate input.** Both functions validate before doing any work and surface typed errors (see [1.6. Error Handling](../Chapter-01/1.6._Error_Handling.md)):

| Condition | Error variant |
|---|---|
| Empty array | `Error::EmptyInput` |
| Any `NaN`/`Inf` in the input | `Error::NonFinite` |
| `Row`/`Column` axis on a 1-D array | `Error::InvalidInput` |
| `normalize` with `Lp(p)`, `p <= 0` or non-finite | `Error::InvalidParameter` |
| A norm accumulation overflowing to non-finite | `Error::NonFinite` |

```rust
use ndarray::array;
use rustyml::error::Error;
use rustyml::utils::normalize::{normalize, NormalizationAxis, NormalizationOrder};
use rustyml::utils::standardize::{standardize, StandardizationAxis};

fn main() {
    // Constant column: zero variance. The divisor is forced to 1.0, so the centered
    // values collapse to exactly 0.0 with no NaN or Inf.
    let constant = array![[3.0, 1.0], [3.0, 3.0], [3.0, 5.0]];
    let z = standardize(&constant, StandardizationAxis::Column).unwrap();
    println!("constant-column result: {z:?}");
    assert!(z.iter().all(|v| v.is_finite()));

    // Zero row under normalization: norm below 10*f64::EPSILON is treated as 1.0, so the
    // (near-)zero lane is left exactly as-is instead of dividing by ~0.
    let with_zero_row = array![[3.0, 4.0], [0.0, 0.0]];
    let n = normalize(&with_zero_row, NormalizationAxis::Row, NormalizationOrder::L2).unwrap();
    println!("zero-row preserved: {n:?}");

    // Non-finite input is rejected up front, before any scaling happens.
    let bad = array![[1.0, f64::NAN], [3.0, 4.0]];
    match standardize(&bad, StandardizationAxis::Column) {
        Err(Error::NonFinite(_)) => println!("rejected non-finite input, as expected"),
        other => panic!("expected NonFinite, got {other:?}"),
    }
}
```

Because non-finite input is rejected up front, neither function can produce a `NaN` from clean data. If you have missing values encoded as `NaN`, impute or drop them before scaling — the functions will not silently pass them through.

## 4.2.7. Performance and determinism notes

Both functions clone the input once (they never mutate it) and then rescale in place on the clone. The heavy statistics — the Welford mean/variance pass for standardization, the per-lane norm for normalization — run sequentially per lane, but the work is parallelized *across* lanes with rayon once the element count clears an internally calibrated gate, and the two levels never nest. Global standardization uses a deterministic blocked parallel reduction, so it reproduces the same result across runs on the same machine (not necessarily bit-for-bit across different machines or thread counts). For datasets small enough to fit comfortably in cache the sequential path is taken and there is no threading overhead; you do not tune any of this by hand. A fitted `StandardScaler` runs on the same machinery, minus the statistics: `transform` is a single fused pass per row over stored vectors, so scaling inside a tight loop costs one pass instead of the Welford sweep the free function would repeat on every call — that, not the parallelism, is where the time goes. `StandardScaler::fit_transform` on a 2-D array is bit-for-bit identical to `standardize(&x, Column)`; the two share the same Welford pass and the same constant-feature rule, so switching between them never moves a number. See [7.3. Performance Tuning and Parallelism](../Chapter-07/7.3._Performance_Tuning_and_Parallelism.md) for the gate model, and [4.3. Label Encoding](./4.3._Label_Encoding.md) for the remaining preprocessing step.
