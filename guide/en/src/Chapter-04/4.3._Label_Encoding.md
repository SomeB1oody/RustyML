# 4.3. Label Encoding

Classifiers in RustyML never see your string classes. A softmax head emits a probability per column, a cross-entropy loss reads either a one-hot row or an integer index, and every metric in [Chapter 5](../Chapter-05/5.0._Model_Evaluation.md) counts integer class ids. Label encoding is the translation layer between the labels you have (`"cat"`, `"spam"`, `42`) and the two numeric shapes the training code accepts. RustyML gives you three free functions for this, living in `rustyml::utils::label_encoding` and re-exported at `rustyml::utils` and through the [prelude](../Chapter-01/1.5._The_Prelude_and_Imports.md).

If you come from scikit-learn, drop the mental model of a stateful `LabelEncoder`/`OneHotEncoder` you `fit` once and then `transform` many times. There is no encoder object here and nothing to persist: each function is a pure transformation of the array you hand it. That keeps the API tiny and thread-safe, but it moves one responsibility onto you — holding the label-to-index mapping yourself so you can decode predictions and apply the same scheme to future data. The rest of this page is mostly about doing that correctly.

## 4.3.1. The API surface: three stateless functions

Everything is these three functions. There is no `LabelEncoder` struct, no `fit`/`transform`/`inverse_transform` methods, and no separate ordinal encoder — the surface is deliberately flat.

| Function | Input | Output | Purpose |
|---|---|---|---|
| `to_categorical` | `&ArrayBase<S, Ix1>` where `S: Data<Elem = i32>`, `Option<usize>` | `Result<Array2<f64>, Error>` | Consecutive integer labels → one-hot matrix |
| `to_categorical_with_mapping` | `&[T]` where `T: Clone + Eq + Hash`, `Option<usize>` | `Result<(Array2<f64>, AHashMap<T, usize>), Error>` | Arbitrary labels (strings, sparse ints) → one-hot + the mapping used |
| `to_sparse_categorical` | `&ArrayBase<S, Ix2>` where `S: Data<Elem = f64>` | `Result<Array1<i32>, Error>` | One-hot or probability rows → integer labels via argmax |

Two facts about the types are worth pinning down now, because they cause the most friction later. First, `to_categorical` only accepts `i32` labels, while `to_categorical_with_mapping` accepts anything `Clone + Eq + Hash` — that generic bound is what lets you feed it `&str`, `String`, `u8`, enums, whatever your raw labels are. Second, the one-hot matrix comes back as `Array2<f64>` and the decoded labels as `Array1<i32>`, but the neural-network stack (`Tensor = ArrayD<f32>`) wants `f32`. That `f64 → f32` cast is a required, easy-to-forget step covered in [4.3.5](#435-picking-the-target-format-one-hot-vs-sparse-integer).

## 4.3.2. Integer labels to one-hot: `to_categorical`

Use this when your labels are already the consecutive integers `0..n_classes`. It builds a `(n_samples, n_classes)` matrix with a single `1.0` per row at the column named by the label.

```rust
use ndarray::array;
use rustyml::utils::to_categorical;

fn main() {
    let labels = array![0i32, 1, 2, 1, 0];

    // num_classes = None infers the width from max_label + 1 = 3.
    let onehot = to_categorical(&labels, None).unwrap();
    assert_eq!(onehot.shape(), &[5, 3]);

    // Pin a wider width so train / validation / test share a column layout even
    // when a split happens to miss the last class. Extra columns are all-zero.
    let padded = to_categorical(&labels, Some(4)).unwrap();
    assert_eq!(padded.shape(), &[5, 4]);
    println!("{onehot:?}");
}
```

The `num_classes` argument is the reason this function is worth its own entry rather than a one-liner. Passing `None` infers the width from `max_label + 1`, which is convenient but dangerous across a [train/test split](./4.1._Train_Test_Split.md): if your test fold happens to contain no examples of the highest class, `to_categorical(&test_labels, None)` produces a matrix one column narrower than the training matrix, and every downstream shape check will reject it. Pin `num_classes` to the true class count on every split and the layouts stay aligned. Widening is cheap — the surplus columns are simply zero — and it is the standard fix for "my validation targets don't match the output layer."

Two inputs are rejected rather than silently mangled, and both surface as typed [errors](../Chapter-01/1.6._Error_Handling.md):

```rust
use ndarray::array;
use rustyml::error::Error;
use rustyml::utils::to_categorical;

fn main() {
    // A negative label cannot index a one-hot column.
    let bad = array![0i32, -1, 2];
    assert!(matches!(
        to_categorical(&bad, None),
        Err(Error::InvalidInput(_))
    ));

    // num_classes narrower than max_label + 1 would drop a class.
    let labels = array![0i32, 1, 2];
    assert!(matches!(
        to_categorical(&labels, Some(2)),
        Err(Error::InvalidParameter { .. })
    ));
    println!("error paths behave as documented");
}
```

A negative label is an `Error::InvalidInput` because it has no valid column; a `num_classes` smaller than `max_label + 1` is an `Error::InvalidParameter` because it would truncate a real class. An empty input array is not an error — it returns shape `(0, 1)`, defaulting to one class so the matrix is still 2D.

## 4.3.3. Arbitrary labels to one-hot: `to_categorical_with_mapping`

Real datasets rarely arrive as `0..n`. They arrive as `"cat"/"dog"/"bird"`, or non-consecutive integer ids like `10/20/30`. `to_categorical_with_mapping` handles those in one pass: it assigns each distinct label a column index **in first-seen order**, one-hot encodes against that assignment, and hands back both the matrix and the `AHashMap<T, usize>` it built.

```rust
use rustyml::utils::to_categorical_with_mapping;

fn main() {
    let labels = vec!["cat", "dog", "bird", "dog", "cat"];
    let (onehot, mapping) = to_categorical_with_mapping(&labels, None).unwrap();

    assert_eq!(onehot.shape(), &[5, 3]);
    // First-seen order fixes the column assignment.
    assert_eq!(mapping["cat"], 0);
    assert_eq!(mapping["dog"], 1);
    assert_eq!(mapping["bird"], 2);
    println!("{mapping:?}");
}
```

First-seen order, not sorted order, is the contract — `"cat"` is column 0 because it appears first, not because it sorts first. This matters for reproducibility: the same slice always yields the same mapping, but two datasets that introduce classes in a different order produce different column assignments. That is precisely why the function returns the mapping instead of discarding it. The mapping is the only record of what each column means; keep it, because you will need it to decode predictions and, if you encode more data later, to reproduce the exact same layout (see [4.3.7](#437-unseen-categories-and-the-stateless-model)). The `num_classes` argument works as it does in `to_categorical` — `None` uses the unique-label count, `Some(n)` pads wider and errors if `n` is smaller than the number of distinct labels.

One edge case differs from `to_categorical`: an empty slice returns shape `(0, 0)` with an empty mapping, because with zero unique labels the inferred class count is zero. `to_categorical` on an empty array instead returns `(0, 1)`. Neither is wrong, but if you branch on the column count of an empty batch, know which function produced it.

## 4.3.4. Decoding predictions and round-trips: `to_sparse_categorical`

`to_sparse_categorical` is the inverse direction: it takes a 2D matrix and reduces each row to the index of its largest value. Feed it a strict one-hot matrix and it recovers the original integer labels; feed it a softmax probability matrix and it returns the predicted class per sample. That second use is the common one — it is how you turn a model's `predict` output into class ids.

```rust
use ndarray::array;
use rustyml::utils::{to_categorical, to_sparse_categorical};

fn main() {
    let original = array![0i32, 1, 2, 1, 0];
    let one_hot = to_categorical(&original, None).unwrap();
    let recovered = to_sparse_categorical(&one_hot).unwrap();
    assert_eq!(recovered, original);
    println!("round-trip ok: {recovered:?}");
}
```

Two behaviors are worth knowing. Ties resolve to the **first** (lowest) index — two columns sharing the row maximum pick the earlier one, matching numpy/Keras `argmax` rather than `max_by`, which would keep the last. And a non-finite value anywhere in the matrix is rejected with `Error::NonFinite` up front, so the per-row comparison is total and never silently treats `NaN` as a winner or loser. If your probabilities can contain `NaN`, that is a bug in the model output, and this function tells you rather than hiding it.

For the string case, the round trip needs one more hop, because `to_sparse_categorical` only recovers **indices** — it has never seen your labels. Invert the mapping yourself to get from index back to label:

```rust
use rustyml::utils::{to_categorical_with_mapping, to_sparse_categorical};
use std::collections::HashMap;

fn main() {
    let labels = vec!["cat", "dog", "bird", "dog", "cat"];
    let (one_hot, mapping) = to_categorical_with_mapping(&labels, None).unwrap();

    // Decode to class indices, then invert the mapping to recover the strings.
    let idx = to_sparse_categorical(&one_hot).unwrap();
    let inverse: HashMap<usize, &str> = mapping.iter().map(|(&k, &v)| (v, k)).collect();
    let recovered: Vec<&str> = idx.iter().map(|&i| inverse[&(i as usize)]).collect();

    assert_eq!(recovered, labels);
    println!("{recovered:?}");
}
```

Building the `index → label` inverse once and reusing it is the idiom for reporting predictions in their original labels, which is what [4.3.5](#435-picking-the-target-format-one-hot-vs-sparse-integer) closes with.

## 4.3.5. Picking the target format: one-hot vs sparse integer

Multi-class classification in the [neural-network stack](../Chapter-03/3.1._The_Sequential_Model.md) offers two losses, and your choice of loss dictates the encoding you feed to `fit`. The two are numerically equivalent — same forward value, same gradient — they differ only in how the target is stored. See [3.3. Loss Functions](../Chapter-03/3.3._Loss_Functions.md) for the loss side of this.

| | `CategoricalCrossEntropy` | `SparseCategoricalCrossEntropy` |
|---|---|---|
| Target shape | `[batch, num_classes]` one-hot | `[batch, 1]` integer class id |
| Build it with | `to_categorical` (+ `f64 → f32`) | reshape codes to a column, cast to `f32` |
| Target storage | `O(batch × classes)` | `O(batch)` |
| `from_logits` flag | yes | yes |

`CategoricalCrossEntropy` wants the full one-hot matrix. Because `to_categorical` returns `f64` but `Tensor` is `f32`, the `.mapv(|v| v as f32)` cast is mandatory — skip it and the types will not line up with your `f32` feature matrix:

```rust
use ndarray::array;
use rustyml::neural_network::{
    layers::{Activation, Dense},
    losses::CategoricalCrossEntropy,
    optimizers::Adam,
    sequential::Sequential,
};
use rustyml::utils::to_categorical;

fn main() {
    let x = array![
        [5.1f32, 3.5, 1.4, 0.2],
        [4.9, 3.0, 1.4, 0.2],
        [6.2, 3.4, 5.4, 2.3],
        [5.9, 3.0, 5.1, 1.8],
        [6.0, 2.2, 4.0, 1.0],
        [5.5, 2.4, 3.8, 1.1],
    ]
    .into_dyn();
    let labels = array![0i32, 0, 2, 2, 1, 1];

    // One-hot, then bridge f64 -> f32 and into the dynamic-dim Tensor shape.
    let y = to_categorical(&labels, None)
        .unwrap()
        .mapv(|v| v as f32)
        .into_dyn();

    let mut model = Sequential::new();
    model
        .add(Dense::new(4, 8, Activation::ReLU).unwrap())
        .add(Dense::new(8, 3, Activation::Softmax).unwrap())
        .compile(
            Adam::new(0.01, 0.9, 0.999, 1e-8, 0.0).unwrap(),
            CategoricalCrossEntropy::new(false),
        );

    model.fit(&x, &y, 5).unwrap();
    let preds = model.predict(&x).unwrap();
    println!("prediction shape: {:?}", preds.shape()); // [6, 3]
}
```

`SparseCategoricalCrossEntropy` skips the one-hot entirely. It reads the class id directly from a `[batch, 1]` tensor, so there is no matrix to build — you just reshape your integer codes into a column and cast to `f32`. With two classes that saves little; with thousands of classes (word vocabularies, product catalogs) the one-hot matrix is almost all zeros and the sparse form saves both the memory and the allocation:

```rust
use ndarray::{array, Axis};
use rustyml::neural_network::{
    layers::{Activation, Dense},
    losses::SparseCategoricalCrossEntropy,
    optimizers::Adam,
    sequential::Sequential,
};

fn main() {
    let x = array![
        [5.1f32, 3.5, 1.4, 0.2],
        [4.9, 3.0, 1.4, 0.2],
        [6.2, 3.4, 5.4, 2.3],
        [5.9, 3.0, 5.1, 1.8],
        [6.0, 2.2, 4.0, 1.0],
        [5.5, 2.4, 3.8, 1.1],
    ]
    .into_dyn();

    // Sparse targets: integer class ids as a [batch, 1] f32 column. No one-hot.
    let labels = array![0i32, 0, 2, 2, 1, 1];
    let y = labels.mapv(|v| v as f32).insert_axis(Axis(1)).into_dyn();

    let mut model = Sequential::new();
    model
        .add(Dense::new(4, 8, Activation::ReLU).unwrap())
        .add(Dense::new(8, 3, Activation::Softmax).unwrap())
        .compile(
            Adam::new(0.01, 0.9, 0.999, 1e-8, 0.0).unwrap(),
            SparseCategoricalCrossEntropy::new(false),
        );

    model.fit(&x, &y, 5).unwrap();
    println!("target shape fed to fit: {:?}", y.shape()); // [6, 1]
}
```

Note the required `[batch, 1]` shape for the sparse target: `insert_axis(Axis(1))` turns the length-`batch` label vector into a column. `SparseCategoricalCrossEntropy` validates this and rejects a bare `[batch]` vector, non-integer values, and any label `>= num_classes` with a descriptive error rather than an out-of-bounds panic inside a worker thread.

The full loop for a string-labeled dataset ties all of this together — encode with a mapping, train, predict, and decode back to the original labels for reporting:

```rust
use ndarray::{array, Ix2};
use rustyml::neural_network::{
    layers::{Activation, Dense},
    losses::CategoricalCrossEntropy,
    optimizers::Adam,
    sequential::Sequential,
};
use rustyml::utils::{to_categorical_with_mapping, to_sparse_categorical};
use std::collections::HashMap;

fn main() {
    let x = array![[0.1f32, 0.2], [0.9, 0.8], [0.15, 0.25], [0.85, 0.95]].into_dyn();
    let raw = vec!["cat", "dog", "cat", "dog"];

    // Encode targets and keep the mapping; size the output layer from it.
    let (y_f64, mapping) = to_categorical_with_mapping(&raw, None).unwrap();
    let y = y_f64.mapv(|v| v as f32).into_dyn();
    let n_classes = mapping.len();

    let mut model = Sequential::new();
    model
        .add(Dense::new(2, 8, Activation::ReLU).unwrap())
        .add(Dense::new(8, n_classes, Activation::Softmax).unwrap())
        .compile(
            Adam::new(0.01, 0.9, 0.999, 1e-8, 0.0).unwrap(),
            CategoricalCrossEntropy::new(false),
        );
    model.fit(&x, &y, 5).unwrap();

    // Predict -> f32 probabilities -> f64 2D -> argmax indices -> original labels.
    let probs = model.predict(&x).unwrap();
    let probs_2d = probs.mapv(|v| v as f64).into_dimensionality::<Ix2>().unwrap();
    let class_ids = to_sparse_categorical(&probs_2d).unwrap();

    let inverse: HashMap<usize, String> =
        mapping.iter().map(|(k, &v)| (v, k.to_string())).collect();
    let predicted: Vec<String> = class_ids
        .iter()
        .map(|&i| inverse[&(i as usize)].clone())
        .collect();
    println!("predicted labels: {predicted:?}");
}
```

The two type conversions on the return path are the counterparts of the cast on the way in: `predict` yields `f32` in the dynamic `ArrayD` shape, and `to_sparse_categorical` wants a 2D `f64` array, so you cast to `f64` and fix the dimensionality to `Ix2` before decoding. Sizing the output layer from `mapping.len()` rather than a hard-coded constant keeps the network in step with the encoding.

## 4.3.6. Ordinal encoding: when integer codes lie

There is a real trap hiding in how convenient integer codes are. For a **classification target** fed to a cross-entropy loss, the code is just an identity — the loss looks up "which column is the true one" and never compares `2` against `1` as magnitudes, so `SparseCategoricalCrossEntropy` treating class `2` as a bare integer is perfectly safe. The trap is reaching for the same integer codes to encode a categorical **input feature** for a model that does arithmetic on its inputs. Linear and [logistic regression](../Chapter-02/2.2._Logistic_Regression.md), SVMs, and every distance-based method ([KNN](../Chapter-02/2.3._K_Nearest_Neighbors.md), KMeans) will read those codes as numbers on a line: with `red=0, green=1, blue=2`, the model is told green sits exactly between red and blue and that blue is "twice" green. Those relationships are fabricated, and a linear model will happily fit a coefficient to them and generalize the fiction.

The fix is to one-hot the categorical feature so no false order or spacing survives — every category becomes its own axis, mutually equidistant:

```rust
use ndarray::{array, concatenate, Axis};
use rustyml::utils::to_categorical;

fn main() {
    let price = array![[10.0f64], [12.0], [11.0]];
    let color_code = array![0i32, 2, 1]; // red, blue, green

    // WRONG for a linear / distance model: the codes invent an order and spacing.
    let color_ordinal = color_code.mapv(|c| c as f64).insert_axis(Axis(1));
    let ordinal = concatenate(Axis(1), &[price.view(), color_ordinal.view()]).unwrap();
    assert_eq!(ordinal.shape(), &[3, 2]);

    // RIGHT: one-hot so red, green, blue are mutually equidistant.
    let color_onehot = to_categorical(&color_code, None).unwrap();
    let encoded = concatenate(Axis(1), &[price.view(), color_onehot.view()]).unwrap();
    assert_eq!(encoded.shape(), &[3, 4]); // price + 3 color columns
    println!("{encoded:?}");
}
```

When is a bare integer code actually fine as a feature? Two cases. When the category is genuinely ordinal and the integers respect its order — `small=0, medium=1, large=2` — the "order" the model reads is real, though even then the *spacing* is an assumption. And [decision trees / tree ensembles](../Chapter-02/2.4._Decision_Trees.md) split on thresholds rather than multiplying features by weights, so they tolerate arbitrary integer codes far better than a linear model does, at the cost of needing deeper splits to isolate individual categories. For everything linear or distance-based with a nominal feature, one-hot. The extra columns are the price of not lying to the model about geometry. Note that one-hot columns pair naturally with the scalers in [4.2. Standardization and Normalization](./4.2._Standardization_and_Normalization.md) — the indicator columns are already `0`/`1` and usually left as-is while the continuous features are scaled.

## 4.3.7. Unseen categories and the stateless model

Because these functions are stateless, the scikit-learn question "what happens when `transform` meets a category it didn't see during `fit`?" has a different answer here: there is no `fit` and no stored encoder, so a fresh call to `to_categorical_with_mapping` on new data builds a **new** mapping from whatever that data contains — and with first-seen ordering, that mapping can assign different columns than the one your model trained against. Re-encoding your inference data from scratch is the actual footgun, silent because it produces a valid-looking matrix that means something different.

The correct pattern is to encode once, keep the returned mapping, and at inference time look labels up against that saved mapping instead of re-encoding. The one sharp edge to remember: indexing the map with `mapping[key]` panics if the key is absent, which is exactly the unseen-category case. Use `.get` so a novel label is a value you handle, not a crash:

```rust
use rustyml::utils::to_categorical_with_mapping;

fn main() {
    let train = vec!["red", "green", "blue"];
    let (_matrix, mapping) = to_categorical_with_mapping(&train, None).unwrap();

    // At inference you hold the mapping yourself and look labels up.
    let incoming = ["green", "purple"]; // "purple" was never seen at fit time
    for label in incoming {
        match mapping.get(label) {
            Some(&idx) => println!("{label} -> class {idx}"),
            None => println!("{label} -> UNSEEN, route to a fallback"),
        }
    }
    // Indexing panics on a missing key, so prefer `.get`:
    // let _ = mapping["purple"]; // would panic: key not found
}
```

What you do with an unseen label is a modeling decision the library leaves to you — drop the row, route it to a reserved "unknown" column you set aside by training with an explicit `num_classes` one wider than the observed classes, or reject the request. RustyML does not invent an "unknown" bucket for you, which is the honest behavior: a category the model never trained on has no learned representation, and silently folding it into an existing class would only hide that.

The mapping is an ordinary `AHashMap`, so persisting it is your job too — it is not part of the model weights that [save/load](../Chapter-03/3.9._Saving_and_Loading_Weights.md) handle. A model reloaded without its label mapping can still emit column indices, but nothing can turn those indices back into `"cat"` and `"dog"`. Serialize the mapping alongside the weights (serde handles the `HashMap` directly) and you have a complete, reproducible pipeline; see [7.2. Model Persistence in Depth](../Chapter-07/7.2._Model_Persistence_in_Depth.md) for the broader story.
