# 2.3. K-Nearest Neighbors

K-Nearest Neighbors (KNN) is the algorithm that does the least at training time and the most at prediction time. RustyML implements it as `KNN<T>`, a generic classifier over any label type `T` you can hash and compare. If you are coming from scikit-learn's `KNeighborsClassifier`, the mental model transfers almost verbatim, but a few things are RustyML-specific: the label type is generic (not just integers), the distance metric is a single `DistanceCalculationMetric` enum shared with [DBSCAN](./2.8._DBSCAN.md) and the clustering metrics, tie-breaking is fully deterministic and defined by label-encounter order, and there is a separate parallel prediction entry point. This page walks the real API and the design choices behind it.

## 2.3.1. Lazy Learning: Where the Cost Lives

KNN is the purest lazy learner in the crate. Its `fit` does almost no learning: it validates the input, copies the training feature matrix, encodes the labels to compact `usize` indices so voting is a cheap integer operation, and returns. Nothing is compressed into weights or a tree of splits the way [logistic regression](./2.2._Logistic_Regression.md) or a [decision tree](./2.4._Decision_Trees.md) would. All of the real work is deferred to `predict`.

That deferral has a concrete cost. Because there is no trained model to consult, classifying one query means measuring its distance to training rows and keeping the k smallest. On the brute-force path, for `n_test` queries against `n_train` training rows in `d` dimensions, the distance stage is `O(n_train * n_test * d)`, plus an `O(n_train)` partial selection per query — a Quickselect via `select_nth_unstable`, not a full `O(n_train log n_train)` sort — to pull out the k nearest. Memory is `O(n_train * d)`: the entire training set stays resident for the life of the model, because it *is* the model. This is the tradeoff you accept for a non-parametric classifier with no training phase and no assumptions about the decision boundary's shape.

Two consequences follow directly. First, prediction latency scales with your training-set size, so KNN that is fast on a few thousand rows becomes the bottleneck on a few hundred thousand. Second, everything about accuracy is decided at query time by geometry, which is why the distance metric and feature scaling (below) matter more here than in almost any other model.

## 2.3.2. Constructing a Classifier

The constructor takes only `k`. Everything else has a default and is set through chained builder methods:

```rust,ignore
// Core surface (from src/machine_learning/neighbors/knn.rs)
pub fn new(k: usize) -> Result<Self, Error>;                       // Err if k == 0
pub fn with_weighting_strategy(self, s: WeightingStrategy) -> Self;
pub fn with_metric(self, m: DistanceCalculationMetric) -> Result<Self, Error>; // validates Minkowski p

pub fn fit<S1, S2>(&mut self, x: &ArrayBase<S1, Ix2>, y: &ArrayBase<S2, Ix1>)
    -> Result<&mut Self, Error>;
pub fn predict<S>(&self, x: &ArrayBase<S, Ix2>) -> Result<Array1<T>, Error>;
pub fn predict_parallel<S>(&self, x: &ArrayBase<S, Ix2>) -> Result<Array1<T>, Error>; // T: Sync + Send
pub fn fit_predict<S1, S2>(&mut self, x: &..., y: &...) -> Result<Array1<T>, Error>;
```

`new` is the only fallible part of construction that everyone hits: it returns `Error::InvalidParameter` when `k == 0`. `with_metric` is also fallible, but only because it validates the Minkowski order (covered in the next section); `with_weighting_strategy` cannot fail and returns `Self` directly. The result is that a fully specified builder chain ends on the metric's `?` or `.unwrap()`, matching the order used throughout the test suite.

The two enums that parameterize the model:

| Parameter | Type | Variants | Default |
| --- | --- | --- | --- |
| Weighting | `WeightingStrategy` | `Uniform`, `Distance` | `Uniform` |
| Metric | `DistanceCalculationMetric` | `Euclidean`, `Manhattan`, `Minkowski(f64)` | `Euclidean` |

`KNN::<T>::default()` gives you `k = 5` with `Uniform` weighting and `Euclidean` distance — the same defaults you would reach by calling `new(5)` and touching nothing else. Read the stored configuration back with `get_k`, `get_weighting_strategy`, `get_metric`, and `get_x_train` (which returns `Option<&Array2<f64>>`, `None` before `fit`).

The label type `T` is genuinely generic: anything that is `Clone + Hash + Eq` works, so integer class codes, `String` labels, or your own enum are all fine. `fit` encodes the labels it sees into indices in first-appearance order and stores the reverse map; `predict` decodes back to the original `T`, so you get `Array1<String>` out if you fed `Array1<String>` in. Note this is a classifier only — there is no KNN *regressor* in the crate. If you need neighbor-averaged regression, you would build it yourself on top of the distance primitives in [Chapter 6.1](../Chapter-06/6.1._Distance_Metrics.md).

A first end-to-end run, using both the sequential and parallel entry points:

```rust
use ndarray::array;
use rustyml::machine_learning::{DistanceCalculationMetric, KNN, WeightingStrategy};

fn main() {
    let x_train = array![
        [1.0, 2.0],
        [2.0, 3.0],
        [3.0, 4.0],
        [6.0, 6.0],
        [7.0, 7.0],
        [8.0, 8.0],
    ];
    let y_train = array![0, 0, 0, 1, 1, 1];

    let mut knn = KNN::new(3)
        .unwrap()
        .with_weighting_strategy(WeightingStrategy::Uniform)
        .with_metric(DistanceCalculationMetric::Euclidean)
        .unwrap();

    knn.fit(&x_train, &y_train).unwrap();

    let x_test = array![[1.5, 2.5], [7.5, 7.0]];
    let seq = knn.predict(&x_test).unwrap();
    let par = knn.predict_parallel(&x_test).unwrap();

    assert_eq!(seq, par); // deterministic: both paths agree exactly
    println!("k = {}", knn.get_k());
    println!("predictions: {:?}", seq);
}
```

`fit` guards against the mistakes that would otherwise surface as panics at predict time. It returns `Error::EmptyInput` for a zero-row `x`, `Error::NonFinite` if `x` holds a NaN or infinity, `Error::DimensionMismatch` when `y.len()` differs from `x.nrows()`, and `Error::InvalidInput` when you have fewer training samples than `k` — you cannot ask for 5 neighbors from 3 points. `predict` and `predict_parallel` add `Error::NotFitted` when called before `fit`, plus `EmptyInput`, `DimensionMismatch` (wrong feature count against training), and `NonFinite` for the query matrix. See [Error Handling](../Chapter-01/1.6._Error_Handling.md) for the full `Error` enum.

`fit_predict` is a convenience that fits and then predicts on the *same* training matrix. With `k = 1` it returns the training labels unchanged, because every point's nearest neighbor is itself at distance zero — useful as a sanity check, useless as an accuracy estimate. For a real generalization estimate, hold data out with [Train-Test Split](../Chapter-04/4.1._Train_Test_Split.md) and score with the [classification metrics](../Chapter-05/5.2._Classification_Metrics.md).

## 2.3.3. Distance Metrics and the Minkowski Order

The metric decides what "nearest" means, and RustyML exposes three through one enum shared across the library. `Euclidean` (L2) is the straight-line default. `Manhattan` (L1) sums absolute coordinate differences and is the metric to reach for when features are independent axes measured in different units, or when you want robustness to a single outlying coordinate. `Minkowski(p)` generalizes both: `p = 1` reduces to Manhattan and `p = 2` reduces to Euclidean, exactly (the test suite asserts these equalities on shared data), while intermediate or larger `p` interpolate and extrapolate the geometry of the unit ball.

`with_metric` validates the Minkowski order and returns `Error::InvalidParameter` if `p < 1` or `p` is not finite. This is a real constraint, not a stylistic one: orders below 1 violate the triangle inequality, so the result is no longer a metric, and it would break the pruning logic of the kd-tree index described later. The bare distance function `minkowski_distance_row` *panics* on `p < 1`; routing through `with_metric` converts that into a recoverable `Err` you can handle. Passing `Minkowski(2.0)` is legal and numerically identical to `Euclidean`, but prefer the `Euclidean` variant when you want L2 — it enables a matrix-multiply fast path (section 2.3.7) that the general Minkowski code does not have.

```rust
use ndarray::array;
use rustyml::machine_learning::{DistanceCalculationMetric, KNN, WeightingStrategy};

fn main() {
    let x_train = array![[3.0, 0.0], [0.0, 4.0]];
    let y_train = array![0, 1];

    let mut knn = KNN::new(1)
        .unwrap()
        .with_weighting_strategy(WeightingStrategy::Uniform)
        .with_metric(DistanceCalculationMetric::Minkowski(3.0))
        .unwrap();
    knn.fit(&x_train, &y_train).unwrap();

    // Under L3: dist((0,3),(3,0)) = 54^(1/3) ~= 3.78 > dist((0,3),(0,4)) = 1
    let x_test = array![[0.0, 3.0]];
    println!("{:?}", knn.predict(&x_test).unwrap()); // nearest is (0,4) -> class 1
}
```

The metric abstraction is described in more depth, with the "comparable-distance" trick that lets the spatial index skip the final root, in [Chapter 6.1 Distance Metrics](../Chapter-06/6.1._Distance_Metrics.md).

## 2.3.4. Weighting Strategies and Tie-Breaking

Once the k neighbors are found, `WeightingStrategy` decides how their labels combine into one prediction.

`Uniform` is a plain majority vote: each of the k neighbors contributes one vote to its class, and the class with the most votes wins. `Distance` weights each neighbor by `1.0 / distance`, so a neighbor twice as close counts twice as much. Distance weighting is what you want when `k` is large enough that the neighbor set reaches into genuinely dissimilar points — the far ones still vote, but their influence decays — and it softens the sensitivity to the exact value of `k`.

Distance weighting has one edge case the implementation handles explicitly: a query that coincides with a training point sits at distance zero, and `1.0 / 0.0` is infinity. Rather than propagate that, the code checks for exact matches first. If any of the k neighbors is at distance exactly `0.0`, only those exact-match neighbors vote, by count, and the rest are ignored. This makes an exact hit behave like a lookup, which is almost always what you want.

```rust
use ndarray::array;
use rustyml::machine_learning::{DistanceCalculationMetric, KNN, WeightingStrategy};

fn main() {
    let x_train = array![[0.0, 0.0], [10.0, 0.0]];
    let y_train = array![0, 1];

    let mut knn = KNN::new(2)
        .unwrap()
        .with_weighting_strategy(WeightingStrategy::Distance)
        .with_metric(DistanceCalculationMetric::Euclidean)
        .unwrap();
    knn.fit(&x_train, &y_train).unwrap();

    // Both points are always in the k=2 set; the nearer one wins the weighted vote.
    let x_test = array![[1.0, 0.0], [9.0, 0.0]];
    println!("weighted: {:?}", knn.predict(&x_test).unwrap()); // [0, 1]

    // Exact match short-circuits the 1/0 problem: it votes by count, not weight.
    let x_exact = array![[0.0, 0.0]];
    println!("exact:    {:?}", knn.predict(&x_exact).unwrap()); // [0]
}
```

Tie-breaking is where RustyML makes a deliberate, documented choice that differs from the "arbitrary" behavior you might expect. When two classes are tied — equal vote counts under `Uniform`, or equal summed weight under `Distance` — the winner is the class with the *smallest encoded index*. Crucially, that index is not the smallest label value; it is assigned in the order labels are first encountered during `fit`. If your training targets begin with label `7` and later contain label `3`, then `7` encodes to index 0 and wins ties against `3`. The upshot is that ties are broken **deterministically and reproducibly**, but the resolution depends on training-row order, so reordering your data can flip a tied prediction. This determinism is also what lets `predict` and `predict_parallel` guarantee identical results.

## 2.3.5. Choosing k

`k` is the one knob that most changes behavior, and it is a straight bias-variance dial. Small `k` (the extreme being `k = 1`) gives a low-bias, high-variance classifier: the decision boundary hugs the data and follows every wrinkle, including mislabeled points and noise. Large `k` averages over a wider neighborhood, lowering variance but raising bias — push it far enough and the model drifts toward always predicting the globally most common class, and it starts to wash out small but real minority regions. A common starting point is `k` near the square root of the training-set size, then tuned against a validation split; there is no substitute for measuring.

The classic advice to use an **odd `k` for binary classification** is about ties. With RustyML's deterministic tie-break an even `k` never errors — a 50/50 split is resolved by first-encounter order — but that resolution can feel arbitrary and is data-order dependent, so an odd `k` keeps binary votes from ever landing on it. (Distance weighting largely sidesteps the issue too, since exact ties in summed real-valued weights are unlikely.) Note also the hard floor from section 2.3.2: `fit` rejects any `k` greater than the number of training samples.

This example makes the variance concrete. A single mislabeled point is dropped into the class-0 region, and a query is placed right next to it. At `k = 1` the noise wins; at `k = 3` and `k = 5` the surrounding genuine class-0 points outvote it:

```rust
use ndarray::array;
use rustyml::machine_learning::{DistanceCalculationMetric, KNN, WeightingStrategy};

fn main() {
    // Two clean clusters plus one mislabeled point at (2.5, 0): it sits inside
    // the class-0 region but carries the class-1 label.
    let x_train = array![
        [0.0, 0.0], [1.0, 0.0], [2.0, 0.0], [3.0, 0.0],     // class 0
        [10.0, 0.0], [11.0, 0.0], [12.0, 0.0], [13.0, 0.0], // class 1
        [2.5, 0.0],                                         // noise, class 1
    ];
    let y_train = array![0, 0, 0, 0, 1, 1, 1, 1, 1];

    let x_test = array![[2.4, 0.0]]; // right next to the noisy point

    for k in [1usize, 3, 5] {
        let mut knn = KNN::new(k)
            .unwrap()
            .with_weighting_strategy(WeightingStrategy::Uniform)
            .with_metric(DistanceCalculationMetric::Euclidean)
            .unwrap();
        knn.fit(&x_train, &y_train).unwrap();
        let pred = knn.predict(&x_test).unwrap();
        println!("k = {k}: prediction = {}", pred[0]);
    }
}
```

The prediction flips from the noisy label to the correct one as `k` grows:

```text
k = 1: prediction = 1
k = 3: prediction = 0
k = 5: prediction = 0
```

That single-point sensitivity at `k = 1` is exactly the high-variance failure mode; increasing `k` trades it for the smoother, more biased boundary.

## 2.3.6. Feature Scaling Is Not Optional

This is the mistake that bites people most, so it gets its own section. KNN ranks neighbors by raw distance, and every metric here sums per-coordinate differences. If one feature ranges over the thousands and another over `[0, 1]`, the large-range feature dominates the distance and the small one is invisible — regardless of which one actually carries the label. Unlike a linear model that can learn a small coefficient for a large-scale feature, KNN has no coefficients to compensate. You must scale the features yourself before fitting.

The example below encodes the label entirely in a small-range column while a large-range column is uninformative. On raw features the large column dictates the nearest neighbor and the prediction is wrong; after standardizing with the training set's per-column mean and standard deviation (applied to both train and query), the informative column is finally on equal footing and the prediction is right:

```rust
use ndarray::{array, Axis};
use rustyml::machine_learning::KNN;

fn main() {
    // Column 0 spans the ~1000s and is uninformative; column 1 in {0, 10} carries the label.
    let x_train = array![
        [1000.0, 0.0],  // class 0
        [3000.0, 0.0],  // class 0
        [1050.0, 10.0], // class 1
        [3050.0, 10.0], // class 1
    ];
    let y_train = array![0, 0, 1, 1];

    // Column 1 = 9.0 says class 1; column 0 = 1010.0 is closest to a class-0 row.
    let x_test = array![[1010.0, 9.0]];

    let mut raw = KNN::new(1).unwrap();
    raw.fit(&x_train, &y_train).unwrap();
    let raw_pred = raw.predict(&x_test).unwrap();

    // Standardize with statistics computed on the TRAINING set, applied to both.
    let mean = x_train.mean_axis(Axis(0)).unwrap();
    let std = x_train.std_axis(Axis(0), 0.0);
    let x_train_s = (&x_train - &mean) / &std;
    let x_test_s = (&x_test - &mean) / &std;

    let mut scaled = KNN::new(1).unwrap();
    scaled.fit(&x_train_s, &y_train).unwrap();
    let scaled_pred = scaled.predict(&x_test_s).unwrap();

    println!("raw features:  {:?}", raw_pred);    // dominated by column 0 -> [0]
    println!("standardized:  {:?}", scaled_pred); // respects column 1  -> [1]
}
```

The example scales by hand so it stays self-contained, and it does the right thing statistically: the mean and standard deviation come from the training data only and are then applied to the query, never re-estimated on the test set. In real pipelines use the crate's [`standardize`](../Chapter-04/4.2._Standardization_and_Normalization.md) helper (or `normalize`) rather than open-coding it, and remember that whatever transform you fit on the training set must be the one you apply to new data — re-fitting on the test set leaks information. Standardization to zero mean and unit variance is the usual choice; min-max normalization is the alternative when you want features bounded to a fixed range.

## 2.3.7. Sequential vs Parallel Prediction, the kd-tree, and the Euclidean Fast Path

RustyML gives you two prediction entry points. `predict` is sequential and works for any label type. `predict_parallel` fans the per-query work across a Rayon pool and is the one to use for large query batches, at the cost of requiring `T: Sync + Send`. Both build any shared index once, up front and single-threaded, before the queries run; `predict_parallel` then parallelizes over test rows. Because the tie-break is deterministic, the two paths return bit-identical label arrays — the test suite asserts this across `Uniform`, `Distance`, and large-`k` configurations, so you can develop with `predict` and switch to `predict_parallel` for throughput without changing a single result.

Under the hood the search takes one of two routes. In low dimensions — at most 8 features — `predict` builds a **kd-tree** over the training data on first use and caches it, giving average-case neighbor lookups that beat scanning every row. Above 8 features the tree stops pruning effectively (the curse of dimensionality: nearly everything is roughly equidistant), so the code falls back to a **brute-force scan** and the `O(n_train * n_test * d)` cost from section 2.3.1 applies in full. This 8-feature ceiling is a single-shape calibration, not a universal law — clustered data and different dataset sizes shift the crossover — but it is the fixed threshold the current implementation uses.

The brute-force Euclidean case gets a dedicated optimization. Squared Euclidean distance expands to `||x||^2 + ||t||^2 - 2 * x . t`, so the only per-pair term is the dot product `x . t`, which is a matrix multiply. RustyML precomputes the training rows' squared norms once, shares them across every query, and computes the cross terms through its GEMM/GEMV matrix-multiply kernels (which dispatch to the `gemm` crate's SIMD backend) — blocking the work to stay cache-resident on large training sets. Manhattan and Minkowski have no such algebraic shortcut and fall back to a straightforward per-pair metric scan, which is another reason to prefer the `Euclidean` variant when L2 is what you want. The kd-tree is rebuilt lazily and dropped whenever you re-`fit`, so a refitted model never serves stale neighbors. For the broader story on the parallelism gates and tuning, see [Performance Tuning and Parallelism](../Chapter-07/7.3._Performance_Tuning_and_Parallelism.md).

## 2.3.8. Persistence

`KNN<T>` serializes with `save_to_path` / `load_from_path` when `T` is `Serialize + Deserialize` (as `i32` and `String` are). Persistence writes the compact postcard binary format regardless of the file extension you choose, and it stores exactly what defines the model: `k`, the weighting strategy, the metric, the training matrix, and the label encoding. The kd-tree is *not* serialized — it is marked `#[serde(skip)]` and rebuilt lazily on the loaded model's first `predict` — so a reloaded classifier produces predictions identical to the original with no extra ceremony.

```rust
use ndarray::array;
use rustyml::machine_learning::{DistanceCalculationMetric, KNN};

fn main() {
    let x_train = array![
        [0.0, 0.0], [1.0, 0.0], [2.0, 0.0],
        [10.0, 0.0], [11.0, 0.0], [12.0, 0.0],
    ];
    let y_train = array![0, 0, 0, 1, 1, 1];

    let mut knn = KNN::new(3)
        .unwrap()
        .with_metric(DistanceCalculationMetric::Manhattan)
        .unwrap();
    knn.fit(&x_train, &y_train).unwrap();

    let path = "knn_model.bin";
    knn.save_to_path(path).unwrap();

    // Rebuilds its kd-tree lazily on first predict; k, metric, and labels are restored.
    let loaded = KNN::<i32>::load_from_path(path).unwrap();

    let x_test = array![[0.5, 0.0], [11.5, 0.0]];
    assert_eq!(
        knn.predict(&x_test).unwrap(),
        loaded.predict(&x_test).unwrap()
    );
    println!("round-trip predictions match");

    std::fs::remove_file(path).unwrap();
}
```

Because a KNN model carries its entire training set, the serialized file grows with `n_train * d` — persistence here is saving your data plus a little metadata, not a handful of learned parameters. If model size matters, that alone is a reason to consider a parametric classifier. [Model Persistence in Depth](../Chapter-07/7.2._Model_Persistence_in_Depth.md) covers the format and its guarantees.

For completeness: `KNN<T>` also implements the crate's shared `Fit` and `Predict` traits from `machine_learning::traits`, where `Fit` takes the training data as a `(x, y)` tuple. The inherent `fit`/`predict`/`predict_parallel` methods shown throughout this page are what you will normally call; the traits exist so generic code can treat estimators uniformly.
