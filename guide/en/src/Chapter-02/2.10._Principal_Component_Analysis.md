# 2.10. Principal Component Analysis

Principal Component Analysis finds an orthonormal set of directions in feature space — the principal axes — ordered so the first captures the most variance in your data, the second the most of what remains orthogonal to the first, and so on down the line. Projecting onto the top `k` axes gives the `k`-dimensional linear subspace that preserves the most variance, which is exactly the same subspace that minimizes squared reconstruction error. That dual reading (maximize retained variance = minimize what you throw away) is the whole intuition, and it is why PCA is the default first move for compressing, denoising, or plotting high-dimensional data.

RustyML's `PCA` mirrors `sklearn.decomposition.PCA`: fit on a feature matrix, `transform` to scores, `inverse_transform` back. If you are arriving from scikit-learn, three things will surprise you, and this page leans into all three. First, it centers but never scales, so the numbers you feed it matter more than in a pipeline that standardizes for you. Second, the solver knob is an enum called `SVDSolver` with three concrete strategies, and the right choice is driven by how many features you have and how many components you want. Third, every factorization underneath is hand-rolled pure Rust — no LAPACK, no BLAS — which is what makes the solver tradeoffs concrete rather than academic.

## 2.10.1. The surface you work with

Everything lives under `rustyml::machine_learning::decomposition::{PCA, SVDSolver}`, and both are re-exported through [the prelude](../Chapter-01/1.5._The_Prelude_and_Imports.md). The model is unsupervised: it takes an `f64` feature matrix with samples as rows and features as columns, and there are no labels anywhere.

```rust,ignore
// Construction — n_components must be > 0, checked here
PCA::new(n_components: usize) -> Result<PCA, Error>
PCA::default()                                         // n_components = 2, Full solver
pca.with_svd_solver(solver: SVDSolver) -> PCA          // builder, consumes and returns self

// Learning and projecting — fit takes &mut self
pca.fit(&x)                -> Result<&mut PCA, Error>
pca.transform(&x)          -> Result<Array2<f64>, Error>   // (n_samples, n_components)
pca.fit_transform(&x)      -> Result<Array2<f64>, Error>
pca.inverse_transform(&scores) -> Result<Array2<f64>, Error> // (n_samples, n_features)

// Fitted state — every getter is None before fit, Some(&…) after
pca.get_mean()                     -> Option<&Array1<f64>>   // per-feature centering mean
pca.get_components()               -> Option<&Array2<f64>>   // (n_components, n_features), rows are axes
pca.get_explained_variance()       -> Option<&Array1<f64>>
pca.get_explained_variance_ratio() -> Option<&Array1<f64>>
pca.get_singular_values()          -> Option<&Array1<f64>>
pca.get_n_components() -> usize
pca.get_svd_solver()   -> SVDSolver
pca.get_n_samples()    -> Option<usize>
pca.get_n_features()   -> Option<usize>
```

The constructor validates only that `n_components > 0`; the harder bound, `n_components <= min(n_samples, n_features)`, is checked at `fit` time because it depends on the data. The getters double as your "is it fitted?" probe: they all hand back `None` until a successful `fit` fills them in. `get_components` returns the axes as **rows** of an `(n_components, n_features)` matrix — this is the scikit-learn `components_` layout, so `transform` is just centered data times `components.T`, and `inverse_transform` is scores times `components`.

Here is the whole loop on a tiny 2-D set, keeping one component:

```rust
use ndarray::array;
use rustyml::machine_learning::decomposition::PCA;

fn main() {
    let x = array![
        [2.5, 2.4],
        [0.5, 0.7],
        [2.2, 2.9],
        [1.9, 2.2],
        [3.1, 3.0],
        [2.3, 2.7],
    ];

    // fit_transform needs &mut self; it is fit followed by transform on the same data.
    let mut pca = PCA::new(1).unwrap();
    let scores = pca.fit_transform(&x).unwrap();

    println!("scores shape: {:?}", scores.shape()); // [6, 1]
    println!("mean:         {:?}", pca.get_mean().unwrap());
    println!("component:    {:?}", pca.get_components().unwrap());
    println!("variance:     {:?}", pca.get_explained_variance().unwrap());
    println!("ratio:        {:?}", pca.get_explained_variance_ratio().unwrap());
    println!("singular:     {:?}", pca.get_singular_values().unwrap());
}
```

`fit_transform(&x)` is not a fused shortcut with a different result — it literally calls `fit` then `transform` on the same matrix, so it is identical to doing the two steps yourself, and you use the two-step form whenever you need to project a *different* matrix (new samples) through an already-fitted model. Because `fit` returns `&mut Self`, you can also chain into a getter, but reading state back out through the `get_*` methods is the normal path.

## 2.10.2. It centers, it does not scale

Before decomposing anything, `fit` subtracts the per-feature mean and stores it in `get_mean()`. That is the *only* preprocessing it does. It does not divide by standard deviation, does not whiten, does not touch the units of your columns. `transform` re-uses the stored training mean to center new samples, and `inverse_transform` adds it back — so the mean is genuinely part of the fitted model, not a per-call convenience.

This is the single most common way to get a misleading PCA. Variance is not scale-invariant: a feature measured in millimeters carries a thousand-fold larger variance than the same feature in meters, and PCA will happily dedicate its first component to that one column. The fix is to standardize your features *before* fitting, which puts every column on unit variance so PCA compares them on equal footing. Reach for [`standardize`](../Chapter-04/4.2._Standardization_and_Normalization.md) with `StandardizationAxis::Column`; the difference is stark:

```rust
use ndarray::array;
use rustyml::machine_learning::decomposition::PCA;
use rustyml::utils::standardize::{standardize, StandardizationAxis};

fn main() {
    // Feature 0 lives in tiny units, feature 1 in huge ones. Same information content,
    // wildly different variance.
    let x = array![
        [0.1, 1000.0],
        [0.2, 1005.0],
        [0.3, 1002.0],
        [0.4,  998.0],
        [0.5, 1010.0],
    ];

    let mut raw = PCA::new(2).unwrap();
    raw.fit(&x).unwrap();
    println!("raw ratios:          {:?}", raw.get_explained_variance_ratio().unwrap());

    let xs = standardize(&x, StandardizationAxis::Column).unwrap();
    let mut scaled = PCA::new(2).unwrap();
    scaled.fit(&xs).unwrap();
    println!("standardized ratios: {:?}", scaled.get_explained_variance_ratio().unwrap());
}
```

On the raw data the first ratio is essentially `1.0` — column 1's numeric spread swamps everything and PC1 points almost exactly along it. After column standardization the two features contribute comparably and the ratios reflect the actual correlation structure. Whether you *should* standardize is a modeling decision (if your features are already in the same meaningful unit — pixel intensities, say — centering-only is the honest choice), but you should always make it deliberately, because rustyml will not make it for you. This is the "PCA on covariance vs. PCA on correlation" distinction from the statistics literature: standardizing first is exactly PCA of the correlation matrix.

## 2.10.3. Choosing a solver, and the pure-Rust machinery behind it

`SVDSolver` picks how the components are computed. The name is a slight misnomer — only one of the three variants literally forms an SVD — but the interface is uniform: whichever you choose, you get the same component rows, explained variances, and singular values out, just computed by a different route with different cost and accuracy.

```rust,ignore
pub enum SVDSolver {
    Full,             // default: exact eigendecomposition of the covariance matrix
    Randomized(u64),  // randomized range finder; the u64 seeds the sketch
    PowerIteration,   // deflated power iteration for the top-k eigenpairs
}
```

| Variant | What it computes | Reach for it when |
| --- | --- | --- |
| `Full` (default) | Builds the `d x d` covariance `XᵀX/(n-1)` and eigendecomposes it exactly (Householder tridiagonalization + implicit-shift QL). | Small to mid-sized data — roughly under 10,000 samples and features. Accurate to near machine precision; the safe default. |
| `Randomized(seed)` | Sketches `X` into a `k`-wide random subspace, runs a couple of subspace iterations, and takes a small SVD in the reduced space. Never materializes the `d x d` covariance. | Large, wide data (10,000+ features) where speed matters and a tiny approximation is acceptable. The `seed` makes the random sketch reproducible. |
| `PowerIteration` | Forms the covariance, then extracts only the top `k` eigenpairs by power iteration with Hotelling deflation instead of a full eigendecomposition. | You need only a handful of components (`k` far smaller than `d`) and want to skip the full `O(d³)` eigensolve. |

The cost picture is worth internalizing, because it is exactly what the benches probe. `Full` and `PowerIteration` both build the dense `d x d` covariance, so both pay `O(n·d²)` to form it and `O(d²)` memory to hold it; the difference is what happens next — `Full` does a complete `O(d³)` eigendecomposition, while `PowerIteration` extracts `k` eigenpairs with a bounded number of matrix-vector products each and deflates each one out before finding the next, which wins on compute precisely when `k << d`. `Randomized` is the one that never touches a `d x d` matrix at all: its working set is the `n x k` sketch and the `k x d` reduced projection, so it is the memory-frugal option when `d` is genuinely large. On small problems all three agree to several digits; the approximate solvers only start to matter, in either speed or drift, once the matrices grow.

```rust
use ndarray::array;
use rustyml::machine_learning::decomposition::{PCA, SVDSolver};

fn main() {
    let x = array![
        [2.5, 2.4],
        [0.5, 0.7],
        [2.2, 2.9],
        [1.9, 2.2],
        [3.1, 3.0],
        [2.3, 2.7],
        [2.0, 1.6],
        [1.0, 1.1],
    ];

    for solver in [SVDSolver::Full, SVDSolver::Randomized(42), SVDSolver::PowerIteration] {
        let mut pca = PCA::new(1).unwrap().with_svd_solver(solver);
        pca.fit(&x).unwrap();
        let sigma = pca.get_singular_values().unwrap();
        println!("{:?}: sigma_1 = {:.6}", solver, sigma[0]);
    }
}
```

Two honest caveats about the knobs that are *not* there. `PowerIteration` exposes no iteration count or tolerance — internally it runs up to 1000 iterations per component to a `1e-6` eigenvalue tolerance with a fixed seed, and none of that is user-tunable through the public API. `Randomized` exposes only its seed; the oversampling and the number of subspace iterations are fixed. So the entire configuration surface for PCA is `n_components` plus `with_svd_solver` — deliberately small. All of this rides on the crate's in-house `machine_learning::linalg` module, which reimplements symmetric eigendecomposition, SVD (one-sided Jacobi), and QR (modified Gram-Schmidt) directly on `ndarray` arrays, so there is no LAPACK dependency to install, link, or vendor. That is the same [pure-Rust numerics](../Chapter-06/6.0._Math_Utilities.md) posture the rest of the crate takes, and the covariance and projection multiplies underneath route through the parallel [`gemm`](../Chapter-06/6.2._Matrix_Multiplication.md) backend.

## 2.10.4. Reading the variance and choosing `n_components`

After a fit, three vectors describe how variance is distributed across the kept axes. `get_singular_values` returns the singular values `σ_i` of the centered data in descending order. `get_explained_variance` returns `σ_i² / (n − 1)`, i.e. the actual variance along each component in the data's own units. `get_explained_variance_ratio` divides each of those by the **total** variance of the centered data — the full trace, summed over *all* features, not just the ones you kept — so each entry is the fraction of overall variance that component accounts for. That denominator choice matters: if you keep fewer components than features, the ratios sum to less than one, and the shortfall is precisely the variance you discarded.

That property is what makes the ratio the right tool for choosing `n_components`. The standard recipe is a scree/cumulative rule: fit the full-rank decomposition once, read the cumulative ratio, and keep the smallest number of axes that clears a variance target you care about (90%, 95%, 99%).

```rust
use ndarray::array;
use rustyml::machine_learning::decomposition::PCA;

fn main() {
    // 8 samples, 3 features; feature 2 is almost a linear echo of feature 0,
    // so the data is effectively low-rank.
    let x = array![
        [1.0, 0.2, 1.19],
        [2.0, 0.1, 2.09],
        [3.0, 0.4, 3.38],
        [4.0, 0.2, 4.19],
        [5.0, 0.5, 5.48],
        [6.0, 0.3, 6.29],
        [7.0, 0.1, 7.09],
        [8.0, 0.6, 8.58],
    ];

    // Fit the full decomposition (n_components = min(n_samples, n_features) = 3),
    // then decide how many axes to actually keep.
    let mut pca = PCA::new(3).unwrap();
    pca.fit(&x).unwrap();

    let ratio = pca.get_explained_variance_ratio().unwrap();
    let mut cumulative = 0.0;
    for (i, r) in ratio.iter().enumerate() {
        cumulative += r;
        println!("PC{}: individual = {:.4}, cumulative = {:.4}", i + 1, r, cumulative);
    }

    // Smallest k whose cumulative ratio clears 95%.
    let mut acc = 0.0;
    let mut k = ratio.len();
    for (i, r) in ratio.iter().enumerate() {
        acc += r;
        if acc >= 0.95 {
            k = i + 1;
            break;
        }
    }
    println!("keep {} component(s) to retain >= 95% variance", k);
}
```

There is a subtlety worth flagging: you fit once at full rank to *read* the spectrum, then refit with the chosen `k` if you want the smaller projection — refitting is cheap here and gives you a model whose `transform` outputs exactly `k` columns. If refitting is expensive on your data, note that the first `k` component rows of the full fit are the same axes the `k`-component fit would produce (up to the sign convention below), so you can slice rather than refit. Do not try to pick `k` from a single ratio in isolation; the cumulative curve is what tells you where the returns flatten out.

## 2.10.5. Reconstruction and `inverse_transform`

`inverse_transform` maps scores back to feature space: `reconstructed = scores · components + mean`. When you keep all `min(n_samples, n_features)` components it is a lossless round-trip (up to floating-point error); when you keep fewer, the reconstruction is the orthogonal projection of your data onto the retained subspace, and the residual is the variance living in the axes you dropped. Measuring that residual is the cleanest way to put a number on "how much did compression cost me".

```rust
use ndarray::array;
use rustyml::machine_learning::decomposition::PCA;

fn main() {
    let x = array![
        [1.0, 0.2, 1.19],
        [2.0, 0.1, 2.09],
        [3.0, 0.4, 3.38],
        [4.0, 0.2, 4.19],
        [5.0, 0.5, 5.48],
        [6.0, 0.3, 6.29],
    ];

    // Keep a single axis, then round-trip back into the original 3-D feature space.
    let mut pca = PCA::new(1).unwrap();
    pca.fit(&x).unwrap();

    let scores = pca.transform(&x).unwrap();                     // (6, 1)
    let reconstructed = pca.inverse_transform(&scores).unwrap(); // (6, 3)

    // Frobenius norm of the residual = the variance thrown away with PC2 and PC3.
    let err: f64 = (&reconstructed - &x).iter().map(|d| d * d).sum::<f64>().sqrt();
    println!("scores shape:         {:?}", scores.shape());
    println!("reconstruction shape: {:?}", reconstructed.shape());
    println!("reconstruction error: {:.6}", err);
}
```

Mind the shape contract, because it is the reverse of `transform`. `transform` wants `n_features` columns and yields `n_components`; `inverse_transform` wants `n_components` columns and yields `n_features`. Feed it a matrix whose column count is not `n_components` and you get an `Error::DimensionMismatch`, not a silent broadcast. Because the sign fix (next section) flips a whole axis together with its scores, reconstruction is invariant to it — the product `scores · components` is unchanged whether or not an axis was negated — so you never have to worry that a sign flip corrupted a round-trip.

## 2.10.6. Determinism: sign convention and seeds

Eigenvectors and singular vectors are only defined up to sign: `−v` spans the same axis as `v`. scikit-learn users know this as the reason PC signs sometimes flip between runs or library versions. RustyML pins the sign deterministically after the decomposition: each component row is negated, if necessary, so that its largest-magnitude loading is non-negative. The upshot is that all three solvers, and repeated runs of any one of them, agree on the orientation of every axis on the same data — the sign is stable, and `fit` is reproducible without you doing anything.

Two consequences. First, the specific sign convention is rustyml's own — it keys off the component vectors themselves, not off the `U` factor the way scikit-learn's `svd_flip` does — so a component's signs may differ from what scikit-learn prints for the same data. That is cosmetic; the axis, the variance it explains, and every reconstruction are identical. Second, the only genuine source of run-to-run variation is `SVDSolver::Randomized`, whose random sketch is seeded by the `u64` you pass: the same seed gives bit-identical output, a different seed gives a slightly different approximate subspace. `Full` and `PowerIteration` carry no external randomness at all (`PowerIteration` seeds its own starting vector internally with a fixed value). If you care about exact reproducibility across a pipeline, see [Reproducibility and Random Seeds](../Chapter-07/7.1._Reproducibility_and_Random_Seeds.md); the one lever here is the `Randomized` seed.

A fitted `PCA` serializes with `save_to_path` / `load_from_path`, which write and read the whole model — mean, components, variances, singular values — as compact [postcard](https://docs.rs/postcard) binary. The file extension is arbitrary (the bytes are postcard regardless of what you name it), and a reloaded model transforms identically to the original:

```rust,ignore
pca.save_to_path("pca_model.bin")?;
let loaded = PCA::load_from_path("pca_model.bin")?;
let scores = loaded.transform(&x_new)?; // identical to the pre-save model
```

The mechanics — versioning concerns, when the binary format is safe to persist long-term — are covered in [Model Persistence in Depth](../Chapter-07/7.2._Model_Persistence_in_Depth.md).

## 2.10.7. Errors and edge cases

PCA validates aggressively and returns typed [errors](../Chapter-01/1.6._Error_Handling.md) rather than panicking, so `.unwrap()` in these examples is brevity, not a recommendation for production. The paths you will actually hit:

| Situation | Error variant |
| --- | --- |
| `PCA::new(0)` | `Error::InvalidParameter` |
| `n_components > min(n_samples, n_features)` at `fit` | `Error::InvalidParameter` |
| Empty feature matrix at `fit` | `Error::EmptyInput` |
| Fewer than 2 samples at `fit` | `Error::InvalidInput` |
| `NaN` / `Inf` in the input (fit or transform) | `Error::NonFinite` |
| `transform` / `inverse_transform` before `fit` | `Error::NotFitted` |
| `transform` given the wrong feature count | `Error::DimensionMismatch` |
| `inverse_transform` given the wrong score-column count | `Error::DimensionMismatch` |

The two-sample minimum is not arbitrary: variance needs an `n − 1` denominator, so a single row has nothing to decompose. The `n_components` ceiling of `min(n_samples, n_features)` is the rank bound — you cannot extract more orthogonal directions than the data spans, and asking for more is a parameter error rather than a silently truncated result. Note that this is checked against the *data*, so the same `PCA::new(5)` instance can succeed on a 100×20 matrix and fail on a 3×4 one.

PCA is linear by construction — it can only find directions that are linear combinations of your features, so structure that lives on a curved manifold is invisible to it. When a scree plot refuses to flatten and reconstruction stays poor at every `k`, that is usually the signal to move to a nonlinear method: [Kernel PCA](./2.11._Kernel_PCA.md) applies the same variance-maximizing idea in a kernel feature space, and [t-SNE](./2.12._t-SNE.md) is the tool for 2-D visualization of nonlinear neighborhood structure. If your goal is separating *labeled* classes rather than capturing raw variance, the supervised counterpart is [Linear Discriminant Analysis](./2.6._Linear_Discriminant_Analysis.md), which projects toward class separation instead of total spread.
