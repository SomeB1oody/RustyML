# 3.4. Optimizers

An optimizer in RustyML is the object that turns gradients into parameter updates. After a layer's `backward` pass has stashed a gradient for every trainable tensor, the optimizer walks those tensors and moves each one downhill. You pick one when you call `compile` on a [`Sequential`](./3.1._The_Sequential_Model.md) model, alongside a [loss function](./3.3._Loss_Functions.md), and from then on `fit` drives it for you.

There are five: [`SGD`](https://docs.rs/rustyml), [`Adam`](https://docs.rs/rustyml), [`AdamW`](https://docs.rs/rustyml), [`RMSprop`](https://docs.rs/rustyml), and [`AdaGrad`](https://docs.rs/rustyml), all living in `rustyml::neural_network::optimizers` and re-exported through the prelude. Every constructor returns `Result<Self, Error>` because it validates its hyperparameters up front, so every one ends in `.unwrap()` (or real error handling) in the examples below. If you come from Keras or PyTorch the algorithms are exactly the ones you know; what differs is that the constructors are positional and total (no keyword defaults), and that gradient clipping and weight decay are wired into the optimizer rather than bolted onto the training loop.

## 3.4.1. The optimizer interface and how updates flow

Every optimizer implements the `Optimizer` trait, all five methods of which matter to you — three the training loop calls for you, and the `learning_rate`/`set_learning_rate` pair a schedule reads and writes itself (3.4.8):

```rust,ignore
pub trait Optimizer {
    fn step(&mut self);                                         // once per batch
    fn update(&mut self, layer: &mut dyn Layer, grad_scale: f32); // once per layer
    fn global_clipnorm(&self) -> Option<f32>;                        // clip threshold, or None
    fn learning_rate(&self) -> f32;                            // current step size
    fn set_learning_rate(&mut self, learning_rate: f32);       // scheduling hook
}
```

The training loop calls `step` exactly once per batch, before touching any layer, then calls `update` once per layer. `step` is where a stateful optimizer advances its notion of time: Adam and AdamW increment a bias-correction timestep here; SGD, RMSprop, and AdaGrad only use it to rewind an internal cursor. This split is the reason Adam advances its timestep once per *batch* and not once per *layer* — a subtlety that silently breaks hand-rolled loops that call the update per parameter.

`update` receives a `grad_scale` factor that the loop computes from `global_clipnorm` (below); pass-through is `1.0`. Inside, the optimizer asks the layer for its parameters via `layer.parameters()`, which yields a flat `ParamGrad` per trainable tensor — a mutable `value` slice, its matching `grad` slice, and a `decays: bool` flag. That flag is how weight decay stays honest: weight matrices and conv/recurrent kernels carry `decays = true`, while biases and normalization `gamma`/`beta` carry `decays = false` and are **never** decayed, no matter what `weight_decay` you set. You do not manage any of this; layers set the flag and optimizers respect it.

Because parameters are exposed as flat `&mut [f32]` slices, a single per-element kernel handles any tensor shape, and every kernel transparently switches to a Rayon parallel path once a tensor crosses an element-count threshold (see [7.3](../Chapter-07/7.3._Performance_Tuning_and_Parallelism.md)). One consequence worth internalizing: an optimizer's per-parameter state is keyed by the *position* at which a layer yields each tensor, so the parameter order must be stable across steps (it is), and a given optimizer instance belongs to one model — do not share it.

## 3.4.2. SGD

```rust,ignore
SGD::new(learning_rate, momentum, nesterov, weight_decay) // all f32 except nesterov: bool
```

Plain stochastic gradient descent, with optional momentum, Nesterov acceleration, and decoupled weight decay. With `momentum = 0.0` the update is the textbook one:

```text
param -= lr * grad
```

Set `momentum > 0.0` and a per-parameter velocity buffer accumulates, optionally with the Nesterov look-ahead:

```text
v    = momentum * v + grad
step = grad + momentum * v   (nesterov = true)   or   v   (nesterov = false)
param -= lr * step
```

`0.9` is the conventional momentum; `nesterov` only means anything when momentum is non-zero. The `weight_decay` here is **decoupled** (the SGDW formulation): before the gradient step, weight tensors are shrunk by `param *= (1 - lr * weight_decay)`, independent of the gradient. That is the same decoupling AdamW uses, applied to SGD.

```rust
use rustyml::prelude::*;
use rustyml::neural_network::sequential::Sequential;
use ndarray::Array;

fn main() {
    // Tiny inline regression: y = 2*x
    let x = Array::from_shape_vec((4, 1), vec![0.5_f32, 1.0, 1.5, 2.0])
        .unwrap()
        .into_dyn();
    let y = Array::from_shape_vec((4, 1), vec![1.0_f32, 2.0, 3.0, 4.0])
        .unwrap()
        .into_dyn();

    let mut model = Sequential::new();
    model
        .add(Dense::new(1, 1, Activation::Linear).unwrap())
        // learning_rate, momentum, nesterov, weight_decay
        .compile(SGD::new(0.05, 0.9, true, 0.0).unwrap(), MeanSquaredError::new());

    let before = model.predict(&x).unwrap();
    model.fit(&x, &y, 10).unwrap();
    let after = model.predict(&x).unwrap();
    println!("shapes: {:?} -> {:?}", before.shape(), after.shape());
}
```

Reach for SGD (with momentum) when you want fine control and predictable behavior: its dynamics are well understood, its single moving average is cheap, and momentum+SGD still sets the generalization bar that adaptive methods are measured against. The cost is sensitivity to the learning rate — too large and it diverges, too small and it crawls — which is exactly the knob Adam papers over.

## 3.4.3. Adam

```rust,ignore
Adam::new(learning_rate, beta1, beta2, epsilon, weight_decay) // all f32
```

Adam maintains two per-parameter moving averages — a first moment `m` (the mean gradient) and a second moment `v` (the mean squared gradient) — and uses them to give every parameter its own adaptive step size. The full update, run per element, is:

```text
t += 1                                  (advanced once per batch, in step())
m = beta1*m + (1 - beta1)*grad
v = beta2*v + (1 - beta2)*grad^2
m_hat = m / (1 - beta1^t)               <- bias correction
v_hat = v / (1 - beta2^t)               <- bias correction
param -= lr * m_hat / (sqrt(v_hat) + epsilon)
```

The bias correction is the part people gloss over. `m` and `v` start at zero, so on the first few steps they are biased toward zero — badly, since `beta2 = 0.999` means `v` barely moves off zero at `t = 1`. Dividing by `(1 - beta^t)` rescales them: at `t = 1` the denominator `1 - beta1` cancels the `(1 - beta1)` factor in `m`, recovering the raw gradient; as `t` grows, `beta^t -> 0` and the correction fades to a no-op. This is why the timestep advances in `step` (once per batch) rather than in `update`: with full-batch [`fit`](./3.1._The_Sequential_Model.md), `t` equals the epoch count; with `fit_with_batches`, it advances per mini-batch. The timestep saturates rather than overflowing, so extremely long runs stay well-defined.

One detail that reads like an inconsistency but is deliberate: Adam adds `epsilon` **outside** the square root, while RMSprop and AdaGrad (3.4.5 and 3.4.6) add theirs **inside** it. Keras is split the same way — its `Adam` adds epsilon after the root, its `RMSprop` and `Adagrad` add it before — and RustyML matches Keras optimizer for optimizer rather than forcing one form on all three. The consequence is that `epsilon` is not measured on the same scale everywhere, so read the scale note under RMSprop before carrying a value from one optimizer to another.

Adam's `weight_decay` is **classic coupled L2 regularization**: `weight_decay * param` is folded into the gradient *before* the moment update, so the penalty flows through `m` and `v` and gets rescaled by the adaptive `1 / (sqrt(v_hat) + epsilon)` denominator. That coupling is usually not what you want (see AdamW next); with `weight_decay = 0.0` the point is moot and Adam and AdamW are byte-for-byte identical. Keeping the coupling here is a deliberate divergence from Keras 3, whose base optimizer applies *decoupled* decay to every optimizer and so makes `Adam(weight_decay=x)` and `AdamW(weight_decay=x)` numerically the same thing; RustyML agrees with PyTorch instead, where `torch.optim.Adam(weight_decay=)` is coupled and `AdamW`'s is not, which keeps the two names genuinely distinct.

```rust
use rustyml::prelude::*;
use rustyml::neural_network::sequential::Sequential;
use ndarray::Array;

fn main() {
    // Tiny inline regression: y = x0 + 2*x1
    let x = Array::from_shape_vec((4, 2), vec![0.0_f32, 1.0, 1.0, 0.0, 1.0, 1.0, 2.0, 1.0])
        .unwrap()
        .into_dyn();
    let y = Array::from_shape_vec((4, 1), vec![2.0_f32, 1.0, 3.0, 4.0])
        .unwrap()
        .into_dyn();

    let mut model = Sequential::new();
    model
        .add(Dense::new(2, 8, Activation::ReLU).unwrap())
        .add(Dense::new(8, 1, Activation::Linear).unwrap())
        // learning_rate, beta1, beta2, epsilon, weight_decay
        .compile(Adam::new(0.01, 0.9, 0.999, 1e-8, 0.0).unwrap(), MeanSquaredError::new());

    model.fit(&x, &y, 50).unwrap();

    let preds = model.predict(&x).unwrap();
    println!("prediction shape: {:?}", preds.shape());
}
```

`Adam::new(0.001, 0.9, 0.999, 1e-8, 0.0)` is the default answer. If you are not sure which optimizer to use, use this one: it is forgiving about learning rate, converges quickly on messy loss surfaces, and needs almost no tuning to get moving.

## 3.4.4. AdamW

```rust,ignore
AdamW::new(learning_rate, beta1, beta2, epsilon, weight_decay) // identical signature to Adam
```

AdamW runs the exact same moment math and bias correction as Adam. The only difference is where weight decay enters, and it is a difference that matters the moment you turn decay on. AdamW is **decoupled** (the Loshchilov–Hutter formulation): the weight is shrunk directly, `param *= (1 - lr * weight_decay)`, *before* an ordinary Adam step, and the decay never touches `m` or `v` and is never divided by the adaptive denominator.

Here is why that is not a cosmetic distinction. In Adam's coupled scheme, the `weight_decay * param` term rides through the second moment `v`, so a parameter that has seen large gradients gets a large `v`, a large denominator, and therefore *less* effective decay than a quiet parameter. Your regularization strength ends up tangled with each weight's gradient history — the opposite of the uniform shrink "weight decay" is supposed to mean. AdamW severs that link: every weight decays by the same `(1 - lr * weight_decay)` factor regardless of its gradients. This is why AdamW generalizes better and is the standard choice for training anything you actually care about regularizing.

The practical rule: **any time you want non-zero weight decay with an adaptive optimizer, use `AdamW`, not `Adam`'s `weight_decay`.** Use plain `Adam` (with `weight_decay = 0.0`) when you are not regularizing at all. With `weight_decay = 0.0` the two are the same algorithm, so there is no reason to prefer `Adam` except habit.

```rust
use rustyml::prelude::*;
use rustyml::neural_network::sequential::Sequential;
use ndarray::Array;

fn main() {
    let x = Array::from_shape_vec(
        (4, 3),
        vec![0.0_f32, 1.0, 2.0, 1.0, 0.0, 1.0, 2.0, 1.0, 0.0, 1.0, 1.0, 1.0],
    )
    .unwrap()
    .into_dyn();
    let y = Array::from_shape_vec((4, 1), vec![1.0_f32, 0.5, 0.5, 0.75])
        .unwrap()
        .into_dyn();

    let mut model = Sequential::new();
    model
        .add(Dense::new(3, 16, Activation::ReLU).unwrap())
        .add(Dense::new(16, 1, Activation::Linear).unwrap())
        // decoupled weight_decay = 0.01
        .compile(
            AdamW::new(0.01, 0.9, 0.999, 1e-8, 0.01).unwrap(),
            MeanSquaredError::new(),
        );

    model.fit(&x, &y, 30).unwrap();
    println!("trained: {:?}", model.predict(&x).unwrap().shape());
}
```

## 3.4.5. RMSprop

```rust,ignore
RMSprop::new(learning_rate, rho, epsilon, weight_decay) // all f32
```

Note the spelling: the type is `RMSprop` (lowercase `p`). It keeps one moving average of squared gradients per parameter and normalizes each step by its root:

```text
cache = rho*cache + (1 - rho)*grad^2
param -= lr * grad / sqrt(cache + epsilon)
```

`rho` (the squared-gradient decay, conventionally `0.9`) is RMSprop's answer to AdaGrad's fatal flaw. Because `cache` is an exponential moving average rather than a running sum, it forgets old gradients and never grows without bound, so the effective step size stabilizes instead of decaying to zero. Think of RMSprop as Adam without the first moment: adaptive per-parameter scaling, but no momentum and no bias correction. Its `weight_decay` is decoupled (AdamW-style), applied to weight tensors before the adaptive step. RMSprop is a reasonable pick for recurrent networks and non-stationary objectives, though on most problems Adam subsumes it.

Note that `epsilon` goes **inside** the root, matching Keras (`sqrt(velocity + epsilon)`), and the placement is not cosmetic — it decides what unit epsilon is measured in. `cache` accumulates *squared* gradients, so an epsilon added before the root lives on the `grad^2` scale, while one added after it (Adam's form above, and PyTorch's RMSprop) lives on the `grad` scale; the two correspond roughly as `eps_inside = eps_outside^2`. Keras' default `1e-7` inside the root is the same guard as `3.2e-4` outside it, so a value carried over from the other form is off by orders of magnitude in whichever direction you moved it. AdaGrad below uses the inside form too.

## 3.4.6. AdaGrad

```rust,ignore
AdaGrad::new(learning_rate, epsilon, weight_decay) // all f32; note: no rho/beta
```

AdaGrad accumulates squared gradients and never forgets:

```text
accumulator += grad^2
param -= lr * grad / sqrt(accumulator + epsilon)
```

The `accumulator` is a monotonically growing sum, so `sqrt(accumulator)` only ever increases and the effective learning rate `lr / sqrt(accumulator + epsilon)` decays monotonically toward zero. That is AdaGrad's defining property, and it cuts both ways. For convex problems and sparse features it is a feature: rarely-seen parameters keep a large step while frequently-updated ones anneal automatically, and the decay-to-zero gives clean convergence guarantees. For deep nets trained for many steps it is a bug: the step size shrinks until learning effectively stalls, which is precisely the problem RMSprop's decay factor and Adam's second-moment average were invented to fix. `learning_rate` here is genuinely an *initial* rate (typically `0.01`); it is the ceiling, and the accumulator only pulls it down. Its `epsilon`, like RMSprop's, sits inside the root and is therefore on the squared-gradient scale. Weight decay, as with the others, is decoupled and weights-only.

## 3.4.7. Parameter validation

Every constructor validates before returning, so a bad hyperparameter fails loudly at construction time with `Error::InvalidParameter` rather than producing NaNs three epochs into training. The rules, taken straight from the validators:

| Parameter | Accepted values | Applies to |
| --- | --- | --- |
| `learning_rate` | positive and finite (`> 0`) | all five |
| `momentum` | non-negative and finite (`>= 0`) | SGD |
| `nesterov` | any `bool` (never validated) | SGD |
| `beta1`, `beta2` | in `[0, 1)` and finite | Adam, AdamW |
| `rho` | in `[0, 1)` and finite | RMSprop |
| `epsilon` | positive and finite (`> 0`) | Adam, AdamW, RMSprop, AdaGrad |
| `weight_decay` | non-negative and finite (`>= 0`) | all five |
| `global_clipnorm` | positive and finite (`> 0`) | all five (via `with_global_clipnorm`) |

The decay-rate ranges are half-open on purpose: `beta1 = 0.0` and `rho = 0.0` are accepted (an inclusive lower bound), but `1.0` is rejected (exclusive upper bound), because a decay of `1.0` would freeze the moving average and never incorporate a new gradient. SGD has no `epsilon` because it never divides by an adaptive denominator. Note that `0.0` is valid for `momentum` and `weight_decay` — it is how you disable those features — but invalid for `learning_rate` and `epsilon`. And while `epsilon` is validated identically for all four adaptive optimizers, it does not *mean* the same thing in all four: RMSprop and AdaGrad add it inside the square root (squared-gradient scale), Adam and AdamW add it outside (gradient scale), so a value that is sane for one pair is roughly the square, or the square root, of the sane value for the other.

```rust
use rustyml::neural_network::optimizers::{AdaGrad, Adam, AdamW, RMSprop, SGD};
use rustyml::error::Error;

fn main() {
    // learning_rate must be positive and finite
    assert!(matches!(
        SGD::new(0.0, 0.0, false, 0.0),
        Err(Error::InvalidParameter { .. })
    ));
    // beta1 must be in [0, 1): 1.0 is out of range
    assert!(matches!(
        Adam::new(0.001, 1.0, 0.999, 1e-8, 0.0),
        Err(Error::InvalidParameter { .. })
    ));
    // epsilon must be positive and finite
    assert!(matches!(
        RMSprop::new(0.01, 0.9, 0.0, 0.0),
        Err(Error::InvalidParameter { .. })
    ));
    // weight_decay must be non-negative and finite
    assert!(matches!(
        AdaGrad::new(0.01, 1e-8, -0.1),
        Err(Error::InvalidParameter { .. })
    ));
    // global_clipnorm must be positive and finite
    assert!(matches!(
        AdamW::new(0.001, 0.9, 0.999, 1e-8, 0.0)
            .unwrap()
            .with_global_clipnorm(0.0),
        Err(Error::InvalidParameter { .. })
    ));

    // A fully valid configuration, clipping enabled
    let opt = Adam::new(0.001, 0.9, 0.999, 1e-8, 0.0).unwrap();
    let _clipped = opt.with_global_clipnorm(1.0).unwrap();
    println!("validation checks passed");
}
```

## 3.4.8. Gradient clipping and learning-rate scheduling

Gradient clipping is off by default and opt-in through a consuming builder, `with_global_clipnorm`, on any of the five. It is **clip-by-global-norm**, not per-element clamping: the training loop sums the squared gradients across *every* tensor in the model, takes the global L2 norm, and if that exceeds your threshold it scales every gradient by the single factor `max_norm / global_norm` before the update. One uniform factor means the descent direction is preserved exactly; per-element clamping would bend it. A non-finite global norm is deliberately left unscaled, so a genuine divergence still surfaces as a NaN instead of being silently masked. This is the recommended way to tame large-but-finite gradients (RNNs, deep stacks) — the backward pass itself does no clamping. The name is Keras' `global_clipnorm` and matches it exactly; if you are porting a Keras model that sets `clipnorm` instead, note that Keras' `clipnorm` renormalizes each variable's gradient *independently*, which points somewhere else entirely once more than one tensor is over the limit. Only the global form exists here, so a `clipnorm` threshold cannot be carried across unchanged.

Learning-rate scheduling goes through a read/write pair, `learning_rate` and `set_learning_rate`, exposed on the model as `Sequential::learning_rate` — an `Option<f32>` that is `None` until you `compile` — and `Sequential::set_learning_rate`. Call the setter between epochs or batches to retune the step size; critically, it preserves all accumulated state — Adam's moments, SGD's velocities, RMSprop's cache — so you are re-tuning the same optimizer, not resetting it. There is no built-in scheduler object; you write the schedule as a plain loop, and the getter is what spares that loop from shadowing the rate in a variable of its own, a copy that goes stale the moment anything else retunes the optimizer. What comes back is whatever was last written: unlike the constructors, `set_learning_rate` validates nothing, so a zero or negative rate is stored and read back unchanged rather than rejected.

```rust
use rustyml::prelude::*;
use rustyml::neural_network::sequential::Sequential;
use ndarray::Array;

fn main() {
    let x = Array::from_shape_vec((4, 2), vec![0.0_f32, 1.0, 1.0, 0.0, 1.0, 1.0, 2.0, 1.0])
        .unwrap()
        .into_dyn();
    let y = Array::from_shape_vec((4, 1), vec![2.0_f32, 1.0, 3.0, 4.0])
        .unwrap()
        .into_dyn();

    let mut model = Sequential::new();
    model
        .add(Dense::new(2, 8, Activation::ReLU).unwrap())
        .add(Dense::new(8, 1, Activation::Linear).unwrap())
        .compile(
            Adam::new(0.01, 0.9, 0.999, 1e-8, 0.0)
                .unwrap()
                .with_global_clipnorm(1.0) // clip the global gradient norm to 1.0
                .unwrap(),
            MeanSquaredError::new(),
        );

    // Manual step-decay: halve the LR each block; optimizer state carries across
    for _ in 0..3 {
        model.fit(&x, &y, 10).unwrap();
        // The optimizer holds the rate, so read it back instead of shadowing it
        let lr = model.learning_rate().unwrap();
        model.set_learning_rate(lr * 0.5);
    }

    assert_eq!(model.learning_rate(), Some(0.01_f32 / 8.0));
}
```

## 3.4.9. Per-layer state, memory, and persistence

Each optimizer allocates its state lazily, one buffer per parameter tensor, sized to that tensor and created on the first `update` that reaches it. The buffers are indexed by the order layers yield parameters; if a tensor's length changes at a given position, that buffer is reset to match. This is why the two-layer convergence tests exercise correct buffer allocation across layers — the state has to line up with the parameters it shadows.

The memory cost is the number and size of those buffers:

| Optimizer | Per-parameter state | Extra memory vs. parameters |
| --- | --- | --- |
| SGD, `momentum = 0.0` | none | 0x |
| SGD, `momentum > 0.0` | velocity | 1x |
| RMSprop | squared-gradient cache | 1x |
| AdaGrad | squared-gradient accumulator | 1x |
| Adam, AdamW | first moment `m` + second moment `v` | 2x |

For a model with `P` weights in `f32`, Adam and AdamW carry roughly `2 * 4 * P` bytes of optimizer state on top of the parameters and their gradients — the price of adaptivity, and the reason a model that trains fine with SGD can run out of memory under Adam. Plain SGD carries none, which is occasionally the deciding factor on tight budgets.

That state lives entirely in the optimizer instance and is **not** persisted. `Sequential::save_to_path` serializes layer architecture and weights only; the optimizer and loss are explicitly excluded, so after `load_from_path` you must `compile` a fresh optimizer, and its moments, velocities, and timestep all start from zero. Reloading weights and resuming training therefore restarts Adam's bias-correction warmup — usually harmless, but worth knowing if you checkpoint mid-run. See [3.9. Saving and Loading Weights](./3.9._Saving_and_Loading_Weights.md) and [7.2. Model Persistence in Depth](../Chapter-07/7.2._Model_Persistence_in_Depth.md) for the full persistence story.

## 3.4.10. Choosing an optimizer

The short version: **start with Adam** (`0.001, 0.9, 0.999, 1e-8, 0.0`). It is the least fussy about learning rate and gets almost any model training, which is what you want while you are still figuring out the architecture.

Reach for **SGD with momentum** (`momentum = 0.9`, `nesterov = true`) when you want fine control and are willing to tune the learning rate — its generalization is the reference standard, its state is cheap, and its behavior is transparent. Use **AdamW with a non-zero `weight_decay`** whenever regularization is the goal; its decoupled decay is the correct way to regularize an adaptive optimizer, and it should be your default over `Adam`'s coupled `weight_decay` in every case that decay is on. **RMSprop** is a solid fallback for recurrent and non-stationary problems, and **AdaGrad** shines on convex, sparse-feature problems where its decaying step size is an asset rather than a liability — but avoid AdaGrad for long deep-net runs, where that same decay stalls learning.

One cross-cutting subtlety when you tune: the effective learning rate is entangled with your loss function's averaging convention. Switching between a per-element loss (MSE, MAE, binary cross-entropy) and a per-prediction-site one (categorical cross-entropy) rescales the gradient magnitude and therefore the step size — see the averaging note in [3.3. Loss Functions](./3.3._Loss_Functions.md). Change the loss and you will likely need to re-tune the learning rate, whichever optimizer you chose.
