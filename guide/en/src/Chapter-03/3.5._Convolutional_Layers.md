# 3.5. Convolutional Layers

RustyML ships five convolutional layers — `Conv1D`, `Conv2D`, `Conv3D`, `DepthwiseConv2D`, and `SeparableConv2D` — all in `rustyml::neural_network::layers` and re-exported by the layers glob. They share one design: a layer struct owns the weights, bias, activation, and forward/backward caches, and the actual numerics for the plain convolutions are delegated to a single dimension-generic engine. If you are coming from Keras the constructors will feel familiar, but two things differ and bite people early: tensors are channels-first (not channels-last), and you pass the full input shape into the constructor so the layer can size its weights up front rather than lazily on the first batch. This page covers the layouts, the constructor and padding semantics, the im2col + GEMM engine that powers the standard convolutions, the depthwise/separable factorization and its cost math, and the error surface.

## 3.5.1. Tensor Layouts and the Layer Family

Every convolution here is channels-first: the channel axis sits immediately after the batch axis, and the spatial axes follow. A `Conv2D` reads `[batch, channels, height, width]` and writes `[batch, filters, out_height, out_width]`. This is the PyTorch `NCHW` convention, not the Keras/TensorFlow default `NHWC`; if you build inputs by hand with `ndarray`, put channels second. The weight tensor mirrors the input rank: one filter row per output channel, then the input channels, then the kernel taps.

| Layer | Input tensor | Weight tensor | Bias | Output tensor |
| --- | --- | --- | --- | --- |
| `Conv1D` | `[N, Cin, L]` | `[F, Cin, k]` | `[1, F]` | `[N, F, L']` |
| `Conv2D` | `[N, Cin, H, W]` | `[F, Cin, kh, kw]` | `[1, F]` | `[N, F, H', W']` |
| `Conv3D` | `[N, Cin, D, H, W]` | `[F, Cin, kd, kh, kw]` | `[1, F]` | `[N, F, D', H', W']` |
| `DepthwiseConv2D` | `[N, C, H, W]` | `[C, 1, kh, kw]` | `[C]` | `[N, C, H', W']` |
| `SeparableConv2D` | `[N, Cin, H, W]` | depthwise `[dm, Cin, kh, kw]`, pointwise `[F, Cin·dm, 1, 1]` | `[1, F]` | `[N, F, H', W']` |

Two rows there are worth pausing on. `DepthwiseConv2D` pins its filter count to the input channel count and carries one `kh×kw` kernel per channel, so its weight tensor has a singleton channel axis and its bias is a plain 1-D `Array1` — the only layer in the family whose bias is not `[1, F]`. `SeparableConv2D` holds two weight tensors because it is two convolutions fused into one layer; more on that in 3.5.4.

The forward math is cross-correlation, the same convention Keras and PyTorch use — the kernel is not flipped — and the bias is added last, once per filter, after the multiply-accumulate. Weights initialize with Xavier/Glorot uniform bounds and biases start at zero. A layer-level forward with hand-set weights shows the layout and the Valid output size concretely:

```rust
use ndarray::{Array, Array2, Array4};
use rustyml::neural_network::layers::*;
use rustyml::neural_network::traits::Layer;

fn main() {
    // Channels-first: [batch, channels, height, width].
    let mut layer = Conv2D::new(1, (2, 2), vec![1, 1, 4, 4], (1, 1), Activation::Linear).unwrap();

    // Weights are [filters, channels, kernel_h, kernel_w]; bias is [1, filters].
    let weights = Array4::from_elem((1, 1, 2, 2), 1.0f32);
    let bias = Array2::zeros((1, 1));
    layer.set_weights(weights, bias).unwrap();

    let pixels: Vec<f32> = (1..=16).map(|v| v as f32).collect();
    let x = Array::from_shape_vec((1, 1, 4, 4), pixels).unwrap().into_dyn();

    let out = layer.forward(&x).unwrap();
    // Valid padding: (4 - 2)/1 + 1 = 3 along each spatial axis -> [1, 1, 3, 3].
    assert_eq!(out.shape(), &[1, 1, 3, 3]);
    println!("output shape: {:?}", out.shape());
}
```

## 3.5.2. Constructors, Padding, and Output Shapes

The constructors take the hyperparameters positionally, and the shape of the kernel/stride argument tracks the rank: `Conv1D` uses scalar `kernel_size` and `stride`, while the 2-D and 3-D layers take tuples. `SeparableConv2D` inserts a `depth_multiplier` before the activation.

```rust,ignore
Conv1D::new(filters, kernel_size: usize, input_shape: Vec<usize>, stride: usize, activation) -> Result<Conv1D, Error>
Conv2D::new(filters, kernel_size: (usize, usize), input_shape: Vec<usize>, strides: (usize, usize), activation) -> Result<Conv2D, Error>
Conv3D::new(filters, kernel_size: (usize, usize, usize), input_shape: Vec<usize>, strides: (usize, usize, usize), activation) -> Result<Conv3D, Error>
DepthwiseConv2D::new(filters, kernel_size: (usize, usize), input_shape: Vec<usize>, strides: (usize, usize), activation) -> Result<DepthwiseConv2D, Error>
SeparableConv2D::new(filters, kernel_size: (usize, usize), input_shape: Vec<usize>, strides: (usize, usize), depth_multiplier: usize, activation) -> Result<SeparableConv2D, Error>
```

`activation` is `impl Into<Activation>`, so you can pass an `Activation` variant (`Activation::ReLU`, `Activation::Sigmoid`, `Activation::Tanh`, `Activation::Softmax`, `Activation::Linear`) or a standalone activation layer such as `ReLU::new()`. The `input_shape` you supply is the full expected input including the batch dimension; only `input_shape[1..]` (the channels and spatial extents) actually sizes the weights, so the batch value you write is informational. See [3.2. Dense Layers and Activations](./3.2._Dense_Layers_and_Activations.md) for the activation set in depth.

Three builder methods refine a constructed layer, each consuming and returning `self` so they chain: `with_padding(PaddingType)` switches the padding mode, `with_random_state(u64)` re-runs the Xavier initialization deterministically from a seed (call it before assigning custom weights or training — see [7.1. Reproducibility and Random Seeds](../Chapter-07/7.1._Reproducibility_and_Random_Seeds.md)), and `set_weights(...)` installs weights and bias you control. `set_weights` validates every array against the layer's expected shape; note `DepthwiseConv2D::set_weights` takes an `Array1` bias, and `SeparableConv2D::set_weights` takes three arrays — depthwise weights, pointwise weights, then bias.

Padding is the `PaddingType` enum with two variants, `Valid` (the default) and `Same`, and it drives the output size:

- `Valid` applies no padding and computes only where the kernel fully overlaps: `out = (in - k) / stride + 1` (integer floor division) per spatial axis. It requires every input axis to be at least the kernel size.
- `Same` zero-pads the borders so `out = ceil(in / stride)`. With `stride == 1` the spatial size is preserved exactly; with larger strides the output is the input length divided by the stride, rounded up. The total padding is split with the extra cell on the trailing edge (`pad_before = pad_total / 2`), matching TensorFlow's `SAME`.

A few worked numbers make this concrete. A `[N, 1, 8, 8]` input through a `3×3` kernel: Valid, stride 1 gives `(8-3)/1+1 = 6`, so `[N, F, 6, 6]`; Same, stride 1 gives `8`, so `[N, F, 8, 8]`; Same, stride 2 gives `ceil(8/2) = 4`. A `Conv1D` over length 6 with kernel 3, stride 2, Valid gives `(6-3)/2+1 = 2`. `Conv3D` applies the same rule independently on depth, height, and width. `model.summary()` prints these computed output shapes and the per-layer parameter counts, so you can sanity-check a stack before training it (the [3.1. Sequential Model](./3.1._The_Sequential_Model.md) page covers `summary` in full).

## 3.5.3. The im2col + GEMM Engine

`Conv1D`, `Conv2D`, and `Conv3D` do not each carry their own loop nest. A plain convolution is the same operation at every rank — only the number of spatial axes changes — so all three delegate their forward and backward numerics to one implementation in `convolution_engine.rs`, generic over the spatial rank `R = ndim - 2`. The layer wrapper keeps the public API, the weight storage, the activation, and the caches; the engine does the arithmetic.

The engine is im2col plus GEMM, the same strategy the major frameworks use. For the forward pass it gathers each output window into a column, forming a `[Cin·k_plane, out_plane]` matrix whose rows align with the flat weight matrix `[F, Cin·k_plane]`, then a single matrix multiply produces `[F, out_plane]` and the bias is added per filter. Trading the six-deep loop nest for a matrix multiply is what lets the layer lean on the crate's tuned in-house GEMM (see [6.2. Matrix Multiplication](../Chapter-06/6.2._Matrix_Multiplication.md)) rather than a naive triple loop. The backward pass runs two GEMMs per batch item — one for the weight gradient, one for the input-gradient columns that are then scattered back (col2im) into the input-gradient tensor.

Parallelism is gated on estimated FLOPs, not element counts, because a `7×7×512` and a `3×3×3` convolution with the same output-element count cost wildly different amounts. The forward gate compares `2 · batch · F · out_plane · Cin·k` against `CONV_PARALLEL_MIN_FLOPS` (default 4,000,000, runtime-tunable via `rustyml::tuning`). Below it the pass runs serial; above it the forward parallelizes over `(batch item, output-position block)` tasks, so a single large image still fills every core even at `batch == 1` — each task builds its own im2col block and GEMM into a disjoint output region. The backward pass parallelizes over batch items and reduces the weight and bias partials in batch order, which keeps results bit-reproducible across runs on the same machine; it also routes its per-item GEMMs through a switch that keeps them parallel while the batch is too short to fill the thread pool and flips them serial once the batch alone saturates it, so batch tasks do not each fork rayon inside a GEMM. The practical upshot: the parallel path returns the same numbers as the serial path, and you rarely need to touch the gate — but if you profile a workload that sits just under it, [7.3. Performance Tuning and Parallelism](../Chapter-07/7.3._Performance_Tuning_and_Parallelism.md) shows how to move it.

## 3.5.4. Depthwise and Separable Convolutions

A standard convolution mixes across channels and across space in one shot: every output channel is a weighted sum over all input channels and all kernel taps. That coupling is where the parameters live — the weight tensor is `F · Cin · kh · kw`. Depthwise separable convolution factors the operation into two cheaper stages: a depthwise convolution that filters each input channel independently (spatial mixing, no cross-channel mixing), followed by a pointwise `1×1` convolution that recombines channels (cross-channel mixing, no spatial extent). This is the MobileNet/Xception idea, and RustyML exposes both halves.

`DepthwiseConv2D` is the first stage alone. Its `filters` argument must equal the input channel count — the constructor rejects anything else with `InvalidParameter` — because it carries exactly one `kh×kw` kernel per channel and produces one output channel per input channel. It does no channel recombination, so on its own it cannot change the channel count; it is almost always paired with a `1×1` convolution downstream. Note the difference from Keras here: Keras `DepthwiseConv2D` has a `depth_multiplier`, but RustyML's `DepthwiseConv2D` does not — if you want more than one filter per channel, reach for `SeparableConv2D`, which owns the `depth_multiplier` parameter and expands the intermediate channel count to `Cin · depth_multiplier` before the pointwise stage collapses it to `filters`.

The parameter arithmetic is the whole point. For `Cin` input channels, `F` output filters, and a `kh×kw` kernel:

- Standard `Conv2D`: `F · Cin · kh · kw + F`.
- `DepthwiseConv2D`: `C · kh · kw + C` (with `F = C`).
- `SeparableConv2D`: `dm · Cin · kh · kw` (depthwise) `+ F · Cin · dm` (pointwise) `+ F` (bias).

Ignoring bias, the separable-to-standard ratio is `1/F + 1/(kh·kw)`, so the savings grow with both the filter count and the kernel area. Because each parameter costs one multiply-accumulate per output position, that same ratio is the compute (FLOP) ratio. Concretely, replacing a 64-filter `3×3` convolution over 3 channels: the standard layer has `64·3·3·3 + 64 = 1792` parameters, the separable equivalent has `27 + 192 + 64 = 283` — about 6.3× fewer — and a depthwise-only layer over those 3 channels has just `30`. The following program builds all three and checks the counts:

```rust
use rustyml::neural_network::layers::*;
use rustyml::neural_network::traits::Layer;

fn count(p: TrainingParameters) -> usize {
    match p {
        TrainingParameters::Trainable(n) | TrainingParameters::NonTrainable(n) => n,
        TrainingParameters::NoTrainable => 0,
    }
}

fn main() {
    let input_shape = vec![1, 3, 32, 32]; // [batch, channels, H, W]

    // Standard 64-filter 3x3 convolution over 3 input channels.
    let standard =
        Conv2D::new(64, (3, 3), input_shape.clone(), (1, 1), Activation::ReLU).unwrap();

    // Separable equivalent: depthwise (depth_multiplier = 1) then a pointwise 1x1 to 64 filters.
    let separable =
        SeparableConv2D::new(64, (3, 3), input_shape.clone(), (1, 1), 1, Activation::ReLU).unwrap();

    // Depthwise-only keeps filters == channels (3 here) and does no cross-channel mixing.
    let depthwise = DepthwiseConv2D::new(3, (3, 3), input_shape, (1, 1), Activation::ReLU).unwrap();

    println!("standard  Conv2D params: {}", count(standard.param_count()));
    println!("separable Conv2D params: {}", count(separable.param_count()));
    println!("depthwise Conv2D params: {}", count(depthwise.param_count()));

    assert_eq!(count(standard.param_count()), 1792); // 64*3*3*3 + 64
    assert_eq!(count(separable.param_count()), 283); // 27 + 192 + 64
    assert_eq!(count(depthwise.param_count()), 30); // 3*3*3 + 3
}
```

Reach for these when channel counts are high and you want to cut parameters and compute — wide feature maps, or a model you intend to run on modest hardware — and accept the modeling tradeoff that the factored form is strictly less expressive than a full convolution for the same `F` and kernel. Their engine is different from the standard layers: `DepthwiseConv2D` uses a direct loop nest (the channels are independent, so im2col buys little), parallelized over `(batch item, channel)` and gated on `NAIVE_CONV_PARALLEL_MIN_FLOPS` (default 1,000,000). `SeparableConv2D` runs its depthwise stage through the same naive path, then routes its pointwise `1×1` stage back through the shared im2col + GEMM engine, since a `1×1` convolution is exactly a per-position cross-channel matrix multiply.

## 3.5.5. Building a Small CNN

Convolutions emit rank-3/4/5 tensors, but a `Dense` classifier head wants a rank-2 `[batch, features]` matrix. `Flatten` is the bridge: `Flatten::new(input_shape: Vec<usize>)` builds a parameter-free layer that reshapes `[batch, ...]` into `[batch, product-of-the-rest]`, accepting 3-D, 4-D, or 5-D input at forward time. You give it the shape of the tensor entering it — the convolution's output shape — and it works out the flattened feature count. Here is a complete stack: a `Conv2D` over synthetic single-channel `8×8` "images", flattened, into a `Dense` regression head, trained for a few epochs through [the Sequential model](./3.1._The_Sequential_Model.md).

```rust
use ndarray::{Array2, Array4};
use rustyml::neural_network::layers::*;
use rustyml::neural_network::losses::*;
use rustyml::neural_network::optimizers::*;
use rustyml::neural_network::sequential::Sequential;

fn main() {
    // Synthetic "images": 6 samples, 1 channel, 8x8.
    let mut x = Array4::<f32>::zeros((6, 1, 8, 8));
    for n in 0..6 {
        for i in 0..8 {
            for j in 0..8 {
                x[[n, 0, i, j]] = ((n + i + j) as f32 * 0.1).sin();
            }
        }
    }
    let x = x.into_dyn();

    // Three regression targets per sample.
    let y = Array2::<f32>::from_shape_fn((6, 3), |(n, k)| (n as f32) * 0.01 + (k as f32) * 0.1)
        .into_dyn();

    let mut model = Sequential::new();
    model
        // [6, 1, 8, 8] -> Conv2D(4 filters, 3x3, Valid) -> [6, 4, 6, 6]
        .add(
            Conv2D::new(4, (3, 3), vec![6, 1, 8, 8], (1, 1), Activation::ReLU)
                .unwrap()
                .with_random_state(42),
        )
        // [6, 4, 6, 6] -> Flatten -> [6, 144]
        .add(Flatten::new(vec![6, 4, 6, 6]).unwrap())
        // [6, 144] -> Dense -> [6, 3]
        .add(Dense::new(4 * 6 * 6, 3, Activation::Linear).unwrap().with_random_state(7))
        .compile(SGD::new(0.01, 0.0, false, 0.0).unwrap(), MeanSquaredError::new());

    model.summary();
    model.fit(&x, &y, 3).unwrap();

    let pred = model.predict(&x).unwrap();
    assert_eq!(pred.shape(), &[6, 3]);
    println!("prediction shape: {:?}", pred.shape());
}
```

The `Dense` input dimension is not guessed — it is the flattened feature count `4 · 6 · 6 = 144`, which you can read straight off the convolution's output shape. Get it wrong and the `Dense` layer's matrix multiply will reject the batch. `summary()` prints the shape at each stage and the parameter budget, which is the fastest way to catch a mis-sized head:

```text
┏━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┳━━━━━━━━━━━━━━━━━━━━━━━━┳━━━━━━━━━━━━━━━┓
┃ Layer (type)                    ┃ Output Shape           ┃       Param # ┃
┡━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━╇━━━━━━━━━━━━━━━━━━━━━━━━╇━━━━━━━━━━━━━━━┩
│ conv2d (Conv2D)                 │ (6, 4, 6, 6)           │            40 │
│ flatten (Flatten)               │ (None, 144)            │             0 │
│ dense (Dense)                   │ (None, 3)              │           435 │
└─────────────────────────────────┴────────────────────────┴───────────────┘
```

Swap in a [pooling layer](./3.6._Pooling_Layers.md) between the convolution and the flatten when you want to shrink the spatial extent before the dense head, and persist the trained stack with the tools in [3.9. Saving and Loading Weights](./3.9._Saving_and_Loading_Weights.md).

## 3.5.6. Errors and How to Avoid Them

The convolution layers validate aggressively and return typed errors rather than panicking on bad configuration. The common cases and their variants:

| Condition | Error |
| --- | --- |
| `filters`, a kernel dim, or a stride is `0` | `Error::InvalidParameter` |
| `depth_multiplier == 0` (`SeparableConv2D`) | `Error::InvalidParameter` |
| `DepthwiseConv2D` `filters != channels` | `Error::InvalidParameter` |
| `input_shape` wrong rank, zero channels, or smaller than the kernel (constructor) | `Error::InvalidInput` |
| `forward` handed a tensor of the wrong rank | `Error::InvalidInput` |
| Valid convolution whose runtime spatial dim is below the kernel | `Error::InvalidInput` |
| `DepthwiseConv2D` runtime channel count `!= filters` | `Error::DimensionMismatch` |
| `set_weights` shape does not match | `Error::NeuralNetwork(NnError::WeightShape)` |
| `backward` called before `forward` | `Error::NeuralNetwork(NnError::ForwardPassNotRun)` |

Two of these deserve emphasis. First, "kernel larger than input under Valid padding" is caught both at construction (against the declared `input_shape`) and at forward time (against the actual tensor) — the engine computes `in - k` in `usize`, and rather than let that underflow it returns `InvalidInput`. Second, a channel mismatch is only a recoverable error on `DepthwiseConv2D`, which explicitly checks the runtime channel count and returns `DimensionMismatch`. The standard `Conv1D`/`Conv2D`/`Conv3D` layers size their weight matrix from the channel count in the declared `input_shape` and do not re-validate it on every forward, so you must feed the channel count you declared; treat the declared channels as a contract. The following program exercises the recoverable paths:

```rust
use ndarray::Array;
use rustyml::error::Error;
use rustyml::neural_network::layers::*;
use rustyml::neural_network::traits::Layer;

fn main() {
    // 1. Kernel larger than the declared input under Valid padding: rejected at construction.
    let too_big = Conv2D::new(1, (3, 3), vec![1, 1, 2, 2], (1, 1), Activation::Linear);
    assert!(matches!(too_big, Err(Error::InvalidInput(_))));

    // 2. DepthwiseConv2D requires filters == input channels.
    let bad_filters = DepthwiseConv2D::new(3, (2, 2), vec![1, 2, 4, 4], (1, 1), Activation::Linear);
    assert!(matches!(bad_filters, Err(Error::InvalidParameter { .. })));

    // 3. A runtime tensor smaller than the kernel: Valid geometry returns an error, not a panic.
    let mut conv = Conv2D::new(1, (3, 3), vec![1, 1, 5, 5], (1, 1), Activation::Linear).unwrap();
    let small = Array::ones((1, 1, 2, 5)).into_dyn(); // height 2 < kernel 3
    assert!(matches!(conv.forward(&small), Err(Error::InvalidInput(_))));

    // 4. DepthwiseConv2D turns a runtime channel mismatch into a recoverable error.
    let mut dw =
        DepthwiseConv2D::new(2, (2, 2), vec![1, 2, 4, 4], (1, 1), Activation::Linear).unwrap();
    let wrong_channels = Array::ones((1, 3, 4, 4)).into_dyn(); // 3 channels, layer expects 2
    assert!(matches!(
        dw.forward(&wrong_channels),
        Err(Error::DimensionMismatch { .. })
    ));

    println!("all error paths behaved as documented");
}
```

The `ForwardPassNotRun` guard is the one that surprises people mid-training: the backward pass reads caches written by `forward`, so calling `backward` on a fresh layer — or twice in a row without an intervening `forward` — returns that variant instead of reading stale state. Inside `Sequential` the ordering is handled for you; you only meet it when driving layers by hand. For the full error taxonomy and the smart constructors behind these variants, see [1.6. Error Handling](../Chapter-01/1.6._Error_Handling.md).
