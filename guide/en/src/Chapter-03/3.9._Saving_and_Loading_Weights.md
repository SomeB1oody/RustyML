# 3.9. Saving and Loading Weights

RustyML persists a trained [`Sequential`](./3.1._The_Sequential_Model.md) model through exactly two methods: `save_to_path` and `load_from_path`. They are deliberately narrow. If you come from Keras, where `model.save()` writes a self-describing bundle that reconstructs the graph, the compiler config, and the optimizer state, adjust your expectations now: RustyML saves the layer *weights* and nothing you could rebuild a model from. Loading is a two-step dance — you construct the identical layer stack in code first, then pour the saved arrays back into it. This section covers what is actually on disk, why that boundary sits where it does, the failure modes, and the recipes that make the weights-only model comfortable to live with.

## 3.9.1. What actually gets written to disk

`save_to_path` walks the layers and, for each one, records a small metadata tag plus its weights, then serializes the whole vector with [postcard](https://docs.rs/postcard) into a compact binary blob written through a buffered writer. `load_from_path` reads the file back, deserializes it, checks that the model you built matches the file, and applies the arrays layer by layer. The signatures:

```rust,ignore
pub fn save_to_path(&self, path: impl AsRef<std::path::Path>) -> RustymlResult<()>;
pub fn load_from_path(&mut self, path: impl AsRef<std::path::Path>) -> RustymlResult<()>;
```

Both accept anything that is `AsRef<Path>` — `&str`, `String`, `Path`, `PathBuf` — so the `"model.bin"` literals below are just the ergonomic case. The file extension is cosmetic; postcard writes raw bytes regardless of what you name the file. `save_to_path` uses `File::create`, which truncates and overwrites, so re-saving to the same path clobbers the previous checkpoint — exactly what you want for a "keep only the best" loop.

The crucial thing to internalize is what the per-layer metadata is *for*. Each layer contributes a type-name string (`"Dense"`, `"Conv2D"`, ...) and an output-shape string, but these are validation tags, not a construction recipe. Nothing in the file records a layer's activation function, its `epsilon` or `momentum`, its stride, kernel size, dilation, or group count. You cannot hand `load_from_path` an empty `Sequential` and get a working model back. That is why the doc calls this "weights-only": the architecture lives in your source code, and the file only carries the numbers that fill it.

| Persisted in the file | Not persisted |
| --- | --- |
| Per-layer type-name tag (validated on load) | Activation functions, hyperparameters (`epsilon`, `momentum`, stride, ...) |
| Per-layer output-shape tag (informational only) | Optimizer and its accumulated state (Adam moments, SGD momentum) |
| Every layer's weight arrays (see [3.9.2](#392-the-layerweight-enum-per-layer-payloads)) | Loss function and compile state |
| BatchNormalization running mean and variance | Fit-time shuffle seed, training-mode flag |

## 3.9.2. The `LayerWeight` enum: per-layer payloads

The on-disk weight format *is* a Rust enum, `LayerWeight<'a>`, with one variant per supported layer type plus an `Empty` variant for parameterless layers. Each variant wraps a small struct whose arrays are stored as [`Cow`](https://doc.rust-lang.org/std/borrow/enum.Cow.html), which is the trick that lets one type serve both directions: [`Sequential::get_weights`](./3.1._The_Sequential_Model.md) borrows the live arrays (`Cow::Borrowed`, no clone) when saving, while `load_from_path` deserializes into owned arrays (`Cow::Owned`). The enum uses serde's default externally-tagged representation because postcard is not self-describing and needs the discriminant written explicitly.

What each variant captures is worth memorizing, because it determines whether a round-trip is exact:

| Variant | Payload |
| --- | --- |
| `Dense` | `weight (in, out)`, `bias (1, out)` |
| `SimpleRNN` | `kernel`, `recurrent_kernel`, `bias` |
| `LSTM` / `GRU` | fused `kernel`, `recurrent_kernel`, `bias` (gate blocks `[i\|f\|g\|o]` / `[r\|z\|h]`) |
| `Conv1D` / `Conv2D` / `Conv3D` | convolution `weight` kernel and `bias` |
| `SeparableConv2D` / `DepthwiseConv2D` | depthwise/pointwise kernels and `bias` |
| `BatchNormalization` | `gamma`, `beta`, **`running_mean`, `running_var`** |
| `LayerNormalization` / `InstanceNormalization` / `GroupNormalization` | `gamma`, `beta` only |
| `Empty` | nothing (Dropout, pooling, flatten, pure activation layers) |

The asymmetry among the normalization layers is intentional and correct. [BatchNormalization](./3.8._Regularization_and_Normalization_Layers.md) accumulates running statistics during training and *uses them at inference*, so those two arrays are part of the trained state and must survive serialization — drop them and your reloaded model would normalize eval-mode inputs with default statistics and produce garbage. Layer, instance, and group normalization compute their statistics from the current input on every forward pass, so they hold no running state; `gamma` and `beta` are all there is to save. [3.9.4](#394-normalization-running-statistics-survive-the-round-trip) demonstrates the BatchNorm case explicitly.

## 3.9.3. A complete round-trip

Here is the whole loop end to end: build, train briefly, save, rebuild the *same* stack, load, and confirm the restored model predicts identically. Note the `make_arch` closure — defining the architecture once and calling it for both the live model and the reload target is the single most useful habit for weights-only persistence, because it guarantees the two stacks cannot drift apart.

```rust
use ndarray::Array;
use rustyml::error::Error;
use rustyml::neural_network::Tensor;
use rustyml::neural_network::layers::activation::linear::Linear;
use rustyml::neural_network::layers::dense::Dense;
use rustyml::neural_network::losses::MeanSquaredError;
use rustyml::neural_network::optimizers::SGD;
use rustyml::neural_network::sequential::Sequential;

// One source of truth for the architecture, reused by the live and the reloaded model.
fn make_arch() -> Sequential {
    let mut m = Sequential::new();
    m.add(Dense::new(4, 3, Linear::new()).unwrap())
        .add(Dense::new(3, 2, Linear::new()).unwrap());
    m
}

fn main() -> Result<(), Error> {
    let x: Tensor = Array::from_shape_vec((2, 4), vec![0.1f32, 0.2, 0.3, 0.4, -0.1, -0.2, -0.3, -0.4])
        .unwrap()
        .into_dyn();
    let y: Tensor = Array::from_shape_vec((2, 2), vec![1.0f32, 0.0, 0.0, 1.0])
        .unwrap()
        .into_dyn();

    let mut model = make_arch();
    model.compile(SGD::new(0.01, 0.0, false, 0.0).unwrap(), MeanSquaredError::new());
    model.fit(&x, &y, 5)?;
    let before = model.predict(&x)?;

    // Save weights, then rebuild the identical stack and load into it.
    let path = "roundtrip_demo.bin";
    model.save_to_path(path)?;

    let mut restored = make_arch();
    restored.load_from_path(path)?;
    let after = restored.predict(&x)?;

    // The two prediction tensors must agree element-wise.
    let max_diff = (&after - &before)
        .mapv(f32::abs)
        .iter()
        .cloned()
        .fold(0.0f32, f32::max);
    println!("max abs difference after round-trip: {max_diff:e}");
    assert!(max_diff < 1e-6);

    std::fs::remove_file(path).unwrap();
    Ok(())
}
```

The round-trip is exact, not approximate: postcard stores each `f32` losslessly, and `load_from_path` writes the arrays straight into the layers, so the reloaded model is bit-for-bit the same computation. The `1e-6` tolerance above is defensive slack, not a hedge against drift.

## 3.9.4. Normalization running statistics survive the round-trip

Because BatchNorm's inference path reads `running_mean` and `running_var`, the interesting test is to train those statistics away from their defaults, save, reload into a *fresh untrained* model, and check that eval-mode predictions still match. They do — the running arrays travel in the `BatchNormalization` variant.

```rust
use ndarray::Array;
use rustyml::neural_network::Tensor;
use rustyml::neural_network::layers::regularization::normalization::batch_normalization::BatchNormalization;
use rustyml::neural_network::losses::MeanSquaredError;
use rustyml::neural_network::optimizers::SGD;
use rustyml::neural_network::sequential::Sequential;

fn make_arch() -> Sequential {
    let mut m = Sequential::new();
    m.add(BatchNormalization::new(vec![4, 3], 0.9, 1e-5).unwrap());
    m
}

fn main() {
    let x: Tensor = Array::from_shape_vec(
        (4, 3),
        vec![0.5f32, -1.0, 2.0, 1.5, 0.2, -0.7, -1.2, 0.8, 1.1, 0.3, -0.4, 0.9],
    )
    .unwrap()
    .into_dyn();

    // Train so running_mean / running_var move away from their initial values.
    let mut model = make_arch();
    model.compile(SGD::new(0.001, 0.0, false, 0.0).unwrap(), MeanSquaredError::new());
    model.fit(&x, &x, 8).unwrap();
    let before = model.predict(&x).unwrap(); // eval mode uses the running stats

    let path = "batchnorm_demo.bin";
    model.save_to_path(path).unwrap();

    let mut restored = make_arch(); // fresh: running stats at their defaults
    restored.load_from_path(path).unwrap();
    let after = restored.predict(&x).unwrap();

    let max_diff = (&after - &before)
        .mapv(f32::abs)
        .iter()
        .cloned()
        .fold(0.0f32, f32::max);
    println!("running-stat round-trip max abs difference: {max_diff:e}");
    assert!(max_diff < 1e-6);

    std::fs::remove_file(path).unwrap();
}
```

Had the running statistics not been persisted, `after` would diverge sharply from `before`, since the fresh model's defaults do not match the eight epochs of accumulated batch statistics.

## 3.9.5. What is not saved, and why it bites

The optimizer, its accumulated state, the loss function, and the entire compile configuration stay behind. This is the sharpest departure from Keras, whose default save format bundles the optimizer so `fit` resumes seamlessly. In RustyML, loading gives you weights on a blank model — `optimizer` and `loss` are `None` — so two consequences follow.

First, you must call `compile` again before you can `fit` or even before the model is training-ready; prediction works immediately because `predict` needs no optimizer. Second, and easy to miss: resuming training after a load **restarts the optimizer from scratch**. [Adam's](./3.4._Optimizers.md) first- and second-moment estimates reset to zero, SGD's momentum buffer resets, and Adam's bias-correction timestep starts over at one. For a few fine-tuning steps this is harmless. For a long training run split across a save/load boundary, the first post-load steps take larger, less-damped updates than an uninterrupted run would — a transient bump in the loss curve that is a persistence artifact, not a data problem. If you need to pause and resume long optimization without that discontinuity, keep the process alive rather than round-tripping through disk, because RustyML has no API to serialize optimizer moments. The fit-time shuffle seed is likewise not saved; re-set it with [`set_seed`](../Chapter-07/7.1._Reproducibility_and_Random_Seeds.md) after loading if you want the resumed shuffle to be reproducible.

## 3.9.6. Error variants on load

Every failure surfaces as `Error::Io(...)` (see [1.6. Error Handling](../Chapter-01/1.6._Error_Handling.md)). There are exactly three shapes, and they map cleanly to the three things that can go wrong:

| Error | Cause |
| --- | --- |
| `IoError::Std` | The file could not be opened/read (missing path, permissions) or written |
| `IoError::Serialization` | The bytes are not valid postcard for the expected schema (corruption, truncation, or a schema mismatch — see [3.9.8](#398-workflow-recipes)) |
| `IoError::ModelStructureMismatch` | The model you built does not match the file: wrong layer *count*, a wrong layer *type* at some position, or a weight whose *shape* disagrees with the target layer |

`ModelStructureMismatch` is the one you will hit while iterating. It is raised in three places: a layer-count check, a per-position type-name check, and — subtly — during weight application, where a shape disagreement from a layer's `set_weights` is wrapped up into the same variant. So a `Dense::new(2, 2, ...)` file loaded into a `Dense::new(3, 3, ...)` target passes the count and type checks but fails on shape, still as `ModelStructureMismatch`. The message string tells you which. Matching it is straightforward:

```rust
use rustyml::error::{Error, IoError};
use rustyml::neural_network::layers::activation::linear::Linear;
use rustyml::neural_network::layers::dense::Dense;
use rustyml::neural_network::sequential::Sequential;

fn main() {
    // Save a one-layer model.
    let mut saved = Sequential::new();
    saved.add(Dense::new(2, 2, Linear::new()).unwrap());
    let path = "mismatch_demo.bin";
    saved.save_to_path(path).unwrap();

    // Rebuild with the wrong layer count and try to load it.
    let mut wrong = Sequential::new();
    wrong
        .add(Dense::new(2, 2, Linear::new()).unwrap())
        .add(Dense::new(2, 2, Linear::new()).unwrap());

    match wrong.load_from_path(path) {
        Err(Error::Io(IoError::ModelStructureMismatch(msg))) => {
            println!("rejected as expected: {msg}");
        }
        Err(other) => panic!("unexpected error: {other:?}"),
        Ok(()) => panic!("load must not succeed on a structure mismatch"),
    }

    std::fs::remove_file(path).unwrap();
}
```

The type-name check is by string, so it catches the common mistakes — a Conv layer where a Dense was saved, a missing or extra layer — but it does not validate hyperparameters that leave the type name and weight shapes unchanged. Two `Dense` layers with the same shapes but different activations will load without complaint, because the activation is not on disk. This is the concrete downside of storing metadata tags rather than a full architecture, and the reason the `make_arch`-closure discipline matters.

## 3.9.7. The postcard format: size, speed, portability

postcard is a compact, non-self-describing binary format. Non-self-describing means field names are absent from the stream — only the values are written, in declaration order — which is why the files are small but also why they are tied to the exact struct/enum layout of the crate that wrote them. Size is easy to predict: each parameter is an `f32`, four bytes, plus a small fixed overhead for array dimensions (varint-encoded), enum discriminants (one byte each for these small enums), and the short metadata strings. The `Total params: N (N*4 B)` line printed by `Sequential::summary` is therefore a close upper estimate of the on-disk size — a 100k-parameter model lands around 400 KB. Serialization is a single linear pass with one buffered write, so I/O, not CPU, dominates.

The format is portable across machines. postcard specifies its own byte order rather than dumping native-endian memory, so a checkpoint written on one architecture deserializes correctly on another regardless of the host's endianness — no conversion step, no per-platform variants. What it is *not* portable across is crate versions; that is the subject of the next section.

## 3.9.8. Workflow recipes

**Checkpoint the best model.** Train in short rounds, evaluate a validation metric after each, and overwrite a single file whenever the metric improves. Because `save_to_path` truncates, the file always holds the best-so-far weights, and the final in-memory model — which may have overfit past the best point — is discarded in favor of the reload. Compute the metric however you like; here it is a hand-rolled MSE so the example stays self-contained.

```rust
use ndarray::Array;
use rustyml::error::Error;
use rustyml::neural_network::Tensor;
use rustyml::neural_network::layers::activation::linear::Linear;
use rustyml::neural_network::layers::dense::Dense;
use rustyml::neural_network::losses::MeanSquaredError;
use rustyml::neural_network::optimizers::SGD;
use rustyml::neural_network::sequential::Sequential;

fn make_arch() -> Sequential {
    let mut m = Sequential::new();
    m.add(Dense::new(4, 3, Linear::new()).unwrap())
        .add(Dense::new(3, 2, Linear::new()).unwrap());
    m
}

fn mse(pred: &Tensor, target: &Tensor) -> f32 {
    (pred - target).mapv(|v| v * v).mean().unwrap()
}

fn main() -> Result<(), Error> {
    let x: Tensor = Array::from_shape_vec((2, 4), vec![0.1f32, 0.2, 0.3, 0.4, -0.1, -0.2, -0.3, -0.4])
        .unwrap()
        .into_dyn();
    let y: Tensor = Array::from_shape_vec((2, 2), vec![1.0f32, 0.0, 0.0, 1.0])
        .unwrap()
        .into_dyn();

    let mut model = make_arch();
    model.compile(SGD::new(0.05, 0.0, false, 0.0).unwrap(), MeanSquaredError::new());

    let path = "best.bin";
    let mut best = f32::INFINITY;
    for round in 0..10 {
        model.fit(&x, &y, 2)?;
        let val = mse(&model.predict(&x)?, &y);
        if val < best {
            best = val;
            model.save_to_path(path)?; // overwrites the previous checkpoint
            println!("round {round}: new best {val:.6}, checkpoint written");
        }
    }

    // best.bin holds the lowest-loss weights, not necessarily the final ones.
    let mut deployed = make_arch();
    deployed.load_from_path(path)?;
    println!("restored best MSE: {:.6}", mse(&deployed.predict(&x)?, &y));

    std::fs::remove_file(path).unwrap();
    Ok(())
}
```

**Transfer weights between programs.** A training binary builds the architecture, trains, and calls `save_to_path`; a separate serving binary builds the *identical* architecture and calls `load_from_path`. Share the `make_arch` function through a common module or crate so the two programs cannot disagree — the type-name and count checks will catch a drift, but only after a failed load, whereas a shared constructor catches it at compile time. The serving binary never needs to `compile`, since it only calls `predict`.

**Versioning across crate upgrades.** This is the one that bites silently. The file has no magic bytes and no version header, and postcard is non-self-describing, so the decoder assumes the exact weight-struct layout of the crate doing the loading. If a future RustyML release adds a field to a weight struct, reorders the `LayerWeight` variants, or changes a field's type, an old file will at best fail with `IoError::Serialization` and at worst misparse into plausible-looking but wrong arrays. Nothing in the format detects this. So for any checkpoint you need to reload weeks or versions later, pin the RustyML version in `Cargo.toml`, and after a deliberate upgrade, re-run training (or load under the old version and re-save under the new one) rather than trusting an old blob against new code. For a deeper treatment of the persistence machinery — the `get_weights` inspection path, the `SerializableSequential` wrapper, and how weights are applied back through downcasting — see [7.2. Model Persistence in Depth](../Chapter-07/7.2._Model_Persistence_in_Depth.md).
