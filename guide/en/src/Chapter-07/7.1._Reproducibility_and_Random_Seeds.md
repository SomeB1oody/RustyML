# 7.1. Reproducibility and Random Seeds

Every stochastic component in RustyML draws its randomness through one internal chokepoint, the crate-level `random` module, so a single seed can pin an entire experiment. That design is deliberate and worth understanding in full: the rules are simple, but a couple of their consequences (order-sensitivity, thread-locality) bite people who assume seeding works the way it does in NumPy's process-global `np.random`. If you come from scikit-learn's per-estimator `random_state` or Keras' global `keras.utils.set_random_seed`, RustyML gives you both mechanisms at once, and this page is about how they interact.

## 7.1.1. The two public entry points

The entire public surface is two free functions, re-exported at the crate root:

```rust,ignore
pub fn set_global_seed(seed: u64);
pub fn clear_global_seed();
```

`set_global_seed` installs a seed for the calling thread; `clear_global_seed` removes it, restoring entropy-based behavior. There is no getter, no global object to pass around, and no per-call RNG you construct yourself. Instead, each component takes an `Option<u64>` — usually surfaced as a `.with_random_state(seed)` builder method or a `random_state` argument — and the internal resolver reconciles that against the global seed. You call `set_global_seed` once, before you construct the models whose randomness you want to fix, and everything downstream falls into line.

Two internal resolvers do the reconciling. `make_rng(random_state)` always returns a concrete RNG, falling back to OS entropy when nothing is seeded; almost every component uses it. `make_rng_opt(random_state)` returns `Option<StdRng>` and yields `None` when neither a local nor a global seed is in effect — that is the signal "no randomization was requested." The decision tree uses this second form so that split tie-breaking stays fully deterministic unless you actually ask for randomness (see [2.4. Decision Trees](../Chapter-02/2.4._Decision_Trees.md)); with `make_rng_opt`, an unseeded tree does not randomize ties at all, rather than randomizing them from entropy.

## 7.1.2. The three-way seed resolution rule

Given a component's `random_state: Option<u64>` and the thread-local global seed, resolution is exactly this:

| Component `random_state` | Global seed set? | Result |
| --- | --- | --- |
| `Some(seed)` | either | Use `seed` directly. The global stream is **ignored and left untouched**. |
| `None` | yes | Derive an independent sub-seed by advancing the global stream one step. |
| `None` | no | Seed from OS entropy — **not reproducible**. |

The mechanism is small enough to read in one glance:

```rust,ignore
match random_state {
    Some(seed) => StdRng::seed_from_u64(seed),           // independent; global untouched
    None => match global_seed_rng {
        Some(global) => StdRng::seed_from_u64(global.next_u64()), // sub-seed from the stream
        None => StdRng::from_rng(&mut rng()),            // no seed anywhere: OS entropy
    },
}
```

The important structural fact is the asymmetry between the two branches. An explicit `Some(seed)` builds its RNG from that number alone and never calls `next_u64()` on the global stream. A `None` under a global seed *consumes one draw* from the stream. So the global seed behaves like a generator of sub-seeds, handed out in the order that unseeded draws ask for them, while an explicit `Some` seed resolves without touching the stream at all. Whether that makes a whole *component* inert, though, depends on when the component draws — which is the subject of the next section.

## 7.1.3. Order-sensitivity and when a seed is really inert

Two consequences of the rule matter in practice, and one of them is a common trap.

The first is order-sensitivity. Unseeded components draw their sub-seeds from the shared stream in the order they ask for them, so their reproducibility depends on construction order. Build model A then model B and each gets a specific sub-seed; build B then A and the sub-seeds swap. This is exactly Keras' global-seed behavior, and it means a global seed only reproduces a run whose construction sequence is also the same.

The second is inertness, and here you have to be precise about *what* is inert. The resolver guarantees that `make_rng(Some(seed))` never calls `next_u64()` on the global stream — an explicit seed consumes nothing from it. Whether that makes a whole *component* inert depends on when the component actually draws, and RustyML has two families:

- **Deferred-draw estimators** — `KMeans`, `SVC`, `LinearSVC`, `IsolationForest`, the decision tree, `t-SNE`, `train_test_split`, and the `Sequential` shuffle seed — store `random_state` as a plain field and resolve it exactly once, inside `fit`. For these the inertness property holds end to end: constructing one with `.with_random_state(s)` touches nothing at build time, and fitting it uses seed `s` without advancing the global stream, so splicing one in leaves every *un*seeded estimator's sub-seed untouched.
- **Eagerly-initialized NN layers** — `Dense`, the dropout/noise layers, the convolutional and recurrent layers — initialize their weights or masks *at construction*, through `make_rng(None)`, which draws one sub-seed from the global stream. `.with_random_state(s)` is a post-hoc re-initialization: it overwrites that layer's own weights, but the sub-seed its `Dense::new` already pulled is gone for good. So a seeded layer still advances the global stream by exactly one — its *construction*, not its seededness, is what fixes the sub-seeds of the layers built after it.

That second family is where people get caught out. The program below splices a `.with_random_state(999)` layer between two unseeded layers and watches the layer *after* it shift, because the spliced layer's `Dense::new` consumed a sub-seed on the way in:

```rust
use ndarray::Array2;
use rustyml::neural_network::Tensor;
use rustyml::neural_network::layers::Activation;
use rustyml::neural_network::layers::dense::Dense;
use rustyml::neural_network::traits::Layer;
use rustyml::{clear_global_seed, set_global_seed};

fn row() -> Tensor {
    Array2::from_shape_vec((1, 4), vec![0.5, -1.0, 2.0, 0.25])
        .unwrap()
        .into_dyn()
}

fn max_abs_diff(a: &Tensor, b: &Tensor) -> f32 {
    a.iter()
        .zip(b.iter())
        .map(|(x, y)| (x - y).abs())
        .fold(0.0_f32, f32::max)
}

fn main() {
    let x = row();

    // Run A: two consecutive unseeded layers draw sub-seed #1 then sub-seed #2.
    set_global_seed(42);
    let a1 = Dense::new(4, 3, Activation::Linear).unwrap();
    let a2 = Dense::new(4, 3, Activation::Linear).unwrap();

    // Run B: identical, except a .with_random_state(999) layer is spliced in between.
    set_global_seed(42);
    let b1 = Dense::new(4, 3, Activation::Linear).unwrap();
    let _seeded = Dense::new(4, 3, Activation::Linear)
        .unwrap()
        .with_random_state(999);
    let b2 = Dense::new(4, 3, Activation::Linear).unwrap();
    clear_global_seed();

    let (pa1, pa2) = (a1.predict(&x).unwrap(), a2.predict(&x).unwrap());
    let (pb1, pb2) = (b1.predict(&x).unwrap(), b2.predict(&x).unwrap());

    // The first unseeded layer is unaffected: same seed, same construction position.
    assert_eq!(max_abs_diff(&pa1, &pb1), 0.0);

    // Two consecutive unseeded layers differ: the stream advanced between them.
    assert!(max_abs_diff(&pa1, &pa2) > 1e-4);

    // b2 does NOT match a2. The spliced layer's Dense::new drew a sub-seed before
    // with_random_state re-initialized it, so b2 received sub-seed #3, not #2.
    assert!(max_abs_diff(&pa2, &pb2) > 1e-4);

    println!("layer construction advances the global stream, seeded or not");
}
```

The takeaway is the same for both families: to make a run survive refactoring that inserts or reorders stochastic components, give each one its own explicit `random_state` rather than leaning on the global stream's ordering. For a deferred-draw estimator that decouples it completely; for an eagerly-initialized layer it fixes that layer's own weights, and you additionally keep the sequence of layer constructions between your seed call and each draw stable. The global seed is the convenient path for a fixed, linear pipeline; explicit per-component seeds are the robust one.

## 7.1.4. Thread-local semantics

The global seed lives in a `thread_local!` cell. This is what keeps `set_global_seed` lock-free and contention-free, but it has a hard consequence: **the seed only affects the thread that called `set_global_seed`.** Set it on the same thread that constructs your models, and everything is fine. Move construction to another thread and the seed is invisible there.

This matters in three settings.

**Spawned threads and async runtimes.** If you `std::thread::spawn` a worker that builds an unseeded model, or you construct models inside `tokio`/`rayon` tasks, those threads start with no global seed and fall back to entropy. Call `set_global_seed` at the top of each worker, or — better — give each component an explicit `random_state`, which is thread-independent by construction.

**Internal parallelism.** Some estimators build their RNGs on the calling thread before parallelizing (KMeans creates its k-means++ RNG once, up front, so a global seed reaches it). But the `IsolationForest` is the sharp edge here: it constructs one RNG *inside each per-tree closure*, and once `n_estimators >= 10` those closures run on Rayon worker threads via `into_par_iter()`. On the `None` path, each worker calls the resolver, finds no thread-local global (the seed lives on your thread, not theirs), and falls back to entropy — so **a global seed alone does not make a parallel `IsolationForest` reproducible.** Its explicit path is built to survive this: `.with_random_state(s)` gives tree `i` the seed `s + i`, computed with no reference to any thread-local state, so it reproduces identically no matter which worker runs which tree. The rule of thumb: for any component that constructs randomness across worker threads, use an explicit `random_state`, not the global seed. See [7.3. Performance Tuning and Parallelism](./7.3._Performance_Tuning_and_Parallelism.md) for where parallelism kicks in.

**The test harness.** Rust's default test harness spawns a fresh thread per test, so each test starts with the global seed unset — clean isolation for free. Under `cargo test -- --test-threads=1`, however, every test runs on one shared thread, and a test that calls `set_global_seed` leaks that seed into every later test that expected unseeded (entropy) behavior. Clear it afterwards, panic-safely, with a drop guard. The crate's own integration tests use exactly this pattern:

```rust,ignore
#[must_use]
pub struct GlobalSeedGuard;

impl GlobalSeedGuard {
    pub fn set(seed: u64) -> Self {
        rustyml::set_global_seed(seed);
        GlobalSeedGuard
    }
}

impl Drop for GlobalSeedGuard {
    fn drop(&mut self) {
        rustyml::clear_global_seed(); // runs even on panic/unwind
    }
}
```

Bind it to a variable (`let _seed = GlobalSeedGuard::set(123);`) so it lives for the test body and clears on the way out. An unbound `GlobalSeedGuard::set(123);` drops immediately and clears the seed before you use it — hence the `#[must_use]`.

## 7.1.5. What draws randomness across the crate

Everything below routes through the same resolver, so one global seed covers all of it on the constructing thread — with the parallelism caveat from the previous section. Each row also lists the per-component override, which is the seed you reach for when you want independence from construction order or from the calling thread.

| Component | How to seed it | Reached by the global seed? | Notes |
| --- | --- | --- | --- |
| NN layer weight init (`Dense`, conv, recurrent, ...) | `.with_random_state(seed)` | Yes | Re-runs Xavier/Glorot uniform init; call it *before* training. See [3.2](../Chapter-03/3.2._Dense_Layers_and_Activations.md). |
| Dropout / spatial dropout / gaussian noise masks | `.with_random_state(seed)` | Yes | The mask RNG is owned by the layer. See [3.8](../Chapter-03/3.8._Regularization_and_Normalization_Layers.md). |
| `Sequential` minibatch shuffle | `.set_seed(seed)` or `Sequential::new_with_seed(seed)` | Yes (seed field defaults to `None`) | Only affects `fit_with_batches`; does not touch layer weights. See [3.1](../Chapter-03/3.1._The_Sequential_Model.md). |
| `KMeans` (k-means++ init) | `.with_random_state(seed)` | Yes | RNG built once on the calling thread. See [2.7](../Chapter-02/2.7._KMeans_Clustering.md). |
| `SVC` / `LinearSVC` | `.with_random_state(seed)` | Yes | Working-set selection (`SVC`) and minibatch shuffling (`LinearSVC`). See [2.5](../Chapter-02/2.5._Support_Vector_Machines.md). |
| `estimate_bandwidth` (Mean Shift helper) | `estimate_bandwidth(x, quantile, n_samples, Some(seed))` | Yes | Randomness is in the subsampling; `MeanShift::fit` itself (bin seeding included) is deterministic. See [2.9](../Chapter-02/2.9._Mean_Shift.md). |
| `IsolationForest` | `.with_random_state(seed)` | **Not on the parallel path** | Explicit seed required for reproducibility once `n_estimators >= 10`; per-tree seed is `seed + i`. See [2.13](../Chapter-02/2.13._Isolation_Forest.md). |
| Decision tree split tie-breaking | `.with_random_state(seed)` | Yes | Uses `make_rng_opt`: ties are randomized *only* when a seed is in effect, otherwise fully deterministic. |
| `t-SNE` random init | `.with_random_state(seed)` **and** `.with_init(Init::Random)` | Yes | The default `Init::PCA` is deterministic and ignores `random_state`. See [2.12](../Chapter-02/2.12._t-SNE.md). |
| `train_test_split` / `train_test_split_stratified` | `random_state: Option<u64>` argument | Yes | Controls the index shuffle. See [4.1](../Chapter-04/4.1._Train_Test_Split.md). |

Two of these deserve a second look. The `t-SNE` seed does nothing on the default code path: `Init::PCA` initializes the embedding from the top principal components, which is deterministic, so `random_state` only matters after you opt into `.with_init(Init::Random)`. And Mean Shift is often mistaken for a seeded estimator — the `MeanShift` struct has no `random_state` at all; the only draw in that module is the optional subsampling inside the free `estimate_bandwidth` helper, which you call yourself to pick a bandwidth.

### Intentional exclusions

Not every pseudo-random draw in the crate is routed through this module — only the ones with a persistent effect on the result. The `pca` and `kernel_pca` dimensionality reducers are deliberately left out. Their iterative eigensolvers (power iteration, Lanczos) seed a random *starting vector* with a fixed constant; such methods converge to the same eigenvectors regardless of the generic starting vector, so the seed is observationally inert — it only pins otherwise-arbitrary eigenvector signs, and routing it through ambient global state would make that sign choice *less* reproducible for no benefit. Randomized SVD (`pca`'s `SVDSolver::Randomized(u64)`) takes its seed inside the public solver variant, so the caller always pins it explicitly and there is no `None` path for the global to fill. The general rule the crate follows: route a draw through this module only when it makes a pseudo-random choice that changes the result.

## 7.1.6. What a seed does not freeze

A seed makes the *pseudo-random choices* reproducible. It does not make everything about a run bit-identical.

**Floating-point reduction order is a separate axis.** Summing a vector or a matrix product in parallel can produce results that differ in the last bits from a serial sum, because floating-point addition is not associative — and that has nothing to do with seeding. If you need bit-stable numeric results, you control it through the parallelism knobs, not the seed. See [6.3. Parallel Reductions](../Chapter-06/6.3._Parallel_Reductions.md) and [7.3. Performance Tuning and Parallelism](./7.3._Performance_Tuning_and_Parallelism.md).

**Cross-machine bit-identity is not guaranteed.** Two machines with the same seed will make the same random choices, but differences in floating-point rounding, SIMD width, thread count, and BLAS-free reduction order can still make the final weights differ in low-order bits. Same seed gives you the same *sequence of decisions*; it does not give you byte-for-byte identical floats across architectures.

**A seed does not survive a thread hop or persist across a save/load boundary by itself.** Reloading a trained model from disk gives you its frozen weights, not the RNG stream that produced them; if you continue training a reloaded model, re-establish the seed on the current thread. See [7.2. Model Persistence in Depth](./7.2._Model_Persistence_in_Depth.md).

## 7.1.7. Recipes

### Reproducible experiment template

For a single, linear construction sequence on one thread, `set_global_seed` once at the top is the least intrusive way to make an entire pipeline reproducible. Leave every component unseeded (`random_state == None`) and let them draw sub-seeds from the stream in order — including the `Sequential` shuffle, whose seed field defaults to `None` and is therefore covered by the global too:

```rust
use ndarray::Array2;
use rustyml::neural_network::Tensor;
use rustyml::neural_network::layers::Activation;
use rustyml::neural_network::layers::dense::Dense;
use rustyml::neural_network::losses::MeanSquaredError;
use rustyml::neural_network::optimizers::SGD;
use rustyml::neural_network::sequential::Sequential;
use rustyml::set_global_seed;

fn t2(rows: usize, cols: usize, data: Vec<f32>) -> Tensor {
    Array2::from_shape_vec((rows, cols), data).unwrap().into_dyn()
}

fn main() {
    // One call up front. Every unseeded draw below derives from this, in order.
    set_global_seed(2026);

    #[rustfmt::skip]
    let x = t2(4, 4, vec![
        0.5, -1.0,  2.0,  0.25,
        1.0,  0.0, -0.5,  1.5,
       -2.0,  0.5,  1.0, -1.0,
        0.25, 2.0, -1.5,  0.0,
    ]);
    let y = t2(4, 1, vec![1.0, 0.0, -1.0, 0.5]);

    let mut model = Sequential::new(); // no per-layer seeds, no explicit set_seed
    model
        .add(Dense::new(4, 3, Activation::ReLU).unwrap())   // sub-seed #1
        .add(Dense::new(3, 1, Activation::Linear).unwrap()) // sub-seed #2
        .compile(SGD::new(0.05, 0.0, false, 0.0).unwrap(), MeanSquaredError::new());

    // batch_size < n_samples exercises the per-epoch shuffle (sub-seed #3).
    model.fit_with_batches(&x, &y, 5, 2).unwrap();

    let p = model.predict(&t2(1, 4, vec![0.5, -1.0, 2.0, 0.25])).unwrap();
    println!("prediction shape: {:?}", p.shape());
}
```

Run this twice and the trained weights are byte-identical, because the construction order — two layer inits, then the shuffle RNG — pulls the same three sub-seeds from the `2026` stream each time. The moment you reorder those `.add` calls, the sub-seed assignment changes; that is the order-sensitivity from 7.1.3, made concrete.

### Per-component `random_state` overrides

When you want each component pinned independently of construction order and of which thread runs it — the robust choice for library code, parallel estimators, and anything you refactor often — set `random_state` on each component directly. Explicit seeds ignore the global stream entirely, so this is also how you reproduce one component while leaving the rest free:

```rust
use ndarray::{Array1, Array2, array};
use rustyml::prelude::*;

fn main() {
    // Two well-separated blobs, 6 samples, 2 features.
    let x: Array2<f64> = array![
        [0.0, 0.0], [0.2, 0.1], [0.1, -0.2],
        [5.0, 5.0], [5.2, 4.9], [4.8, 5.1],
    ];
    let y: Array1<usize> = array![0, 0, 0, 1, 1, 1];

    // Same random_state => same index shuffle => same split, every run.
    let split_a = train_test_split(x.clone(), y.clone(), Some(0.5), Some(42)).unwrap();
    let split_b = train_test_split(x.clone(), y.clone(), Some(0.5), Some(42)).unwrap();
    assert_eq!(split_a.0, split_b.0); // x_train identical
    assert_eq!(split_a.2, split_b.2); // y_train identical

    // Same random_state => same k-means++ init => same labels, independent of the above.
    let labels_1 = KMeans::new(2, 100, 1e-4)
        .unwrap()
        .with_random_state(7)
        .fit_predict(&x)
        .unwrap();
    let labels_2 = KMeans::new(2, 100, 1e-4)
        .unwrap()
        .with_random_state(7)
        .fit_predict(&x)
        .unwrap();
    assert_eq!(labels_1, labels_2);

    println!("split and k-means both reproducible under explicit seeds");
}
```

Mix the two styles freely. A common shape is `set_global_seed` for the ambient defaults plus an explicit `random_state` on the one estimator you need to hold fixed while you sweep everything else — and because explicit seeds are inert against the global stream, pinning that one estimator does not disturb the sub-seeds every other component receives.
