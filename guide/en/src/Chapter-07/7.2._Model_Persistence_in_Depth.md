# 7.2. Model Persistence in Depth

RustyML has two persistence stories that share one wire format, and knowing exactly where they diverge is the difference between a checkpoint you can trust and a file that silently loads the wrong numbers. Classical estimators serialize the *entire* model — hyperparameters, learned parameters, and training metadata — so loading gives you a ready-to-predict object with no reconstruction. Neural networks serialize *weights only*: you rebuild the architecture in code and pour the arrays back in. Both write [postcard](https://docs.rs/postcard), a compact non-self-describing binary format, and that single choice explains why the files are small, why they are Rust-only, and why loading across a version boundary is a hazard you have to manage yourself. This page is the under-the-hood companion to [3.9. Saving and Loading Weights](../Chapter-03/3.9._Saving_and_Loading_Weights.md): where 3.9 teaches the neural-network workflow, this one takes both worlds down to the byte level, the failure surface, and the operational patterns — versioning, atomic writes, and interop — that the two convenience methods do not give you for free.

## 7.2.1. Two APIs, one format

The two subsystems expose deliberately different signatures, and the mismatch bites if you assume they are the same method.

```rust,ignore
// Classical ML models — generated by the `model_save_and_load_methods!` macro in lib.rs:
impl LinearRegression {
    pub fn save_to_path(&self, path: &str) -> Result<(), rustyml::error::Error>;
    pub fn load_from_path(path: &str) -> Result<Self, rustyml::error::Error>;
}

// Sequential neural network:
impl Sequential {
    pub fn save_to_path(&self, path: impl AsRef<std::path::Path>) -> rustyml::error::RustymlResult<()>;
    pub fn load_from_path(&mut self, path: impl AsRef<std::path::Path>) -> rustyml::error::RustymlResult<()>;
}
```

Three asymmetries matter. First, the classical `save_to_path`/`load_from_path` take `&str` only — not `impl AsRef<Path>` — so a `PathBuf` needs an explicit `.to_str().unwrap()` or you get a type error; the neural-network methods accept any `AsRef<Path>`. Second, classical `load_from_path` is an *associated function* that returns an owned `Self` (there is nothing to load *into*, because the whole model comes off disk), whereas `Sequential::load_from_path` takes `&mut self` and mutates a model you already built. Third, `RustymlResult<()>` is just an alias for `Result<(), Error>`, so the error type is identical across both — every failure is a variant of the crate's unified [`Error`](../Chapter-01/1.6._Error_Handling.md). The macro that stamps out the classical pair lives in `lib.rs` as `model_save_and_load_methods!`, and it is applied verbatim to `LinearRegression`, `LogisticRegression`, `KNN`, `DecisionTree`, `SVC`, `LinearSVC`, `LDA`, `KMeans`, `DBSCAN`, `MeanShift`, `PCA`, `KernelPCA`, and `IsolationForest` — every model in the classical module gets the same two methods with the same behavior.

## 7.2.2. Classical ML: the whole model on disk

The macro body is short enough to hold in your head: `save_to_path` calls `postcard::to_allocvec(self)` and writes the bytes through a buffered writer; `load_from_path` reads the file and calls `postcard::from_bytes::<Model>(&bytes)`. Because the model struct derives `Serialize` and `Deserialize`, *every field* travels — for `LinearRegression` that is the `coefficients`, the `intercept`, `fit_intercept`, `learning_rate`, `max_iter`, `tol`, the post-fit `n_iter`, the `regularization_type`, and the `solver` enum. There is no separate "config" and "weights"; the distinction that dominates the neural-network side simply does not exist here. That is why a loaded model is immediately usable: `load_from_path` hands you back an object indistinguishable from the one you trained, with no `fit`, no re-parameterization, and no compile step.

```rust
use rustyml::machine_learning::*;
use ndarray::{Array1, Array2};

fn main() {
    let x = Array2::from_shape_vec((4, 2), vec![1.0, 2.0, 2.0, 1.0, 3.0, 5.0, 4.0, 3.0]).unwrap();
    let y = Array1::from_vec(vec![5.0, 5.0, 13.0, 11.0]);

    let mut model = LinearRegression::new(true, 0.05, 500, 1e-7).unwrap();
    model.fit(&x, &y).unwrap();

    let path = "lr_whole_model.bin";
    model.save_to_path(path).unwrap();

    // Load returns a fully usable model — no re-fit, no reconstruction, no compile step.
    let restored = LinearRegression::load_from_path(path).unwrap();

    // Both the learned parameters and the hyperparameters survived the round-trip.
    assert_eq!(restored.get_max_iterations(), 500);
    assert_eq!(restored.get_coefficients().unwrap().len(), 2);

    let probe = Array2::from_shape_vec((1, 2), vec![2.0, 4.0]).unwrap();
    let a = model.predict(&probe).unwrap();
    let b = restored.predict(&probe).unwrap();
    println!("live vs restored prediction gap: {:e}", (a[0] - b[0]).abs());

    std::fs::remove_file(path).unwrap();
}
```

If you come from scikit-learn's `pickle`/`joblib`, this is the same *mental* model — the whole estimator round-trips — but with two honest differences. Postcard is not `pickle`: it executes no code on load, so there is no arbitrary-code-execution risk from a hostile file, only the possibility of malformed or mismatched bytes. And postcard carries no class identity, no `__module__`, no version stamp — which is exactly what the next sections are about.

## 7.2.3. Neural networks: weights, and the enum that carries them

The neural-network path is covered end to end in [3.9](../Chapter-03/3.9._Saving_and_Loading_Weights.md); here is the mechanism one level lower. `Sequential::save_to_path` builds a `SerializableSequential { layers: Vec<SerializableLayer> }`, where each `SerializableLayer` pairs a `LayerInfo { layer_type, output_shape }` metadata tag with a `LayerWeight<'a>` enum value obtained from `layer.get_weights()`. That enum is the on-disk weight format:

```rust,ignore
pub enum LayerWeight<'a> {
    Dense(DenseLayerWeight<'a>),
    SimpleRNN(SimpleRNNLayerWeight<'a>),
    LSTM(LSTMLayerWeight<'a>),
    GRU(GRULayerWeight<'a>),
    Conv1D(Conv1DLayerWeight<'a>),
    Conv2D(Conv2DLayerWeight<'a>),
    Conv3D(Conv3DLayerWeight<'a>),
    SeparableConv2D(SeparableConv2DLayerWeight<'a>),
    DepthwiseConv2D(DepthwiseConv2DLayerWeight<'a>),
    BatchNormalization(BatchNormalizationLayerWeight<'a>),
    LayerNormalization(LayerNormalizationLayerWeight<'a>),
    InstanceNormalization(InstanceNormalizationLayerWeight<'a>),
    GroupNormalization(GroupNormalizationLayerWeight<'a>),
    Empty, // layers with no trainable parameters: Dropout, pooling, flatten, pure activations
}
```

Two design choices are worth pinning down. Each per-layer struct stores its arrays as [`Cow`](https://doc.rust-lang.org/std/borrow/enum.Cow.html), so the same type serves both directions — `get_weights` borrows the live arrays with `Cow::Borrowed` (saving clones nothing), and deserialization fills `Cow::Owned` arrays, used as `LayerWeight<'static>` on the load path. And the enum uses serde's default *externally tagged* representation, writing an explicit variant discriminant before the payload, because postcard is non-self-describing and cannot otherwise tell a `Dense` payload from a `Conv2D` one. What is deliberately absent from the file is any *constructor* information: no activation function, no `epsilon`, `momentum`, stride, kernel size, dilation, or group count. Those live in your source code. The `layer_type` and `output_shape` strings in `LayerInfo` are validation tags, not a build recipe — which is precisely why loading needs a pre-built model to pour into.

That pre-built model is what lets the neural-network loader do something the classical loader cannot: **validate structure**. `load_from_path` checks the layer count, checks each position's `layer_type` string against the model you built, and — inside `apply_weights_to_layer` — downcasts each layer to its concrete type and calls `set_weights`, so a shape disagreement is caught too. Any of these raises `Error::Io(IoError::ModelStructureMismatch)` with a message telling you which. The classical macro has no analogue: it deserializes bytes straight into the target struct with zero guard. Loading a `LinearRegression` file into `KMeans::load_from_path` is not rejected by any type check — postcard reads the bytes positionally, and you get either a `Serialization` error (the usual outcome, when the layouts disagree enough) or, in the unlucky case where the bytes happen to fit the other layout, a plausibly-parsed but meaningless model. Treat the filename or an external tag as the only thing standing between you and that outcome for classical models.

## 7.2.4. The postcard wire format

Postcard is a minimal binary serialization format with one property that governs everything else: it is **non-self-describing**. The bytes contain values in field order and nothing else — no field names, no type names, no schema, no length-prefixed envelope you can skip. Serializing `LinearRegression` does not write the string `"learning_rate"` anywhere; it writes the eight bytes of the `f64` at the position where `learning_rate` sits in the struct. That is the whole reason the files are tiny, and equally the reason they are brittle: correct interpretation depends entirely on the deserializing side having the *exact same* type layout the serializing side had.

The per-type encoding is worth knowing when you reason about file size or debug a corrupt file:

| Rust type | postcard encoding | bytes |
| --- | --- | --- |
| `bool` | single byte `0`/`1` | 1 |
| `f32` (neural-network weights) | fixed-width little-endian | 4 |
| `f64` (classical parameters) | fixed-width little-endian | 8 |
| `usize` / `u64` (e.g. `max_iter`, lengths) | LEB128 varint | 1–10 |
| enum variant (`Solver`, `LayerWeight`) | varint discriminant | 1 (+ payload) |
| `Option<T>` | 1 tag byte (`0`=None, `1`=Some) | 1 (+ `T` if Some) |
| `String` (layer type tags) | varint length + UTF-8 bytes | var |
| ndarray `Array` (via serde) | small version/shape header + varint element count + elements | var |

Floats are fixed-width, so an array of `N` values is `N × 4` (`f32`) or `N × 8` (`f64`) bytes plus a handful for the shape header and length prefix — the round-trip is lossless, not lossy. Integers and lengths are varints, so small counts cost one byte. There is no compression and no alignment padding. The format's compactness is exactly its fragility: because nothing is labeled, a struct whose layout drifted — a field added, removed, reordered, or retyped between the version that wrote the file and the version that reads it — deserializes without any name to check against. The likely result is an "unexpected end of input" or bad-tag `Serialization` error; the dangerous result is a silent misparse when the drifted layout still happens to consume the bytes. This is not a bug in postcard — it is the deal you accept for the small file — and it is why versioning (below) is your responsibility, not the format's.

## 7.2.5. File size: a back-of-envelope you can trust

Because the encoding has no compression and no framing, file size is predictable to within a few bytes. For a classical model the payload is dominated by its learned arrays: a `LinearRegression` with `p` features is essentially `p × 8` bytes of coefficients plus a couple dozen bytes of scalar hyperparameters and headers. For a neural network it is the sum over layers of `(weight_elements + bias_elements) × 4` bytes, since neural-network weights are `f32`, plus the small per-layer type/shape strings. A `Dense(784 → 128)` layer is `784 × 128 + 128 = 100,480` parameters ≈ 392 KB; the same layer in a classical `f64` world would be twice that. Measure it directly rather than guessing:

```rust
use rustyml::machine_learning::*;
use ndarray::{Array1, Array2};

fn main() {
    let n_features = 8usize;
    let n_samples = 20usize;
    let x = Array2::from_shape_fn((n_samples, n_features), |(i, j)| (i + j) as f64 * 0.1);
    let y = Array1::from_shape_fn(n_samples, |i| i as f64);

    let mut model = LinearRegression::new(true, 0.01, 100, 1e-6).unwrap();
    model.fit(&x, &y).unwrap();

    let path = "lr_size_probe.bin";
    model.save_to_path(path).unwrap();

    let on_disk = std::fs::metadata(path).unwrap().len();
    // Dominant term: one f64 per coefficient. Everything else is scalars + small headers.
    let coefficient_bytes = (n_features * std::mem::size_of::<f64>()) as u64;
    println!("file: {on_disk} bytes, coefficient payload ~= {coefficient_bytes} bytes");

    std::fs::remove_file(path).unwrap();
}
```

The practical consequence: postcard checkpoints are cheap to keep many of. A "save every epoch, keep the best" loop over a small model costs kilobytes per checkpoint, so the constraint on how often you snapshot is disk-write latency, not size. For large convolutional stacks the `f32` weights dominate and the file tracks parameter count almost exactly, which makes capacity planning trivial: count the parameters, multiply by four.

## 7.2.6. What loading actually rejects

Every persistence failure surfaces as `Error::Io(...)`, and there are exactly three shapes underneath. `IoError::Std` wraps a `std::io::Error` — a missing path, a permissions problem, a read or write that failed. `IoError::Serialization` wraps a `postcard::Error` — the bytes are not valid postcard for the expected layout: corruption, truncation, or a schema that no longer matches. `IoError::ModelStructureMismatch` is neural-network-only and, as covered in 7.2.3, has no classical counterpart. The two `From` impls in `error.rs` are what let `?` lift a raw `std::io::Error` into `IoError::Std` and a raw `postcard::Error` into `IoError::Serialization`, so the mapping is automatic and consistent across both subsystems. Both `Error` and `IoError` are `#[non_exhaustive]`, so always include a trailing catch-all arm when you match them.

```rust
use rustyml::machine_learning::*;
use rustyml::error::{Error, IoError};

fn main() {
    // A file full of bytes that are not valid postcard for a LinearRegression.
    let junk = "corrupt_lr.bin";
    std::fs::write(junk, b"\xff\xff\xff not a model").unwrap();

    match LinearRegression::load_from_path(junk) {
        Ok(_) => println!("unexpected success"),
        Err(Error::Io(IoError::Serialization(e))) => println!("bad bytes -> Serialization: {e}"),
        Err(Error::Io(IoError::Std(e))) => println!("io failure: {e}"),
        Err(e) => println!("other: {e}"),
    }
    std::fs::remove_file(junk).unwrap();

    // A path that does not exist surfaces as IoError::Std, not Serialization.
    match LinearRegression::load_from_path("no_such_model_9f3a.bin") {
        Err(Error::Io(IoError::Std(e))) => println!("missing file -> Std: {e}"),
        other => println!("unexpected: {other:?}"),
    }
}
```

The neural-network test suite pins these mappings down against the real API: a nonexistent path yields `IoError::Std`, deliberately corrupt bytes yield `IoError::Serialization`, and layer-count, layer-type, and weight-shape disagreements all yield `IoError::ModelStructureMismatch`. The lesson for classical models is the gap in that list — there is no structural error to catch, so `Serialization` is the *only* signal that a file is wrong, and it is not a reliable one. If a corrupt classical file happens to deserialize, `load_from_path` returns `Ok`. Guard against that with your own integrity check, which is what the next two sections build.

## 7.2.7. Versioning across RustyML releases

Postcard files carry no version stamp, and RustyML makes no guarantee that a model struct's field layout is stable across releases. Add a hyperparameter to `LinearRegression`, reorder a field, or change a type, and files written by the older version become undefined-to-error input for the newer one — usually a `Serialization` failure, occasionally a silent misparse. There is no built-in migration path. Two habits keep this from surprising you in production.

First, pin the exact `rustyml` version that writes your long-lived checkpoints, so a routine `cargo update` cannot silently change the on-disk layout underneath a directory of saved models:

```toml
[dependencies]
rustyml = { version = "=0.13.0", features = ["full"] }
```

Second, because the format cannot version itself, write a version *sidecar*: a tiny companion file next to the model recording the format identity, and refuse to load when it does not match what your binary expects. This turns a silent misparse into a loud, early error.

```rust
use rustyml::machine_learning::*;
use ndarray::{Array1, Array2};

// Bump this whenever you upgrade the rustyml dependency that writes your checkpoints.
const CHECKPOINT_FORMAT: &str = "rustyml-0.13";

fn main() {
    let x = Array2::from_shape_vec((3, 2), vec![1.0, 2.0, 2.0, 3.0, 3.0, 4.0]).unwrap();
    let y = Array1::from_vec(vec![6.0, 9.0, 12.0]);

    let mut model = LinearRegression::new(true, 0.01, 200, 1e-6).unwrap();
    model.fit(&x, &y).unwrap();

    let model_path = "sidecar_model.bin";
    let version_path = "sidecar_model.bin.version";
    model.save_to_path(model_path).unwrap();
    std::fs::write(version_path, CHECKPOINT_FORMAT).unwrap();

    // On load, gate the deserialize on the recorded format string.
    let recorded = std::fs::read_to_string(version_path).unwrap();
    if recorded != CHECKPOINT_FORMAT {
        panic!("checkpoint written by {recorded}, this binary expects {CHECKPOINT_FORMAT}");
    }
    let restored = LinearRegression::load_from_path(model_path).unwrap();
    println!("loaded {} coefficients", restored.get_coefficients().unwrap().len());

    std::fs::remove_file(model_path).unwrap();
    std::fs::remove_file(version_path).unwrap();
}
```

Use a version string granular enough to matter — the `rustyml` version at minimum, and your own schema counter if you wrap models in a larger record. The sidecar costs nothing to write and converts the format's worst failure mode (silent wrong numbers) into a `panic` you catch in testing.

## 7.2.8. Atomic checkpoints

Both `save_to_path` variants call `File::create`, which **truncates the target immediately**. If the process crashes, the disk fills, or a training loop is killed partway through the write, you are left with a truncated file at the exact path your restart logic will try to load — and truncation is a `Serialization` error at best, a subtly short array at worst. The standard defense is write-then-rename: serialize to a temporary path on the same filesystem, then `std::fs::rename` it over the final path. Rename is atomic on POSIX filesystems, so a reader either sees the complete old file or the complete new one, never a half-written one.

```rust
use rustyml::machine_learning::*;
use ndarray::{Array1, Array2};

/// Save through a temp file and an atomic rename so a crash mid-write never
/// leaves a half-written checkpoint at `final_path`.
fn save_atomically(model: &LinearRegression, final_path: &str) -> std::io::Result<()> {
    let tmp_path = format!("{final_path}.tmp");
    model
        .save_to_path(&tmp_path)
        .expect("serialize to temp file");
    std::fs::rename(&tmp_path, final_path)
}

fn main() {
    let x = Array2::from_shape_vec((3, 2), vec![1.0, 2.0, 2.0, 3.0, 3.0, 4.0]).unwrap();
    let y = Array1::from_vec(vec![6.0, 9.0, 12.0]);

    let mut model = LinearRegression::new(true, 0.01, 200, 1e-6).unwrap();
    model.fit(&x, &y).unwrap();

    let path = "atomic_model.bin";
    save_atomically(&model, path).unwrap();

    let restored = LinearRegression::load_from_path(path).unwrap();
    println!("intercept present after atomic save: {}", restored.get_intercept().is_some());

    std::fs::remove_file(path).unwrap();
}
```

Keep the temporary file on the same filesystem as the destination — `rename` across filesystems is not atomic and degrades to a copy-plus-delete. Pair this with the sidecar from 7.2.7 by renaming the model *first* and the version file *second*, and a torn write leaves the version sidecar pointing at the previous, complete model rather than a corrupt new one. For a "keep only the best" loop, atomic replace also means your best-so-far file is never momentarily absent.

## 7.2.9. Crossing the language boundary

Postcard is a Rust-ecosystem format. There is no maintained Python or R reader for it, and even if there were, the non-self-describing bytes would be useless without a hand-written schema mirroring RustyML's exact struct layout — which changes between versions. So treat a `.bin` checkpoint as a RustyML-to-RustyML artifact and nothing else. When another tool has to consume a trained model, do not try to parse the postcard file; **export the parameters through the getters** into a portable format the other side already reads. Classical models expose everything you need: `LinearRegression::get_coefficients` and `get_intercept`, `KMeans::get_centroids`, and the corresponding accessors on the other estimators.

```rust
use rustyml::machine_learning::*;
use ndarray::{Array1, Array2};

fn main() {
    let x = Array2::from_shape_vec(
        (3, 3),
        vec![1.0, 0.0, 2.0, 0.0, 1.0, 1.0, 2.0, 2.0, 0.0],
    )
    .unwrap();
    let y = Array1::from_vec(vec![4.0, 3.0, 6.0]);

    let mut model = LinearRegression::new(true, 0.01, 500, 1e-7).unwrap();
    model.fit(&x, &y).unwrap();

    // Pull learned parameters out through the getters and emit portable CSV that a
    // Python / R / spreadsheet consumer can read directly — no postcard involved.
    let coefficients = model.get_coefficients().expect("model is fitted");
    let intercept = model.get_intercept().unwrap_or(0.0);

    let mut csv = String::from("term,value\n");
    for (i, c) in coefficients.iter().enumerate() {
        csv.push_str(&format!("x{i},{c}\n"));
    }
    csv.push_str(&format!("intercept,{intercept}\n"));

    print!("{csv}");
}
```

The same pattern generalizes: dump the getter output as CSV for a spreadsheet or a pandas `read_csv`, or assemble it into a JSON object your service already speaks. For a neural network, iterate `Sequential::get_weights()` and write each `LayerWeight` variant's arrays out layer by layer — the arrays are ndarrays, so `.iter()` plus your formatter of choice is all it takes. This costs you the compactness of postcard and the exactness guarantee of a same-format round-trip, so keep the postcard file as your canonical checkpoint for reloading *into RustyML* and treat the exported CSV/JSON as a one-way view for other tools. When you export, remember what the getters do and do not include — a classical export captures the fitted parameters but, unlike the postcard file, drops the hyperparameters and metadata, and a neural-network export is weights only for the same reasons [3.9](../Chapter-03/3.9._Saving_and_Loading_Weights.md) spells out.

For the neighboring operational concerns — reseeding a model after a load so a resumed shuffle stays reproducible, or the throughput of writing many checkpoints under parallelism — see [7.1. Reproducibility and Random Seeds](./7.1._Reproducibility_and_Random_Seeds.md) and [7.3. Performance Tuning and Parallelism](./7.3._Performance_Tuning_and_Parallelism.md).
