# 6.3. Parallel Reductions

If you came here expecting a `sum()` and a `mean()`, adjust your expectations: `rustyml::math::reduction` does not ship named reductions. It ships two generic fold combinators — [`det_reduce`](https://docs.rs/rustyml/latest/rustyml/math/reduction/fn.det_reduce.html) and [`det_reduce_range`](https://docs.rs/rustyml/latest/rustyml/math/reduction/fn.det_reduce_range.html) — plus one constant, [`DET_REDUCE_BLOCK`](https://docs.rs/rustyml/latest/rustyml/math/reduction/constant.DET_REDUCE_BLOCK.html). Everything the crate reduces in parallel — sum-of-squared-errors in linear regression, the global gradient norm for clip-by-global-norm, one-pass Welford moments in standardization, k-means inertia, the logistic log-loss — is built on top of these two functions. They exist for one reason that ordinary parallel summation cannot give you: a result that does not depend on how many threads happened to run.

## 6.3.1. What the module actually exposes

The whole public surface is three items. It lives behind the `math` feature, which every other feature (`machine_learning`, `neural_network`, `utils`, `metrics`) pulls in, so if RustyML compiles at all these are available (see [1.2. Installation and Feature Flags](../Chapter-01/1.2._Installation_and_Feature_Flags.md)).

| Item | Signature (elided bounds) | Role |
| --- | --- | --- |
| `DET_REDUCE_BLOCK` | `pub const DET_REDUCE_BLOCK: usize = 16_384` | Fixed block size, in elements, that defines the grouping |
| `det_reduce` | `fn det_reduce<T, A, F, M>(slice: &[T], parallel: bool, fold_block: F, merge: M, identity: A) -> A` | Folds a slice in fixed blocks |
| `det_reduce_range` | `fn det_reduce_range<A, F, M>(n: usize, parallel: bool, fold_block: F, merge: M, identity: A) -> A` | Folds the index range `0..n` in fixed blocks |

The full bounds are worth reading once, because the compiler errors around them confuse people:

```rust,ignore
pub fn det_reduce<T, A, F, M>(slice: &[T], parallel: bool, fold_block: F, merge: M, identity: A) -> A
where
    T: Sync,
    A: Send,
    F: Fn(&[T]) -> A + Sync + Send,   // serial fold over one block
    M: Fn(A, A) -> A,                 // combines two partial results
{ /* ... */ }
```

`fold_block` reduces one block down to a partial result of your accumulator type `A`; `merge` combines two partials; `identity` is the value returned for an empty input and the seed of the final combine. `fold_block` must be `Sync + Send` (rayon may call it from any worker) even when you pass `parallel = false` — the bounds are on the type, not the flag — but `merge` needs neither, because it always runs on one thread in block order. `A` can be anything `Send`: a scalar, a tuple `(sum, sum_of_squares)`, a Welford triple, an array of per-bucket sums. `det_reduce_range` is the same machine over an index range instead of a slice, for reductions that read several arrays at once or index rows of a matrix — its `fold_block` receives a `Range<usize>` rather than a `&[T]`.

There is deliberately no `sum` wrapper. A one-line `slice.iter().sum()` is already the right tool below the parallel threshold, and above it the caller almost always wants to fuse a map (square, `exp`, distance) into the same pass rather than materialize an intermediate. Handing you the fold instead of a fixed reduction keeps that fusion at the call site.

## 6.3.2. Why naive parallel summation is non-deterministic

Floating-point addition is not associative: `(a + b) + c` and `a + (b + c)` can round to different `f64` values. That is not a bug in your hardware; it is the definition of rounding to 53 bits after every operation. As long as a sum runs left-to-right on one thread, the order is fixed and the result is reproducible. The moment you parallelize it, the order stops being fixed.

A bare `slice.par_iter().sum::<f64>()` (or `fold().reduce()`) splits the work adaptively and lets rayon's work-stealing scheduler decide which worker folds which sub-range and in what order the partial sums combine. Run it on a machine with 4 idle cores and you get one grouping; run the same input with `RAYON_NUM_THREADS=1` and you get another; run it twice on a busy 16-core box and the two runs can disagree because a thread got preempted at a different moment. Every one of those results is a correct sum of the same numbers — they just round differently, typically in the last few ULPs.

For a lot of numerical code that jitter is harmless. For a machine-learning library it is corrosive. A loss that wobbles in its low bits makes an early-stopping check fire on different iterations across runs; a gradient norm that depends on thread count makes clip-by-global-norm clip slightly differently; and it makes "I ran the exact same fit twice and got two models" a real support question. Reproducibility is a first-class promise in RustyML (see [7.1. Reproducibility and Random Seeds](../Chapter-07/7.1._Reproducibility_and_Random_Seeds.md)), and a scheduler-dependent reduction breaks it from underneath, no matter how carefully you seeded the RNG.

## 6.3.3. The blocked algorithm

The fix is to take the grouping away from the scheduler and nail it to a constant. `det_reduce` cuts the input into fixed `DET_REDUCE_BLOCK`-element chunks, folds each chunk serially with your `fold_block`, collects the per-block partials **in block order**, and merges them left-to-right with your `merge`. The parallel and serial paths differ only in how the blocks are dispatched:

```rust,ignore
if parallel {
    let parts: Vec<A> = slice.par_chunks(DET_REDUCE_BLOCK).map(fold_block).collect();
    parts.into_iter().fold(identity, merge)          // merge in block order
} else {
    slice.chunks(DET_REDUCE_BLOCK).map(fold_block).fold(identity, merge)
}
```

The load-bearing detail is that rayon's `par_chunks(...).collect::<Vec<_>>()` is an **indexed** parallel iterator: however work-stealing distributes the blocks across threads, the collected `Vec` comes back in the original block order. So the reduction tree — which elements land in which block, and in what order the blocks combine — is a pure function of the input length and `DET_REDUCE_BLOCK`. It does not depend on the thread count, on scheduling, or on the `parallel` flag. Both paths fold the same 16 384-element blocks in the same order and combine them the same way. `det_reduce_range` does the identical thing over `n.div_ceil(DET_REDUCE_BLOCK)` index blocks, where block `b` covers `b * BLOCK .. ((b + 1) * BLOCK).min(n)`.

That makes the `parallel` argument a pure performance hint. It never changes which numbers get added in which order — it only decides whether the blocks run on the rayon pool or in a plain sequential loop. The crate's own tests assert this with bitwise `==` (not an epsilon) across empty, sub-block, exactly-one-block, and ragged multi-block lengths. So on a given build the two paths are bit-for-bit identical, and varying `RAYON_NUM_THREADS` cannot change the result. The module docs still hedge "not necessarily bit-for-bit" reproducible — that caveat is about *cross-machine* and *cross-build* differences (a different libm `sin`, FMA contraction toggled by a different target-cpu, a different rounding of your own `fold_block`), not about thread count, which the blocking pins down completely.

`DET_REDUCE_BLOCK` is 16 384 because that is where the throughput plateau sits: on a 4.2M-element sum-of-squares the speedup is flat (about 17–18x) for block sizes from 4K to 64K, with 16K the fastest, and it degrades at 256K because there are then too few blocks to balance across cores. The constant counts **elements**, not bytes, and is shared by every element type — 16 384 `f32` values (64 KB per block) and 16 384 `f64` values (128 KB) both sit comfortably mid-plateau. Because the value defines the grouping, it is part of the reproducibility surface: changing it changes the (still deterministic) result in the low bits, so it is a `const`, not a knob.

## 6.3.4. Accuracy is a side effect, not the goal

Blocking was chosen for determinism, but it buys a real accuracy improvement for free, and it is worth understanding because it applies to **both** paths — the serial path chunks into blocks too, so even `parallel = false` is not a naive whole-array left-fold.

The worst-case rounding error of summing `n` floats left-to-right grows like `(n - 1) * ε * Σ|xᵢ|` — linearly in `n`. `det_reduce` is a two-level scheme: each block folds `b = 16 384` terms serially, then the `⌈n / b⌉` block partials fold serially. The error bound becomes roughly `(b + n/b) * ε * Σ|xᵢ|`. For a 4.2M-element sum that is about `(16 384 + 256) * ε` against the naive `4.2M * ε` — a ~250x tighter worst-case bound, and the same improvement whether you ran the blocks in parallel or not. Be honest about what this is, though: it is flat blocking plus a serial merge, not a full pairwise (`log n`) summation tree. The accumulator width matters more than the tree shape in practice — note that `global_grad_norm` reduces `f32` gradients into an `f64` accumulator inside `fold_block` (the SSE loop is `f64` end to end), which does far more for accuracy than the blocking does. Blocking is the deterministic floor; a wide accumulator is what you reach for when accuracy is the actual concern.

## 6.3.5. When the parallel path turns on

`det_reduce` does not decide `parallel` for you — you pass it. In the crate, that boolean is the output of a calibrated size gate, because below roughly one block there is nothing to parallelize (an input shorter than 16 384 elements is a single block, and forking it onto rayon only adds join overhead). The gates live in `rustyml::tuning::reduction` and are shared per cost class rather than per call site:

| Gate (getter in `tuning::reduction`) | Default | Guards |
| --- | --- | --- |
| `get_sum_f64` | 262 144 | `f64` sum-style reductions (SSE, Welford moments, k-means inertia) |
| `get_sq_sum_f32` | 65 536 | `f32`→`f64` square-sum for clip-by-global-norm |
| `get_scan_f64` | 262 144 | short `f64` per-row scans (arg-min, distance scans) |
| `get_exp_reduce` | 32 768 | the exp-heavy logistic log-loss reduction |

The pattern at every call site is the same — pass `slice.len() >= gate()` as the flag — so the gate moves the crossover without ever touching correctness, exactly because the blocked fold gives the same answer on either side. Each gate has a matching setter (`set_sum_f64`, `set_sq_sum_f32`, …) if you want to tune the crossover for your hardware; the mechanics and the calibration story are covered in [7.3. Performance Tuning and Parallelism](../Chapter-07/7.3._Performance_Tuning_and_Parallelism.md). The exp-reduction gate sits lowest (32 768) because each element there pays for an `exp` and an `ln`, so parallelism amortizes sooner than for a plain add.

## 6.3.6. Using them in your own code

The minimal call — a fused sum of squares over a `Vec<f64>`, kept serial:

```rust
use rustyml::math::reduction::det_reduce;

fn main() {
    let data: Vec<f64> = (0..1_000).map(|i| (i as f64).sin()).collect();
    let sum_sq = det_reduce(
        &data,
        false, // performance hint; small input, stay serial
        |block| block.iter().map(|&x| x * x).sum::<f64>(),
        |a, b| a + b,
        0.0,
    );
    println!("sum of squares = {sum_sq}");
}
```

Two things bite people here. First, `det_reduce` takes a `&[T]`, so the data must be a contiguous slice; an `ndarray` array only yields one via `as_slice()`, which returns `None` for a non–standard-layout view. The idiomatic pattern — the one the crate itself uses — is to reduce through `det_reduce` on the contiguous fast path and fall back to ndarray's serial kernel otherwise, gating the flag on the size class:

```rust
use ndarray::Array1;
use rustyml::math::reduction::det_reduce;
use rustyml::tuning::reduction::get_sum_f64;

fn main() {
    let v: Array1<f64> = (0..10_000).map(|i| i as f64).collect();
    let sum = match v.as_slice() {
        Some(slice) => det_reduce(
            slice,
            slice.len() >= get_sum_f64(),
            |block| block.iter().sum::<f64>(),
            |a, b| a + b,
            0.0,
        ),
        None => v.sum(), // non-contiguous: ndarray's serial fold
    };
    println!("sum = {sum}");
}
```

Second, the accumulator does not have to be a scalar — that is the whole point of handing you the fold. A single pass that returns both the sum and the sum of squares (enough for a mean and a variance) is a tuple accumulator with a tuple `merge`:

```rust
use rustyml::math::reduction::det_reduce;

fn main() {
    let data: Vec<f64> = (0..10_000).map(|i| (i as f64).sin()).collect();
    let (sum, sum_sq) = det_reduce(
        &data,
        false,
        |block| block.iter().fold((0.0f64, 0.0f64), |(s, sq), &x| (s + x, sq + x * x)),
        |(sa, sqa), (sb, sqb)| (sa + sb, sqa + sqb),
        (0.0, 0.0),
    );
    let n = data.len() as f64;
    let mean = sum / n;
    let variance = sum_sq / n - mean * mean;
    println!("mean = {mean}, variance = {variance}");
}
```

When the reduction needs to read more than one array at once — a dot product, a distance accumulation, a per-row pick — reach for `det_reduce_range` and index inside the block instead:

```rust
use rustyml::math::reduction::det_reduce_range;

fn main() {
    let xs: Vec<f64> = (0..5_000).map(|i| i as f64).collect();
    let ys: Vec<f64> = (0..5_000).map(|i| (i as f64).cos()).collect();
    let dot = det_reduce_range(
        xs.len(),
        false,
        |range| range.map(|i| xs[i] * ys[i]).sum::<f64>(),
        |a, b| a + b,
        0.0,
    );
    println!("dot = {dot}");
}
```

### `det_reduce` versus ndarray's `.sum()`

ndarray's `.sum()`, `.dot()`, and `.mean()` are serial and single-threaded, and their internal grouping is their own — it will not generally match `det_reduce`'s blocking bit-for-bit. For small arrays they are the right call: shorter to write, no closures, and below the gate `det_reduce` would run serially anyway with more ceremony. Reach for `det_reduce` when you have a genuinely large contiguous buffer *and* you want it reduced in parallel *and* you need that parallel result to be reproducible — which is precisely the combination ndarray does not offer, since even with ndarray's `rayon` feature a bare parallel sum is back to being scheduler-dependent. It is also the tool when you want to fuse a map into the reduction or accumulate something richer than a scalar. A good rule: default to ndarray for convenience and small data; switch to `det_reduce` at the point where you were about to write a `par_iter().sum()` and care about the answer being stable. See [1.3. Working with ndarray](../Chapter-01/1.3._Working_with_ndarray.md) for the interop story, and [4.2. Standardization and Normalization](../Chapter-04/4.2._Standardization_and_Normalization.md) for a real Welford reduction built on exactly this fold.

## 6.3.7. Verifying determinism across thread counts

The claim is testable from the outside, and it is worth doing once so you trust it. This program reduces two million values on the rayon path and prints the sum with full precision:

```rust
use rustyml::math::reduction::det_reduce;

fn main() {
    let data: Vec<f64> = (0..2_000_000).map(|i| (i as f64 * 0.001).sin()).collect();
    let sum = det_reduce(
        &data,
        true, // force the parallel path
        |block| block.iter().sum::<f64>(),
        |a, b| a + b,
        0.0,
    );
    // Full-precision print so a low-bit difference would show
    println!("{sum:.17e}");
}
```

Build it once and run it under different thread counts by setting `RAYON_NUM_THREADS`, which caps rayon's global pool:

```bash
RAYON_NUM_THREADS=1 ./target/release/demo
RAYON_NUM_THREADS=2 ./target/release/demo
RAYON_NUM_THREADS=8 ./target/release/demo
```

All three print the identical 17-digit mantissa, because every run folds the same 16 384-element blocks and merges them in the same block order regardless of how many workers carried them. Flip the flag to `false` and the output does not move either. Contrast this with swapping the body for `data.par_iter().sum::<f64>()`: under different `RAYON_NUM_THREADS` values that version will, on a large enough input, print sums that differ in their last digits — the exact failure mode `det_reduce` was written to close. The related numeric primitives share the same determinism discipline: see [6.1. Distance Metrics](./6.1._Distance_Metrics.md) and [6.2. Matrix Multiplication](./6.2._Matrix_Multiplication.md), and the broader [6.0. Math Utilities](./6.0._Math_Utilities.md) overview.
