# 6. Math Utilities

The `math` module is the numeric floor the rest of RustyML stands on: the pairwise distance kernels, the `gemm`-backed matrix products, and the deterministic parallel reductions that every estimator, neural-network layer, and metric calls underneath. Most of the time you use these primitives without naming them — KNN reaches for a distance kernel, a `Dense` layer reaches for a GEMM, a variance computation reaches for a blocked reduction — but the callable ones are exported so you can use them directly when you build something the higher-level API does not cover, and the tunable ones expose knobs you can fit to your hardware. The module compiles under the `math` feature, which any of `machine_learning`, `neural_network`, `utils`, or `metrics` turns on transitively and which `full` includes, so if you use RustyML at all these primitives are already built. See [Installation and Feature Flags](../Chapter-01/1.2._Installation_and_Feature_Flags.md).

One theme runs through all three sections: these primitives are parallel but reproducible. Each decides serial-versus-rayon by comparing a work estimate against a calibrated threshold, and the reductions never let that choice change the result — they are bit-identical either way — while the matrix products reproduce run to run (a flipped strategy can move the last few bits; see 6.2.4). That property is what makes the knobs in [Performance Tuning and Parallelism](../Chapter-07/7.3._Performance_Tuning_and_Parallelism.md) safe to move and what backs the guarantees in [Reproducibility and Random Seeds](../Chapter-07/7.1._Reproducibility_and_Random_Seeds.md). You should be comfortable with ndarray's `Array1`/`Array2` and views before reading on; [Working with ndarray](../Chapter-01/1.3._Working_with_ndarray.md) covers what you need. Read the sections in order — 6.1 and 6.3 give you functions you can call today, while 6.2 is mostly context for a backend you invoke indirectly.

## 6.1. Distance Metrics

[Distance Metrics](./6.1._Distance_Metrics.md) covers the three allocation-free per-row kernels — `squared_euclidean_distance_row`, `manhattan_distance_row`, and `minkowski_distance_row` — and the `DistanceCalculationMetric` enum layered on top of them, the single dispatcher that KNN, DBSCAN, and the silhouette score all share so the choice of metric becomes a runtime value instead of a hard-coded `match`. The kernels are the fast path (the Euclidean one deliberately skips the square root); the enum is the ergonomic one. Start here — it is the most directly usable piece of the chapter.

```rust
use ndarray::array;
use rustyml::math::{DistanceCalculationMetric, squared_euclidean_distance_row};

fn main() {
    let a = array![0.0_f64, 0.0];
    let b = array![3.0_f64, 4.0];

    // The raw kernel returns the *squared* distance — no root taken.
    println!("squared: {}", squared_euclidean_distance_row(&a, &b)); // 25.0

    // The dispatcher takes the root and lets the metric vary at runtime.
    let metric = DistanceCalculationMetric::Euclidean;
    println!("euclidean: {}", metric.distance(a.view(), b.view())); // 5.0
}
```

## 6.2. Matrix Multiplication

[Matrix Multiplication](./6.2._Matrix_Multiplication.md) explains the `gemm`-crate backend behind every dense product in the library: how it dispatches to the widest available SIMD, when it parallelizes over the output columns versus splitting rows across rayon, and why a matrix-vector product is treated as its own cost class. You rarely call this layer by name — it sits under the linear models and the dense and convolution layers — so the section is less about an API to invoke than about understanding the strategy and, more usefully, the `rustyml::tuning::matmul` knobs that retune the serial-versus-parallel crossovers for your core count and cache sizes. Read it when a model's throughput is what you care about.

## 6.3. Parallel Reductions

[Parallel Reductions](./6.3._Parallel_Reductions.md) covers `det_reduce` and `det_reduce_range`, the blocked folds that give a sum, dot product, or per-bucket accumulator the same bits whether they run on one thread or all of them. A bare `par_iter().sum()` reorders its float additions by however rayon happens to steal work; these helpers instead cut the input into fixed `DET_REDUCE_BLOCK`-sized chunks so the grouping — and therefore the rounding — never depends on scheduling. Reach for them whenever you write your own parallel numeric loop and want a result that does not drift between runs or thread counts.
